# 본인확인 테스트 케이스 정의

정본 목록은 [`../spec-qa.md`](../spec-qa.md). 용어는 [`../../../../wiki/WIKI.md`](../../../../wiki/WIKI.md).

## 개요

- **검증 목적**: 사용자가 넣은 **생년월일로 전달 데이터가 복원되는지**로 본인을 확인하는 절차가 정확한지, 그리고 그 최초 성공 시점에 **추적 레코드가 정확히 1건** 만들어지는지 확인한다. 판정 1·2단계 실패(재입력)와 3·4단계 실패(규약 위반)의 경계가 흔들리면 결과 구분과 화면 경로가 함께 무너지므로 이 경계가 본 파일의 핵심 검증 대상이다.
- **관련 PRD 요구사항**: [`../../../prd/PRD.md`](../../../prd/PRD.md) §제공 가치 — "전달 데이터는 이중 암호화(encX/encY)되어 전달되고 **사용자의 생년월일 입력으로만 복원**된다." · §수행 범위 9 — "연동 추적 키 기준 **단일 추적 레코드**를 **사용자가 진입한 시점에 생성**하고 …"
- **관련 IA 항목**: `USR-03` (본 파일의 전 TC 공통)
- **검증 방법(qa 케이스)**: **웹·SPA UI** (제출 접점의 HTTP 계약 확인은 API·서버 절차를 병용)
- **공통 전제**: `ENV-WEB` · `ENV-API` 기동 · `ENV-DB` 시드 투입 완료 · `SEED-CONST-OK` 상수 주입
- **공통 판정 기준**: **Pass** = 모든 단계의 기대 결과 일치 / **Fail** = 하나 이상 불일치(불일치 항목 기록) / **Block** = 전제 조건 미충족으로 실행 불가(사유 기록).
- **매핑 PROC 단계**: [`../../processes/process_PROC-102.md`](../../processes/process_PROC-102.md) 의 라벨(`B1`~`B8` · `F1`~`F3`)과 [`../../processes/process_PROC-301.md`](../../processes/process_PROC-301.md)·[`../../processes/process_PROC-303.md`](../../processes/process_PROC-303.md) 의 라벨을 인용한다.

### USR-03_017 본인확인 제출의 응답 미수신 → `Retryable`(승인 제출과 다른 상태)

| 계층·유형 | 검증 대상 | 검증 PROC | 검증 분기/예외 | 우선순위 | 자동화 |
|---|---|---|---|---|---|
| E2E · 시스템예외 | SCR-001 §화면 상태 전이 `Retryable` · `SEC-002-05` · `BIZ-002-03` ② · SCR-003 `Unconfirmed` 와의 대비 | PROC-102 | `EX-BIZ-003`(문구 공유 — 응답 미수신에는 EX 코드가 없다) | 높음 | 자동 |

- **전제**: `SEED-VEC-01`(파일) · 브라우저 자동화의 **전송 계층 단절 수단**(요청 발신 후 응답 차단)
- **단계**: ① 올바른 생년월일로 확인을 눌러 `POST <INTERLOCK_ENTRY_PATH>/verify` 를 발신한 직후 전송 계층을 끊어 **응답을 받지 못하게** 한다 `F3` → 화면은 **SCR-001 을 유지**하고 SCR-004 로 전이하지 않는다 ② 상태 확인 → **`Retryable`** — InlineAlert + 확인 버튼 **재활성**(입력 값 유지) ③ 문구 확인 → `EX-BIZ-003` **기본 문구 "처리 중 문제가 발생했습니다. 잠시 후 다시 시도해 주세요." 그대로**이며, 응답이 없다는 사실을 구분해 알리는 별도 문구·사유 코드가 없다(`SEC-002-05`) ④ 대기를 이어 가며 **화면 자체 타임아웃이 없음**을 확인(시간이 지나도 문구가 바뀌거나 다른 상태로 넘어가지 않는다) ⑤ 연결을 복구하고 **같은 값으로 그대로 재제출** `B3`~`B8` → 200 `stage = CONSENT` 로 정상 진행(이 제출은 어떤 결과도 확정하지 않아 재시도가 안전하다 — `BIZ-002-03` ②) ⑥ 승인 제출의 응답 미수신(`USR-02_015` 의 `Unconfirmed` — 재진입 안내)과 **다른 상태**로 가며, 두 접점의 응답 미수신이 하나로 합쳐지지 않음을 확인
- **데이터 검증**: 서버 도달 여부와 무관하게 **결과 구분은 확정되지 않는다**(`result_code IS NULL`) — 서버가 처리를 마쳤으면 레코드가 `OPEN` 으로 남고 ⑤ 재제출이 그 레코드를 **이어 쓰며 `request_count` 를 다시 올리지 않는다**(`USR-03_010` 과 같은 거동), 서버에 닿지 않았으면 ⑤ 가 최초 생성이 되어 `request_count` +1
- **판정**: 공통 판정 기준
