# 처리상태 확인 API 테스트 케이스 정의

정본 목록은 [`../spec-qa.md`](../spec-qa.md). 용어는 [`../../../../wiki/WIKI.md`](../../../../wiki/WIKI.md).

## 개요

- **검증 목적**: 발송처가 추적 키로 처리·결과 확인 상태를 조회하는 접점이 정확한 값을 돌려주는지, 그리고 **응답이 상태를 바꾸는**(결과 확인 표시 → 보관 기간 기산 개시) 부작용이 정확히 최초 1회만 일어나는지 확인한다. 인증이 없으므로 추적 키를 아는 누구든 이 기산을 시작시킬 수 있고, 그 사실 자체가 수용 리스크로 확인 대상이다.
- **관련 PRD 요구사항**: [`../../../prd/PRD.md`](../../../prd/PRD.md) §수행 범위 7 — "**처리상태 확인 API** · 연동 완료 확인 API · 완료 콜백 API: 발송처의 상태·완료 조회와 수신처의 완료 통지." · §시스템 제약사항 — "**조회로 인한 보관 기산 개시** … 이 수준을 수용한다."
- **관련 IA 항목**: `API-01` (본 파일의 전 TC 공통)
- **검증 방법(qa 케이스)**: **API·서버**
- **공통 전제**: `ENV-API` 기동 · `ENV-DB` 시드 투입 완료 · `SEED-CONST-OK` 상수 주입
- **공통 판정 기준**: **Pass** = 모든 단계의 기대 결과 일치 / **Fail** = 하나 이상 불일치(불일치 항목 기록) / **Block** = 전제 조건 미충족으로 실행 불가(사유 기록).
- **매핑 PROC 단계**: [`../../processes/process_PROC-201.md`](../../processes/process_PROC-201.md) 의 라벨(`C1`·`C2` · `B1`~`B6`)을 인용한다.
- **엔드포인트**: `POST /api/interlock/status` — 요청 `MDL-011` · 응답 `MDL-012`

### API-01_001 결과 확정 레코드 조회 — 전 필드 응답

| 계층·유형 | 검증 대상 | 검증 PROC | 검증 분기/예외 | 우선순위 | 자동화 |
|---|---|---|---|---|---|
| INTG · Positive | SVC-010 · MDL-011 · MDL-012 · FN-006 · FN-007 | PROC-201 | BR-002(`FIXED`) | 높음 | 자동 |

- **전제**: `SEED-TRK-FIXED-SUCCESS`(SQL)
- **단계**: ① `{"trackingKey":"<확정 레코드 키>"}` 로 POST `C1`·`B1` → 200 · `application/json; charset=utf-8` ② 응답 본문 `B4`·`B6` → `trackingKey`·`isSuccess`·`resultCode`·`isResultConfirmed`·`resultAt`·`resultConfirmedAt` 6 속성이 모두 있다 ③ 값 확인 → `resultCode = "SUCCESS"` · `isSuccess = true`(결과 구분에서 산출한 파생값) · `resultAt` 이 ISO 8601 + 오프셋 문자열 ④ 캐시 금지 헤더가 지정되어 있는지 확인
- **판정**: 공통 판정 기준

### API-01_002 결과 미확정 레코드 조회

| 계층·유형 | 검증 대상 | 검증 PROC | 검증 분기/예외 | 우선순위 | 자동화 |
|---|---|---|---|---|---|
| INTG · Positive | MDL-012 · FN-007 · ENT-001 §속성 정의 · `BIZ-002-03` ② | PROC-201 | BR-002(`OPEN`) | 높음 | 자동 |

- **전제**: `SEED-TRK-OPEN`(SQL)
- **단계**: ① 미확정 레코드 키로 POST `B3` → 200 ② 응답 `B4` → `resultCode = null` · **`isSuccess = null`** · `resultAt = null` · `isResultConfirmed = false` · `resultConfirmedAt = null` ③ **`isSuccess` 가 `false` 가 아님을 따로 확인한다** — `false` 는 "결과가 확정됐고 성공이 아니다"라는 뜻이라 미확정과 뭉개지면 결과 구분 3종 체계가 무너진다(`BIZ-001-01`). 값 비교는 **타입까지** 본다(`null !== false`) ④ 조회가 성립함을 확인(결과가 없어도 404 가 아니다 — 레코드는 존재한다)
- **판정**: 공통 판정 기준. **기대값 `null` 의 근거는 정본 3문서가 일치한다** — [`../../datas/model_MDL-011-015.md`](../../datas/model_MDL-011-015.md) `MDL-012` §속성 정의("결과 미확정이면 null")·[`../../functions/function_FN-007-008.md`](../../functions/function_FN-007-008.md) `FN-007` 3(`행.result_code == NULL ? null : …`)·[`../../processes/process_PROC-201.md`](../../processes/process_PROC-201.md) `B4`("null 가능(결과 미확정)"). `MDL-001` §속성 정의도 같다.

- **판정**: 공통 판정 기준

### API-01_015 경합 삭제 — 사전 조회 후 표시 직전 소실 → 404

| 계층·유형 | 검증 대상 | 검증 PROC | 검증 분기/예외 | 우선순위 | 자동화 |
|---|---|---|---|---|---|
| INTG · 조합경계값 | FN-010 §반환값 규약 · `DATA-002-05` · `BIZ-002-05` · PROC-201 `B5` 경합 삭제 분기 · 처리상태 확인 API §처리 순서 5 | PROC-201 · PROC-301 · PROC-304 | BR-002(`NONE` — `B5` 재성립) · `EX-DATA-001` | 높음 | 반자동 |

- **전제**: `SEED-TRK-FIXED-SUCCESS`(SQL — `result_confirmed_at IS NULL`) · **`CHK-RACEDEL` 경합 삭제 주입 절차** — `B3` 사전 조회가 성립한 뒤 `B5` 표시 갱신이 실행되기 **전에** 그 추적 키의 행을 하드 삭제할 수 있어야 한다(보관 배치 `PROC-304` `B5` 와 같은 `DELETE`).
- **재현 방법·전제**: **허브 단독으로는 재현되지 않는다** — 보관 배치의 실제 발화 시점을 밀리초 단위로 `B3`·`B5` 사이에 맞출 수단이 없기 때문이다. 재현은 둘 중 하나로 한다 — ⓐ fault 주입 하네스가 `B3` 반환 직후에 실행을 잠시 멈추는 훅을 제공하고, 그 사이에 별도 세션이 같은 키를 `DELETE` + `COMMIT` 한다 ⓑ 하네스가 `B5` 의 조건부 UPDATE 직전에 같은 커넥션 밖에서 삭제를 수행하도록 주입한다. **어느 수단도 없으면 이 TC 는 🟠 Block 이며 🔴 Fail 로 올리지 않는다**(관측 수단의 부재를 제품 결함으로 보고하는 것이 된다).
- **단계**: ① 사전 조회가 `FIXED` 로 성립하게 조회를 시작한다 `B3` ② `B5` 진입 직전에 같은 추적 키의 행을 하드 삭제한다(위 재현 수단) ③ 표시 갱신 `B5` → **0행**이고, 같은 경계의 재조회가 `NONE` 이라 `EX-DATA-001` 이 올라온다 ④ 응답 확인 → **404 `EX-DATA-001`** 이며 **200 이 아니다** — 사전 조회 시점의 값으로 만든 200 응답이 나가면 Fail(삭제된 레코드에 정상 응답이 나가 `DATA-002-05` 가 깨진다) ⑤ **500 이 아님**을 확인한다 — 저장 실패가 아니라 대상 없음이며, `EX-BIZ-003` 으로 응답하면 Fail("잠시 후 다시 시도"는 영구히 없어진 레코드에 성립하지 않는다) ⑥ 응답 본문을 **미진입 키(`API-01_010`)·보관 만료 키(`API-01_011`)의 404 와 대조** → 문구·코드·부가 필드가 **완전히 동일**(삭제 시점이 사전 조회의 앞이냐 뒤냐로 응답이 갈리지 않는다) ⑦ 데이터 확인 → 경계가 되돌려지고(갱신 0행이라 되돌릴 변경이 없다) **레코드가 되살아나지 않는다** ⑧ 지표 카운터 무변화 확인
- **판정**: 공통 판정 기준 (Block 사유: `CHK-RACEDEL` 경합 삭제 주입 절차 미구축)

### API-01_016 `isResultConfirmed` 파생 일관성 — `resultConfirmedAt !== null`

| 계층·유형 | 검증 대상 | 검증 PROC | 검증 분기/예외 | 우선순위 | 자동화 |
|---|---|---|---|---|---|
| DATA · Positive | MDL-012 §속성 정의 · MDL-001 §속성 정의 · FN-010 §구현 가이드(하드 세팅 금지) · PROC-201 `B5` 파생 산출 · 처리상태 확인 API §처리 순서 4 | PROC-201 · PROC-301 | BR-002(`OPEN`·`FIXED`) · BR-010 | 높음 | 자동 |

- **전제**: `SEED-TRK-OPEN`·`SEED-TRK-FIXED-SUCCESS`(SQL — 표시 전 상태) · `SEED-TRK-CONFIRMED`(SQL — 이미 표시된 상태)
- **단계**: ① 결과 미확정 레코드 조회 `B4` → `resultConfirmedAt = null` **그리고** `isResultConfirmed = false` ② 결과 확정·표시 전 레코드를 **최초로** 조회 `B5` → `resultConfirmedAt` 이 값으로 채워지고 `isResultConfirmed = true` ③ 이미 표시된 레코드를 조회 → 기존 일시가 그대로 실리고 `isResultConfirmed = true` 유지 ④ 세 상태 전부에서 `isResultConfirmed === (resultConfirmedAt !== null)` 이 성립하는지 **타입까지** 확인한다(`API-01_002` ③ 과 같은 방식) — `isResultConfirmed` 는 boolean `true`/`false` 이고 `"false"`·`0`·`""` 같은 값 변형이 아니며, `resultConfirmedAt` 은 ISO 8601 + 오프셋 문자열 또는 `null` 이다 ⑤ **`resultConfirmedAt: null` 인데 `isResultConfirmed: true`** 인 응답이 단 1건도 나오지 않는지 확인 → 나오면 Fail(파생값을 참으로 하드 세팅한 구현) ⑥ 반대 조합(`resultConfirmedAt` 이 값인데 `isResultConfirmed: false`)도 나오지 않는지 확인 ⑦ 응답 속성이 `MDL-012` 의 **6개 그대로**인지 확인 — 파생 여부를 알리는 별도 속성을 늘리지 않는다
- **판정**: 공통 판정 기준. **파생 규칙의 근거는 정본 3문서가 일치한다** — [`../../datas/model_MDL-001.md`](../../datas/model_MDL-001.md) §속성 정의 · [`../../datas/model_MDL-011-015.md`](../../datas/model_MDL-011-015.md) `MDL-012` · [`../../functions/function_FN-009-011.md`](../../functions/function_FN-009-011.md) `FN-010` §반환값 규약.
