# 연동 완료 확인 API 테스트 케이스 정의

정본 목록은 [`../spec-qa.md`](../spec-qa.md). 용어는 [`../../../../wiki/WIKI.md`](../../../../wiki/WIKI.md).

## 개요

- **검증 목적**: 발송처가 **수신처의 처리 완료 여부**만을 확인하는 접점이 처리상태 확인과 구별되는지 확인한다. 판단 대상(수신처의 처리)과 부작용(보관 기산을 시작시키지 않는다)이 다르므로, 이 접점이 레코드를 갱신하지 않는 것이 핵심 검증 대상이다.
- **관련 PRD 요구사항**: [`../../../prd/PRD.md`](../../../prd/PRD.md) §수행 범위 7 — "처리상태 확인 API · **연동 완료 확인 API** · 완료 콜백 API: 발송처의 상태·완료 조회와 수신처의 완료 통지." · [`../../../prd/ia/IA.md`](../../../prd/ia/IA.md) `API-02`.
- **관련 IA 항목**: `API-02` (본 파일의 전 TC 공통)
- **검증 방법(qa 케이스)**: **API·서버**
- **공통 전제**: `ENV-API` 기동 · `ENV-DB` 시드 투입 완료 · `SEED-CONST-OK` 상수 주입
- **공통 판정 기준**: **Pass** = 모든 단계의 기대 결과 일치 / **Fail** = 하나 이상 불일치(불일치 항목 기록) / **Block** = 전제 조건 미충족으로 실행 불가(사유 기록).
- **매핑 PROC 단계**: [`../../processes/process_PROC-202.md`](../../processes/process_PROC-202.md) 의 라벨(`C1`·`C2` · `B1`~`B5`)을 인용한다.
- **엔드포인트**: `POST /api/interlock/completion` — 요청 `MDL-011` · 응답 `MDL-013`

---

### API-02_001 콜백 수신 레코드 → 완료 응답

| 계층·유형 | 검증 대상 | 검증 PROC | 검증 분기/예외 | 우선순위 | 자동화 |
|---|---|---|---|---|---|
| INTG · Positive | SVC-011 · MDL-011 · MDL-013 · FN-006 · FN-007 | PROC-202 | BR-011(수신) · BR-002(`FIXED`) | 높음 | 자동 |

- **전제**: `SEED-TRK-CALLBACK`(SQL — `callback_received_at` 이 채워진 레코드)
- **단계**: ① `{"trackingKey":"<키>"}` 로 POST `C1`·`B1` → 200 ② 응답 `B4`·`B5` → `trackingKey`·`isCallbackReceived = true`·`callbackReceivedAt` 이 저장된 최초 수신 일시와 일치 ③ 응답 속성이 정확히 셋인지 확인(결과 구분·처리 성공 여부를 담지 않는다) ④ 일시가 ISO 8601 + 오프셋 문자열인지 확인
- **판정**: 공통 판정 기준

### API-02_002 콜백 미수신 레코드 → 미완료 응답

| 계층·유형 | 검증 대상 | 검증 PROC | 검증 분기/예외 | 우선순위 | 자동화 |
|---|---|---|---|---|---|
| INTG · Positive | MDL-013 · ENT-001 §속성 정의 | PROC-202 | BR-011(미수신) | 높음 | 자동 |

- **전제**: `SEED-TRK-FIXED-SUCCESS`(SQL — `callback_received_at IS NULL`)
- **단계**: ① 해당 키로 POST `B4` → 200 ② 응답 → `isCallbackReceived = false` · `callbackReceivedAt = null` ③ 결과가 `SUCCESS` 인데도 완료가 `false` 인 것이 정상임을 확인(허브의 처리와 수신처의 처리는 다른 사실이다)
- **판정**: 공통 판정 기준

### API-02_003 레코드를 갱신하지 않음 — 기산 미개시

| 계층·유형 | 검증 대상 | 검증 PROC | 검증 분기/예외 | 우선순위 | 자동화 |
|---|---|---|---|---|---|
| DATA · Positive | SVC-011 F-006 · `DATA-002-01` · PROC-202 `B4` | PROC-202 | BR-011 | 높음 | 자동 |

- **전제**: `SEED-TRK-FIXED-SUCCESS`(SQL — `result_confirmed_at IS NULL`)
- **단계**: ① 조회 전 레코드 6 컬럼 전부를 기록 `B3` ② 완료 확인 API 를 5회 호출 `B4` ③ 조회 후 6 컬럼 재확인 → **전부 불변**이며 특히 `result_confirmed_at` 이 `NULL` 그대로 ④ 처리상태 확인 API 와의 차이를 대조 기록(그쪽은 표시로 기산을 시작시킨다) ⑤ 지표 카운터 무변화 확인
- **판정**: 공통 판정 기준

### API-02_004 결과 구분과 무관하게 조회 성립

| 계층·유형 | 검증 대상 | 검증 PROC | 검증 분기/예외 | 우선순위 | 자동화 |
|---|---|---|---|---|---|
| INTG · Boundary | PROC-202 `B4` 완료 판정 · `BIZ-001-01` | PROC-202 | BR-011 · BR-002(`OPEN`·`FIXED`) | 보통 | 자동 |

- **전제**: `SEED-TRK-OPEN`·`SEED-TRK-FIXED-SUCCESS`·`-DECRYPT`·`-DELIVERY`(SQL)
- **단계**: ① 네 상태의 레코드를 각각 조회 `B3`·`B4` → 전건 200(결과 구분·처리 성공 여부를 판정에 쓰지 않는다) ② 전달이 실패한 레코드(`DELIVERY_FAILED`)의 응답 → `isCallbackReceived = false`(콜백이 올 수 없는 상태이므로 항상 미수신) ③ 결과 미확정 레코드도 조회가 성립하는지 확인 ④ **완료 콜백 수신 여부 하나만** 판정 근거임을 기록
- **판정**: 공통 판정 기준

### API-02_005 인증 없이 호출 가능 — 설계된 부재

| 계층·유형 | 검증 대상 | 검증 PROC | 검증 분기/예외 | 우선순위 | 자동화 |
|---|---|---|---|---|---|
| POL · 권한/인증 | `AUTH-001-03` · 인터페이스 §인증·요청 제한 | PROC-202 | BR-011 | 높음 | 자동 |

- **전제**: `SEED-TRK-CALLBACK`(SQL)
- **단계**: ① 인증 헤더 없이 POST `B1` → 200 정상 응답 ② 임의 자격을 실어 POST → 검증 없이 같은 200 응답 ③ 401·403 이 응답 코드 집합에 없음을 확인 ④ 요청 제한이 없어 반복 호출이 차단되지 않음을 확인(`OPS-002-03` 수용 리스크 — 결함으로 올리지 않는다)
- **판정**: 공통 판정 기준. **AUTH 치환** — 토큰 검사 대신 **인증 없이 호출 가능함**을 확인한다.

### API-02_006 추적 키 형식 위반 → 400

| 계층·유형 | 검증 대상 | 검증 PROC | 검증 분기/예외 | 우선순위 | 자동화 |
|---|---|---|---|---|---|
| INTG · Negative | FN-006 · `DATA-004-03` | PROC-202 | `EX-DATA-002` | 높음 | 자동 |

- **전제**: `ENV-API` 기동
- **단계**: ① 빈 값·공백만·256자 키로 각각 POST `B2` → 전건 400 `EX-DATA-002` ② 본문이 JSON 이 아니거나 `trackingKey` 속성이 없으면 400 `EX-DATA-002` ③ 오류 응답 엔벨로프 형식 확인 → `{code,message,details?}` 이며 `details[].reason` 이 `REQUIRED`·`FORMAT`·`LENGTH` 중 하나이고 **값 자체를 담지 않는다** ④ 조회를 수행하지 않았음을 확인
- **판정**: 공통 판정 기준

### API-02_007 없는 추적 키 → 404

| 계층·유형 | 검증 대상 | 검증 PROC | 검증 분기/예외 | 우선순위 | 자동화 |

### API-02_008 내부 처리 실패 → 500·내부 사유 미포함

| 계층·유형 | 검증 대상 | 검증 PROC | 검증 분기/예외 | 우선순위 | 자동화 |
|---|---|---|---|---|---|
| INTG · 시스템예외 | `EX-OPS-002` 정의 규칙(`OPS-003-05`) · `SEC-002-05` · FN-014 · FN-015 | PROC-202 | `EX-OPS-002` | 보통 | 반자동 |

- **전제**: 데이터베이스 연결 차단(fault 주입 하네스)
- **단계**: ① 연결이 끊긴 상태로 조회 `B3` → 500 · `{"code":"EX-OPS-002"}` · "처리 중 문제가 발생했습니다. 잠시 후 다시 시도해 주세요." ② 응답 본문 확인 → 내부 사유·스택·중간 값·연결 문자열이 **하나도 없다** ③ 운영 로그 확인 → 기술적 실패는 남되 금지 항목은 담기지 않는다 ④ 연결 복구 후 재조회 → 정상 200
- **판정**: 공통 판정 기준 (Block 사유: fault 주입 하네스 미구축)
