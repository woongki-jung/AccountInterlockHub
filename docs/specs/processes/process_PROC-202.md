# 연동 완료 확인 API 기능 정의

정본 목록은 [`spec-process.md`](spec-process.md). 단계 라벨 체계도 그 문서가 갖는다. 용어는 [`../../../wiki/WIKI.md`](../../../wiki/WIKI.md).

## 개요

- **정의 대상**: 발송처가 **연동 추적 키로 수신처의 처리 완료 여부를 조회**하는 처리다. 허브의 처리 결과가 아니라 **수신처가 완료를 통지했는지**만 본다. 처리상태 확인(PROC-201)과 달리 **레코드를 갱신하지 않는다** — 이 조회는 보관 기산을 시작시키지 않는다.
- **관련 PRD 요구사항**:
	- [`../../prd/PRD.md`](../../prd/PRD.md) §수행 범위 7 — "**처리상태 확인 API · 연동 완료 확인 API · 완료 콜백 API**: 발송처의 상태·완료 조회와 수신처의 완료 통지."
	- [`../../prd/ia/IA.md`](../../prd/ia/IA.md) `API-02` — "발송처가 연동 추적 키 기준 수신처의 처리완료 여부 확인"

### 진입점 및 진입 조건

- **진입점**: `POST /api/interlock/completion` — 요청 본문 `{ trackingKey }`([`../functions/spec-functions-api-server.md`](../functions/spec-functions-api-server.md) §연동 완료 확인 API).
- **진입 조건**: **인증 없음 — `AUTH-001` 인용.** 401·403 을 정의하지 않는다(`AUTH-001-03`).
- **요청 제한**: **미적용 — 수용 리스크**(`OPS-002-03`).
- **사전 검증**: ① 본문 JSON 해석 ② 추적 키 형식(FN-006).

### 입력/출력 정의

| 구분 | 항목명 | 데이터 타입 | 필수 | 설명 |
|------|--------|------------|------|------|
| 입력 | `trackingKey` | string(1~255) | Y | [`MDL-011`](../datas/model_MDL-011-015.md) |
| 출력 | `trackingKey` | string | - | 입력값 무변형 에코(`DATA-004-01`) |
| 출력 | `isCallbackReceived` | boolean | - | 완료 콜백 수신 여부(파생 — `callback_received_at` 존재 여부) |
| 출력 | `callbackReceivedAt` | string(ISO 8601+오프셋)\|null | - | 최초 수신 일시. 미수신이면 `null` |

### 연관 데이터 및 외부 호출

- **호출 API**: 없음.
- **데이터 조회 대상**: [`ENT-001`](../datas/data_ENT-001.md) 기본 키 단건 조회(PROC-301 `B2`).
- **데이터 변경 대상(CRUD)**: **없음.** 어떤 컬럼도 갱신하지 않는다.

### 실행 제약사항

- **트랜잭션 경계**: **없음(읽기 전용).** 단건 조회 하나로 끝난다.
- **동시성 제어**: 상태를 바꾸지 않으므로 락·멱등 키가 필요 없다.
- **멱등성**: 자명하다 — 반복 호출이 데이터를 바꾸지 않는다.
- **성능 요구**: 기본 키 단건 조회 1회. 목록·정렬·페이지 경로를 만들지 않는다.
- **보안 요구**: **인증 없음**(`AUTH-001-03`). 추적 키를 아는 누구든 조회할 수 있으며 수용 리스크다(`OPS-002-02`). 응답에 결과 구분·처리 일시를 담지 않는다 — 담을 속성이 [`MDL-013`](../datas/model_MDL-011-015.md) 에 없다.

### 로직 실행 순서

#### FE 측 처리 (의사코드)

**사용자 화면이 없다.** 발송처가 서버에서 직접 호출하는 접점이다(`AUTH-001-01` — 관리자 조회 화면을 두지 않는다). FE 자리에는 **호출측(발송처 서버)** 처리를 `C` 라벨로 적는다.

```
C1. 호출측 요청 구성 (발송처 서버)

  진입 트리거: 발송처가 수신처의 처리 완료 여부를 확인하려는 시점
  사용 값: 발송처가 보관·관리하는 trackingKey
  요청 DTO 변환:
    body    = { trackingKey: <발송처 보유 값> }        // 변형하지 않는다
    headers = { 'Content-Type': 'application/json; charset=utf-8' }
    // 인증 헤더·API 키를 붙이지 않는다 (AUTH-001-03)
  호출 수단: POST <허브 기준 URL>/api/interlock/completion
  주의: 이 호출은 부작용이 없다 — 보관 기산을 시작시키지 않으므로 반복 폴링해도 안전하다
        (처리상태 확인 API 와 다른 점이다)

C2. 응답 소비

  200 → isCallbackReceived 로 수신처의 완료 여부를 판단한다
        false 이면 아직 통지가 오지 않았다 (전달이 실패한 연동이면 영영 오지 않는다)
        callbackReceivedAt 은 최초 수신 일시다 — 중복 통지에도 값이 바뀌지 않는다
  400 EX-DATA-002 → 추적 키 형식을 고친다
  404 EX-DATA-001 → 그 키로 진입한 사용자가 없었다 (미진입·보관 만료를 구별하지 않는다)
  500 → 잠시 후 다시 호출한다
  폴링 정책: 발송처 소관이다. 허브는 요청 제한을 두지 않는다 (OPS-002-03)
```

#### BE 측 처리 (의사코드)

```
B1. POST /api/interlock/completion 진입

  엔드포인트·메서드: POST /api/interlock/completion
  인증·인가 검증: 인증 없음 — AUTH-001 인용 (401·403 미정의)
  요청 제한: 미적용 — 수용 리스크 (OPS-002-03)
  메서드 불일치: 405 (본문 없음)
  캐시: 응답에 캐시 금지를 지정한다 (콜백 수신 여부는 시점에 따라 바뀐다)

B2. 입력 검증 — FN-006 · POL DATA-004-03 (validate)

  if (본문을 JSON 으로 해석할 수 없다)          → 400 FN-014('EX-DATA-002')
  if (!FN-006(body.trackingKey))                → 400 FN-014('EX-DATA-002',
                                                     [{ field: 'trackingKey', reason: 'FORMAT' }])
  // 조회를 수행하지 않고 끝낸다

B3. 추적 키 사전 조회 — PROC-301 호출 · POL BIZ-002-05 (validate)

  lookup = PROC-301({ kind: 'LOOKUP', trackingKey: body.trackingKey })
      // PROC-301 B2 (FN-007):
      //   SELECT tracking_key, result_code, result_at, result_confirmed_at,
      //          callback_received_at, created_at
      //   FROM tbl_interlock_tracking
      //   WHERE tracking_key = :trackingKey;
      //   -- 기본 키 단건 · ORDER BY·LIMIT·JOIN·락 없음
  if (lookup.branch == 'NONE')                  → 404 FN-014('EX-DATA-001')

B4. 완료 판정 (validate)

  record = lookup.record
  // 완료 콜백 수신 여부 하나만 본다 — 결과 구분·처리 성공 여부를 함께 보지 않는다
  isReceived = record.isCallbackReceived        // callback_received_at IS NOT NULL 파생
  // 전달이 실패한 연동도 조회할 수 있고, 그때는 항상 미수신으로 답한다
  // 레코드를 갱신하지 않는다 — 이 조회는 보관 기산을 시작시키지 않는다 (SVC-011 F-006)

B5. 응답 구성 — POL DATA-004-01 (mask)

  body = { trackingKey:        body.trackingKey,        // 입력값 무변형 에코
           isCallbackReceived: isReceived,
           callbackReceivedAt: record.callbackReceivedAt → ISO 8601 + 오프셋 (없으면 null) }
  return 200 FN-015(body)                       // MDL-013
  // 결과 구분·처리 일시·결과 확인 상태를 담지 않는다 — 담을 속성이 모델에 없다
  영속화 쿼리: 없음
  후속 이벤트 발행: 없음
```

### 실행 결과

- **정상 결과**: 200 [`MDL-013`](../datas/model_MDL-011-015.md). **영속화·이벤트 발행 없음.**
- **실패 결과**: 400·404·500 오류 응답 엔벨로프.
- **후속 트리거**: 없음.

### 의존 프로세스

- **호출 관계**: PROC-301(동기 — `B3` 조회만).
- **선행 관계**: PROC-102(추적 레코드 생성) · PROC-901(기동). 완료 여부가 `true` 가 되려면 PROC-203 이 먼저 기록해야 한다.
- **이벤트 관계**: 없음.

### 구현 가이드

- **처리상태 확인(PROC-201)과 통합하지 않는다.** 판단 대상(허브의 처리 vs 수신처의 처리)과 부작용(기산 개시 여부)이 다르다. 하나로 합치면 완료 여부만 보려던 폴링이 보관 기산을 앞당긴다.
- **결과 구분을 함께 보지 않는다.** 전달이 실패한 연동에도 통지가 올 수 있고, 허브는 그 정합을 검사하지 않는다(BR-021).
- **어떤 컬럼도 갱신하지 않는다.** 조회 로그·조회 카운터도 두지 않는다(`OPS-003-01`).
- **추적 키를 정규화하지 않는다.** 조회 조건과 응답 에코 모두 입력 문자열 그대로다.
