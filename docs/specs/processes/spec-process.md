# 기능구현 프로세스 정의서 (목록)

AccountInterlockHub 의 코드 구현 단위 프로세스의 단일 출처다. 방향 근거는 [`../../prd/PRD.md`](../../prd/PRD.md), 정보 구조는 [`../../prd/ia/IA.md`](../../prd/ia/IA.md), 준수 규칙은 [`../policies/spec-policies.md`](../policies/spec-policies.md), 서비스 시나리오는 [`../services/spec-services.md`](../services/spec-services.md), 데이터는 [`../datas/spec-models.md`](../datas/spec-models.md), 접점 계약은 [`../functions/spec-functions.md`](../functions/spec-functions.md), 화면은 [`../screens/spec-screens.md`](../screens/spec-screens.md), 용어는 [`../../../wiki/WIKI.md`](../../../wiki/WIKI.md) 를 따른다.

본 문서는 **설계 원칙·코드 체계·단계 라벨 체계·프로세스 목록·의존관계**를 담는다. 개별 프로세스 정의는 `process_<PROC 코드>.md` 가, 상위 사양과의 매핑은 아래 두 문서가 갖는다.

- [`spec-process-mapping.md`](spec-process-mapping.md) — SVC·SCR·FN·ENT·MDL ↔ PROC 매핑과 **단계명 매핑 색인**
- [`spec-process-policy-map.md`](spec-process-policy-map.md) — 정책 규칙 86건 ↔ 적용 PROC·단계 라벨(분량이 커서 별도 분기)

## 프로세스 설계 원칙 및 기본 방향

1. **선행 도메인이 예약한 코드를 그대로 확정한다** — 정책·서비스가 예약 채번한 18종을 **같은 코드에 같은 의미**로 확정했다. 통합 0 · 폐기 0 · 추가 0 · 재배치 0.
2. **한 프로세스는 진입점 하나와 종료 조건 하나를 갖는다** — 접점(엔드포인트)·명령·함수 호출·기동 중 하나가 진입점이고, 응답·반환·종료 코드 중 하나로 끝난다.
3. **없는 것을 만들지 않는다** — 인증·인가 검증 단계(`AUTH-001`), 요청 제한 단계(`OPS-002-03`), 감사 로그 기록 단계(`OPS-003-01`)를 어떤 프로세스에도 두지 않는다. 부재는 누락이 아니라 결정이므로 각 프로세스가 그 사실을 명시한다.
4. **상수 값을 복제하지 않는다** — 경로·주소·기간·문구는 플레이스홀더로만 참조한다(`OPS-001-04`).
5. **값 체계를 새로 만들지 않는다** — SVC·FN·MDL·ENT·SCR·정책 규칙 ID·EX·BR 를 **인용만** 한다. 본 도메인의 신설 코드는 0건이다.
6. **저장은 셋뿐이다** — 영속화가 있는 프로세스는 `ENT-001`·`ENT-002`·`ENT-003` 만 건드린다(`DATA-001-01`).

## 프로세스 코드 체계

- **프로세스 코드**: `PROC-<대역 1자리><순번 2자리>` — 본 문서의 목록이 정본이다. 한 번 부여한 코드는 재사용하지 않으며 폐기 시 결번으로 남긴다.
- **대역 구분**: `1xx` 사용자 연동 본체 · `2xx` 서버 대면 API · `3xx` 기록·보관 · `4xx` 연동 라이브러리 · `9xx` 운영·횡단.
- **분류 태그**: `RR`(요청-응답형) · `EVT`(이벤트 처리형) · `BAT`(배치/스케줄형) · `WF`(워크플로형) · `INT`(연동형) 중 1개 이상.
- **개별 파일**: `process_<PROC 코드>.md` — PROC 1개 = 파일 1개. 분량이 300줄을 넘는 프로세스는 로직을 `process_<PROC 코드>-logic.md` 로 분기하고 본문에 경로를 적는다.

## 단계 라벨 체계 (본 도메인 확정)

선행 도메인은 프로세스 단계를 **단계명**(예: "복호화 판정", "결과 확정·기록")으로 인용했고, 의사코드 라벨 부여는 프로세스 도메인에 위임했다([`../services/spec-services-codes.md`](../services/spec-services-codes.md) §프로세스(PROC) 매핑). 아래 라벨을 확정한다.

| 접두 | 레이어 | 실행 위치 | 쓰는 프로세스 |
|---|---|---|---|
| `F` | FE — 사용자 웹 화면 | 사용자 브라우저 | PROC-101 ~ PROC-105 |
| `B` | BE — 허브 서버 | 허브 애플리케이션(단일 배포 단위) | 허브가 실행하는 전 프로세스 |
| `C` | 호출측 — 허브 밖의 실행 주체 | 발송처·수신처 서버 · 스케줄러 · 운영자 명령 · 라이브러리 호출 코드 | 사용자 화면이 없는 프로세스의 FE 자리 |
| `L` | 라이브러리 내부 | 발송처 프로세스 안(별도 배포 단위) | PROC-401 ~ PROC-404 |

- **번호는 레이어별로 1부터** 붙이고 실행 시간 순으로 증가한다(`F1`·`F2` … / `B1`·`B2` …).
- **한 단계가 갈라지면 접미 문자**를 쓴다 — `B4a`(승인) · `B4b`(거부). 세부 절차는 하이픈 — `B2-1`.
- **`C` 는 FE 자리를 대신한다.** 사용자 화면이 없는 프로세스(서버 대면 API·기록·배치·기동·라이브러리)도 "FE 측 처리" 섹션을 비우지 않고, 그 자리에 **호출측이 무엇을 준비해 무엇을 받는지**를 적는다. 허브가 통제하지 않는 구간임을 각 문서가 밝힌다.
- **`L` 은 BE 자리를 대신한다.** 라이브러리는 허브 서버가 아니라 발송처 프로세스 안에서 실행되므로 FE/BE 구분이 성립하지 않는다(§라이브러리 프로세스의 레이어 대응).
- **선행 도메인 단계명 ↔ 라벨 매핑표**를 각 `process_*.md` 의 §단계명 매핑에 두고, 전체 목록은 [`spec-process-mapping.md`](spec-process-mapping.md) §단계명 매핑 색인이 갖는다.

### 라이브러리 프로세스의 레이어 대응

`PROC-401`~`PROC-404` 는 **허브 애플리케이션 안에서 실행되지 않는다.** 발송처의 C# 프로젝트가 참조하는 별도 배포 단위이거나(401·402), 사람이 수행하는 배포·대조 절차다(403·404). 따라서 브라우저 화면도 허브 서버 처리도 존재하지 않는다([`../functions/spec-functions-api.md`](../functions/spec-functions-api.md) §표면 구분 — "연동 라이브러리는 허브 애플리케이션이 아니라 발송처 프로세스 안에서 실행되는 별도 배포 단위다").

- "FE 측 처리" 자리 → **라이브러리 호출측**(발송처 애플리케이션 코드 · 허브 운영자의 배포 작업) 처리를 `C` 라벨로 기술한다.
- "BE 측 처리" 자리 → **라이브러리 내부**(또는 배포 산출물 생성 절차) 처리를 `L` 라벨로 기술한다.
- 이 대응은 네 문서 본문에 근거와 함께 명시한다. 빈 섹션으로 두지 않는다.

## 프로세스 간 의존관계

한 행이 **본 프로세스가 무엇에 의존하고 무엇을 부르는지**를 나타낸다. 화살표는 제어 흐름이며 도식 대신 표로 표현한다.

- **순환 의존이 없다.** 허브 안의 호출 깊이는 세 층이다 — 0층 `PROC-901`, 1층 접점 프로세스(101·102·103·201~204·304), 2층 하위 프로세스(104·105·301·302·303). `PROC-301 → PROC-303` 이 유일한 2층 내부 호출이며 역방향 호출이 없다.
- **PROC-104 의 두 구간**은 PROC-103 이 순서대로 호출한다 — ① 복호화 구간(승인·거부 공통) ② 전달 구간(승인 확정·증적 기록 이후). 두 구간 사이에 PROC-103 의 게이팅이 놓이는 이유는 **증적 없는 전달을 만들지 않기 위해서다**(`BIZ-003-04`). 상세는 [`process_PROC-104.md`](process_PROC-104.md) §진입점 및 진입 조건.
- **화면이 부르는 것은 접점**이지 하위 프로세스가 아니다. 한 화면 액션은 하나의 접점 프로세스를 트리거하고, 그 안의 호출 관계는 서버가 갖는다([`../screens/screen_SCR-002.md`](../screens/screen_SCR-002.md) §사용자 인터랙션).

| PROC-104 | 전달 호출은 트랜잭션 밖 · 결과 확정(PROC-301+303)만 트랜잭션 | 조건부 UPDATE(`result_code IS NULL`) |
| PROC-201 | 결과 확인 표시 + 응답 구성 = **같은 처리 경계** | 조건부 UPDATE(`result_confirmed_at IS NULL`) |
| PROC-203 | 콜백 기록 단일 트랜잭션 | 조건부 UPDATE(`callback_received_at IS NULL`) — 중복 통지가 최초 시각 유지 |
| PROC-301 · PROC-303 | 호출한 상위 프로세스의 트랜잭션에 참여 | 위 조건부 UPDATE·원자적 UPSERT |
| PROC-302 | 상위(PROC-103) 트랜잭션에 참여 | 추적 레코드 행 잠금으로 중복 증적 차단 |
| PROC-304 | 대상별 독립 트랜잭션(순서 제약 없음 — FK 부재) | 기준 일시 기반 재산정으로 두 번째 실행은 0건(`DATA-002-04`) |
| PROC-401·402·403·404·901 | 영속화 없음 | 상태를 공유하지 않는 순수 계산·절차 |

- **외부 호출(수신처 전달)을 트랜잭션 안에 넣지 않는다** — 재시도 총 소요 상한(`BIZ-004-02`)만큼 걸릴 수 있는 호출을 트랜잭션이 감싸면 연결이 그 시간만큼 점유된다. 값은 정책이 정본이며 본 사양에 복제하지 않는다.
- **보상 트랜잭션을 두지 않는다.** 전달이 성공한 뒤 결과 확정이 실패해도 허브는 수신처에 취소를 보낼 수단이 없다 — 이 경우 결과 미확정으로 끝나고 사용자는 다시 시도할 수 있으며, 재시도는 확정 결과 재안내 또는 재전달로 수렴한다([`process_PROC-104.md`](process_PROC-104.md) §실행 제약사항).

### 담당자 확인 대기 — 기본안 적용

- **수신처 전달 실패 후의 재시도 경로**(PRD §미결·확인 필요 ⑦) — 진입 중 즉시 재시도(`PROC-104`)만 수행하고 확정 후 재연동은 발송처가 새 추적 키로 새 요청을 발행하는 **기본안**을 적용했다.
- **자가진단 API 의 운영 환경 노출**(같은 문서 ⑧) — **운영 환경에도 노출**하되 비공개 경로를 유지하는 **기본안**을 적용했다(`PROC-204`·`PROC-901`).
