# 연동 결과 안내 기능 정의

정본 목록은 [`spec-process.md`](spec-process.md). 단계 라벨 체계도 그 문서가 갖는다. 용어는 [`../../../wiki/WIKI.md`](../../../wiki/WIKI.md).

## 개요

- **정의 대상**: 연동이 어떻게 끝났는지를 **세 경로 중 하나로 골라 안내 정보를 구성**하는 처리다. 결과 구분 → 경로 번호 대응이 이 프로세스 한 곳에만 있다 — 대응을 여러 곳에 두면 화면이 보는 결과와 발송처가 조회하는 결과가 갈린다.
- **관련 PRD 요구사항**:
	- [`../../prd/PRD.md`](../../prd/PRD.md) §수행 범위 6 — "결과를 **세 경로**로 구분해 사용자에게 표시한다 — 연동 완료 · 링크·복호화 오류 · 수신처 전달 실패 … 결과가 이미 확정된 링크로 다시 진입하면 **그 결과 경로를 그대로 다시 안내**한다(경로를 추가하지 않는다)."
	- [`../../prd/PRD.md`](../../prd/PRD.md) §수행 범위 6 — "**연동 완료 결과만** … **복귀 주소로 자동 이동**한다 … **완료가 아닌 결과는 이동할 주소를 받지 못하므로**(허브가 복귀 주소를 싣지 않는다) 결과 화면에 머문다."

### 진입점 및 진입 조건

본 프로세스는 외부 표면을 갖지 않는다. **결과 또는 실패가 확정된 지점에서 상위 프로세스가 응답을 만들기 직전에 호출**한다.

| 호출 지점 | 입력 출처(`source`) | 전달 값 |
|---|---|---|
| PROC-101 `B6` | `ENTRY_FAILURE` | 진입 단계 실패 사유(`EX-SEC-001`·`EX-SEC-004`·`EX-OPS-002`) |
| PROC-102 `B7` | `RECORD` | 확정된 [`MDL-001`](../datas/model_MDL-001.md) + `isReAnnouncement = true` |
| PROC-102 `B4b` · PROC-103 `B2` | `REASON_CODE` | `EX-SEC-002` 등 실패 사유 |
| PROC-103 `B4` | `RECORD` | 확정된 `MDL-001` + `isReAnnouncement = true` |
| PROC-103 `B8` | `RESULT_CODE` | 이번에 확정된 결과 구분 |

- **진입 조건**: **인증 없음 — `AUTH-001` 인용.** 상위 프로세스 안에서 실행되므로 자체 진입 조건이 없다.
- **사전 검증**: 입력이 위 네 출처 중 하나여야 한다. 어느 것에도 해당하지 않으면 **경로 ②** 로 안내한다(`SVC-005` F-003).
- **`RECORD` 출처가 실어 오는 결과 구분은 둘뿐이다** — `SUCCESS`·`DELIVERY_FAILED`. `DECRYPT_FAILED` 는 추적 레코드에 기록되는 경로가 없어(EXC-BIZ-14) `RECORD` 로 들어오지 않는다. 복호화 실패는 `REASON_CODE`(`EX-SEC-002`)로 들어와 `resultCode = null` 경로를 타고 ② 가 된다. **미동의 이탈은 결과를 확정하지 않아 어떤 출처로도 들어오지 않는다**(`BIZ-003-03` — 결과 단계로 보내지 않는다).

### 입력/출력 정의

| 구분 | 항목명 | 데이터 타입 | 필수 | 설명 |
|------|--------|------------|------|------|
| 입력 | `source` | string | Y | `ENTRY_FAILURE` · `REASON_CODE` · `RESULT_CODE` · `RECORD` |
| 입력 | `resultCode` | string | N | `RESULT_CODE`·`RECORD` 일 때. 결과 구분 3종(`BIZ-001-01`) |
| 입력 | `reasonCode` | string | N | `ENTRY_FAILURE`·`REASON_CODE` 일 때. EX 코드 |
| 입력 | `isReAnnouncement` | boolean | N | 확정 결과 재안내 여부(기본 `false`) |
| 입력(주입) | `<COMPLETION_REDIRECT_URL>` | 상수 | Y | [`MDL-022`](../datas/model_MDL-019-022.md). **호출측이 실어 오지 않고 본 프로세스가 구성 상수에서 직접 읽는다**(근거는 §구현 가이드). **값을 본 사양에 복제하지 않는다**(`OPS-001-04`) |
| 출력 | `resultPath` | number(1~3) | - | [`MDL-009`](../datas/model_MDL-007-010.md) |
| 출력 | `isReAnnouncement` | boolean | - | 화면 보조 표시 판단에만 쓴다 |
| 출력 | `returnUrl` | string | N | [`MDL-009`](../datas/model_MDL-007-010.md) 복귀 주소. **경로 ① 에만 나타나고 ②·③ 에는 속성 자체가 없다**(`BIZ-001-06` — 빈 문자열·`null` 로 채우지 않는다) |

### 연관 데이터 및 외부 호출

- **호출 API**: 없음.
- **데이터 조회 대상**: **없음 — 어떤 ENT·MDL 도 조회하지 않는다.** 호출측이 이미 확보한 값과 **기동 시 주입된 구성 상수**([`MDL-022`](../datas/model_MDL-019-022.md) — `B3` 의 복귀 주소)만 읽는다. 구성 상수는 애플리케이션 설정에서 기동 시 한 번 읽어 보유하는 불변 값이라 **DB 조회가 아니다**(`DATA-001-05` — 구성을 데이터베이스에 두지 않는다). 따라서 대상 ENT·조건절·정렬·조인·락이 성립하지 않는다.
- **데이터 변경 대상(CRUD)**: **없음.** 재안내는 레코드를 갱신하지 않고(`BIZ-002-04`) 지표도 계수하지 않는다(`BIZ-005-03`). **결과 확인 표시(FN-010)를 호출하지 않는다** — 사용자 화면의 재안내는 발송처의 결과 수령이 아니다.

### 실행 제약사항

- **트랜잭션 경계**: **없음.** 영속화가 없는 순수 변환이다.
- **동시성 제어**: 상태를 갖지 않으므로 락·멱등 키가 필요 없다. 같은 입력은 항상 같은 출력을 낸다.
- **성능 요구**: 상수 시간 매핑이다.
- **보안 요구**: 응답에 담는 것은 **결과 경로 번호·재안내 여부, 그리고 연동 완료 결과(①)에 한해 복귀 주소뿐**이다 — **사유 코드·처리 일시·재시도 횟수·내부 단계·추적 키는 여전히 담지 않는다**(`SEC-002-05`·`DATA-001-04`). 복귀 주소는 개인정보·비밀 값이 아니라 상수 유래 URL 이라 마스킹 대상이 아니며(FN-015 §금지 항목의 예외), 경로 ②·③ 과 오류 응답 엔벨로프에는 실리지 않는다(`BIZ-001-06`). 사유 코드는 오류 응답 엔벨로프의 `code` 로 이미 전달되며 화면이 설명 문구를 고르는 데만 쓴다.

### 로직 실행 순서

#### FE 측 처리 (의사코드)

```
F1. 결과 상태 수신

  진입 트리거: 아래 셋 중 하나
    ① 진입 응답의 초기 상태 stage = 'RESULT'      (PROC-101 F1 에서 넘어옴)
    ② 본인확인 응답 stage = 'RESULT'              (PROC-102 F2)
    ③ 승인 응답 또는 오류 응답 엔벨로프             (PROC-103 F5)
  사용 상태:
    resultPath        = 로컬 상태<1|2|3>
    isReAnnouncement  = 로컬 상태<boolean>(기본 false)
    reasonCode        = 로컬 상태<string | null>   // 경로 ② 의 설명 문구 선택에만 쓴다
    returnUrl         = 로컬 상태<string | null>   // 있으면 이동 · 없으면 잔류 (유일한 신호)
  응답 어댑터 변환:
    if (응답이 오류 엔벨로프)
        reasonCode = err.code
        resultPath = (err.code == 'EX-BIZ-002' ? 3 : 2)
        returnUrl  = null                          // 엔벨로프는 { code, message, details? } 로 닫혀 있다 (FN-014)
        // 502 EX-BIZ-002 도 정상 종료다 — 처리 실패 화면이 아니라 결과 안내다
    else
        resultPath       = res.resultPath
        isReAnnouncement = res.isReAnnouncement
        returnUrl        = HAS_FIELD(res, 'returnUrl') ? res.returnUrl : null
  검증:
    if (resultPath 가 1~3 밖이거나 없다)   resultPath = 2   // 빈 화면·예외 화면을 만들지 않는다
    if (returnUrl != null
        AND NOT (returnUrl 이 'https://' 또는 'http://' 로 시작한다))
        returnUrl = null                           // 절대 URL 재확인 — 미달이면 이동하지 않는다 (SVC-005 F-008)
    // resultPath 로 이동 여부를 다시 판정하지 않는다 — 신호는 필드 존재 여부 하나뿐이다 (POL BIZ-001-06)

F2. 경로별 패널 렌더 (SCR-004)

  경로 → 아이콘·색·제목·설명·다음 안내는 SCR-004 §결과 3경로가 정본이다
  if (resultPath == 2)   설명 문구를 reasonCode 로 고른다 (제목·아이콘·색은 사유와 무관하게 같다)
  if (isReAnnouncement)  배지 `재안내` + 덧붙이는 문장 (제목 바로 아래)
  if (returnUrl != null)
      이동을 사전 고지하고 남은 시간을 함께 표시한다
      // 문구·표시 형태와 대기 시간 값은 SCR-004 가 정본이다 — 본 사양은 시간 값을 갖지 않는다
  캐시·전역 상태 갱신: 없다
  표시 금지: 추적 키 · 사유 코드 원문 · 처리 일시 · 재시도 횟수 · 내부 단계

F3. 폐기·복귀 이동 (또는 잔류)

  정리 (이동보다 먼저 수행한다):
      페이지 메모리의 암호값 쌍·생년월일을 폐기한다 (POL DATA-001-03)
      // 이동이 일어나지 않아도 잔류 화면에 민감값이 남지 않는다.
      //   이동에 필요한 값은 returnUrl 뿐이라 폐기가 이동을 막지 않는다
  UI 전이:
      if (returnUrl == null)                       // 경로 ②·③ · 오류 엔벨로프 · 형식 미달
          잔류한다 — 화면이 제공하는 이동 수단을 두지 않는다
      else
          SCR-004 가 정한 대기 시간이 지나면 returnUrl 로 이동한다
              이동은 브라우저 이력을 치환(replace)한다 — 새 이력 항목을 쌓지 않는다
          이동과 함께 화면은 수동 이동 수단을 제공한다 (형태·문구는 SCR-004)
          // 이동이 막혀도 화면은 그대로 남고 사용자가 스스로 갈 수 있다.
          //   막혔는지를 애플리케이션이 판정하지 않는다 — 판정 수단이 없고, 판정할 필요도 없다
  실패 처리: 이 단계에는 서버 호출이 없어 실패 경로가 없다.
            이동 실패는 예외가 아니다 — EX 코드를 만들지 않고 결과 경로도 바꾸지 않는다
            (POL BIZ-001-06 · SVC-005 §예외 사항)
```

#### BE 측 처리 (의사코드)

```
B1. 결과 확보 (호출 진입)

  엔드포인트·메서드: 없음 — 상위 프로세스 안에서 함수로 실행된다
  인증·인가 검증: 인증 없음 — AUTH-001 인용
  입력 재검증:
    if (source not in ['ENTRY_FAILURE','REASON_CODE','RESULT_CODE','RECORD'])
        → resultPath = 2 로 확정하고 B3 으로 간다        // 매핑되지 않는 상태는 경로 ②
  값 확보:
    if (source == 'RECORD')       resultCode = input.record.resultCode
                                  // 레코드가 실어 오는 값은 SUCCESS·DELIVERY_FAILED 뿐이다 (EXC-BIZ-14)
    if (source == 'RESULT_CODE')  resultCode = input.resultCode
    if (source in ['ENTRY_FAILURE','REASON_CODE'])  resultCode = null

B2. 결과 경로 선택 — POL BIZ-001-02 · BIZ-001-03 (validate)

  // 결과 구분 → 경로 번호 대응은 이 자리 한 곳에만 둔다
  switch (resultCode)
      case 'SUCCESS'          → resultPath = 1
      case 'DECRYPT_FAILED'   → resultPath = 2     // 방어적 분기 — 현 설계에서 도달하지 않는다 (EXC-BIZ-14)
      case 'DELIVERY_FAILED'  → resultPath = 3
      case null               → resultPath = 2     // 진입 단계 실패·규약 위반(추적 레코드 없음) — 복호화 실패는 실제로 이 자리로 온다
      default                 → resultPath = 2     // 매핑되지 않는 상태 (SVC-005 F-003)
  // 네 번째 경로를 만들지 않는다 — 미동의 이탈에도 경로를 부여하지 않는다 (POL BIZ-003-03)
  // 결과 구분 값을 변환·별칭화하지 않는다 (POL BIZ-001-03)
  정책 적용 지점: BIZ-004-04 — 확정 후 재연동은 허브가 수행하지 않는다.
                  경로 ②·③ 의 "다음 안내"가 발송처 재요청·새 링크 요청을 가리키는 근거다

B3. 결과 안내 구성 — POL BIZ-002-04 ③ · SEC-002-05 (mask) · POL BIZ-001-06 (mask)

  info = { resultPath, isReAnnouncement: (input.isReAnnouncement ?? false) }

  // 복귀 주소 동봉 판정 — BR-025 (BR-008 이 고른 경로를 입력으로 받는 후속 판정)
  // 이 판정은 서버의 이 자리 한 곳뿐이다 — 호출측·화면·다른 프로세스가 다시 판정하지 않는다
  url = 구성 상수 <COMPLETION_REDIRECT_URL>          // MDL-022 — 기동 시 주입된 불변 값
  if (info.resultPath == 1                           // ① 연동 완료 한정 (POL BIZ-001-06 · EXC-BIZ-15)
      AND url 이 'https://' 또는 'http://' 로 시작한다)   // 절대 URL 한정 (SVC-005 F-008)
      info.returnUrl = url
  // 조건을 벗어나면 속성 자체를 두지 않는다 — 빈 문자열·null 로 채우지 않는다 (MDL-009)
  // isReAnnouncement 를 조건에 넣지 않는다 — 재안내는 같은 경로의 재표시이므로 거동이 같다
  //   (BR-009 와 독립 · POL BIZ-002-04 ③)
  // 대상 조건은 담당자 확정으로 종결됐다 — 넓히려면 PRD 개정이 선행된다 (EXC-BIZ-15)

  // 영속화하지 않는다 — 재안내 여부·복귀 주소 모두 안내 구성에만 쓰는 표시 정보다
  // 추적 레코드를 갱신하지 않는다 (보관 기산점이 밀리지 않는다)
  // 지표를 계수하지 않는다 (POL BIZ-005-03)
  // 결과 확인 표시(FN-010)를 호출하지 않는다 — 사용자 재안내는 발송처의 결과 수령이 아니다
  마스킹: FN-015 — 추적 키·복호화 원문·암호값·생년월일·처리 일시를 담지 않는다
  사전 조회 쿼리: 없음 · 영속화 쿼리: 없음
  return info                                      // MDL-009
  후속 이벤트 발행: 없음
```

### 실행 결과

- **정상 결과**: [`MDL-009`](../datas/model_MDL-007-010.md) `{ resultPath, isReAnnouncement, returnUrl? }`. `returnUrl` 은 **경로 ① 에만 나타난다**(`BIZ-001-06` · BR-025). **영속화·이벤트 발행 없음** — 복귀 주소도 저장하지 않고 매 응답 구성 시점에 상수에서 실린다.
- **실패 결과**: 없음 — 본 프로세스에는 실패 경로가 없다. 호출측의 실패는 이미 경로 값으로 표현된다.
- **후속 트리거**: 없음 — **허브 안에서는 어떤 프로세스도 부르지 않는다.** 다만 경로 ① 은 여기서 화면이 끝나지 않고, 화면이 복귀 주소로 사용자를 출발지로 돌려보낸다(허브 밖으로 나가는 브라우저 이동이며 허브의 후속 처리가 아니다). 경로 ②·③ 은 결과 화면에 머문다. 이후 확인은 발송처의 조회(PROC-201·PROC-202)로 이어진다.

- **선행 관계**: PROC-101 · PROC-102 · PROC-103 · PROC-104 중 하나에서 결과 또는 실패가 확정돼야 한다.
- **이벤트 관계**: 없음.

### 구현 가이드

- **결과 구분 → 경로 대응을 한 곳에만 둔다.** 화면·조회 API·다른 프로세스가 각자 구현하면 같은 연동이 자리마다 다르게 읽힌다([`../datas/model_MDL-007-010.md`](../datas/model_MDL-007-010.md) `MDL-009` 구현 가이드).
- **경로 ② 는 두 출처를 받는다** — 결과 구분 `DECRYPT_FAILED` 와 추적 레코드가 없는 진입 단계 실패다(둘 다 실제로는 사유 코드로 도착한다 — 복호화 실패는 `EX-SEC-002`). 따라서 **결과 구분 값이 없어도 이 경로를 그릴 수 있어야 한다**.
- **`case 'DECRYPT_FAILED'` 는 방어적 분기다 — 현 설계에서 어느 출처로도 이 값이 들어오지 않는다.** ① `RECORD` 는 그 값이 담긴 행이 만들어지는 경로가 없어(EXC-BIZ-14) 실어 올 수 없고 ② `RESULT_CODE` 는 PROC-103 이 이번에 확정한 결과라 `SUCCESS`·`DELIVERY_FAILED` 뿐이며 ③ 복호화 실패는 `REASON_CODE`(`EX-SEC-002`)로 들어와 `resultCode = null` 자리에서 ② 가 된다. **분기를 지우지 않는다** — 열거형 전건을 다루는 편이 안전하고, 값 체계는 3종을 유지한다(`BIZ-001-01`·`BIZ-001-03`). 후행 단계는 이 분기의 도달 불가를 결함으로 보고하지 않는다.
- **`USER_DENIED` 분기는 되살리지 않는다.** 거부가 결과 경로에서 폐지되면서 값 자체가 값 체계에서 제거됐다(`BIZ-001-01` 구현 가이드 — 거부 값을 되살리지 않는다). `DECRYPT_FAILED` 와 성질이 다르다 — 그 값은 지표 집계에 실제로 누적되지만 `USER_DENIED` 는 어디에도 누적되지 않는다. 미동의 이탈은 **결과 미확정**이라 이 프로세스에 도달하지 않는다(`BIZ-003-03`).
- **`RECORD` 출처에 `reasonCode` 가 없어도 문제가 되지 않는다.** 경로 ② 의 설명 문구는 사유 코드가 고르는데, 확정 결과 재안내로 경로 ② 가 나오는 경우가 없기 때문이다([`../screens/screen_SCR-004.md`](../screens/screen_SCR-004.md) §확정 결과 재안내 — 배지가 붙는 경로는 ①·③).
- **재안내에서 아무것도 쓰지 않는다.** `result_confirmed_at` 을 건드리면 보관 기산점이 밀리고(`BIZ-002-04`), 요청 수를 올리면 지표가 중복된다(`BIZ-005-03`).
- **`isReAnnouncement` 를 저장하지 않는다.** 안내 구성에만 쓰는 표시 정보이며 대응 컬럼이 없다.
- **경로 값이 범위를 벗어나면 화면이 아니라 서버가 먼저 보정한다.** 서버가 `1~3` 을 보장해야 화면이 빈 상태를 다루지 않는다.
- **동봉 판정은 `B3` 한 곳뿐이고, `B2` 는 경로만 고른다.** `B2` 에 동봉 조건을 넣으면 경로 선택과 이동 판정이 한 덩어리가 되어, 적용 경로가 바뀔 때 경로 대응까지 흔들린다. 이 분리 덕에 **적용 경로가 ①·② 둘에서 ① 하나로 좁혀졌을 때**(`EXC-BIZ-15`) 실제로 바뀐 것은 `B3` 의 조건 한 줄뿐이고 `B2`·화면·계약 형상은 그대로였다.
- **`isReAnnouncement` 는 동봉 판정에 관여하지 않는다.** 확정 결과 재안내는 새 경로가 아니라 **같은 경로의 재표시**이므로(`BIZ-002-04` ③) 거동도 같아야 값 체계가 갈리지 않는다 — BR-025 와 BR-009 는 독립이다([`../services/service_SVC-005.md`](../services/service_SVC-005.md) §분기 흐름).
- **화면은 필드 존재 여부만 본다.** "있으면 이동·없으면 잔류"가 유일한 신호이며, **화면이 `resultPath` 로 이동 여부를 다시 판정하지 않는다**(`BIZ-001-06`). 오류 응답 엔벨로프 경로에는 필드가 없으므로 자연히 잔류한다 — 화면에 오류 경로용 분기를 따로 두지 않아도 된다.
- **이동은 브라우저 이력을 치환(replace)한다.** ① 새 이력을 쌓으면 뒤로 가기로 결과 화면에 돌아오는데, 그때 화면은 이미 상태를 잃어 진입부터 다시 시작하고 URL 의 암호값이 다시 판정을 탄다 ② 암호값이 실린 URL 을 이력에 덜 남긴다(`DATA-001-04`).
- **메모리 폐기를 이동보다 먼저 한다.** 이동이 일어나지 않아도 잔류 화면에 암호값 쌍·생년월일이 남지 않고(`DATA-001-03`), 이동에 필요한 값은 `returnUrl` 뿐이라 폐기가 이동을 막지 않는다.
- **이동 실패에 EX 코드를 두지 않는다.** 창 차단·이동 불가는 이미 확정된 결과를 바꾸지 않는 화면 후처리다. EX 코드를 만들면 오류 응답 엔벨로프가 필요해지고 그 엔벨로프는 경로 ②·③ 으로 읽혀 확정 결과를 뒤엎는다(`BIZ-001-04`). **화면 잔류 + 수동 이동 수단**으로 흡수하며 형태는 `SCR-004` 가 정한다.
- **대기 시간 값을 본 사양에 두지 않는다.** 결과를 보여 주고 이동하기까지의 시간은 **화면 사양이 정본**이다([`../screens/screen_SCR-004.md`](../screens/screen_SCR-004.md)). 프로세스가 값을 복제하면 정본이 둘이 된다(`OPS-001-04`).
- **복귀 주소를 호출측 입력으로 받지 않고 `B3` 이 구성 상수에서 직접 읽는다.** 호출측이 넷(PROC-101·102·103·104)이라 실어 나르게 하면 **전달 경로가 넷**이 되고, 그중 하나만 빠뜨려도 같은 경로 ① 인데 응답이 달라진다 — 판정을 한 곳에 둔다는 `BIZ-001-06` 이 무너진다. 상수는 기동 시 한 번 읽어 보유하는 불변 값이므로(`MDL-022`) 매 요청 조회 비용도 없다. `B3` 의 절대 URL 확인은 기동 검증(PROC-901 `B3`)에 이은 **2차 방어**이며, 주소의 출처가 외부 입력으로 확정되면(PRD §미결·확인 필요 ⑦) 그때는 1차 검증이 된다 — 그 경우에도 바뀌는 것은 **값을 얻는 자리뿐**이고 동봉 규칙·필드 형상은 그대로다.
