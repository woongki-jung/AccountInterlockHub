# 동의·승인 제출 기능 정의

정본 목록은 [`spec-process.md`](spec-process.md). 단계 라벨 체계도 그 문서가 갖는다. 용어는 [`../../../wiki/WIKI.md`](../../../wiki/WIKI.md).

## 개요

- **정의 대상**: 상수로 고정된 동의 항목을 사용자에게 그대로 보여 주고, **전 항목 동의를 조건으로 승인 제출을 받아 연동을 진행**하는 처리다. 승인 제출 하나가 재복호화·증적 기록·수신처 전달·결과 확정을 차례로 발화시키는 **오케스트레이션 지점**이다. **거부를 제출하는 경로는 없다** — 미동의 제출은 화면이 막고 결과 단계로 보내지 않는다(`BIZ-003-03`).
- **관련 PRD 요구사항**:
	- [`../../prd/PRD.md`](../../prd/PRD.md) §제공 가치 — "**동의 기반 투명성**: … **전 항목 동의가 진행 조건**이므로 동의 없이 연동이 실행되는 경로가 없다."
	- [`../../prd/PRD.md`](../../prd/PRD.md) §수행 범위 4 — "… 상수로 고정된 동의 항목 노출, **전 항목 동의를 조건으로 승인 제출**. 동의하지 않은 채 제출하면 동의 화면의 **유효성 안내**로 막고 결과 단계로 보내지 않는다 — **사용자 거부는 결과 경로가 아니다**. 동의하지 않으려는 사용자의 종료 수단은 창을 닫는 것이며, 그 연동은 결과 미확정으로 남아 보관 기한에 삭제된다."

### 진입점 및 진입 조건

- **진입점**: `POST <INTERLOCK_ENTRY_PATH>/approve` — 요청 본문 `{ encX, encY, birthDate, agreedItemCodes }`([`../functions/spec-functions-api-user.md`](../functions/spec-functions-api-user.md) §동의·승인 제출).
- **진입 조건**: **인증 없음 — `AUTH-001` 인용.** 본인확인 통과 사실을 서버가 기억하지 않으므로 **승인 요청이 생년월일과 암호값을 다시 실어 오고, 서버는 매번 처음처럼 검증한다**(§생년월일 재수신 규약).
- **요청 제한**: **미적용 — 수용 리스크**(`OPS-002-03`).
- **사전 검증**: ① `birthDate` 형식(PROC-104 `B1`) ② 재복호화 판정(PROC-104 `B2`) ③ 추적 레코드 확보(PROC-301) ④ 필수 동의 충족(`B5b`).
- **이 접점에 종료 통지가 오지 않는다.** 동의하지 않는 사용자의 종료 수단은 **창을 닫는 것**이고 그 연동은 **결과 미확정**으로 남는다(`EXC-BIZ-05`) — 종료를 알리는 요청·필드·단계를 두지 않는다.

### 연관 데이터 및 외부 호출

- **호출 API**: 없음(직접). 수신처 전달은 **PROC-104 `B4`** 가 수행한다.
- **데이터 조회 대상**: [`ENT-001`](../datas/data_ENT-001.md) 기본 키 단건 조회(PROC-301 `B2`) · `B6` 의 행 잠금 재조회(`tracking_key`·`result_code`·`created_at`) · [`ENT-002`](../datas/data_ENT-002.md) **전달 시도 표지 조회**(`B6` — `tracking_key` + `consented_at >= 레코드 created_at` 건수).
- **데이터 변경 대상(CRUD)**: [`ENT-002`](../datas/data_ENT-002.md) INSERT 1건(승인 확정 시 · `B6` 표지 검사에서 기존 증적이 없을 때만) · [`ENT-001`](../datas/data_ENT-001.md) 결과 확정 UPDATE 1건 · [`ENT-003`](../datas/data_ENT-003.md) 결과 카운터 +1.

### 실행 제약사항

- **트랜잭션 경계**: **다중 트랜잭션**이다. ① `B3` 레코드 확보(+요청 수 계수) ② `B6` 동의 증적 기록 ③ `B7` 이후 전달 결과 확정(+카운터). **수신처 전달 호출은 어떤 트랜잭션에도 들어가지 않는다** — 재시도 총 소요 상한(`BIZ-004-02`)만큼 연결을 점유시키기 때문이다.
- **동시성 제어**: 같은 추적 키의 동시 승인은 **추적 레코드 행을 잠근 뒤 그 잠금 안에서 기존 증적의 유무를 확인**해 중복 증적과 중복 전달을 막는다(`B6` · [`../datas/data_ENT-002.md`](../datas/data_ENT-002.md) §구현 가이드). **행 잠금만으로는 막히지 않는다** — 잠금은 두 요청의 순서를 세울 뿐이고, 증적 테이블에 유일 제약이 없어(§구현 가이드) 뒤선 요청을 멈출 수단이 없다. 결과 확정은 조건부 UPDATE 로 한 번만 성립한다(`BIZ-001-04`).
- **멱등성**: 같은 승인이 두 번 오면 두 번째는 **둘 중 하나로 수렴하며 어느 쪽도 증적·전달을 추가하지 않는다** — ① 결과가 이미 확정됐으면 `B4` 또는 `B6` 이 **아무것도 갱신하지 않고 확정 결과를 재안내**한다(`BIZ-002-04`) ② 결과가 아직 확정되지 않았으면(선행 요청이 전달 구간에 있다) `B6` 이 500 `EX-BIZ-003`(결과 미확정)으로 끝낸다. `result_code` 는 전달 **이후**에야 확정되므로 `B4` 만으로는 ② 를 거를 수 없고, 그 자리를 `B6` 의 전달 시도 표지 검사가 메운다.
- **성능 요구**: 사용자가 `SCR-003` 에서 기다리는 구간이다. 전달 재시도 총 소요 상한은 `BIZ-004-02` 가 정한다.
- **보안 요구**: **인증 없음**(`AUTH-001`). 응답·로그에 추적 키·복호화 원문·암호값·생년월일을 담지 않는다(FN-015).
- **보상 처리**: **보상 트랜잭션을 두지 않는다.** 전달 성공 후 결과 확정이 실패하면 허브가 수신처에 취소를 보낼 수단이 없다 — 결과 미확정 500 `EX-BIZ-003` 으로 끝나고 사용자가 다시 시도한다. **재시도가 전달을 되풀이하지 않는 근거는 `B6` 의 전달 시도 표지 검사**이며, 증적이 이미 있어 재제출이 `B6` 에서 멈춘다([`process_PROC-104.md`](process_PROC-104.md) §실행 제약사항).

### 로직 실행 순서

의사코드 전문은 [`process_PROC-103-logic.md`](process_PROC-103-logic.md) 이 갖는다 — `#### FE 측 처리`·`#### BE 측 처리`·`#### 데이터 변환 흐름`·`#### 단계 통합 흐름` 네 절.

- **FE 단계 라벨**: `F1`·`F2`·`F3`·`F5` — **`F4` 는 결번**(§단계명 매핑).
- **BE 단계 라벨**: `B1`·`B2`·`B3`·`B4`·`B5b`·`B6`·`B7`·`B8` — **`B5a` 는 결번**(§단계명 매핑).

### 단계명 매핑

| 선행 도메인 단계명 | 출처 | 라벨 |
|---|---|---|
| 동의 항목 구성 | SVC-003 Happy Path 1·2 · `DATA-003-01`·`DATA-003-05` | `F1` |
| 동의 항목 구성·승인 버튼 활성 판정 | `BIZ-003-01` | `F1`·`F2` |
| 미동의 제출 차단 | `BIZ-003-03` | `F2`·`F3`(화면 게이팅) · `B5b`(서버 재검증이 실제 게이트) |
| 승인 요청 재검증 | SVC-003 Happy Path 3·4 · `BIZ-003-02` | `B5b` |
| 승인 확정·동의 증적 기록 | SVC-003 Happy Path 5 · `BIZ-003-04`·`DATA-003-04` | `B6` |
| 연동 실행 이관 | SVC-003 Happy Path 6 | `B7` |

- **`F4`(거부 제출)·`B5a`(거부 처리)는 삭제되고 결번으로 남는다.** 거부 제출 경로가 폐지돼(`BIZ-003-03`) 두 단계가 사라졌다. **뒤 라벨을 당기지 않은 이유**는 살아남은 단계가 저마다 뜻을 그대로 유지해야 후행 도메인(화면·TC)의 인용이 같은 지점을 계속 가리키기 때문이다 — 라벨을 당기면 `F4`·`B5` 가 **다른 뜻으로 재사용**돼 "같은 라벨, 다른 단계"가 생긴다. 따라서 `F5`(응답 처리)와 `B5b`(승인 요청 재검증)는 라벨을 그대로 둔다.
- **`B5b` 의 접미 문자는 분기의 잔재다.** `B5a` 가 사라져 분기가 아니게 됐지만 위 이유로 이름을 바꾸지 않는다([`spec-process.md`](spec-process.md) §단계 라벨 체계 — 결번 처리).

### 실행 결과

- **승인 정상 결과**: 200 `{ resultPath: 1, isReAnnouncement: false, returnUrl }`. 영속화 — `ENT-002` 증적 1건 · `ENT-001` `result_code = SUCCESS` · `ENT-003` `success_count` +1.
- **전달 실패 결과**: 502 `EX-BIZ-002` + 결과 경로 ③. **`returnUrl` 없음**(오류 엔벨로프 — `BIZ-001-06`). 영속화 — 증적 1건 · `result_code = DELIVERY_FAILED` · `delivery_failed_count` +1.
- **미동의 결과**: **없다.** 미동의 제출은 화면이 막아 요청 자체가 오지 않고(BR-004), 화면을 우회한 제출은 400 `EX-BIZ-001` 로 끝난다(BR-005). 어느 쪽도 **결과를 확정하지 않고 어떤 카운터도 올리지 않는다**(`BIZ-005-04`). 이미 만들어진 추적 레코드는 **결과 미확정**으로 남아 보관 상한에 삭제된다(`EXC-BIZ-05`).
- **후속 트리거**: PROC-105(결과 안내) · PROC-203(수신처가 이후 완료를 통지) · PROC-201(발송처가 결과를 조회).

### 의존 프로세스

- **호출 관계**: PROC-104(동기 — 복호화 구간 `B2`, 전달 구간 `B7`) · PROC-301(동기·트랜잭션 — `B3`) · PROC-302(동기·트랜잭션 — `B6`) · PROC-303(PROC-301 경유) · PROC-105(동기 — `B4`·`B8`).
- **선행 관계**: PROC-102(본인확인 성공·레코드 확보) · PROC-901(동의 항목 구성·버전 식별자 산출).
- **이벤트 관계**: 없음. 응답으로 흐름이 끝나고, 수신처 통지는 별도 접점(PROC-203)이 받는다.

### 구현 가이드

- **증적 기록과 전달의 순서를 바꾸지 않는다.** 전달을 먼저 하면 "전달했는데 증적이 없는" 상태가 생기고, 그 상태는 사후 입증이 불가능하다(`BIZ-003-04`).
- **필수 동의 재검증에서 화면이 보낸 목록을 신뢰하지 않는다.** 항목 코드가 상수에 실재하는지까지 확인해야 증적 스냅샷과 동의 목록의 정합이 성립한다([`../datas/data_ENT-002.md`](../datas/data_ENT-002.md) §구현 가이드).
- **화면 게이팅(BR-004)이 있다고 서버 재검증(BR-005)을 생략하지 않는다.** 화면이 막는 것은 사용자 경험이고 실제 게이트는 `B5b` 다(`BIZ-003-02`). 게이팅만 두고 재검증을 생략한 구현은 반려된다.
- **거부를 받는 자리를 만들지 않는다.** 진행 의사 필드·거부 버튼·종료 통지 접점 어느 것도 두지 않는다(`BIZ-003-03`). 미동의 이탈은 서버가 인지하지 못하는 사건이라 **프로세스에 대응 단계가 없는 것이 정상**이며, 그 연동은 결과 미확정으로 남는다.
- **`FOR UPDATE` 는 추적 레코드 행에만 걸고, 그 잠금 안에서 반드시 기존 증적을 확인한다.** 잠금은 두 요청의 **순서만** 세울 뿐 뒤선 요청을 멈추지 않는다 — 잠금을 얻은 뒤 "이 레코드로 이미 전달을 시도했는가"를 묻지 않으면 두 번째 요청이 그대로 증적을 하나 더 넣고 `B7` 로 내려가 **수신처에 같은 데이터가 두 번 전달된다.** `result_code` 는 전달 **이후**(PROC-104 `B6`)에야 확정되므로 `B4` 재안내로도 걸러지지 않는다. **증적이 곧 표지인 이유**는 증적이 전달 직전에 커밋되기 때문이다(§구현 가이드 첫 항 — 증적 기록과 전달의 순서).
- **증적 조회 범위를 이번 레코드로 한정한다.** 조건은 `tracking_key` 만으로 부족하고 `consented_at >= 잠근 레코드의 created_at` 을 함께 건다. 보관 기간이 지나 추적 레코드가 삭제된 뒤 같은 키가 다시 들어오면(EXC-BIZ-04) 앞선 주기의 증적이 아직 남아 있는데([`../datas/data_ENT-002.md`](../datas/data_ENT-002.md) §관계 정의 — 증적이 더 오래 남는다), 키만으로 세면 **정상적인 새 연동이 영구히 승인되지 않는다**(매 제출이 500 으로 끝난다). 한 레코드의 생애에 승인 주기는 하나뿐이므로 이 조건이 "이번 레코드에 속한 증적"과 정확히 같다.
- **`tbl_consent_proof(tracking_key)` 에 유일 제약을 두어 해결하지 않는다.** 같은 추적 키의 증적은 **보관 주기를 넘어 여럿 공존하는 것이 정상**이라(EXC-BIZ-04 · [`../datas/data_ENT-002.md`](../datas/data_ENT-002.md) §관계 정의 · [`../datas/spec-datas.md`](../datas/spec-datas.md) §엔터티 관계 요약 2) 유일 제약은 애초에 성립하지 않는다 — 넣으면 `DATA-002-02`(증적 존속)가 깨진다. 불변식은 **행 잠금 + 범위 한정 존재 검사**로 성립하며, 이 판단은 되돌리지 않는다.
- **트랜잭션 경계를 여는 자리가 이 프로세스다.** `B3`(레코드 확보)·`B6`(증적 기록)의 `BEGIN` 이 그 두 지점이고, PROC-301·PROC-302·PROC-303 과 그 하위 FN 은 넘겨받은 실행 문맥(`exec`)으로 **참여만 한다** — 열지도 닫지도 않는다. `exec` 를 넘기지 않으면 하위가 경계 **밖**의 별도 커넥션을 잡아 `B3` 은 레코드 기록과 요청 수 계수가 각각 커밋되고(`SVC-014` F-008 원자성 파괴), `B6` 은 `FOR UPDATE` 를 건 커넥션과 갈려 직렬화가 성립하지 않는다(`BIZ-003-04`). 어느 쪽이든 요청 하나가 커넥션을 둘 점유한다([`../functions/function_FN-007-008.md`](../functions/function_FN-007-008.md) FN-008 · [`../functions/function_FN-012-013.md`](../functions/function_FN-012-013.md) FN-012 §시그니처). **`B7` 의 결과 확정 경계만 예외로 PROC-104 `B6` 이 스스로 연다** — 전달 호출을 트랜잭션 안에 넣지 않기 위해 구간이 나뉘어 있기 때문이다.
- **`EX-BIZ-002` 를 오류처럼 다루지 않는다.** 502 이지만 결과가 확정된 정상 종료이며 화면은 결과 경로 ③ 을 그린다.
- **`F5` 의 미분류 코드를 결과 경로 ② 로 보내지 않는다.** 이 접점은 `B7`(전달 실행 — PROC-301·PROC-303 으로 **결과 확정**) 다음에 `B8`(결과 안내 구성)이 오고, `EX-OPS-002` 는 정의상 **어디서 났는지 분류되지 않은** 실패라 `result_code` 가 이미 영속화된 뒤에도 날 수 있다 — 사양이 "결과 미확정"을 보장하지 못한다. 그 상태에서 결과 패널을 그리면 실제로는 완료됐을 수 있는 연동을 "새 링크를 받아 다시 진행해 주세요"(경로 ②)로 확정 통보하는 것이며, 화면이 결과 구분을 추측해 만들어 내는 셈이다(`BIZ-001-02`). **재시도 안내도 쓸 수 없다.** 다만 그 이유는 **재시도 기구가 위험해서가 아니다** — 재제출이 증적·전달을 되풀이하지 않는 것은 `B6` 의 전달 시도 표지 검사가 이미 보장한다(§구현 가이드 `FOR UPDATE` 항). 쓸 수 없는 이유는 **문구가 참이 아니게 되기 때문**이다: "다시 시도해 주세요"는 결과가 아직 확정되지 않았다는 단정인데 `EX-OPS-002` 에는 그 단정의 근거가 없다. `EX-BIZ-003` 이 `BackToConsent` 로 승인 버튼을 되살리는 것과 **갈리는 지점이 여기다** — 그 코드는 **분류된 실패라 "결과 미확정"이 코드의 뜻 자체**여서 같은 문구가 참이 된다(발생 지점이 전달 이전이라서가 아니다 — 전달 이후의 결과 확정 실패도 같은 코드를 쓴다). `Unconfirmed` 의 "받으신 링크로 다시 들어오면 결과를 확인할 수 있습니다"는 재진입을 안내하므로, 확정·미확정 어느 쪽이든 사용자가 할 일을 정확히 가리킨다. 승인 요청 발신 즉시 카드가 `SCR-003` 으로 바뀌어 승인 버튼이 사라지는 것([`../screens/screen_SCR-002.md`](../screens/screen_SCR-002.md) §화면 상태 전이 `SubmittingApprove`)은 **이 판단의 결과일 뿐 근거가 아니다.** 그래서 catch-all 은 `SCR-003` `Unconfirmed`(재진입 안내)로 받는다 — 같은 링크로 다시 들어오면 확정 결과가 재안내된다(`BIZ-002-03` ③·`BIZ-002-04`). **[`process_PROC-102.md`](process_PROC-102.md) `F3` 의 catch-all 과 목적지가 다른 이유**는 본인확인 제출이 **어떤 결과도 확정하지 않아** 미매핑 코드를 경로 ② 로 흘려도 뒤집을 결과가 없기 때문이며, 같은 비대칭이 응답 미수신에도 이미 적용돼 있다(`SCR-001` `Retryable` vs `SCR-003` `Unconfirmed`).
