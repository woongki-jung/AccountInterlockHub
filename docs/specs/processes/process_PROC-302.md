# 동의 증적 기록 기능 정의

정본 목록은 [`spec-process.md`](spec-process.md). 단계 라벨 체계도 그 문서가 갖는다. 용어는 [`../../../wiki/WIKI.md`](../../../wiki/WIKI.md).

## 개요

- **정의 대상**: 사용자가 **어느 시점의 어떤 동의 항목에 동의했는지**를 개인정보 없이 남기는 처리다. 동의 항목은 배포 상수라 시간이 지나면 내용이 바뀌므로, 버전 식별자와 함께 **그 시점의 항목 내용 스냅샷**을 보존한다.
- **관련 PRD 요구사항**:
	- [`../../prd/PRD.md`](../../prd/PRD.md) §수행 범위 10 — "**동의 증적 기록**: 사용자가 **어느 시점의 어떤 동의 항목에 동의했는지**를 개인정보 없이 남긴다(추적 키·동의 시각·동의 항목 버전). 추적 레코드와 별도 보존 기간을 갖는다."
- **관련 법규**: 개인정보 보호법 제17조(개인정보의 제공) — 제3자 제공 동의 사실의 입증 수단이다(`DATA-003`).

### 진입점 및 진입 조건

- **진입점**: PROC-103 `B6`(승인 확정) 이 **유일한 호출 지점**이다. 다른 계기에서 부르지 않는다.
- **진입 조건**: **인증 없음 — `AUTH-001` 인용.** 상위 프로세스 안에서 실행된다.
- **사전 검증**: ① 계기가 승인(`decision = APPROVE`)일 것 ② 동의한 항목 코드가 모두 상수 항목에 실재할 것. **필수 동의 충족 여부는 이 프로세스에 도달하기 전에 걸러진다**(PROC-103 `B5b` — 400 `EX-BIZ-001`).
- **거부·본인확인 실패·진입 단계 실패에는 호출되지 않는다**(`DATA-003-04`·BR-022).

### 입력/출력 정의

| 구분 | 항목명 | 데이터 타입 | 필수 | 설명 |
|------|--------|------------|------|------|
| 입력 | `trackingKey` | string(1~255) | Y | 증적과 사용자를 잇는 유일한 값 |
| 입력 | `submission.decision` | string | Y | **`APPROVE` 만 허용** |
| 입력 | `submission.agreedItemCodes` | string[] | Y | 사용자가 동의한 항목 코드([`MDL-007`](../datas/model_MDL-007-010.md)) |
| 입력 | `consent` | [`MDL-008`](../datas/model_MDL-007-010.md) | Y | 기동 시 파싱한 항목 구성 — `version`·`notice`·`items` |
| 입력 | `at` | datetime | Y | 승인 확정 시각(동의 일시·보존 기간 기산점) |
| 출력 | `proof` | [`MDL-002`](../datas/model_MDL-002.md) | - | 기록된 증적(생성 후 불변) |

### 연관 데이터 및 외부 호출

- **호출 API**: 없음.
- **데이터 조회 대상**: 없음. 버전 식별자는 기동 시 산출된 값을 읽고, 항목 구성도 상수 파싱 결과다.
- **데이터 변경 대상(CRUD)**: [`ENT-002`](../datas/data_ENT-002.md) INSERT 1건. **UPDATE·DELETE 경로를 만들지 않는다**(생성 후 불변 — 삭제는 PROC-304 소관).

### 실행 제약사항

- **트랜잭션 경계**: **호출측(PROC-103 `B6`) 트랜잭션에 참여**한다. 증적 없는 승인이나 승인 없는 증적이 생기지 않게 한다(`BIZ-003-04`).
- **동시성 제어**: 같은 추적 키의 동시 승인은 호출측이 **추적 레코드 행을 `FOR UPDATE` 로 잠근 상태**에서 부르므로 직렬화된다. 증적 테이블에는 유일 제약을 두지 않는다 — 보관 기간 차이로 **같은 추적 키의 증적이 둘 이상 공존할 수 있기 때문**이다([`../datas/data_ENT-002.md`](../datas/data_ENT-002.md) §관계 정의).
- **멱등성**: 본 프로세스 자체는 멱등하지 않다(부르면 1건이 생긴다). **승인 1건당 1회만 호출되도록 상위가 보장**한다 — 확정 레코드 재제출은 PROC-103 `B4` 재안내로 걸러진다.
- **성능 요구**: INSERT 1회. 조회가 없다.
- **보안 요구**: **인증 없음**(`AUTH-001`). 증적에 **추적 키 외의 어떤 사용자 식별 값도 넣지 않는다** — 담을 컬럼이 스키마에 없는 것이 1차 방어다(`DATA-003-02`).

### 로직 실행 순서

#### FE 측 처리 (의사코드)

**사용자 화면이 없다.** 내부 기록 기능이며 증적을 조회·표시하는 표면을 두지 않는다. FE 자리에는 **호출측(PROC-103)** 처리를 `C` 라벨로 적는다.

```
C1. 승인 확정 계기 전달 (PROC-103 B6)

  진입 트리거: 필수 동의 재검증(PROC-103 B5b)을 통과한 승인 제출
  선행 조건 확인 (호출측 책임):
    decision == 'APPROVE'                      // 거부는 부르지 않는다 (POL BIZ-003-03)
    branch != 'FIXED'                          // 확정 레코드는 재안내로 이미 걸러졌다
  트랜잭션: BEGIN 후 추적 레코드 행을 FOR UPDATE 로 잠근 상태에서 호출한다
  전달 값: { trackingKey, submission, consent, at }
           consent 는 PROC-901 이 기동 시 산출한 MDL-008 그대로다 (재파싱하지 않는다)

C2. 결과 수령

  성공 → 같은 트랜잭션을 COMMIT 하고 전달 구간(PROC-104 B3~B8)으로 넘어간다
  EX-BIZ-003 → 트랜잭션을 되돌리고 500 으로 응답한다
               결과를 확정하지 않고 수신처 전달도 수행하지 않는다 (POL BIZ-003-04)
               사용자는 다시 시도할 수 있다
```

#### BE 측 처리 (의사코드)

```
B1. 기록 계기 수신 — POL DATA-003-04 (validate)

  엔드포인트·메서드: 없음 — 상위 프로세스 안에서 함수로 실행된다
  인증·인가 검증: 인증 없음 — AUTH-001 인용
  입력 재검증:
    if (submission.decision != 'APPROVE')       → throw EX-BIZ-003 (500)
        // 승인 확정 시점에만 1건 만든다. 다른 계기의 호출은 오류다
    for each code in submission.agreedItemCodes:
        if (code 가 consent.items 의 항목 코드에 없다)   → throw EX-BIZ-003 (500)
        // 스냅샷과 동의 목록의 정합을 응용 계층에서 확인한다 —
        // JSONB 간 참조를 DB 제약으로 강제하면 스냅샷 구조 변경이 곧 제약 변경이 된다

B2. 버전 식별자 확보 — POL DATA-003-03 (transform)

  version = consent.version                     // PROC-901 B4 가 기동 시 산출한 값
  // 기록 시점에 다시 계산하지 않는다 — 같은 배포 안에서 값이 흔들리면 안 된다
  // 산출 규칙(정규화 → SHA-256 → 소문자 16진수 64자)의 정본은
  //   data_ENT-002.md §버전 식별자 산출 규칙이며 여기서 복제하지 않는다

B3. 스냅샷 구성 — POL DATA-003-02 · DATA-003-05 (transform)

  snapshot.notice = consent.notice              // 값이 없으면 빈 문자열 (안내 영역 미표시)
  snapshot.items  = SORT_BY_CODE_ASC(consent.items)
      // 각 항목은 상수표가 정의한 속성 전부 — 항목 코드·항목명·필수 여부·설명
      // 화면이 실제로 노출한 내용과 같아야 한다 (POL DATA-003-05)
  // 개인정보를 담지 않는다 — 스냅샷의 출처는 배포 상수뿐이다

B4. 동의 증적 기록 — FN-012 · POL DATA-003-04 · BIZ-003-04 (트랜잭션 참여)

  INSERT INTO tbl_consent_proof
      (tracking_key, consented_at, consent_version, consent_snapshot, agreed_item_codes)
  VALUES
      (:trackingKey, :at, :version, :snapshot, :submission.agreedItemCodes);
  -- consent_proof_id 는 기본값 gen_random_uuid()
  -- WHERE 절 없음(INSERT) · 유일 제약 없음(같은 키의 증적이 시간차로 여럿 존재할 수 있다)
  -- tracking_key 를 변형하지 않는다 (POL DATA-004-01)
  실패 시                                        → throw EX-BIZ-003 (500)

B5. 기록 결과 반환

  return { consentProofId: 생성된 행.consent_proof_id, trackingKey,
           consentedAt: at, consentVersion: version,
           consentSnapshot: snapshot, agreedItemCodes: submission.agreedItemCodes }
  // MDL-002 · 생성 후 불변 — 갱신 경로를 만들지 않는다
  마스킹: FN-015 — 로그·오류 메시지에 스냅샷 원문·추적 키를 함께 흘리지 않는다
  후속 이벤트 발행: 없음
```

### 실행 결과

- **정상 결과**: [`MDL-002`](../datas/model_MDL-002.md) 1건 반환. 영속화 — `ENT-002` 행 1건(생성 후 불변).
- **실패 결과**: `EX-BIZ-003` — 호출측 트랜잭션 되돌림. **결과 미확정·전달 미수행.**
- **후속 트리거**: PROC-304 — 동의 일시 기산 `<CONSENT_PROOF_RETENTION_MONTHS>` 경과분이 삭제 대상이 된다.

### 의존 프로세스

- **호출 관계**: 없음.
- **선행 관계**: PROC-103 승인 확정(필수 동의 재검증 통과) · PROC-901 동의 항목 파싱·버전 식별자 산출.
- **이벤트 관계**: PROC-304 — 보존 기간 경과 시 삭제된다.

### 구현 가이드

- **증적 기록과 승인 확정을 같은 처리 경계에 둔다.** 증적 없는 승인이나 승인 없는 증적이 생기지 않게 한다(`BIZ-003-04`).
- **버전 식별자를 기록 시점에 다시 계산하지 않는다.** 기동 시 산출값을 쓴다 — 같은 배포 안에서 값이 흔들리면 증적이 가리키는 내용이 불명확해진다.
- **스냅샷과 동의 목록을 한 컬럼에 섞지 않는다.** 출처가 다른 두 값(배포 상수 / 사용자 입력)을 섞으면 "무엇이 제시됐고 무엇을 골랐는지"를 가려 읽을 수 없다.
- **증적에 갱신 경로를 만들지 않는다.** 사후 입증 수단이 나중에 바뀌면 증적으로서 성립하지 않는다.
- **문구를 가공하지 않는다.** 화면에 보인 내용과 스냅샷이 어긋나면 증적이 무의미해진다(`DATA-003-05`).
- **증적 테이블에 유일 제약을 두지 않는다.** 보관 기간이 지나 추적 레코드가 삭제된 뒤 같은 키가 다시 들어오면 새 증적이 생기고, 그때 앞선 증적은 아직 보존 기간 안이다.
