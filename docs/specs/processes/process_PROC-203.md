# 완료 콜백 API 기능 정의

정본 목록은 [`spec-process.md`](spec-process.md). 단계 라벨 체계도 그 문서가 갖는다. 용어는 [`../../../wiki/WIKI.md`](../../../wiki/WIKI.md).

## 개요

- **정의 대상**: 수신처가 자기 처리를 마친 뒤 **전달받은 추적 키로 완료를 통지**하면 그 사실을 같은 추적 레코드에 이어 쓰는 처리다. 결과 구분은 건드리지 않는다 — 허브의 처리 결과와 수신처의 처리 완료는 다른 사실이기 때문이다.

	- [`../../prd/PRD.md`](../../prd/PRD.md) §서비스 이용 대상 2 — "**수신처** … 처리 완료를 허브에 콜백으로 통지한다."

### 진입점 및 진입 조건

- **진입점**: `POST /api/interlock/callback` — 요청 본문 `{ trackingKey }`([`../functions/spec-functions-api-server.md`](../functions/spec-functions-api-server.md) §완료 콜백 API).
- **진입 조건**: **인증 없음 — `AUTH-001` 인용.** 통지자가 정말 수신처인지 확인할 수단이 없다 — **위조 통지를 막을 수 없으며 수용 리스크다**(`OPS-002-02`).
- **요청 제한**: **미적용 — 수용 리스크**(`OPS-002-03`).
- **사전 검증**: ① 본문 JSON 해석 ② 추적 키 형식(FN-006) ③ 대상 레코드 존재(FN-007 — **없는 레코드를 새로 만들지 않는다**).

### 입력/출력 정의

| 구분 | 항목명 | 데이터 타입 | 필수 | 설명 |
|------|--------|------------|------|------|
| 입력 | `trackingKey` | string(1~255) | Y | [`MDL-011`](../datas/model_MDL-011-015.md). 허브가 전달한 X 안의 값을 수신처가 되돌려 준다 |
| 출력 | `trackingKey` | string | - | 입력값 무변형 에코(`DATA-004-01`) |
| 출력 | `isCallbackReceived` | boolean | - | 기록 후이므로 **항상 `true`** |
| 출력 | `callbackReceivedAt` | string(ISO 8601+오프셋) | - | **최초 수신 일시**. 중복 통지에도 같은 값 |

- **추적 키 외의 값이 본문에 실려 와도 읽지 않고 저장하지 않는다**(`DATA-001-01`).

### 연관 데이터 및 외부 호출

- **호출 API**: 없음.
- **데이터 조회 대상**: [`ENT-001`](../datas/data_ENT-001.md) 기본 키 단건 조회(PROC-301 `B2`).
- **데이터 변경 대상(CRUD)**: [`ENT-001`](../datas/data_ENT-001.md) `callback_received_at` 조건부 UPDATE 최대 1건(PROC-301 `B6`). **`result_code` 를 건드리지 않는다.**

### 실행 제약사항

- **트랜잭션 경계**: `B4` 단일 트랜잭션(조건부 UPDATE 1건). 응답 구성은 그 결과를 읽어 만든다.
- **동시성 제어**: 조건부 UPDATE(`callback_received_at IS NULL`)라 **중복 통지가 동시에 와도 최초 값 하나만 남는다**(BR-012 멱등).
- **멱등성**: 같은 통지가 여러 번 와도 최초 수신 일시가 유지되고 응답도 같다 — 수신처는 자기 통지가 이미 반영됐음을 알 수 있다.
- **성능 요구**: 단건 조회 1회 + 조건부 UPDATE 1회.
- **보안 요구**: **인증 없음**(`AUTH-001-03`). **위조 통지를 막을 수단이 없다** — 추적 키를 아는 쪽이면 누구든 통지할 수 있으며 수용 리스크다(`OPS-002-02`). 응답에 복호화 원문·암호값을 담지 않는다(담을 속성이 모델에 없다).

### 로직 실행 순서

#### FE 측 처리 (의사코드)

**사용자 화면이 없다.** 수신처가 서버에서 직접 호출하는 접점이다. FE 자리에는 **호출측(수신처 서버)** 처리를 `C` 라벨로 적는다.

```
C1. 호출측 통지 발신 (수신처 서버)

  진입 트리거: 수신처가 허브에게 전달받은 X 로 자기 회원 연결 처리를 마친 시점
  사용 값: 허브가 전달한 X 안의 trackingKey (수신처가 그대로 보관했다가 되돌려 준다)
  요청 DTO 변환:
    body    = { trackingKey: <전달받은 값 그대로> }     // 변형하지 않는다
    headers = { 'Content-Type': 'application/json; charset=utf-8' }
    // 인증 헤더·서명을 붙이지 않는다 — 허브가 요구하지도 검증하지도 않는다 (AUTH-001-03)
  호출 수단: POST <허브 기준 URL>/api/interlock/callback
  재발신 정책: 실패하면 다시 보내도 안전하다 — 최초 수신 일시가 유지된다 (BR-012 멱등)

C2. 응답 소비

  200 → callbackReceivedAt 이 최초 수신 일시다.
        자기 통지가 처음 반영됐는지, 이미 반영돼 있었는지는 이 값으로 판단한다
        trackingKey 에코로 요청·응답 대응을 확인한다
  400 EX-DATA-002 → 추적 키 형식을 고친다 (전달받은 값을 변형했을 가능성)
  404 EX-DATA-001 → 그 키의 레코드가 없다 (미진입·보관 만료 삭제 — 구별하지 않는다).
                    허브는 레코드를 되살리지 않으므로 재발신해도 결과가 같다
  500 → 잠시 후 다시 보낸다 (멱등하므로 안전하다)
```

#### BE 측 처리 (의사코드)

```
B1. POST /api/interlock/callback 진입

  엔드포인트·메서드: POST /api/interlock/callback
  인증·인가 검증: 인증 없음 — AUTH-001 인용 (401·403 미정의)
                  통지자가 수신처인지 확인하지 않는다 — 위조 통지를 막을 수단이 없다 (OPS-002-02)
  요청 제한: 미적용 — 수용 리스크 (OPS-002-03)
  메서드 불일치: 405 (본문 없음)
  캐시: 응답에 캐시 금지를 지정한다

B2. 입력 검증 — FN-006 · POL DATA-004-03 (validate)

  if (본문을 JSON 으로 해석할 수 없다)          → 400 FN-014('EX-DATA-002')
  if (!FN-006(body.trackingKey))                → 400 FN-014('EX-DATA-002',
                                                     [{ field: 'trackingKey', reason: 'FORMAT' }])
  // 기록을 수행하지 않고 끝낸다
  // 추적 키 외의 필드는 읽지 않는다 (POL DATA-001-01)

B3. 추적 키 사전 조회 — PROC-301 호출 · POL BIZ-002-03 · BIZ-002-05 (validate)

  lookup = PROC-301({ kind: 'LOOKUP', trackingKey: body.trackingKey })
      // exec 를 넘기지 않는다 — 이 자리는 아직 경계를 열지 않았다(BEGIN 은 B4 다).
      //   LOOKUP 은 단독 읽기로 성립한다 (빠뜨린 것이 아니다 — PROC-301 §입력/출력 정의)
      // PROC-301 B2 (FN-007):
      //   SELECT tracking_key, result_code, result_at, result_confirmed_at,
      //          callback_received_at, created_at
      //   FROM tbl_interlock_tracking
      //   WHERE tracking_key = :trackingKey;
  if (lookup.branch == 'NONE')                  → 404 FN-014('EX-DATA-001')
      // 없는 레코드를 새로 만들지 않는다 · 삭제된 레코드를 되살리지 않는다

B4. 완료 콜백 기록 — PROC-301 호출 · BR-012 · POL BIZ-001-04 (트랜잭션)

  BEGIN ISOLATION LEVEL READ COMMITTED;          // 경계를 여는 자리는 여기다
    receivedAt = PROC-301({ kind: 'RECORD_CALLBACK',
                            trackingKey: body.trackingKey, at: NOW(), exec })
        // exec = 여기서 연 커넥션·실행자를 그대로 넘긴다 — 이 전달이 참여의 성립 조건이다
        // PROC-301 B6 (FN-011):
        //   UPDATE tbl_interlock_tracking
        //   SET callback_received_at = :at
        //   WHERE tracking_key = :trackingKey AND callback_received_at IS NULL;
        // 갱신 1행 → 이번이 최초 수신 → receivedAt = :at
        // 갱신 0행 → 중복 통지 → 기존 callback_received_at 을 그대로 반환
  COMMIT;                                       // 실패 → 500 FN-014('EX-BIZ-003')
  // result_code 를 건드리지 않는다 (BR-021) — 결과 확정과 완료 통지는 다른 사실이다
  // 전달이 실패한 연동에 통지가 와도 사실만 기록하고 정합을 검사하지 않는다
  // 지표를 계수하지 않는다 — 계수 계기 목록에 없다 (POL BIZ-005-02)

B5. 응답 구성 — POL DATA-004-01 (mask)

  body = { trackingKey:        body.trackingKey,        // 입력값 무변형 에코
           isCallbackReceived: true,                    // 기록 후이므로 항상 true
           callbackReceivedAt: receivedAt → ISO 8601 + 오프셋 }
  return 200 FN-015(body)                       // MDL-013 재사용 (새 모델을 만들지 않는다)
  후속 이벤트 발행: 없음. 발송처는 PROC-202 조회로 확인한다 (푸시 통지 경로를 두지 않는다)
```

### 실행 결과

- **정상 결과**: 200 [`MDL-013`](../datas/model_MDL-011-015.md). 최초 수신이면 `ENT-001.callback_received_at` 1건 갱신. 중복 수신이면 **영속화 없음**.
- **실패 결과**: 400·404·500 오류 응답 엔벨로프.
- **후속 트리거**: 없음(푸시 통지를 두지 않는다). 발송처는 PROC-202 조회로 확인한다.

### 의존 프로세스

- **호출 관계**: PROC-301(동기 — `B3` 조회, `B4` 콜백 기록).
- **선행 관계**: PROC-102(레코드 생성) · PROC-104(수신처 전달 — 통지의 계기).
- **이벤트 관계**: 없음.

### 구현 가이드

- **없는 레코드를 새로 만들지 않는다.** 이 규칙이 가장 자주 어겨지는 지점이다 — 통지가 먼저 오면 레코드를 만들고 싶어지지만, 진입하지 않은 연동을 기록으로 만들면 지표와 보관 규칙이 모두 어긋난다(`BIZ-002-03`).
- **중복 통지가 최초 수신 시각을 덮지 않게 한다.** 최근 시각으로 덮으면 발송처가 보는 완료 시각이 흔들린다.
- **결과 구분을 바꾸지 않는다.** 전달이 실패한 연동에 통지가 와도 사실만 기록하고 정합을 검사하지 않는다(BR-021).
- **본문의 다른 필드를 저장하지 않는다.** 담을 컬럼이 스키마에 없는 것이 1차 방어다(`DATA-001-01`).
- **위조 통지 방어를 추가하지 않는다.** 서명·출처 검증 도입은 범위 밖이며 수용 리스크로 관리한다(`OPS-002-02`·`OPS-002-05`).
- **`B4` 의 `BEGIN` 이 경계를 여는 자리다.** PROC-301 과 그 하위 FN 은 넘겨받은 실행 문맥(`exec`)으로 **참여만 한다** — `exec` 를 넘기지 않으면 하위가 경계 **밖**의 별도 커넥션을 잡아 같은 경계의 변경이 보이지 않고 요청 하나가 커넥션을 둘 점유한다([`../functions/function_FN-009-011.md`](../functions/function_FN-009-011.md) FN-011 §시그니처). **`B3` 조회(`LOOKUP`)는 그 반대다** — 아직 경계가 없는 자리라 `exec` 없이 단독 읽기로 부르는 것이 옳다.
