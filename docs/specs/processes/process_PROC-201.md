# 처리상태 확인 API 기능 정의

정본 목록은 [`spec-process.md`](spec-process.md). 단계 라벨 체계도 그 문서가 갖는다. 용어는 [`../../../wiki/WIKI.md`](../../../wiki/WIKI.md).

## 개요

- **정의 대상**: 발송처가 **연동 추적 키로 처리 결과와 결과 확인 상태를 조회**하는 처리다. 결과를 담아 응답한 시점에 그 레코드가 **결과 확인 완료**가 되고 보관 기간 기산이 시작되므로, 조회이면서 상태를 바꾸는 접점이다.
- **관련 PRD 요구사항**:
	- [`../../prd/PRD.md`](../../prd/PRD.md) §수행 범위 7 — "**처리상태 확인 API** … 발송처의 상태·완료 조회"
	- [`../../prd/devspec/external-apis.md`](../../prd/devspec/external-apis.md) §처리상태 확인 API — "허브는 결과를 담아 응답한 시점에 그 레코드를 결과 확인 완료로 표시하고 확인 일시를 남긴다. 이 시점이 보관 기간의 기산점이다."

### 진입점 및 진입 조건

- **진입점**: `POST /api/interlock/status` — 요청 본문 `{ trackingKey }`([`../functions/spec-functions-api-server.md`](../functions/spec-functions-api-server.md) §처리상태 확인 API).
- **진입 조건**: **인증 없음 — `AUTH-001` 인용.** 인증 헤더·서명·API 키를 요구하지도 검증하지도 않으며 401·403 을 정의하지 않는다(`AUTH-001-03`). 자격이 담긴 요청이 와도 무시한다.
- **요청 제한**: **미적용 — 수용 리스크**(`OPS-002-03`).
- **사전 검증**: ① 본문 JSON 해석 ② 추적 키 형식(FN-006 — 1~255자·공백만 불가).
- **메서드 선택 근거**: GET 이 아니라 POST 다 — 응답이 상태를 바꾸고(결과 확인 표시), 추적 키가 불투명 문자열이며, 세 접점이 같은 요청 형상을 공유하기 때문이다.

### 입력/출력 정의

| 구분 | 항목명 | 데이터 타입 | 필수 | 설명 |
|------|--------|------------|------|------|
| 입력 | `trackingKey` | string(1~255) | Y | [`MDL-011`](../datas/model_MDL-011-015.md). 공백만 불가 |
| 출력 | `trackingKey` | string | - | **입력값을 변형 없이 그대로** 되돌린다(`DATA-004-01`) |
| 출력 | `isSuccess` | boolean\|null | - | 결과 구분에서 산출하는 파생값(`SUCCESS` = `true`) |
| 출력 | `resultCode` | string\|null | - | 결과 구분 3종(`BIZ-001-01`). `null` = 결과 미확정 |
| 출력 | `isResultConfirmed` | boolean | - | 결과 확인 여부(파생) |
| 출력 | `resultAt` · `resultConfirmedAt` | string(ISO 8601+오프셋)\|null | - | 처리 일시·결과 확인 일시 |

### 연관 데이터 및 외부 호출

- **호출 API**: 없음.
- **데이터 조회 대상**: [`ENT-001`](../datas/data_ENT-001.md) 기본 키 단건 조회(PROC-301 `B2`).
- **데이터 변경 대상(CRUD)**: [`ENT-001`](../datas/data_ENT-001.md) `result_confirmed_at` 조건부 UPDATE 최대 1건(PROC-301 `B5`). **다른 컬럼을 건드리지 않는다.**

### 실행 제약사항

- **트랜잭션 경계**: `B4`~`B6` 이 **같은 처리 경계**다 — 표시가 실패하면 응답도 내보내지 않는다. "응답은 갔는데 표시가 남지 않은" 상태를 만들지 않기 위해서다.
- **동시성 제어**: 결과 확인 표시는 조건부 UPDATE(`result_confirmed_at IS NULL AND result_code IS NOT NULL`)라 동시 조회에서도 **최초 1회만 성립**한다. 반복 조회가 기산점을 미루지 않는다(BR-010).
- **멱등성**: 같은 요청을 여러 번 보내도 응답은 같고(두 번째부터 `resultConfirmedAt` 이 최초 값), 레코드는 한 번만 바뀐다.
- **성능 요구**: 기본 키 단건 조회 1회 + 조건부 UPDATE 최대 1회. 목록·정렬·페이지 조회 경로를 만들지 않는다.
- **보안 요구**: **인증 없음**(`AUTH-001-03`). **추적 키를 아는 누구든 보관 기산을 시작시킬 수 있다 — 수용 리스크이며 조회 자격 검증을 추가하지 않는다**(`OPS-002-04`). 응답에 복호화 원문·암호값·생년월일을 담지 않는다(담을 속성이 모델에 없다).

### 로직 실행 순서

#### FE 측 처리 (의사코드)

**사용자 화면이 없다.** 발송처가 서버에서 직접 호출하는 접점이며 관리자 조회 화면을 두지 않는다(`AUTH-001-01`). FE 자리에는 **호출측(발송처 서버)** 처리를 `C` 라벨로 적는다([`spec-process.md`](spec-process.md) §단계 라벨 체계).

```
C1. 호출측 요청 구성 (발송처 서버)

  진입 트리거: 발송처가 자기 연동 처리 결과를 확인하려는 시점 (배치·수동 조회 등)
  사용 값: 발송처가 전달 데이터 X 에 넣었던 trackingKey (발송처가 보관·관리한다)
  요청 DTO 변환:
    body    = { trackingKey: <발송처 보유 값> }        // 변형하지 않는다
    headers = { 'Content-Type': 'application/json; charset=utf-8' }
    // 인증 헤더·API 키를 붙이지 않는다 — 허브가 요구하지도 검증하지도 않는다 (AUTH-001-03)
  호출 수단: POST <허브 기준 URL>/api/interlock/status
  주의: 이 호출은 부작용이 있다 — 결과를 받은 시점에 보관 기간 기산이 시작된다.
        프리페치·자동 재시도로 무심코 호출하지 않는다 (POL DATA-002-01 ①)

C2. 응답 소비

  200 → resultCode 로 처리 결과를 판단한다
        resultCode == null 이면 아직 결과가 확정되지 않았다 (사용자가 진행 중이거나 이탈)
        결과 구분 값은 허브가 준 문자열을 그대로 쓴다 — 별칭·대소문자 변형을 만들지 않는다
  400 EX-DATA-002 → 추적 키 형식을 고친다
  404 EX-DATA-001 → 그 키로 진입한 사용자가 없었다 (미진입·보관 만료를 구별하지 않는다)
  500 → 잠시 후 다시 호출한다
  실패 처리: 재시도 정책은 발송처 소관이다. 허브는 요청 제한을 두지 않는다 (OPS-002-03)
```

#### BE 측 처리 (의사코드)

```
B1. POST /api/interlock/status 진입

  엔드포인트·메서드: POST /api/interlock/status
  인증·인가 검증: 인증 없음 — AUTH-001 인용
                  토큰·세션·역할·API 키를 읽지 않는다. 401·403 을 정의하지 않는다
  요청 제한: 미적용 — 수용 리스크 (OPS-002-03)
  메서드 불일치: 405 (본문 없음)
  캐시: 응답에 캐시 금지를 지정한다 (상태를 바꾸는 부작용이 있다)

B2. 입력 검증 — FN-006 · POL DATA-004-03 (validate)

  if (본문을 JSON 으로 해석할 수 없다)          → 400 FN-014('EX-DATA-002')
  if (!FN-006(body.trackingKey))                → 400 FN-014('EX-DATA-002',
                                                     [{ field: 'trackingKey', reason: 'FORMAT' }])
  // details 에 값 자체를 담지 않는다 (FN-014 §구현 가이드)
  // 조회를 수행하지 않고 끝낸다

B3. 추적 키 사전 조회 — PROC-301 호출 · POL BIZ-002-05 · DATA-002-05 (validate)

  lookup = PROC-301({ kind: 'LOOKUP', trackingKey: body.trackingKey })
      // PROC-301 B2 (FN-007):
      //   SELECT tracking_key, result_code, result_at, result_confirmed_at,
      //          callback_received_at, created_at
      //   FROM tbl_interlock_tracking
      //   WHERE tracking_key = :trackingKey;
      //   -- 기본 키 단건 · ORDER BY·LIMIT·JOIN·락 없음 (단건이므로 불필요)
  if (lookup.branch == 'NONE')                  → 404 FN-014('EX-DATA-001')
      // 미진입과 보관 만료 삭제를 구별하지 않는다

B4. 응답 값 산출 — POL BIZ-001-03 (mask)

  record = lookup.record                        // MDL-001 (파생 4종이 산출돼 있다)
  draft  = { trackingKey:       body.trackingKey,      // 입력값 무변형 에코
             isSuccess:         record.isSuccess,      // null 가능(결과 미확정)
             resultCode:        record.resultCode,     // 단일 열거형 값 그대로 — 변환 금지
             isResultConfirmed: record.isResultConfirmed,
             resultAt:          record.resultAt → ISO 8601 + 오프셋,
             resultConfirmedAt: record.resultConfirmedAt → ISO 8601 + 오프셋 }

B5. 결과 확인 표시 — PROC-301 호출 · POL DATA-002-01 ① · BR-010 (트랜잭션)

  if (draft.resultCode != null)                 // §결과 확인 표시 판정 기준
      BEGIN;
        confirmedAt = PROC-301({ kind: 'CONFIRM_RESULT',
                                 trackingKey: body.trackingKey, at: NOW() })
            // PROC-301 B5 (FN-010):
            //   UPDATE tbl_interlock_tracking
            //   SET result_confirmed_at = :at
            //   WHERE tracking_key = :trackingKey
            //     AND result_confirmed_at IS NULL
            //     AND result_code IS NOT NULL;
            // 갱신 1행 → 이번 응답이 보관 기산을 시작시켰다
            // 갱신 0행 → 기존 값을 그대로 돌려준다 (반복 조회가 기산점을 미루지 않는다)
      COMMIT;                                   // 실패 → 500 FN-014('EX-BIZ-003') · 응답 미송출
      draft.resultConfirmedAt = confirmedAt → ISO 8601 + 오프셋
      draft.isResultConfirmed = true
  else
      // 결과 미확정 레코드 조회는 표시하지 않는다 — 결과를 받아 간 것이 아니다
      갱신하지 않는다
  정책 적용 지점: OPS-002-04 — 인증이 없어 추적 키를 아는 누구든 이 기산을 시작시킬 수 있다.
                  조회 자격 검증을 추가하지 않는다 (수용 리스크 확인 지점)

B6. 응답 송출 — POL DATA-004-01 (mask)

  return 200 FN-015(draft)                      // MDL-012
  // 추적 키는 입력값 그대로 · 그 밖의 금지 값은 담을 속성이 모델에 없다
  후속 이벤트 발행: 없음 (보관 기산 개시는 PROC-304 가 나중에 관측한다)
```

### 실행 결과

- **정상 결과**: 200 [`MDL-012`](../datas/model_MDL-011-015.md). 결과가 확정된 레코드를 처음 조회한 경우 `ENT-001.result_confirmed_at` 1건 갱신(보관 기산 개시).
- **실패 결과**: 400·404·500 오류 응답 엔벨로프. 어떤 경우에도 레코드를 만들지 않는다.
- **후속 트리거**: PROC-304 — 기산이 시작된 레코드는 `<RETENTION_MONTHS>` 경과 후 삭제 대상이 된다.

### 의존 프로세스

- **호출 관계**: PROC-301(동기 — `B3` 조회, `B5` 결과 확인 표시).
- **선행 관계**: PROC-102(추적 레코드 생성) · PROC-901(기동).
- **이벤트 관계**: PROC-304 — 결과 확인 일시가 삭제 기준 ①의 기산점이 된다.

### 구현 가이드

- **표시와 응답을 같은 처리 경계에 둔다.** 표시가 실패하면 응답도 내보내지 않는다 — 응답만 나가고 기산이 시작되지 않으면 보관 규칙이 어긋난다.
- **결과 미확정 레코드에는 표시하지 않는다.** 발송처가 결과를 받아 가지 못했는데 삭제 시점이 앞당겨지는 것을 막는다([`../functions/function_FN-009-011.md`](../functions/function_FN-009-011.md) §결과 확인 표시 판정 기준).
- **400·404 로 끝난 요청에는 표시가 발생하지 않는다.** 형식 위반·대상 없음은 결과를 담아 응답한 것이 아니다.
- **추적 키를 정규화하지 않는다.** 조회 조건과 응답 에코 모두 입력 문자열 그대로다(`DATA-004-01`).
- **결과 구분 값을 응답에서 변환하지 않는다.** 화면·지표와 같은 단일 열거형을 써야 두 표면이 같은 사실을 말한다(`BIZ-001-03`).
