# 연동 실행(복호화·수신처 전달) 기능 정의

정본 목록은 [`spec-process.md`](spec-process.md). 단계 라벨 체계도 그 문서가 갖는다. 용어는 [`../../../wiki/WIKI.md`](../../../wiki/WIKI.md).

## 개요

- **정의 대상**: 승인이 확정된 연동에서 **전달 데이터를 다시 복원해 수신처에 넘기고 결과를 확정**하는 처리다. 제품의 핵심 가치가 성립하는 지점이며, 원문을 저장하지 않기 위해 복호화를 여기서 한 번 더 수행하고 전달 직후 폐기한다.
- **관련 PRD 요구사항**:
	- [`../../prd/PRD.md`](../../prd/PRD.md) §수행 범위 5 — "**연동 실행 (복호화·전달)**: 승인 시 허브가 생년월일로 복호화해 X를 얻고, 상수로 고정된 수신처(B) 주소로 전달한다."
	- [`../../prd/PRD.md`](../../prd/PRD.md) §시스템 제약사항 — "복호화는 **연동 실행 시점에 메모리 상에서만** 수행하고 전달 후 폐기한다."

### 진입점 및 진입 조건

본 프로세스는 외부 표면을 갖지 않는다. **PROC-103 승인 제출 처리 안에서 두 구간으로 나뉘어 실행**된다.

| 구간 | 단계 | 호출 시점 | 실행 조건 |
|---|---|---|---|
| **복호화 구간** | `B1`·`B2` | PROC-103 `B2` | **동의 재검증 이전**에 실행한다. 레코드를 확보하려면 추적 키가 필요하고, 추적 키는 복호화로만 얻어진다 |
| **전달 구간** | `B3`~`B8` | PROC-103 `B7` | **승인 확정·동의 증적 기록 이후에만** 실행한다 |

- **두 구간 사이에 PROC-103 의 게이팅이 놓이는 이유** — 필수 동의 재검증(`BIZ-003-02`)과 동의 증적 기록(`BIZ-003-04`)이 전달보다 먼저 성립해야 한다. "전달했는데 증적이 없는" 상태를 만들지 않기 위해 구간을 나눴다.
- **진입 조건**: **인증 없음 — `AUTH-001` 인용.** 상위 프로세스가 인증을 하지 않으므로 본 프로세스도 자격을 확인하지 않는다.
- **사전 검증**: `B1` 생년월일 형식(FN-005) · `B2` 복호화 판정 4단계(FN-004). **앞 단계(PROC-102)의 통과 사실을 신뢰하지 않는다** — 매 요청이 처음처럼 검증된다.

### 연관 데이터 및 외부 호출

- **호출 API**: `POST <RECEIVER_DELIVERY_URL>` — **허브가 밖으로 거는 유일한 호출**이다([`../functions/spec-functions-api-server.md`](../functions/spec-functions-api-server.md) §수신처 전달 접점).
	- 요청 헤더 `Content-Type: application/json; charset=utf-8`
	- 요청 본문 **복호화한 X 의 UTF-8 바이트열 그대로**(재직렬화 금지)
	- 성공 판정 **HTTP 200~299**(본문 미사용·3xx 미추종)
	- 시도 횟수·간격·회당 응답 대기 상한·총 상한은 **`BIZ-004-02` 가 정본**이며 본 사양은 값을 복제하지 않는다
- **데이터 조회 대상**: 없음(전달 구간은 조회하지 않는다). 레코드는 PROC-103 `B3` 이 이미 확보했다.
- **데이터 변경 대상(CRUD)**: [`ENT-001`](../datas/data_ENT-001.md) 결과 확정 UPDATE 1건 · [`ENT-003`](../datas/data_ENT-003.md) 결과 카운터 +1 — 둘 다 `B6` 이 PROC-301·PROC-303 으로 수행한다.

### 실행 제약사항

- **트랜잭션 경계**: **전달 호출은 트랜잭션 밖**이다. `B6` 결과 확정만 단일 트랜잭션이며 PROC-301·PROC-303 이 그 안에 참여한다. 최대 총 소요가 `BIZ-004-02` 상한까지 갈 수 있는 호출을 트랜잭션이 감싸면 연결이 그만큼 점유된다.
- **동시성 제어**: 결과 확정은 조건부 UPDATE(`result_code IS NULL`)라 같은 추적 키의 동시 처리에서도 **한 번만 성립**한다(`BIZ-001-04`). 응용 락을 추가로 잡지 않는다.
- **멱등성**: 전달 호출 자체는 멱등하지 않다 — 재요청이 오면 수신처가 같은 데이터를 다시 받을 수 있다. 다만 **결과가 확정된 뒤의 재요청은 PROC-103 `B4` 재안내로 걸러지므로** 확정 이후의 중복 전달은 발생하지 않는다.
- **보상 처리**: **보상 트랜잭션을 두지 않는다.** 전달 성공 후 결과 확정이 실패하면 허브에는 수신처에 취소를 보낼 수단이 없다(전달 접점이 단방향이다). 이 경우 결과 미확정 500 으로 끝나고, 사용자가 다시 시도하면 레코드가 아직 `OPEN` 이므로 **전달이 한 번 더 일어날 수 있다** — 수신처의 중복 수신은 추적 키로 식별 가능하며, 유일성 책임이 발송처에 있다는 전제(`DATA-004-02`)에서 수용한다.
- **성능 요구**: 사용자가 `SCR-003` 에서 기다리는 구간이므로 총 소요를 `BIZ-004-02` 상한 안에 묶는다. 화면은 자체 타임아웃을 두지 않는다.
- **보안 요구**: **인증 없음**(허브는 수신처에 자격을 제시하지 않는다). 재시도 중에도 X 를 **메모리에만** 둔다 — 큐·파일에 적재하면 무저장 원칙이 깨진다(`DATA-001-03`). 응답 본문을 읽지도 저장하지도 않는다.

### 로직 실행 순서

#### FE 측 처리 (의사코드)

본 프로세스는 **화면 액션을 트리거로 갖지 않는다**([`../screens/screen_SCR-003.md`](../screens/screen_SCR-003.md) §기본 정보 — "트리거 PROC 없음"). FE 자리에는 본 프로세스가 도는 동안 사용자가 보는 **대기 화면의 상태 유지**만 있다. 요청 발신은 PROC-103 `F3` 이 이미 수행했다.

```
F1. 대기 상태 유지 (SCR-003 Waiting)

  진입 트리거: PROC-103 F3 이 승인 요청을 발신한 직후 (stage = 'PROCESSING' — 화면 소유 단계)
  사용 상태:
    encPair · form.birthDate 를 페이지 메모리에 그대로 유지 (저장소에 쓰지 않는다)
  진행 중 UI:
    Spinner + "연동을 진행하고 있습니다" + "창을 닫거나 새로 고치지 마세요."
    조작 요소를 두지 않는다 — 취소 버튼이 있으면 이미 진행 중인 서버 처리와 어긋난다
    진행률·재시도 횟수·남은 시간을 표시하지 않는다 (POL SEC-002-05)
  타임아웃: 화면 쪽 요청 타임아웃을 두지 않는다
            응답 시점을 지배하는 것은 POL BIZ-004-02 의 전달 재시도 총 소요 상한이다

F2. 응답 수신 → 전이 (PROC-103 F5 로 이어진다)

  onSuccess/onError 처리는 PROC-103 F5 가 갖는다 (요청 주체가 그쪽이다)
  전송 계층 단절로 응답을 받지 못한 경우:
    상태 = Unconfirmed
    알림 "처리 결과를 확인하지 못했습니다. 받으신 링크로 다시 들어오면 결과를 확인할 수 있습니다."
    // 네 번째 결과 경로가 아니다 — 화면이 결과 구분을 추측하지 않는다 (POL BIZ-001-02)
    // 서버에서 결과가 이미 확정됐을 수 있고, 재진입하면 확정 결과가 재안내된다 (BIZ-002-03 ③)
```

#### BE 측 처리 (의사코드)

```
── 복호화 구간 (PROC-103 B2 가 호출) ──────────────────────────────

B1. 입력 검증 — FN-005 · POL AUTH-002-02 (validate)

  엔드포인트·메서드: 없음 — 상위 프로세스의 접점(POST <INTERLOCK_ENTRY_PATH>/approve) 안에서 실행
  인증·인가 검증: 인증 없음 — AUTH-001 인용
  try  FN-005(birthDate)                        // ^[0-9]{6}$
  catch                                         → 400 EX-AUTH-001 (재복호화 미시도)
                                                   화면은 SCR-001 로 되돌아간다

B2. 복호화 판정(재복호화) — FN-004 · POL BIZ-002-06 · SEC-002-01 (validate)

  try  payload = FN-004({ encX, encY }, birthDate)
  catch (EX-AUTH-002)  → 400 EX-AUTH-002        // 본인확인 재입력으로 되돌린다 · 결과 미확정
  catch (EX-SEC-001)   → 400 EX-SEC-001         // 결과 경로 ②
  catch (EX-SEC-002)   → PROC-303({ kind: 'UNIDENTIFIED_FAILURE', at: NOW() })
                          → 400 EX-SEC-002      // DECRYPT_FAILED 계수 · 결과 경로 ②
  trackingKey = payload.trackingKey             // 무변형
  return { trackingKey, payload }               // 메모리 전용 — 어떤 저장소에도 넣지 않는다
  // 본인확인(PROC-102)에서 얻은 원문을 재사용하지 않는다 (POL BIZ-002-06)

── 전달 구간 (PROC-103 B7 이 호출 — 승인 확정·증적 기록 이후) ─────

B3. 전달 페이로드 구성 — POL BIZ-004-05 (transform)

  body = payload 의 UTF-8 바이트열 그대로
  // 파싱한 객체를 다시 직렬화하지 않는다 — 숫자 표현·유니코드 이스케이프·필드 순서가 달라진다
  // X 내용의 업무적 유효성을 판단하지 않는다 (허브는 규약대로 중개할 뿐이다)
  headers = { 'Content-Type': 'application/json; charset=utf-8' }

B4. 수신처 전달 호출 — POL BIZ-004-01 (외부 시스템 호출)

  attempt = 1
  loop:
      try  res = HTTP_POST(<RECEIVER_DELIVERY_URL>, headers, body,
                           timeout = POL BIZ-004-02 의 회당 응답 대기 상한)
           // 허브 서버가 직접 호출한다. 사용자 브라우저를 경유하지 않는다
           // 3xx 를 따라가지 않는다 (추종하면 데이터가 예상치 못한 곳으로 나간다)
           if (200 <= res.status <= 299)   → delivery = { ok: true } → B6
           else                            → B5   // 본문을 읽지 않는다
      catch (연결 실패·이름 해석 실패·보안 연결 실패·응답 대기 상한 초과)
                                           → B5

B5. 전달 실패 재시도 — POL BIZ-004-02 (validate)

  if (attempt < POL BIZ-004-02 의 총 시도 횟수)
      정해진 간격만큼 대기한다                   // 간격 값은 POL BIZ-004-02 가 정본
      attempt = attempt + 1
      → B4 를 다시 수행
  else
      delivery = { ok: false }                   // 재시도 소진
      → B6
  // 재시도 중에도 body 는 메모리에만 둔다 — 큐·파일에 적재하지 않는다 (POL DATA-001-03)
  // 사용자가 진입해 있는 동안에만 재시도한다. 확정 후 재연동은 발송처가 새 요청을 발행한다

B6. 결과 확정·기록 — PROC-301 호출 · POL BIZ-004-03 · BIZ-001-04 (트랜잭션)

  resultCode = (delivery.ok ? 'SUCCESS' : 'DELIVERY_FAILED')
  BEGIN ISOLATION LEVEL READ COMMITTED;
    PROC-301({ kind: 'FIX_RESULT', trackingKey, resultCode, at: NOW() })
        // PROC-301 B4: UPDATE tbl_interlock_tracking
        //              SET result_code = :resultCode, result_at = :at
        //              WHERE tracking_key = :trackingKey AND result_code IS NULL;
        // 갱신 1행이면 PROC-303 B4 가 해당 카운터 +1 (같은 트랜잭션)
  COMMIT;                                        // 실패 → 500 EX-BIZ-003 (결과 미확정)
  보안 이벤트 기록: 만들지 않는다 (POL OPS-003-02) — 실패는 결과 구분으로만 남는다

B7. 복호화 결과 폐기 — POL DATA-001-03 (transform)

  payload · body · 복호화 중간 값을 지역 변수에서 버린다
  // 요청 처리 종료와 함께 사라져야 한다. 전역 상태·요청 컨텍스트 저장소에 남기지 않는다

B8. 결과 안내 이관 — POL SEC-002-05 (mask)

  return { resultCode }                          // PROC-103 B8 이 PROC-105 로 넘긴다
  마스킹: 응답·로그에 원문·암호값·생년월일·키·재시도 횟수·수신처 응답 본문을 담지 않는다
  후속 이벤트 발행: 없음. 수신처의 완료 통지는 PROC-203 이 별도 접점으로 받는다
```

| 외부 응답→도메인 | BE `B4` | HTTP 상태 코드 | [`MDL-010`](../datas/model_MDL-007-010.md) 전달 결과 | 200~299 = 성공 / 그 밖·연결 실패·시간 초과 = 실패. **본문 미사용** |
| 도메인→ENT | BE `B6` (PROC-301) | 결과 구분 | `tbl_interlock_tracking` UPDATE | 조건부(`result_code IS NULL`) · `result_at` 동시 기록 |
| 도메인→응답 | BE `B8` | 결과 구분 | `{ resultCode }` | 상위 프로세스에 값만 넘긴다 · FN-015 정제 |

- **`ENT→도메인` 지점이 없다** — 전달 구간은 조회하지 않는다. 최신 레코드가 필요하면 PROC-301 이 반환한다.

### 실행 결과

- **정상 결과**: `{ resultCode: 'SUCCESS' }`. 영속화 — `ENT-001` `result_code`·`result_at` 확정 · `ENT-003` `success_count` +1. 수신처에 X 1건 전달.
- **전달 실패 결과**: `{ resultCode: 'DELIVERY_FAILED' }`. 영속화 — `result_code = DELIVERY_FAILED` · `delivery_failed_count` +1. 상위가 502 `EX-BIZ-002` 로 응답한다.
- **판정 실패 결과**: 결과 미확정(`EX-AUTH-002`) 또는 `DECRYPT_FAILED` 계수만(`EX-SEC-002`). 전달을 수행하지 않는다.
- **후속 트리거**: PROC-105(결과 안내) · PROC-203(수신처가 처리를 마치면 완료를 통지) · PROC-201(발송처 조회).

### 의존 프로세스

- **호출 관계**: PROC-301(동기·트랜잭션 — `B6`) · PROC-303(PROC-301 경유 및 `B2` 실패 계수).
- **선행 관계**: PROC-103 승인 확정·동의 증적 기록(전달 구간에 한함) · PROC-102(레코드 확보) · PROC-901(전달 주소 상수 주입).
- **이벤트 관계**: PROC-203 — 수신처가 자기 처리를 마친 뒤 완료를 통지한다.

### 구현 가이드

- **전달 호출을 트랜잭션 안에 넣지 않는다.** 총 소요가 상한까지 갈 수 있는 호출을 감싸면 연결이 그만큼 점유된다.
- **X 를 재직렬화하지 않는다.** 파싱한 객체를 다시 문자열로 만들면 발송처가 만든 바이트열과 달라져 수신처의 서명·해시 검증이 있는 환경에서 깨진다.
- **수신처 응답 본문을 읽지 않는다.** 전달한 원문이 되비쳐 로그에 남을 위험을 없앤다.
- **재시도 간격·횟수를 코드에 박지 않는다.** 값은 `BIZ-004-02` 가 정본이며 상수·설정으로 주입한다.
- **회당 대기 상한 × 시도 횟수 + 간격 합이 총 상한을 넘지 않게 구성한다.** 사용자가 화면에서 기다리는 시간이다.
- **`B2` 실패와 `B6` 실패를 같은 처리로 묶지 않는다.** 전자는 전달 전이라 결과를 확정하지 않고, 후자는 이미 전달된 뒤라 재시도가 중복 전달을 부른다.
