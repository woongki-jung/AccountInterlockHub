# 보관정책 배치 기능 정의

정본 목록은 [`spec-process.md`](spec-process.md). 단계 라벨 체계도 그 문서가 갖는다. 용어는 [`../../../wiki/WIKI.md`](../../../wiki/WIKI.md).

## 개요

- **정의 대상**: 보관 기간이 지난 기록을 **일 단위로 지워** 개인정보를 지속 보관하지 않는다는 제품 원칙을 실제로 유지시키는 처리다. **스케줄 실행과 명령 진입점을 통한 수동 실행이 같은 삭제 로직을 공유**하며 진입 경로만 다르다.
- **관련 PRD 요구사항**:
	- [`../../prd/PRD.md`](../../prd/PRD.md) §수행 범위 9 — "일 단위 배치로 보관 기간 경과분을 삭제한다."
	- [`../../prd/PRD.md`](../../prd/PRD.md) §프로그램 구성·기술스택·검증 방법 — "보관 배치는 인앱 스케줄 작업이라 명령 실행·종료 코드로 관측할 수 없으므로, **수동 실행 진입점 제공을 요구사항으로 둔다**(선택 사항이 아니다)."

### 진입점 및 진입 조건

**두 진입 경로가 같은 삭제 로직 함수를 부른다.** 진입 경로만 다르고 산정 기준·삭제 로직·결과 요약 레코드가 모두 같다(`DATA-002-04`·BR-015). **다만 그 요약이 놓이는 자리와 성패 판별 수단은 경로마다 다르다** — "표준 출력의 마지막 줄"과 "종료 코드"는 *1회 실행 후 종료하는 프로세스*에서만 성립하는 계약이라 상주 서버 안에서 도는 스케줄 경로에는 없다. 공용 계약의 상한은 [`../functions/spec-functions-api-server.md`](../functions/spec-functions-api-server.md) §관측 표면의 경로별 분리(확정)가 갖고, **스케줄 경로의 관측 표면은 본 문서가 정본이다**(아래 §스케줄 경로의 관측 표면).

| 경로 | 진입점 | 실행 주체 |
|---|---|---|
| **스케줄 실행** | 애플리케이션 안의 일 단위 스케줄 작업 — **`Asia/Seoul` 앵커로 하루 1회 발화**(아래 시간대 규정) | 시스템 |
| **수동 실행** | 배포 단위 안의 **CLI 진입점** — `node dist/cli/retention.js`(개발 편의 별칭 `npm run retention:run`). **인자·옵션 없음** | 허브 운영자 |

- **진입 조건**: **인증 없음 — `AUTH-001` 인용.** 관리자 경로·관리자 인증을 두지 않으며(`AUTH-001-01`), CLI 진입점은 배포 단위 안에 있어 **외부 표면을 늘리지 않는다**. HTTP 관리 엔드포인트를 만들지 않는다.
- **사전 검증**: **필수 상수가 충족되지 않으면 기동 단계(PROC-901)에서 중단**된다 — 이때는 요약 JSON 을 낼 주체가 없으므로 표준 출력에 미충족 상수명을 남기고 0 이외 코드로 끝난다(`OPS-001-02` → `EX-OPS-001`). **이 판독은 CLI 경로의 것이다** — 스케줄 경로는 애플리케이션이 기동하지 못하면 스케줄 작업 자체가 등록되지 않아 실행 시도가 일어나지 않는다.
- **인자를 두지 않는 이유**: 기준 일시를 인자로 받으면 스케줄 실행과 산정 기준이 갈려 `DATA-002-04`(같은 산정 기준)가 깨진다. 검증은 시드 데이터의 일시를 조정해 수행한다.
- **스케줄 발화의 시간대 앵커 — `Asia/Seoul`(UTC+09:00) 고정**: 일 단위 스케줄은 그 벽시계 기준으로 **하루 1회** 발화한다. 서버 OS 의 기본 시간대·UTC 앵커를 쓰지 않는다. 기산 프레임이 `Asia/Seoul` 로 확정돼 있으므로(`DATA-002-06` ①) 앵커가 다르면 **실행 시점의 달력 날짜와 임계값 산출의 달력 날짜가 어긋난다** — EXC-DATA-12 ⓑ 가 프레임 선택의 근거로 든 정합이 바로 이것이며, 자정 직후 발화 시 UTC 앵커는 상시 전일이 된다. 한국은 서머타임이 없어 이 앵커는 결정적이다(같은 근거 ⓒ).
- **구체 발화 시각(시·분)은 사양이 고정하지 않는다 — build 결정이다**: 삭제 대상 산정이 `baseAt` 기반 재산정이고 멱등하므로(`DATA-002-04`) 하루 중 어느 시각에 발화해도 **그날까지 경과한 대상이 지워지고 결과가 갈리지 않는다**. 일 단위 배치에는 최대 1일의 지연이 이미 내재해 있어(EXC-DATA-13) 시각 선택이 정책 준수 여부를 바꾸지 않으며, 시각을 사양에 박으면 운영 부하 창(window)을 조정할 수 없게 된다. **고정되는 것은 "하루 1회"와 "`Asia/Seoul` 앵커" 둘이고, 그 안의 시·분만 열려 있다** — build 는 고른 값을 완료 보고에 남긴다.

### 스케줄 경로의 관측 표면 (확정)

**본 절이 스케줄 경로 관측 표면의 정본이다.** 공용 항목(요약 레코드·직렬화 형상·마스킹·산정 기준·실행 이력 저장소 부재)의 상한은 [`../functions/spec-functions-api-server.md`](../functions/spec-functions-api-server.md) §관측 표면의 경로별 분리(확정)가 갖고 본 절은 그것을 **인용할 뿐 재정의하지 않는다**. 아래는 그 표가 `PROC-304` 로 넘긴 **경로별 항목**의 스케줄 쪽 확정이다.

1. **요약 1줄의 형상** — 스케줄 실행 1회당 **정확히 1줄**, `MDL-021` 요약을 §출력 스키마 그대로 직렬화한 **프리픽스·접미가 없는 순수 JSON 1줄**을 **표준 출력**으로 내보낸다. 타임스탬프·로그 레벨·컨텍스트 같은 로거 장식을 그 줄에 붙이지 않는다 — 붙는 순간 관측자가 줄을 그대로 파싱할 수 없다.
	- **"표준 출력에 다른 텍스트가 없다"는 계약을 세우지 않는다.** 상주 프로세스의 표준 출력에는 사용자 웹·API·기동 로그가 함께 흐르므로 지킬 수 없는 계약이다. 성립하는 계약은 **"요약은 한 줄이고, 그 줄은 그 자체로 파싱 가능하다"** 이며, 관측자는 **줄 단위로 읽어 JSON 파싱에 성공하고 4키를 갖는 줄**을 요약으로 식별한다. CLI 경로의 **"마지막 줄" 규칙을 여기로 옮겨 적지 않는다** — 상주 프로세스에는 마지막 줄이 없다.
2. **성패와 무관하게 내보낸다** — 실패해도 같은 형상의 요약 1줄을 **반드시** 낸다(`failureReason` 을 채운 채로). 스케줄 경로에는 종료 코드가 없으므로 **실패했을 때 요약이 나오지 않으면 관측 수단이 아예 사라진다.** 성공일 때만 내보내는 구현은 반려다.
3. **성패 판별 수단은 요약의 `failureReason`** — `null` = 성공 / 문자열 = 실패이며, CLI 경로의 종료 코드 `0` / `0` 이외에 **1:1 대응**한다. `OPS-003-04` 가 요구하는 "성공·실패 구분"을 두 경로가 각자의 수단으로 충족하는 것이며, 별도 실행 이력 저장소·상태 조회 엔드포인트를 만들어 판별 수단을 늘리지 않는다(`OPS-003-04`·`AUTH-001-01`).
4. **진단 문구는 스트림이 아니라 줄로 가른다** — CLI 경로는 스트림을 가르지만(요약 = 표준 출력 / 진단 = 표준 오류), 스케줄 경로는 상주 프로세스의 로그 스트림을 공유하므로 스트림 분리로는 계약이 서지 않는다. 사람이 읽는 진단은 애플리케이션 로거로 **요약과 다른 줄**에 내보내고, **요약 줄에는 어떤 진단 문구도 섞지 않는다.** 진단 줄이 요약과 같은 내용을 중복해 담아도 무방하다 — 지켜야 하는 것은 **요약 줄의 순수성**이다.
	- **요약을 로거 경로에만 싣지 않는다.** 로거가 실패 레벨을 표준 오류로 라우팅하면 **실패 시 표준 출력이 비어** CLI 경로와 관측 절차가 갈린다. 요약은 표준 출력을 직접 통제해 내보낸다.
5. **실행 실패가 상주 프로세스를 끝내지 않는다** — 새 판단이 아니라 `OPS-004-01` 의 인용이다: 어떤 실패도 **애플리케이션 프로세스를 종료시키지 않으며, 의도된 종료는 기동 시 상수 검증 실패(`OPS-001-02`) 하나뿐**이다. 이유는 EXC-OPS-12 가 갖는다 — 사용자 웹·백엔드 API·보관 배치가 **한 배포 단위** 안에 있어 프로세스가 죽으면 서비스 전체가 내려가고 보관 배치까지 함께 멈춘다. 따라서 스케줄 경로는 실패를 요약으로 알리고 **다음 회차를 기다린다**(멱등이라 남은 대상은 다음 실행이 마저 지운다 — `DATA-002-04`). 스케줄 작업 안에서 프로세스 종료를 호출하지 않고, 예외를 스케줄 작업 밖으로 던지지 않는다.

### 연관 데이터 및 외부 호출

- **호출 API**: 없음.
- **데이터 조회 대상**: [`ENT-001`](../datas/data_ENT-001.md)(두 기준 각각의 범위 조회) · [`ENT-002`](../datas/data_ENT-002.md)(동의 일시 범위 조회).
- **데이터 변경 대상(CRUD)**: 두 엔터티의 **하드 삭제**. **[`ENT-003`](../datas/data_ENT-003.md) 은 건드리지 않는다**(`DATA-002-03`) — 삭제하면 성과 지표 산출 근거가 사라진다.

### 실행 제약사항

- **트랜잭션 경계**: **대상별 독립 트랜잭션**이다. FK 가 없어 삭제 순서 제약이 없으므로(`spec-datas.md` §엔터티 간 주요 의존관계 4) 추적 레코드와 동의 증적을 따로 지운다. 대량이면 나눠 수행해도 되며 멱등성만 유지하면 된다.
- **동시성 제어**: 삭제 대상 산정이 **기준 일시 기반 재산정**이라 두 실행이 겹쳐도 손상이 없다. 이미 지워진 행은 조건에 걸리지 않아 0건이 된다. 락·실행 잠금을 별도로 두지 않는다.
- **멱등성**: **같은 날 여러 번 실행해도 데이터가 손상되지 않고 두 번째부터 건수가 0 이 된다**(`DATA-002-04`).
- **성능 요구**: 두 기준을 **각각의 인덱스로 분리 산정**한다 — 하나의 조건절에 `OR` 로 묶으면 계획이 흔들린다([`../datas/spec-datas.md`](../datas/spec-datas.md) §인덱스 전략).
- **`batchSize` 의 출처**: `B3`·`B4` 의 `LIMIT :batchSize` 는 **애플리케이션 내부 기본값**이며 **실행 인자·옵션으로 노출하지 않는다**(§입력 정의 — 인자·옵션을 두지 않는다). 연동 구성 상수도 아니므로 기동 시 상수 검증 대상이 아니다(`OPS-001-02`). **구체 값은 build 가 확정**한다 — 한 번에 지우는 양만 달라질 뿐 **삭제 대상 산정 기준과 멱등성은 값과 무관**하며, 상한에 걸려 남은 대상은 다음 실행에서 다시 산정된다.
- **보안 요구**: **인증 없음**(`AUTH-001-01`). 표준 출력·표준 오류·로그에 추적 키·개인정보를 담지 않는다(FN-015). **별도 실행 이력 저장소를 두지 않는다**(`OPS-003-04`) — 관측 수단은 **요약(두 경로 공용)과 CLI 경로의 종료 코드**뿐이며, **스케줄 경로에는 종료 코드가 없어 요약이 유일하다**(§스케줄 경로의 관측 표면).

### 구현 가이드

- **두 진입 경로가 같은 함수를 부르게 한다.** 로직이 갈라지면 스케줄과 수동 실행의 결과가 달라져 검증이 의미를 잃는다. **다만 관측 표면까지 같게 만들려 하지 않는다** — "마지막 줄"과 종료 코드는 CLI 경로에만 성립한다.
- **기준 일시를 인자로 받지 않는다.** 받으면 두 경로의 산정 기준이 갈린다(`DATA-002-04`). 검증은 시드 데이터의 일시를 조정한다.
- **개월 감산에 언어·라이브러리의 기본 동작을 그대로 쓰지 않는다.** 다수 런타임의 월 설정 함수는 **월말 자리를 다음 달로 이월**하고(예: 5월 31일 − 3개월 → 3월 3일) **UTC 달력**으로 계산한다 — 둘 다 `DATA-002-06` 위반이며 **조기 삭제(비가역 소실)** 를 만든다. `B2` 의 5단계(벽시계 분해 → 연·월 감산 → 말일 clamp → 시각 보존 → 절대 시각 복원)를 그대로 구현한다.
- **시간대는 반드시 명시 지정한다.** 서버 OS·데이터베이스 세션의 기본 시간대에 기대면 배포 환경에 따라 임계값이 달라진다. 지표 일자 산출이 이미 같은 기법을 쓰므로 새 기법이 아니다([`process_PROC-303.md`](process_PROC-303.md) `B2`).
- **스케줄 앵커도 `Asia/Seoul` 로 명시한다.** 앵커와 기산 프레임이 갈리면 실행 시점의 달력 날짜와 임계값 산출의 달력 날짜가 어긋난다. 발화 시각(시·분)은 열려 있으나 **시간대와 하루 1회는 사양이다.**
- **두 삭제 기준을 `OR` 로 묶지 않는다.** 기준별로 대상을 뽑아 합집합을 지워야 인덱스가 각각 쓰이고 계획이 안정된다.
- **경계 비교에 `<=` 를 쓰지 않는다.** 기준 일시와 정확히 같은 시각의 행은 남긴다(`DATA-002-06` ⑤).
- **지표 집계를 삭제 대상에 넣지 않는다.** 넣으면 보관 기간 이후의 성과 지표 산출 근거가 사라진다.
- **요약 줄을 순수 JSON 으로 유지한다.** 키 4개와 순서를 바꾸지 않는다. **CLI 는 스트림을 갈라**(요약 = 표준 출력 / 진단 = 표준 오류) 표준 출력을 통째로 파싱 가능하게 두고, **스케줄은 줄을 가른다** — 요약 줄에 로거 장식이나 진단 문구를 붙이지 않는다.
- **스케줄 경로에서 요약을 로거로만 내보내지 않는다.** 로거가 실패 레벨을 표준 오류로 라우팅하면 실패했을 때 표준 출력이 비어 관측 수단이 사라진다 — 표준 출력을 직접 통제해 **성패와 무관하게** 1줄을 낸다.
- **스케줄 실행 실패로 프로세스를 끝내지 않는다.** 예외를 스케줄 작업 밖으로 던지거나 종료를 호출하면 사용자 웹·API 까지 함께 내려간다(`OPS-004-01`·EXC-OPS-12).
- **대량 삭제를 나눠 수행해도 된다.** 기준 일시 기반 재산정이라 나눠도 멱등성이 유지된다.
- **삭제 대상 목록을 출력·로그에 남기지 않는다.** 추적 키가 그대로 흘러나간다(FN-015).
