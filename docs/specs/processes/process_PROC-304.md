# 보관정책 배치 기능 정의

정본 목록은 [`spec-process.md`](spec-process.md). 단계 라벨 체계도 그 문서가 갖는다. 용어는 [`../../../wiki/WIKI.md`](../../../wiki/WIKI.md).

## 개요

- **정의 대상**: 보관 기간이 지난 기록을 **일 단위로 지워** 개인정보를 지속 보관하지 않는다는 제품 원칙을 실제로 유지시키는 처리다. **스케줄 실행과 명령 진입점을 통한 수동 실행이 같은 삭제 로직을 공유**하며 진입 경로만 다르다.
- **관련 PRD 요구사항**:
	- [`../../prd/PRD.md`](../../prd/PRD.md) §수행 범위 9 — "일 단위 배치로 보관 기간 경과분을 삭제한다."
	- [`../../prd/PRD.md`](../../prd/PRD.md) §프로그램 구성·기술스택·검증 방법 — "보관 배치는 인앱 스케줄 작업이라 명령 실행·종료 코드로 관측할 수 없으므로, **수동 실행 진입점 제공을 요구사항으로 둔다**(선택 사항이 아니다)."

### 진입점 및 진입 조건

**두 진입 경로가 같은 삭제 로직 함수를 부른다.** 진입 경로만 다르고 산정 기준·삭제 로직·결과 요약·종료 코드 규칙이 모두 같다(`DATA-002-04`·BR-015).

| 경로 | 진입점 | 실행 주체 |
|---|---|---|
| **스케줄 실행** | 애플리케이션 안의 일 단위 스케줄 작업 | 시스템 |
| **수동 실행** | 배포 단위 안의 **CLI 진입점** — `node dist/cli/retention.js`(개발 편의 별칭 `npm run retention:run`). **인자·옵션 없음** | 허브 운영자 |

- **진입 조건**: **인증 없음 — `AUTH-001` 인용.** 관리자 경로·관리자 인증을 두지 않으며(`AUTH-001-01`), CLI 진입점은 배포 단위 안에 있어 **외부 표면을 늘리지 않는다**. HTTP 관리 엔드포인트를 만들지 않는다.
- **사전 검증**: **필수 상수가 충족되지 않으면 기동 단계(PROC-901)에서 중단**된다 — 이때는 요약 JSON 을 낼 주체가 없으므로 표준 출력에 미충족 상수명을 남기고 0 이외 코드로 끝난다(`OPS-001-02` → `EX-OPS-001`).
- **인자를 두지 않는 이유**: 기준 일시를 인자로 받으면 스케줄 실행과 산정 기준이 갈려 `DATA-002-04`(같은 산정 기준)가 깨진다. 검증은 시드 데이터의 일시를 조정해 수행한다.

### 입력/출력 정의

| 구분 | 항목명 | 데이터 타입 | 필수 | 설명 |
|------|--------|------------|------|------|
| 입력 | (없음) | — | - | 인자·옵션을 두지 않는다 |
| 입력(주입) | `<RETENTION_MONTHS>`·`<RETENTION_MAX_MONTHS>`·`<CONSENT_PROOF_RETENTION_MONTHS>` | 상수 | Y | [`MDL-022`](../datas/model_MDL-019-022.md). **값을 본 사양에 복제하지 않는다** |
| 출력 | 표준 출력 마지막 줄 | JSON 1줄 | - | [`MDL-021`](../datas/model_MDL-019-022.md) — `baseAt`·`trackingDeletedCount`·`consentProofDeletedCount`·`failureReason` **4키 고정·순서 불변** |
| 출력 | 표준 오류 | 문자열 | - | 진단 문구는 전부 여기로 — 표준 출력이 항상 파싱 가능하도록 |
| 출력 | 종료 코드 | 정수 | - | `0` = 성공 / `0` 이외 = 실패 |

### 연관 데이터 및 외부 호출

- **호출 API**: 없음.
- **데이터 조회 대상**: [`ENT-001`](../datas/data_ENT-001.md)(두 기준 각각의 범위 조회) · [`ENT-002`](../datas/data_ENT-002.md)(동의 일시 범위 조회).
- **데이터 변경 대상(CRUD)**: 두 엔터티의 **하드 삭제**. **[`ENT-003`](../datas/data_ENT-003.md) 은 건드리지 않는다**(`DATA-002-03`) — 삭제하면 성과 지표 산출 근거가 사라진다.

### 실행 제약사항

- **트랜잭션 경계**: **대상별 독립 트랜잭션**이다. FK 가 없어 삭제 순서 제약이 없으므로(`spec-datas.md` §엔터티 간 주요 의존관계 4) 추적 레코드와 동의 증적을 따로 지운다. 대량이면 나눠 수행해도 되며 멱등성만 유지하면 된다.
- **동시성 제어**: 삭제 대상 산정이 **기준 일시 기반 재산정**이라 두 실행이 겹쳐도 손상이 없다. 이미 지워진 행은 조건에 걸리지 않아 0건이 된다. 락·실행 잠금을 별도로 두지 않는다.
- **멱등성**: **같은 날 여러 번 실행해도 데이터가 손상되지 않고 두 번째부터 건수가 0 이 된다**(`DATA-002-04`).
- **성능 요구**: 두 기준을 **각각의 인덱스로 분리 산정**한다 — 하나의 조건절에 `OR` 로 묶으면 계획이 흔들린다([`../datas/spec-datas.md`](../datas/spec-datas.md) §인덱스 전략).
- **보안 요구**: **인증 없음**(`AUTH-001-01`). 표준 출력·표준 오류에 추적 키·개인정보를 담지 않는다(FN-015). **별도 실행 이력 저장소를 두지 않는다**(`OPS-003-04`) — 요약과 종료 코드가 유일한 관측 수단이다.

### 로직 실행 순서

#### FE 측 처리 (의사코드)

**사용자 화면이 없다.** 스케줄과 명령 진입점으로만 실행하며 관리 화면·HTTP 관리 경로를 두지 않는다. FE 자리에는 **호출측(스케줄러·허브 운영자)** 처리를 `C` 라벨로 적는다.

```
C1. 스케줄 발화 (시스템)

  진입 트리거: 애플리케이션 안의 일 단위 스케줄 작업
  전달 값: 없음 — 기준 일시를 넘기지 않는다 (산정 기준이 갈리면 안 된다)
  관측: 결과 요약은 표준 출력으로 나가고, 별도 실행 이력을 남기지 않는다 (POL OPS-003-04)

C2. 수동 실행 (허브 운영자)

  진입 트리거: 운영자가 배포 단위 안에서 명령을 실행한다
    실행 명령: node dist/cli/retention.js        (개발 편의 별칭 npm run retention:run)
    인자·옵션: 없다
  // HTTP 관리 경로를 쓰지 않는다 — 인증 없는 삭제 트리거를 공개 표면에 두면
  //   관리자 경로를 두지 않기로 한 결정과 정면 충돌한다 (POL AUTH-001-01)

C3. 결과 판독 (검증의 관측 지점)

  종료 코드로 먼저 분기한다
    0        → 성공. 표준 출력 마지막 줄의 요약 JSON 을 파싱해 건수를 확인한다
    0 이외   → 실패
        요약 JSON 이 있으면  failureReason 으로 사유를 읽는다 (건수는 그 시점까지 실제 삭제분)
        요약 JSON 이 없으면  기동 실패로 판독한다 (미충족 상수명이 표준 출력에 있다)
  // 진단 문구는 표준 오류로 나가므로 표준 출력은 항상 파싱 가능하다
```

#### BE 측 처리 (의사코드)

```
B1. 실행 진입 — POL DATA-002-04 · AUTH-001-01 (validate)

  엔드포인트·메서드: 없음 — 스케줄 작업 또는 CLI 진입점이 애플리케이션 컨텍스트를 기동해
                      삭제 로직을 1회 실행하고 종료한다
  인증·인가 검증: 인증 없음 — AUTH-001 인용 (관리자 경로·관리자 인증을 두지 않는다)
  선행 조건: PROC-901 기동 검증 통과. 필수 상수 미충족이면 여기 도달하기 전에 중단된다
             (표준 출력에 미충족 상수명 · 0 이외 종료 · 요약 JSON 없음 — EX-OPS-001)
  두 진입 경로가 같은 함수를 부른다 — 아래 B2~B7 이 그 함수다 (BR-015)

B2. 기준 일시 산정 — POL OPS-001-04 (transform)

  now = NOW()
  baseAt                = now                                  // 요약에 그대로 싣는다
  trackingConfirmBefore = now − <RETENTION_MONTHS> 개월
  trackingCreatedBefore = now − <RETENTION_MAX_MONTHS> 개월
  consentBefore         = now − <CONSENT_PROOF_RETENTION_MONTHS> 개월
  // 상수 주입 값으로 실행 시점에 계산한다. 값을 코드·사양에 복제하지 않는다

B3. 추적 레코드 삭제 대상 산정 — POL DATA-002-01 · BR-016 (validate)

  -- 기준 ① 결과 확인 완료 기산 (부분 인덱스 idx_interlock_tracking_result_confirmed_at)
  SELECT tracking_key FROM tbl_interlock_tracking
  WHERE result_confirmed_at IS NOT NULL
    AND result_confirmed_at < :trackingConfirmBefore
  ORDER BY result_confirmed_at
  LIMIT :batchSize;                         -- 대량 삭제를 나눠 수행하기 위한 상한(멱등 유지)

  -- 기준 ② 생성 기산 절대 상한 (인덱스 idx_interlock_tracking_created_at)
  SELECT tracking_key FROM tbl_interlock_tracking
  WHERE created_at < :trackingCreatedBefore
  ORDER BY created_at
  LIMIT :batchSize;

  targetsTracking = 두 결과의 합집합           -- 먼저 도달한 기준이 자동으로 반영된다
  -- 두 기준을 OR 로 묶지 않는다 — 하나의 조건절에 묶으면 계획이 흔들린다
  -- 지표 집계는 대상에 넣지 않는다 (POL DATA-002-03)

B4. 동의 증적 삭제 대상 산정 — POL DATA-002-02 (validate)

  SELECT consent_proof_id FROM tbl_consent_proof
  WHERE consented_at < :consentBefore
  ORDER BY consented_at
  LIMIT :batchSize;                          -- 인덱스 idx_consent_proof_consented_at
  targetsConsent = 조회 결과
  -- 추적 레코드와 다른 기준을 쓴다. 추적 레코드가 지워진 뒤 증적만 남은 상태가 정상이다

B5. 삭제 수행 — POL DATA-002-04 (대상별 독립 트랜잭션)

  BEGIN;
    DELETE FROM tbl_interlock_tracking WHERE tracking_key IN (:targetsTracking);
    trackingDeletedCount = 삭제 행 수
  COMMIT;

  BEGIN;
    DELETE FROM tbl_consent_proof WHERE consent_proof_id IN (:targetsConsent);
    consentProofDeletedCount = 삭제 행 수
  COMMIT;

  -- 하드 삭제만 쓴다. 논리 삭제 컬럼이 없다 (보관 정책의 목적이 삭제다)
  -- FK 가 없어 순서 제약이 없다. 두 삭제는 서로 독립이다
  -- tbl_interlock_metric_daily 를 건드리지 않는다 (POL DATA-002-03)
  실패 시: 그 시점까지의 건수를 유지하고 failureReason 에 사유를 담은 뒤 B6 으로 간다
          (다음 실행이 남은 대상을 마저 지운다 — 멱등하므로 안전하다)

B6. 결과 요약 출력 — POL OPS-003-04 (mask)

  summary = { baseAt: baseAt → ISO 8601 + 오프셋,
              trackingDeletedCount, consentProofDeletedCount,
              failureReason: (실패 사유 문자열 또는 null) }
  표준 출력의 **마지막 줄**에 JSON 1줄로 내보낸다     // 키 4개 고정 · 순서 불변
  진단 문구·경고는 전부 표준 오류로 내보낸다          // 표준 출력이 항상 파싱 가능하도록
  마스킹: FN-015 — 추적 키·증적 식별자·삭제 대상 목록을 출력에 담지 않는다
  // 지표 집계 삭제 건수 항목이 없다 — 삭제 대상이 아니라 셀 것이 없다
  // 별도 실행 이력 테이블을 두지 않는다 (POL OPS-003-04)

B7. 종료 코드 반환 — POL OPS-003-04

  if (failureReason == null)   exit 0
  else                         exit 1                 // 0 이외 = 실패
  후속 이벤트 발행: 없음
```

### 구현 가이드

- **두 진입 경로가 같은 함수를 부르게 한다.** 로직이 갈라지면 스케줄과 수동 실행의 결과가 달라져 검증이 의미를 잃는다.
- **기준 일시를 인자로 받지 않는다.** 받으면 두 경로의 산정 기준이 갈린다(`DATA-002-04`). 검증은 시드 데이터의 일시를 조정한다.
- **두 삭제 기준을 `OR` 로 묶지 않는다.** 기준별로 대상을 뽑아 합집합을 지워야 인덱스가 각각 쓰이고 계획이 안정된다.
- **지표 집계를 삭제 대상에 넣지 않는다.** 넣으면 보관 기간 이후의 성과 지표 산출 근거가 사라진다.
- **표준 출력에 요약만 내보낸다.** 진단·경고를 섞으면 검증 절차의 파싱이 깨진다. 키 4개와 순서를 바꾸지 않는다.
- **대량 삭제를 나눠 수행해도 된다.** 기준 일시 기반 재산정이라 나눠도 멱등성이 유지된다.
- **삭제 대상 목록을 출력·로그에 남기지 않는다.** 추적 키가 그대로 흘러나간다(FN-015).
