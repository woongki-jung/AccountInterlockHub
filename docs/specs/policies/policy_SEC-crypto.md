# 암호화 연동 규약 정책 정의

정본 목록은 [`spec-policies.md`](spec-policies.md). 용어는 [`../../../wiki/WIKI.md`](../../../wiki/WIKI.md).

## 개요

- **정책 목적**: 연동 라이브러리(암호화)와 허브(복호화)가 **같은 입력에서 항상 같은 결과**를 내도록 규약을 한 곳에 못박는다. 두 구현이 다른 언어·런타임이라 규약이 한 자리라도 흔들리면 연동이 성립하지 않는다.
- **관련 PRD 요구사항**:
	- [`../../prd/PRD.md`](../../prd/PRD.md) §수행 범위 2 — "전달 데이터 X(JSON) → `encX`·`encY` 이중 암호화 규약을 정의한다. 이 규약은 **연동 라이브러리(암호화)와 허브(복호화)가 공유하는 단일 계약**이다."
	- [`../../prd/PRD.md`](../../prd/PRD.md) §시스템 제약사항 — "**암호화·복호화 규약 대칭**: … 규약이 바뀌면 함께 바뀌어야 한다."
	- 상위 규약은 [`../../prd/devspec/external-apis.md`](../../prd/devspec/external-apis.md) §암호화 연동 규약이며, 본 정책은 그 미확정 세부(블록 모드·키 정규화·패딩·IV·전달 형식·길이 한계)를 채운다. 상위 규약과 충돌하는 값을 만들지 않는다.

## SEC-001 암호화 연동 규약

### 기본 정보

| 항목 | 내용 |
|------|------|
| 정책명 | 암호화 연동 규약 |
| 분류 | SEC |
| 적용 범위 | 연동 라이브러리(암호화·요청 URL 생성)와 허브(복호화·자가진단)의 전 구간. 배포 패키지의 규약 버전 표기와 규약 테스트 벡터도 본 규약을 근거로 삼는다 |
| 우선순위 | 높음 |
| 관련 정책 | `SEC-002`(복호화 판정) · `DATA-001`(무저장) · `OPS-002`(수용 리스크) |
| 적용 PROC | PROC-101 · PROC-102 · PROC-104 · PROC-204 · PROC-401 · PROC-402 · PROC-403 · PROC-404(배포 절차 통제) |
| 관련 IA 항목 | 공통 (정본 [`../../../ai/strategies/ia.md`](../../../ai/strategies/ia.md) §참조 규약) |

### 규약 확정값

| 항목 | 확정값 |
|---|---|
| 알고리즘·블록 모드 | AES-256-CBC |
| 패딩 | PKCS#7 |
| 문자 인코딩 | UTF-8 (X 직렬화·키 문자열 바이트화 공통) |
| 키 길이 | 32바이트(256비트) |
| IV 길이 | 16바이트(128비트) |
| 정규화 패딩 문자 | `_` (0x5F) |
| 전달 인코딩 | Base64URL (RFC 4648 §5 — `-`·`_` 알파벳, 패딩 `=` 제거) |
| X 평문 크기 상한 | 1,024 바이트(UTF-8 직렬화 후) |
| 연동 요청 URL 전체 길이 상한 | 2,000 자 |
| 규약 버전 | `1.0` (`<MAJOR>.<MINOR>` 문자열) |

### 정책 규칙

| 규칙 ID | 규칙 내용 | 적용 조건 | 적용 지점 | 위반 시 처리 (HTTP·EX 코드) |
|---------|-----------|-----------|-----------|----------------------------|
| SEC-001-01 | 대칭 암호는 **AES-256-CBC + PKCS#7 패딩**만 쓴다. 다른 블록 모드(ECB·GCM 등)·다른 패딩을 쓰지 않는다 | 암호화·복호화 전 구간 | 검증 | 규약 위반이므로 복호화가 실패한다 → 400 `EX-SEC-002`. 라이브러리는 규약 위반 예외(사유 `EX-SEC-002`) |
| SEC-001-02 | 문자열 ↔ 바이트 변환은 **UTF-8** 로만 한다(X 의 JSON 직렬화, 발송처키·생년월일의 바이트화 공통) | 암호화·복호화 전 구간 | 입력 가공 | 인코딩 불일치는 복호화 실패로 귀결 → 400 `EX-SEC-002` |
| SEC-001-03 | **키 32바이트 정규화**: 키 문자열을 UTF-8 바이트로 바꾼 뒤 32바이트 미만이면 `_`(0x5F)로 우측을 채우고, 32바이트를 넘으면 앞 32바이트만 남긴다 | 모든 키 산출 시 | 입력 가공 | 정규화를 생략·변형하면 키가 달라져 복호화 실패 → 400 `EX-SEC-002` |
| SEC-001-04 | **IV** 는 정규화된 32바이트 키의 **앞 16바이트**를 그대로 쓴다. 난수 IV·별도 IV 전달을 두지 않는다 | 모든 암호화·복호화 | 입력 가공 | IV 불일치는 복호화 실패 → 400 `EX-SEC-002` |
| SEC-001-05 | **`encX` 의 키 원문** = 발송처키 문자열 + 생년월일(`yyMMdd`) 문자열을 **구분자 없이 이어 붙인 값**이며, 이어 붙인 뒤 `SEC-001-03` 으로 정규화한다 | `encX` 산출·복원 | 입력 가공 | 키 불일치 → 400 `EX-AUTH-002`(본인확인 실패로 분류, `SEC-002` 참조) |
| SEC-001-06 | **`encY` 의 키 원문** = 생년월일(`yyMMdd`) 6자이며, `SEC-001-03` 으로 정규화한다(6바이트 + `_` 26개) | `encY` 산출·복원 | 입력 가공 | 키 불일치 → 400 `EX-AUTH-002` |
| SEC-001-07 | **`encY` 의 평문** = `encX` 암호화에 쓴 **정규화된 32바이트 키 바이트열 그대로**다. 허브는 `encY` 복호화 결과를 재정규화하지 않고 그대로 `encX` 의 키로 쓴다 | `encY` 산출·복원 | 입력 가공 | 재정규화 수행 시 키가 어긋나 복호화 실패 → 400 `EX-SEC-002` |
| SEC-001-08 | `encX`·`encY` 는 **Base64URL**(RFC 4648 §5, 패딩 `=` 제거)로 인코딩해 전달한다. 표준 Base64(`+`·`/`·`=`)·퍼센트 인코딩을 겹쳐 쓰지 않는다 | 요청 URL 생성·진입 파싱 | 입력 가공 | 디코드 실패 → 400 `EX-SEC-001` |
| SEC-001-09 | **X 평문은 UTF-8 직렬화 후 1,024바이트 이하**여야 한다 | 라이브러리 암호화 호출 시 | 검증 | 라이브러리가 규약 위반 예외(사유 `EX-SEC-004`)를 던지고 암호화를 수행하지 않는다. 허브 자가진단은 400 `EX-SEC-004` |
| SEC-001-10 | **연동 요청 URL 전체 길이는 2,000자 이하**여야 한다 | 요청 URL 생성·진입 | 검증 | 생성 시 라이브러리 예외(사유 `EX-SEC-004`), 진입 시 400 `EX-SEC-004` |
| SEC-001-11 | 규약 버전은 `<MAJOR>.<MINOR>` 문자열이며 현재 값은 `1.0` 이다. **MAJOR 가 다르면 비호환**(라이브러리 재배포 필요), MINOR 차이는 호환으로 판정한다 | 라이브러리·허브 버전 대조 | 검증 | 비호환 판정 시 발송처에 재배포 안내. 허브는 요청을 거절하지 않는다(버전 값이 요청에 실리지 않으므로 런타임 분기가 아니다) |
| SEC-001-12 | 규약을 바꾸면 **라이브러리와 허브를 함께 배포**하고 규약 버전의 MAJOR 또는 MINOR 를 올린다. 한쪽만 바꾸는 배포를 하지 않는다 | 규약 개정 시 | 검증 | 배포 절차 중단(절차 통제 — 애플리케이션 분기 아님). 규약 테스트 벡터 재생성·대조 통과가 배포 전제다 |

### 예외 사항

- **EXC-SEC-01 (수용 리스크 — 결정적 IV)**: IV 가 키에서 결정적으로 파생되므로 **같은 키·같은 평문은 항상 같은 암호문**이 된다. 이 한계는 상위 규약([`../../prd/devspec/external-apis.md`](../../prd/devspec/external-apis.md) §암호화 연동 규약)이 정한 것이며 [`../../prd/PRD.md`](../../prd/PRD.md) §시스템 제약사항의 수용 리스크(기밀성)에 포함된다. **결함으로 취급하지 않으며** 난수 IV 도입은 이번 범위가 아니다(규약 대칭을 깨므로 라이브러리·허브 동시 개정 사안).
- **EXC-SEC-02 (생년월일 경우의 수)**: 생년월일 6자리는 경우의 수가 작아 오프라인 전수대입에 약하다. 이 역시 수용 리스크이며(`OPS-002`) 규약 강화로 대응하지 않는다.
- **EXC-SEC-03 (자가진단의 규약 판정)**: 자가진단 API 는 발송처가 이미 아는 값(자기가 만든 `encX`·`encY` 와 생년월일)으로 규약 적합성만 판정한다. 판정 절차는 `SEC-002` 와 동일하나 **결과 구분 확정·기록·수신처 전달을 하지 않는다**.
- **EXC-SEC-04 (허브의 발송처키 미보유)**: 허브는 발송처키를 갖지 않으므로 `encX` 의 키를 직접 만들 수 없다. 항상 `encY` 복호화로 얻은 키를 쓴다 — 이것이 `SEC-001-07` 이 재정규화를 금지하는 이유다.

### 구현 가이드

- **양쪽 구현이 같은 결과를 내는지 확인하는 방법**: 알려진 입력(발송처키·생년월일·X)에 대한 기대 출력(`encX`·`encY`·요청 URL)을 규약 테스트 벡터(`LIB-04`)로 고정하고, 라이브러리와 허브가 그 벡터를 통과하는지 대조한다. 벡터는 정규화 경계(키 원문이 32바이트 미만·정확히 32바이트·초과)와 Base64URL 치환 문자(`-`·`_`)가 나오는 값을 반드시 포함한다.
- **정규화 순서 주의**: 이어 붙이기 → 정규화 순서를 지킨다(`SEC-001-05`). 각각 정규화한 뒤 이어 붙이면 다른 키가 나온다.
- **패딩 검증 필수**: 복호화 시 PKCS#7 패딩 검증을 끄지 않는다. 패딩 검증이 잘못된 키를 걸러내는 1차 판정 수단이다(`SEC-002`).
- **암호문 길이**: CBC + PKCS#7 이므로 암호문은 항상 16의 배수 바이트다. 진입 시점의 구조 판정에 쓸 수 있다(`SEC-002-02`).
- **크기 산정 근거**: X 1,024B → CBC 최대 1,040B → Base64URL 약 1,387자, `encY` 48B → 64자, 기준 URL·경로·파라미터명 약 80자 ⇒ 약 1,531자로 URL 상한 안에 들어온다.
- **금지**: 암호값·복호화 원문·키·생년월일을 로그·예외 메시지·응답에 담지 않는다(`DATA-001-04`).
- 특정 라이브러리·프레임워크를 강제하지 않는다. .NET Framework 4.8 과 Node.js 표준 암호 기능이 모두 지원하는 조합이라 별도 의존을 추가할 필요가 없다.
