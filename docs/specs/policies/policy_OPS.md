# 운영 정책 정의

정본 목록은 [`spec-policies.md`](spec-policies.md). 용어는 [`../../../wiki/WIKI.md`](../../../wiki/WIKI.md).

## 개요

- **정책 목적**: 배포 시점 상수로만 움직이는 서비스이므로 **상수가 제대로 주입됐는지**가 곧 서비스 정상성이다. 그 확인 규칙과, 잠정값 상태로 운영에 나가지 않게 하는 통제, 그리고 접근 통제를 두지 않기로 한 결정과 그 수용 리스크를 확정한다.
- **관련 PRD 요구사항**:
	- [`../../prd/devspec/infra.md`](../../prd/devspec/infra.md) §연동 구성 상수 주입 — "애플리케이션은 기동 시 필수 상수의 존재·형식을 확인하고, 충족하지 않으면 기동을 중단한다 … **잠정값 여부는 애플리케이션이 판별하지 않으므로 배포 절차의 확인 항목으로 둔다**."
	- [`../../prd/PRD.md`](../../prd/PRD.md) §시스템 제약사항 — "**접근 통제 없음 (수용 리스크)**: 인증·요청 제한·발송처 검증을 모두 두지 않으므로 접근을 막는 수단이 없다."
	- [`../../prd/PRD.md`](../../prd/PRD.md) §수행 범위 — 제외 — "**보안 이벤트 기록** — 복호화 실패·전달 차단 등의 보안 이벤트를 별도로 남기지 않는다."

## OPS-001 상수 주입·잠정값 배포 통제

### 기본 정보

| 항목 | 내용 |
|------|------|
| 정책명 | 상수 주입·잠정값 배포 통제 |
| 분류 | OPS |
| 적용 범위 | 애플리케이션 기동 시 상수 검증과 운영 배포 절차 |
| 우선순위 | 높음 |
| 관련 정책 | `DATA-001`(구성 미저장) · `DATA-003`(동의 항목) · `SEC-003`(자가진단 경로) |
| 적용 PROC | PROC-901 |
| 관련 IA 항목 | 공통 |

### 정책 규칙

| 규칙 ID | 규칙 내용 | 적용 조건 | 적용 지점 | 위반 시 처리 (HTTP·EX 코드) |
|---------|-----------|-----------|-----------|----------------------------|
| OPS-001-01 | 연동 구성 값은 **배포 시점 상수**로만 존재하고 배포 시 애플리케이션 설정으로 주입된다. 값의 단일 출처는 [`CLAUDE.env.md`](../../../CLAUDE.env.md) §연동 구성 상수이며, 변경은 **재배포로만** 반영된다 | 상시 | 검증 | 런타임 변경 수단(구성 화면·구성 API)을 도입한 사양은 반려 |
| OPS-001-02 | 애플리케이션은 **기동 시 필수 상수의 존재·형식을 확인**하고, 하나라도 충족하지 않으면 **기동을 중단**한다 | 기동 시 | 검증 | 기동 중단(비정상 종료 코드) + 표준 출력에 미충족 상수명. HTTP 응답 없음 — 사유 코드 `EX-OPS-001` |
| OPS-001-03 | **잠정값 상태로 운영 배포하지 않는다.** 잠정 여부는 애플리케이션이 판별하지 않으므로 이는 **배포 절차의 확인 항목**이며, 운영 배포 전 잠정 표기 항목이 실제 값으로 교체됐는지 확인한다 | 운영 배포 시 | 검증 | 배포 절차 중단(절차 통제 — 애플리케이션 분기 아님). 미교체 항목이 있으면 배포하지 않는다 |
| OPS-001-04 | 상수 값을 사양·코드 본문에 **복제하지 않는다.** 값이 필요한 자리에는 플레이스홀더를 쓰고 단일 출처를 참조한다 | 사양·코드 작성 시 | 검증 | 값이 박힌 사양·코드는 반려(확정 시 값 교체만으로 끝나야 한다) |

### 예외 사항

- **EXC-OPS-01 (잠정값 목록)**: 현재 잠정값은 `<RECEIVER_DELIVERY_URL>` · `<HUB_BASE_URL_PROD>` · `<HUB_BASE_URL_DEV>` · `<SELFCHECK_PATH>` · `<CONSENT_NOTICE>` · `<CONSENT_PROOF_RETENTION_MONTHS>` · `<COMPLETION_REDIRECT_URL>` 와 성과 지표 목표치다. 형식 검증은 통과하므로 **개발·검증 환경 기동을 막지 않는다.** `<COMPLETION_REDIRECT_URL>` 의 잠정값은 `<RECEIVER_DELIVERY_URL>` 과 달리 **실 호스트로 연결되는 주소**라 교체를 잊고 배포하면 **연동 완료 결과**를 본 사용자가 무관한 사이트로 이동한다 — 배포 절차 확인(`OPS-001-03`)에서 반드시 걸러야 하는 항목이다. 이 상수를 응답에 싣는 대상은 **연동 완료 결과 하나뿐**이며(`BIZ-001-06`), 완료가 아닌 결과에는 싣지 않으므로 노출 범위도 그만큼이다.
- **EXC-OPS-02 (성과 지표 목표치)**: 목표치는 상수표가 아니라 [`../../prd/PRD.md`](../../prd/PRD.md) §성과 지표의 표에 있다. 상수 주입 대상이 아니므로 사양은 목표치 수치를 옮겨 적지 않고 PRD 를 참조한다. 확정 전까지 미달을 결함으로 다루지 않는다.
- **EXC-OPS-03 (자가진단 경로의 운영 값)**: `<SELFCHECK_PATH>` 의 운영 값은 상수표에 적지 않고 배포 시 주입되는 비밀 값으로 다룬다(`SEC-003-01`). 상수표에는 형식·잠정값만 남는다.
- **EXC-OPS-04 (발송처 호출 입력 값)**: `<HUB_BASE_URL_PROD>`·`<HUB_BASE_URL_DEV>` 는 허브에 주입되는 값이 아니라 발송처가 라이브러리 호출 인자로 넘기는 값이다. 기동 시 필수 상수 검증 대상이 아니다.

|---------|----------|-------------------------------|--------------------------------|

| OPS-001-02 | PROC-901 | 기동 시 상수 형식 검증 | 검증 |
| OPS-001-03 | — (배포 절차) | 운영 배포 전 확인 | 검증 |

### 구현 가이드

- 기동 검증은 **모든 미충족 항목을 모아 한 번에 보고**한 뒤 중단한다. 하나씩 실패시키면 배포자가 여러 번 재시도해야 한다.
- 형식 검증 대상은 상수표가 정의한 형태다 — 경로 형태, URL 형태, 개월 수의 양의 정수, 동의 항목의 JSON 배열 구조와 필수 속성.
- 배포 절차의 잠정값 확인은 체크리스트 항목으로 둔다. 자동 판별 수단을 만들지 않는다(상수표의 잠정 표기는 문서 표기이지 주입 값이 아니다).

## OPS-002 접근 통제 없음(수용 리스크)

### 기본 정보

| 항목 | 내용 |
|------|------|
| 정책명 | 접근 통제 없음(수용 리스크) |
| 분류 | OPS |
| 적용 범위 | 허브의 모든 외부 표면과 그에 따르는 위험의 취급 |
| 우선순위 | 높음 |
| 관련 정책 | `AUTH-001` · `SEC-001` · `SEC-003` · `DATA-002` |
| 적용 PROC | PROC-101 · PROC-102 · PROC-201 · PROC-202 · PROC-203 · PROC-204 |
| 관련 IA 항목 | 공통 |

### 정책 규칙

| 규칙 ID | 규칙 내용 | 적용 조건 | 적용 지점 | 위반 시 처리 (HTTP·EX 코드) |
|---------|-----------|-----------|-----------|----------------------------|
| OPS-002-01 | **수용 리스크 ① 기밀성** — `encX`·`encY` 가 URL 파라미터로 노출되고 생년월일은 경우의 수가 작아, 링크와 암호값을 확보한 자가 오프라인 전수대입으로 원문을 복원할 수 있다. **완화 장치를 추가하지 않고 수용**한다 | 상시 | 검증 | 별도 런타임 처리 없음(수용). 검증·리뷰에서 결함으로 올리지 않는다 |
| OPS-002-02 | **수용 리스크 ② 무결성·출처** — 허브는 발송처키를 갖지 않아 진입 요청이 정당한 발송처에서 왔는지 검증하지 못한다. 규약대로 만든 암호값이면 출처와 무관하게 복호화·중개되며, 완료 콜백도 추적 키를 아는 쪽이면 통지할 수 있다. **발송처 서명 검증을 두지 않고 수용**한다 | 상시 | 검증 | 별도 런타임 처리 없음(수용). 출처 검증을 추가한 사양은 반려 |
| OPS-002-03 | **수용 리스크 ③ 반복 시도** — 요청 제한이 없어 진입 경로·서버 대면 API 에 온라인 반복 시도를 막는 장치가 없다. **"요청 제한 정책 미수립"은 누락이 아니라 의도된 결정**이다. 자가진단 API 가 갖는 장치는 경로 비공개(`SEC-003`) 하나뿐이며, 그 장치가 반복 시도에 대해 갖는 **실제 효력의 범위는 `OPS-002-06`** 이 정한다 | 상시 | 검증 | 별도 런타임 처리 없음(수용). 요청 제한을 도입한 사양은 반려 |
| OPS-002-04 | **수용 리스크 ④ 조회로 인한 보관 기산 개시** — 처리상태 확인 API 에 인증이 없으므로 추적 키를 아는 누구든 조회로 그 레코드를 결과 확인 완료로 만들어 보관 기간 기산을 시작시킬 수 있다. 생성 기산 절대 상한(`DATA-002-01`)과 함께 **이 수준을 수용**한다 | 처리상태 확인 요청 시 | 검증 | 별도 런타임 처리 없음(수용). 조회 자격 검증을 추가한 사양은 반려 |
| OPS-002-05 | 위 네 리스크의 완화를 위한 **링크 만료(TTL)·1회성 사용·발송처 서명 검증·요청 제한을 이번 범위에서 도입하지 않는다.** 도입은 후속 보완 항목이다 | 상시 | 검증 | 도입한 사양·구현은 범위 밖으로 반려 |
| OPS-002-06 | **경로 비공개의 효력 범위** — 자가진단 경로의 비공개는 **경로 값 자체의 추측 난이도**에만 기대는 장치이고, 응답이 서로 구분되지 않는 성질에는 기대지 않는다. `SEC-003-04` 가 입력 부재·본문 해석 불가에 400 `EX-SEC-003` 을 요구하므로 **요청 1건으로 미정의 경로의 404 와 구분되어 경로의 존재가 확인된다.** 요청 제한이 없어(`OPS-002-05`) 후보 경로를 열거하는 시도도 막지 못한다. 따라서 이 장치는 **반복 시도를 막는 완화가 아니라 노출 범위를 줄이는 장치**로만 취급하고, 경로가 드러난 뒤의 반복 시도는 `OPS-002-03` 의 수용 범위에 그대로 든다 | 상시 | 검증 | 별도 런타임 처리 없음(수용). **경로가 드러나지 않는다는 전제 위에 다른 통제를 생략한 사양은 반려** |

### 예외 사항

- **EXC-OPS-05 (완화 장치는 둘뿐)**: 이 제품이 갖는 완화 장치는 ① 자가진단 경로 비공개 ② 수신처 전달의 서버 간 호출(브라우저 미경유)뿐이다. 그 외의 방어는 없다고 전제하고 사양을 짠다. ①의 효력 범위는 `OPS-002-06` 이 정한다.
- **EXC-OPS-06 (수용의 유효 범위)**: 수용은 **이번 범위의 결정**이다. 후속 보완([`../../prd/PRD.md`](../../prd/PRD.md) §미결·확인 필요 ⑮)에서 재검토된다.
- **EXC-OPS-07 (검증에서의 취급)**: 위 네 리스크는 검증 단계에서 **결함이 아니라 수용된 성질**로 다룬다. 리스크가 실제로 존재함을 확인하는 검증은 두되 실패로 판정하지 않는다.
- **EXC-OPS-10 (경로 노출이 수용 한도를 넘기지 않는 근거)**: 자가진단이 주는 능력은 **복호화 성공 여부 판정** 하나다. 그 능력은 경로를 몰라도 **공개된 사용자 진입 경로의 본인확인 재입력**에서 횟수 제한 없이 이미 얻을 수 있고(`SEC-002-04`·`AUTH-002-04`), 링크와 암호값을 확보한 자는 **오프라인 전수대입**으로도 얻는다(`OPS-002-01`). 따라서 경로가 드러나도 이미 수용한 리스크 ①·③ 을 넘는 능력이 새로 생기지 않는다. 이것이 `SEC-003-04` 의 진단 응답을 **일반 404 로 바꾸지 않는** 근거다 — 진단성을 버려도 그 대가로 보호되는 것이 없다.

### 구현 가이드

- 수용 리스크는 **문서로 관리**한다. 애플리케이션이 이를 감지·기록하는 장치를 만들지 않는다(`OPS-003`).
- 본 정책의 "검증"은 요청 진입 시 값을 막는 검증이 아니라 **사양·구현·검증 게이트에서 완화 장치가 추가되지 않았는지 확인하는 지점**이다. 런타임 분기는 만들지 않는다.
- 수신처 전달은 반드시 서버 간 호출로 한다(`BIZ-004-01`) — 몇 안 되는 실질 완화 장치다.

### 예외 사항

- **EXC-OPS-11 (관리형 데이터베이스라는 전제)**: 운영 데이터베이스는 **Azure Database for PostgreSQL** 이다([`../../prd/devspec/database.md`](../../prd/devspec/database.md) §데이터베이스 — "운영: Azure의 PostgreSQL 서비스"). 정기 점검·페일오버·유휴 커넥션 회수와 트랜잭션 안에 오래 머문 세션의 자동 종료·운영자의 세션 정리가 일상적으로 일어나므로, 커넥션의 비정상 종료는 가정이 아니라 **예정된 사건**이다. `OPS-004-01` 을 권고가 아닌 요구로 두는 이유다.
- **EXC-OPS-12 (프로세스 하나가 곧 서비스 전체)**: 운영 배포는 **하나의 Azure App Service** 이고([`../../prd/devspec/infra.md`](../../prd/devspec/infra.md) §배포 형태 — "운영 환경은 하나의 Azure App Service로 배포한다"), 사용자 웹·백엔드 API·보관 배치가 **한 배포 단위** 안에 함께 있다(같은 문서 §애플리케이션 구성). 프로세스가 죽으면 요청 1건이 실패하는 것이 아니라 **서비스 전체가 내려가고 보관 배치도 함께 멈춘다.** 이 정책의 우선순위가 높음인 근거다.

### 구현 가이드

- **두 경로가 갈리는 지점** — 유휴 커넥션의 오류는 **커넥션 풀**이 알리고, 사용 중 커넥션의 오류는 **그 커넥션 자신**이 알린다. 풀에만 처리를 달면 사용 중 구간이 비고, 커넥션에만 달면 유휴 구간이 빈다. `OPS-004-02` 가 "각각"을 요구하는 이유다.
- 사용 중 구간에 단 처리는 **반납 직전에 반드시 떼어** 커넥션을 재사용할 때마다 쌓이지 않게 한다.
- 실제 오류를 겪은 커넥션은 **폐기해서 반납**한다. 그대로 풀에 돌려보내면 다음 요청이 죽은 커넥션을 다시 뽑는다.
- 오류를 삼키는 것과 프로세스를 살리는 것은 다르다 — 처리 중이던 질의의 실패는 `OPS-004-03` 의 분류로 **그대로 전파**되어야 하고, 막는 것은 **프로세스 종료뿐**이다.
- 배치(`PROC-301`~`PROC-304`)에는 응답 표면이 없으므로 `OPS-004-03` 의 귀결은 표준 출력의 결과 요약과 종료 코드로 알린다(`OPS-003-04`).
- 검증은 **운영에서 실제로 일어나는 방식**(서버측 세션 강제 종료)으로 재현한다. 두 경로를 **각각** 재현해 ① 프로세스가 살아 있고 ② 후속 요청이 새 커넥션으로 정상 처리되는지 확인한다.
