# 비즈니스 규칙 정책 정의

정본 목록은 [`spec-policies.md`](spec-policies.md). 용어는 [`../../../wiki/WIKI.md`](../../../wiki/WIKI.md).

## 개요

- **정책 목적**: 연동 1건이 어떤 결과로 끝날 수 있는지, 그 결과를 언제 어디에 남기는지, 같은 연동이 다시 들어오면 어떻게 되는지를 한 곳에서 확정한다. 이 값 체계가 흔들리면 화면·API·집계가 서로 다른 사실을 말하게 된다.
- **관련 PRD 요구사항**:
	- [`../../prd/PRD.md`](../../prd/PRD.md) §수행 범위 6 — "결과를 네 경로로 구분해 사용자에게 표시한다 … 결과가 이미 확정된 링크로 다시 진입하면 **그 결과 경로를 그대로 다시 안내**한다(경로를 추가하지 않는다)."
	- [`../../prd/PRD.md`](../../prd/PRD.md) §수행 범위 9 — "연동 추적 키 기준 **단일 추적 레코드**를 **사용자가 진입한 시점에 생성**하고 …"
	- [`../../prd/devspec/database.md`](../../prd/devspec/database.md) §추적 키 중복 수신 · §연동 지표 집계.

### 정책 규칙

| 규칙 ID | 규칙 내용 | 적용 조건 | 적용 지점 | 위반 시 처리 (HTTP·EX 코드) |
|---------|-----------|-----------|-----------|----------------------------|
| BIZ-001-01 | 저장되는 결과 구분은 **4종뿐**이다 — `SUCCESS`(연동 완료) · `USER_DENIED`(사용자 거부) · `DECRYPT_FAILED`(복호화 실패) · `DELIVERY_FAILED`(수신처 전달 실패). 다섯 번째 값을 만들지 않는다 | 결과를 확정·기록·응답하는 모든 지점 | 검증 | 목록 밖 값을 쓰는 사양·구현은 교차검증에서 반려. 런타임에서는 열거형 밖 값 저장을 거부한다 |
| BIZ-001-02 | 사용자 결과 화면은 **4경로뿐**이다 — ① 연동 완료 ← `SUCCESS` ② 사용자 거부 ← `USER_DENIED` ③ 링크·복호화 오류 ← `DECRYPT_FAILED` **및 추적 레코드가 만들어지지 않은 진입 단계 실패** ④ 수신처 전달 실패 ← `DELIVERY_FAILED`. 다섯 번째 경로를 만들지 않는다 | 결과 안내 화면 선택 | 검증 | 경로를 추가한 사양은 반려. 매핑되지 않은 상태는 경로 ③ 으로 안내한다 |
| BIZ-001-03 | 결과 구분은 **처리상태 확인 API 응답 · 지표 집계 컬럼 · 화면 경로 선택**이 같은 문자열 값을 쓴다. 도메인별 별칭·대소문자 변형·부분집합을 만들지 않는다 | 상시 | 결과 마스킹 | 값 변환을 수행하는 응답 구성은 사양 반려 |
| BIZ-001-04 | 결과 구분은 추적 레코드당 **한 번만 확정**되고 이후 바뀌지 않는다. 확정된 레코드에 다른 결과를 덮어쓰지 않는다 | 결과 확정 시 | 검증 | 이미 확정된 레코드에 대한 결과 갱신 요청은 무시하고 확정 결과를 그대로 응답한다(`BIZ-002-04`) |
| BIZ-001-05 | **생년월일 불일치(본인확인 실패)는 결과가 아니다** — 어떤 결과 구분도 확정·기록하지 않고 재입력 안내로 되돌린다. **재입력 횟수 제한을 두지 않는다** | 복호화 판정 1·2단계 실패 시 | 검증 | 400 `EX-AUTH-002` + 재입력 안내. 추적 레코드·지표 집계 갱신 없음 |

### 예외 사항

- **EXC-BIZ-01**: 진입 단계 실패(암호 파라미터 부재·형식 위반 등)는 추적 레코드가 없으므로 결과 구분이 **레코드에 기록되지 않는다**. 화면은 경로 ③ 으로 안내하고 지표 집계에만 `DECRYPT_FAILED` 로 계수한다(`BIZ-005-02`).
- **EXC-BIZ-02**: 자가진단 API 의 판정 실패는 결과 구분이 아니다. 사유 코드만 응답하고 어떤 기록도 남기지 않는다(`SEC-003-03`).

### 구현 가이드

- 결과 구분은 문자열 상수 4개로 한 곳에 정의하고 화면·API·집계가 그 정의를 가져다 쓴다.
- 화면 경로 ③ 은 두 출처(진입 단계 실패 · `DECRYPT_FAILED`)를 받으므로, 화면은 결과 구분 없이도 이 경로를 그릴 수 있어야 한다.

### 기본 정보

| 항목 | 내용 |

| 정책명 | 추적 레코드 생성 시점·중복 수신 |
| 분류 | BIZ |
| 적용 범위 | 연동 추적 레코드의 생성·이어쓰기·재안내 판정 |
| 우선순위 | 높음 |
| 관련 정책 | `SEC-002`(판정) · `DATA-001`(무저장) · `DATA-002`(보관) · `BIZ-005`(계수) |
| 적용 PROC | PROC-102 · PROC-104 · PROC-105 · PROC-201 · PROC-202 · PROC-203 · PROC-301 |
| 관련 IA 항목 | `BAT-04` · `USR-03` · `USR-05` · `API-01` · `API-02` · `API-03` |

### 정책 규칙

| 규칙 ID | 규칙 내용 | 적용 조건 | 적용 지점 | 위반 시 처리 (HTTP·EX 코드) |
|---------|-----------|-----------|-----------|----------------------------|
| BIZ-002-01 | 추적 레코드는 **본인확인 최초 성공 시점**(복호화 판정 4단계 전부 통과)에 1건 만든다. 이 시점이 허브가 그 연동 요청을 추적 키로 식별할 수 있게 된 최초 시점이다 | 판정 4단계 통과 시 | 검증 | 다른 시점에 생성하는 사양·구현은 반려. 이미 있으면 `BIZ-002-03` 으로 처리 |
| BIZ-002-02 | **추적 키를 알 수 없는 실패**(진입 단계 구조 위반, 판정 3·4단계 실패)에는 추적 레코드를 만들지 않는다. 지표 집계에만 계수한다 | 추적 키 미확보 실패 시 | 검증 | 레코드 생성 시도는 반려. 400 `EX-SEC-001`·`EX-SEC-002` 로 종료 |
| BIZ-002-03 | 같은 추적 키의 수신은 셋으로 나눈다 — ① **레코드 없음**: 새로 만든다 ② **레코드 있고 결과 미확정**: 같은 레코드를 이어 쓴다(새로고침·재진입·본인확인 재시도가 정상 동작) ③ **레코드 있고 결과 확정**: 새 연동으로 받지 않고 확정 결과를 그대로 다시 안내한다 | 추적 키 확보 시 | 검증 | ③ 에서 새 레코드를 만들거나 결과를 덮어쓰면 `BIZ-001-04` 위반 |
| BIZ-002-04 | **확정 결과 재안내**는 ① 지표 집계의 요청 수에 계수하지 않고 ② 추적 레코드를 갱신하지 않는다(결과·일시·결과 확인 상태 모두 유지 — **보관 기산점이 밀리지 않는다**) ③ 화면은 4경로 중 해당 경로를 다시 표시하고 "이미 처리된 요청"임을 **보조 표시**로 알린다 | 중복 수신 ③ | 검증 | 갱신·계수가 일어나면 데이터 정합 위반으로 반려. 응답 자체는 정상(200) |
| BIZ-002-05 | 조회·통지 대상 추적 레코드가 없으면 **"그 추적 키로 진입한 사용자가 없었다"** 로 응답한다. 보관 기간이 지나 삭제된 경우와 구별하지 않는다 | 처리상태 확인·연동 완료 확인·완료 콜백 | 검증 | 404 `EX-DATA-001` |
| BIZ-002-06 | 본인확인 단계에서 복호화한 X 는 **추적 키만 취한 뒤 즉시 폐기**하고, 승인 시점에 다시 복호화해 전달한다. 허브는 X 원문을 세션·저장소 어디에도 남기지 않는다 | 본인확인 성공 후 | 입력 가공 | X 를 요청 간 보존하면 `DATA-001-02`·`DATA-001-03` 위반. 사양·구현 반려 |

### 예외 사항

- **EXC-BIZ-03 (생성 시점 확정의 근거)**: [`../../prd/PRD.md`](../../prd/PRD.md) §수행 범위 9 와 [`../../prd/devspec/database.md`](../../prd/devspec/database.md) §연동 추적 레코드는 레코드를 "사용자가 진입한 시점"에 만들라고 하지만, 레코드의 기준값인 추적 키는 X 안의 필드값이라 **복호화 전에는 알 수 없다**. 그래서 "진입한 시점"을 **허브가 그 연동 요청을 추적 키로 식별할 수 있게 된 최초 시점 = 본인확인 최초 성공 시점**으로 확정했다. 동의·승인 이전이므로 "실제로 들어온 연동만 레코드가 된다"는 원래 취지는 유지된다. 이 확정은 ① 추적 키를 복호화 전에는 알 수 없다는 제약과 ② 복호화 원문 무보관 원칙을 동시에 만족한다.
- **EXC-BIZ-04 (삭제 후 재수신)**: 보관 기간이 지나 레코드가 삭제된 뒤 같은 키가 다시 들어오면 허브는 중복을 알 수 없어 ① 로 동작한다. 유일성 책임이 발송처에 있다는 전제에서 수용한다(`DATA-004-02`).
- **EXC-BIZ-05 (거부·전달 실패의 레코드)**: 거부·전달 실패도 본인확인을 통과한 뒤에 일어나므로 레코드가 이미 있다. 결과 구분만 확정해 이어 쓴다.

### 구현 가이드

- 추적 키 기준 사전 조회 → 3분기 판정 → 생성·이어쓰기·재안내의 순서를 한 곳에서 처리한다. 분기가 흩어지면 ③ 이 누락돼 결과가 덮이는 사고가 난다.
- "결과 확정" 판정은 결과 구분 값의 존재 여부로 한다(`BIZ-001-01` 의 4종 중 하나가 들어 있으면 확정).
- 본인확인 성공 시점과 승인 시점의 복호화는 같은 판정 함수(`SEC-002-01`)를 쓴다.

## BIZ-003 동의·승인 게이팅

### 예외 사항

- **EXC-BIZ-06 (선택 항목)**: 필수가 아닌 동의 항목은 체크 여부와 무관하게 승인을 막지 않는다. 현재 `<CONSENT_ITEMS>` 는 필수 1건이지만 상수가 바뀔 수 있으므로 규칙은 필수·선택을 구분해 둔다.
- **EXC-BIZ-07 (안내 문구 미설정)**: `<CONSENT_NOTICE>` 가 비어 있으면 안내 영역을 표시하지 않는다. 문구 부재가 승인을 막지 않는다.

### 구현 가이드

- 동의 항목은 기동 시 파싱한 상수를 그대로 쓴다. 항목을 DB 에 두지 않는다(`DATA-001-05`).
- 승인 요청에는 사용자가 동의한 항목이 식별 가능한 형태로 담겨야 서버 재검증(`BIZ-003-02`)과 증적 기록(`DATA-003-02`)이 성립한다. 구체 필드는 기능·API 도메인이 정한다.
