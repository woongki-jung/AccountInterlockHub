# 비즈니스 규칙 정책 정의

정본 목록은 [`spec-policies.md`](spec-policies.md). 용어는 [`../../../wiki/WIKI.md`](../../../wiki/WIKI.md).

## 개요

- **정책 목적**: 연동 1건이 어떤 결과로 끝날 수 있는지, 그 결과를 언제 어디에 남기는지, 같은 연동이 다시 들어오면 어떻게 되는지를 한 곳에서 확정한다. 이 값 체계가 흔들리면 화면·API·집계가 서로 다른 사실을 말하게 된다.
- **관련 PRD 요구사항**:
	- [`../../prd/PRD.md`](../../prd/PRD.md) §수행 범위 6 — "결과를 **세 경로**로 구분해 사용자에게 표시한다 — 연동 완료 · 링크·복호화 오류 · 수신처 전달 실패. 결과가 이미 확정된 링크로 다시 진입하면 **그 결과 경로를 그대로 다시 안내**한다(경로를 추가하지 않는다)."
	- [`../../prd/PRD.md`](../../prd/PRD.md) §수행 범위 6 — "**연동 완료 결과만** 결과를 … 보여 준 뒤 **요청 처리 응답이 돌려준 복귀 주소로 자동 이동**한다 … **완료가 아닌 결과는 이동할 주소를 받지 못하므로**(허브가 복귀 주소를 싣지 않는다) 결과 화면에 머문다."
	- [`../../prd/PRD.md`](../../prd/PRD.md) §수행 범위 4 — "**전 항목 동의를 조건으로 승인 제출**. 동의하지 않은 채 제출하면 동의 화면의 **유효성 안내**(`모든 항목에 동의해 주셔야 합니다`)로 막고 결과 단계로 보내지 않는다 — **사용자 거부는 결과 경로가 아니다**. 동의하지 않으려는 사용자의 종료 수단은 창을 닫는 것이며, 그 연동은 결과 미확정으로 남아 보관 기한에 삭제된다."
	- [`../../prd/PRD.md`](../../prd/PRD.md) §수행 범위 9 — "연동 추적 키 기준 **단일 추적 레코드**를 **사용자가 진입한 시점에 생성**하고 …"
	- [`../../prd/devspec/database.md`](../../prd/devspec/database.md) §추적 키 중복 수신 · §연동 지표 집계.

### 정책 규칙

| 규칙 ID | 규칙 내용 | 적용 조건 | 적용 지점 | 위반 시 처리 (HTTP·EX 코드) |
|---------|-----------|-----------|-----------|----------------------------|
| BIZ-001-01 | 저장되는 결과 구분은 **3종뿐**이다 — `SUCCESS`(연동 완료) · `DECRYPT_FAILED`(복호화 실패) · `DELIVERY_FAILED`(수신처 전달 실패). 네 번째 값을 만들지 않으며, **사용자 거부 값(`USER_DENIED`)을 두지 않는다** — 미동의는 진행이 막혀 결과가 확정되지 않으므로 결과 구분에 나타나지 않는다(`BIZ-003-03`) | 결과를 확정·기록·응답하는 모든 지점 | 검증 | 목록 밖 값을 쓰는 사양·구현은 교차검증에서 반려. 런타임에서는 열거형 밖 값 저장을 거부한다 |
| BIZ-001-02 | 사용자 결과 화면은 **3경로뿐**이다 — ① 연동 완료 ← `SUCCESS` ② 링크·복호화 오류 ← `DECRYPT_FAILED` **및 추적 레코드가 만들어지지 않은 진입 단계 실패** ③ 수신처 전달 실패 ← `DELIVERY_FAILED`. 네 번째 경로를 만들지 않으며, **미동의로 끝난 연동에는 결과 경로를 부여하지 않는다**(결과 단계로 보내지 않는다 — `BIZ-003-03`) | 결과 안내 화면 선택 | 검증 | 경로를 추가한 사양은 반려. 매핑되지 않은 상태는 경로 ② 로 안내한다 |
| BIZ-001-03 | 결과 구분은 **처리상태 확인 API 응답 · 지표 집계 컬럼 · 화면 경로 선택**이 같은 문자열 값을 쓴다. 도메인별 별칭·대소문자 변형·부분집합을 만들지 않는다 | 상시 | 결과 마스킹 | 값 변환을 수행하는 응답 구성은 사양 반려 |
| BIZ-001-04 | 결과 구분은 추적 레코드당 **한 번만 확정**되고 이후 바뀌지 않는다. 확정된 레코드에 다른 결과를 덮어쓰지 않는다 | 결과 확정 시 | 검증 | 이미 확정된 레코드에 대한 결과 갱신 요청은 무시하고 확정 결과를 그대로 응답한다(`BIZ-002-04`) |
| BIZ-001-05 | **생년월일 불일치(본인확인 실패)는 결과가 아니다** — 어떤 결과 구분도 확정·기록하지 않고 재입력 안내로 되돌린다. **재입력 횟수 제한을 두지 않는다** | 복호화 판정 1·2단계 실패 시 | 검증 | 400 `EX-AUTH-002` + 재입력 안내. 추적 레코드·지표 집계 갱신 없음 |
| BIZ-001-06 | **복귀 주소는 연동 완료 결과에만 싣는다** — 결과 안내 응답에 복귀 주소 필드(기능·API 도메인이 정한 이름 `returnUrl`, 선택 필드)를 포함하는 경우는 결과 구분이 `SUCCESS`(경로 ①)일 때뿐이다. 경로 ②·③ 과 오류 응답 엔벨로프(502 `EX-BIZ-002` 포함)에는 포함하지 않는다 — 완료가 아닌 결과는 이동할 주소를 받지 못하므로 화면에 머문다. **동봉 여부 판정은 서버 한 곳**(`PROC-105` 결과 안내 구성)**에만 둔다** — 화면은 **필드 존재 여부만** 보고 이동하며 경로 번호로 다시 판정하지 않는다(`BIZ-001-03` 의 한 값 체계·한 판정 지점과 같다). 확정 결과 재안내(`BIZ-002-04` ③)도 같은 경로면 같은 거동이다(경로 ① 재안내는 이동한다). 싣는 값은 `https://`·`http://` 로 시작하는 **절대 URL** 로 한정하며, 그 형식이 아니면 필드를 싣지 않는다. 화면도 받은 값을 같은 기준으로 다시 확인하고 미달이면 이동하지 않는다 | 결과 안내 응답을 구성할 때 | 결과 마스킹 | 정상 응답(200)이며 **필드 유무만** 달라진다. 완료가 아닌 결과·오류 응답 엔벨로프에 복귀 주소를 실은 사양·구현은 반려. 화면이 경로 번호로 이동 여부를 다시 판정하는 사양·구현은 반려. 형식 미달 값은 서버가 필드를 싣지 않고 화면도 이동하지 않는다(화면 잔류) |

### 예외 사항

- **EXC-BIZ-01**: 진입 단계 실패(암호 파라미터 부재·형식 위반 등)는 추적 레코드가 없으므로 결과 구분이 **레코드에 기록되지 않는다**. 화면은 경로 ② 로 안내하고 지표 집계에만 `DECRYPT_FAILED` 로 계수한다(`BIZ-005-02`).
- **EXC-BIZ-02**: 자가진단 API 의 판정 실패는 결과 구분이 아니다. 사유 코드만 응답하고 어떤 기록도 남기지 않는다(`SEC-003-03`).
- **EXC-BIZ-14 (`DECRYPT_FAILED` 는 추적 레코드에 기록되지 않는다 — 구조적 한계)**: `DECRYPT_FAILED` 는 결과 구분 3종 값 체계의 일원이지만([`../../prd/devspec/database.md`](../../prd/devspec/database.md) §연동 지표 집계가 추적 레코드와 **같은 값 체계**를 요구한다), **추적 레코드의 결과 구분으로 확정되는 경로가 없다.** 근거 셋 — ① 추적 키는 X 안의 필드값이라 **복호화 판정 3·4단계를 통과해야만** 얻어지는데([`../functions/function_FN-004.md`](../functions/function_FN-004.md) 단계 5·6), 이 값을 확정시키는 실패가 바로 그 3·4단계 실패다(`SEC-002-03`) — 지목할 레코드의 키 자체가 존재하지 않는다 ② 허브에는 세션이 없어(`AUTH-001`·`BIZ-002-06`·`DATA-001-02`) 앞 요청에서 얻은 추적 키를 다음 요청으로 가져올 수단이 없다 ③ 복호화 판정은 (`encX`·`encY`·생년월일)의 **순수 결정적 함수**라, 3·4단계가 실패하는 입력 조합은 본인확인에서도 같은 이유로 실패했을 것이므로 그 조합으로 만들어진 레코드가 애초에 없다(승인 시점 재복호화 실패도 같다 — 앞서 만든 레코드가 있어도 그것을 지목할 키를 얻지 못하므로 계수만 남는다). 따라서 이 값은 **지표 집계에만** 누적된다(`BIZ-005-02` ②). 결함이 아니라 [`../../prd/PRD.md`](../../prd/PRD.md) §시스템 제약사항(무저장·세션 부재·인증 부재)이 낳는 불가피한 결과다.
- **EXC-BIZ-15 (복귀 이동의 적용 경로 — 확정)**: `BIZ-001-06` 이 **경로 ① 하나**만 대상으로 삼는 것은 [`../../prd/PRD.md`](../../prd/PRD.md) §미결·확인 필요 ⑩ 이 **담당자 확정으로 종결**된 결과다 — **연동 완료 결과만 이동**한다. 완료가 아니면 허브가 복귀 주소를 싣지 않으므로 화면이 이동할 주소를 갖지 못한다. 같은 지시로 사용자 거부가 결과 경로에서 폐지돼(§수행 범위 4·6) 이전 기본안("오류가 아닌 결과 둘")은 대상 자체가 사라져 함께 폐기됐다. **더는 담당자 확인 대기 항목이 아니다** — 본 예외는 확정 사실과 그 근거를 남기는 자리이며, 대상 조건을 다시 넓히려면 PRD 개정이 선행돼야 한다.

### 구현 가이드

- 결과 구분은 문자열 상수 3개로 한 곳에 정의하고 화면·API·집계가 그 정의를 가져다 쓴다.
- 화면 경로 ② 는 두 출처(진입 단계 실패 · `DECRYPT_FAILED`)를 받으므로, 화면은 결과 구분 없이도 이 경로를 그릴 수 있어야 한다.
- **열거형을 2종으로 줄이지 않는다.** `DECRYPT_FAILED` 가 추적 레코드에 기록되지 않더라도(EXC-BIZ-14) 지표 집계·조회 응답·화면 경로가 **같은 값 체계**를 써야 하므로 3종을 그대로 유지한다(`BIZ-001-03`). 이 값을 다루는 저장 계층 분기는 **도달하지 않는 방어적 분기**이며, 도달 불가라는 이유로 결함으로 다루거나 도달 가능한 것처럼 구현하지 않는다.
- **거부 값을 되살리지 않는다.** `USER_DENIED` 는 값 체계에서 완전히 제거됐다 — 도달할 수 없는 값을 열거형·API 계약·집계 컬럼에 남기면 발송처가 쓸모없는 처리 분기를 만들게 된다. `EXC-BIZ-14` 의 `DECRYPT_FAILED` 와 성질이 다르다(그 값은 **지표 집계에는 실제로 누적**되므로 값 체계에 남는다).
- **발송처가 복호화 실패를 인지하는 수단은 셋이다** — ① **연동 지표 집계**의 `DECRYPT_FAILED` 카운터로 일자별 발생 건수를 본다(`BIZ-005-02` ②, 집계 수준) ② **사용자 결과 화면 경로 ②** 가 사용자에게 즉시 안내해 발송처에 새 링크를 요청하게 만든다(`BIZ-001-02` ②) ③ **통합 시점의 자가진단 API**(`API-04`)가 발송처가 만든 암호값의 규약 적합성을 연동 전에 판정한다 — 규약 위반을 운영 트래픽이 아니라 통합 시점에 발견하게 하는 것이 [`../../prd/PRD.md`](../../prd/PRD.md) §제공 가치 "통합 시점의 규약 확인"의 설계 의도이며, 레코드 단위 구별의 부재를 대신하는 주 수단이다.
- **개발사양과의 간극(한계)** — [`../../prd/devspec/database.md`](../../prd/devspec/database.md) §연동 추적 레코드는 "결과 구분은 발송처가 후속 조치를 판단할 수 있도록 최소한 복호화 실패·수신처 전달 실패를 서로 구별한다"고 요구하지만, **레코드 단위로는 복호화 실패가 구별되지 않는다** — 그 값이 담긴 행이 만들어지는 경로가 없기 때문이다(EXC-BIZ-14). 이 한계를 열거형 축소로 덮지 않고 위 세 수단으로 대체한다. 셋 다 "발송처가 후속 조치를 판단한다"는 요구의 목적은 충족하며, 충족하지 못하는 것은 **개별 연동 1건을 사후에 지목해 복호화 실패였다고 읽는 것**뿐이다. 그런 조회가 성립하려면 실패한 요청의 추적 키를 알아야 하는데, 그 키는 실패한 바로 그 복호화로만 얻어진다.
- **복귀 주소 값은 상수에서만 온다** — 허브는 `<COMPLETION_REDIRECT_URL>` 을 그대로 응답에 싣는다. 값을 사양·코드 본문에 복제하지 않고 플레이스홀더로만 참조한다(`OPS-001-01`·`OPS-001-04`).
- **주소의 출처가 미확정이다** — 수신처 전달 응답 / 발송처가 X 에 담아 보내는 값 / 상수 유지 중 무엇으로 정하느냐에 따라 값뿐 아니라 **응답 구성이 함께 바뀔 수 있다**([`../../prd/PRD.md`](../../prd/PRD.md) §미결·확인 필요 ⑦). 그래서 `BIZ-001-06` 은 "무엇을 보고 싣는가"만 정하고 "어디서 얻는가"는 정하지 않는다 — 출처가 확정돼도 규칙은 그대로 선다.
- **정책은 대기 시간을 갖지 않는다** — 결과를 보여 주고 이동하기까지의 대기 시간은 화면 사양([`../screens/screen_SCR-004.md`](../screens/screen_SCR-004.md))이 정본이다. 시간 값을 정책에 복제하지 않는다.
- **이동 실패에 EX 코드를 두지 않는다** — 창 차단·이동 불가는 **결과를 바꾸지 않는 화면 후처리**이므로 새 EX 코드도 네 번째 경로도 만들지 않는다. EX 코드를 만들면 오류 응답 엔벨로프가 필요해지고 그 엔벨로프는 경로 ②·③ 으로 읽혀 이미 확정된 결과를 뒤엎는다(`BIZ-001-04`). 이동 실패는 **화면 잔류 + 수동 이동 수단**으로 흡수하며 그 수단의 형태는 화면 사양이 정한다.

- **EXC-BIZ-05 (전달 실패의 레코드 · 미동의 이탈의 레코드)**: 전달 실패는 본인확인을 통과한 뒤에 일어나므로 레코드가 이미 있다. 결과 구분만 확정해 이어 쓴다. **미동의로 이탈한 연동은 레코드가 이미 있어도 결과 구분을 확정하지 않는다** — **결과 미확정** 상태로 남았다가 생성 기산 보관 상한에 삭제된다(`BIZ-003-03` · `DATA-002-01` ②). 이 레코드는 조회 시 "결과 미확정"으로 응답되며 없는 것으로 다루지 않는다(`BIZ-002-05` 는 레코드 부재에만 적용된다).

### 구현 가이드

- 동의 항목은 기동 시 파싱한 상수를 그대로 쓴다. 항목을 DB 에 두지 않는다(`DATA-001-05`).
- 승인 요청에는 사용자가 동의한 항목이 식별 가능한 형태로 담겨야 서버 재검증(`BIZ-003-02`)과 증적 기록(`DATA-003-02`)이 성립한다. 구체 필드는 기능·API 도메인이 정한다.
- **진행 의사를 별도 값으로 가르지 않는다** — 거부 제출 경로가 없어져 승인 요청의 진행 의사가 하나뿐이 됐으므로, 승인 성립 조건은 **필수 동의 항목 충족**(`BIZ-003-01`·`BIZ-003-02`)으로 일원화한다. 요청 필드를 어떻게 구성할지는 기능·API 도메인 소관이지만, **진행 의사 값으로 결과를 가르는 분기를 두지 않는다** — 값이 하나뿐이라 분기가 성립하지 않고, 분기를 남기면 도달 불가 경로가 계약에 남는다(`BIZ-001-01`).
- **미동의 차단은 화면·서버 두 곳에서 같은 기준으로 판정한다** — 화면이 막는 것은 사용자 경험이고, 서버 재검증(`BIZ-003-02`)이 실제 게이트다. 화면 차단만 두고 서버 검증을 생략한 구현은 반려한다.

### 예외 사항

- **EXC-BIZ-08 (재시도 경로 — 기본안 적용)**: `BIZ-004-02`·`BIZ-004-04` 는 [`../../prd/PRD.md`](../../prd/PRD.md) §미결·확인 필요 ⑧ 의 **담당자 확인 대기 항목이며 기본안(둘을 함께 적용)** 을 사양화한 것이다. 다르게 정해지면 두 규칙만 개정한다.
- **EXC-BIZ-09 (재시도 횟수·간격의 확정 근거)**: [`../../prd/devspec/database.md`](../../prd/devspec/database.md) §추적 키 중복 수신이 "즉시 재시도 횟수·간격은 spec 확정"으로 위임한 값이다. 사용자가 화면에서 기다리는 동안 끝나야 하므로 총 소요를 20초 안으로 묶었다.
- **EXC-BIZ-10 (잠정 전달 주소)**: `<RECEIVER_DELIVERY_URL>` 은 잠정값이며 문서용 예약 도메인이라 실 호스트로 연결되지 않는다. 잠정 상태에서는 전달이 항상 실패해 `DELIVERY_FAILED` 로 끝나는 것이 정상 동작이다. 이 상태로 운영 배포하지 않는다(`OPS-001-03`).

## BIZ-005 지표 집계 계수 기준

### 기본 정보

| 항목 | 내용 |
|------|------|
| 정책명 | 지표 집계 계수 기준 |
| 분류 | BIZ |

### 정책 규칙

| 규칙 ID | 규칙 내용 | 적용 조건 | 적용 지점 | 위반 시 처리 (HTTP·EX 코드) |
|---------|-----------|-----------|-----------|----------------------------|
| BIZ-005-01 | 집계 항목은 **요청 수 1개 + 결과 구분 3종 각각 1개**로 **분리 저장**한다. 파생 비율(성공률 등)을 저장하지 않는다. **거부 카운터를 두지 않는다**(값 체계에 없는 값이다 — `BIZ-001-01`) | 상시 | 검증 | 합산·파생값만 저장하는 설계는 반려(두 성공률 정의를 모두 산출할 수 없게 된다). 결과 구분 3종 밖의 카운터를 둔 설계도 반려 |
| BIZ-005-02 | **요청 수 계수 시점**은 둘뿐이다 — ① 추적 레코드가 **최초 생성**될 때 +1 ② 추적 키를 알 수 없는 실패로 종료될 때 +1(이때 `DECRYPT_FAILED` 도 +1) | 위 두 시점 | 검증 | 다른 시점의 계수는 반려 |

| BIZ-005-05 | 추적 키를 알 수 없는 실패는 같은 요청인지 판정할 수단이 없어 **시도마다 계수된다**. 이 중복은 수용 한계로 기록한다 | 진입 단계 실패·판정 3·4단계 실패 | 검증 | 별도 런타임 처리 없음(수용). 검증에서 결함으로 올리지 않는다 |
