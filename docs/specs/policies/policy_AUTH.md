# 인증·인가 정책 정의

정본 목록은 [`spec-policies.md`](spec-policies.md). 용어는 [`../../../wiki/WIKI.md`](../../../wiki/WIKI.md).

## 개요

- **정책 목적**: 이 제품에는 **관리자 인증도 사용자 계정 인증도 서버 대면 API 인증도 없다.** 그 부재가 누락이 아니라 **의도된 결정**임을 명시하고, 유일하게 남은 신원 확인 수단인 **본인확인(생년월일 복호화)** 의 성립 조건을 확정한다.
- **관련 PRD 요구사항**:
	- [`../../prd/PRD.md`](../../prd/PRD.md) §제공 가치 — "**구성 없는 운용**: … 관리자 화면·구성 저장소·관리자 인증이 없어 운영 부담과 공격면이 함께 줄어든다."
	- [`../../prd/PRD.md`](../../prd/PRD.md) §수행 범위 — 제외 — "**서버 대면 API의 인증** — 처리상태 확인·연동 완료 확인·완료 콜백·자가진단 API에 인증을 두지 않는다."
	- [`../../prd/PRD.md`](../../prd/PRD.md) §서비스 이용 대상 3 — "**사용자**: 발송처가 전달한 링크로 진입해 **생년월일을 입력**하고 …"
- 부재로 남는 리스크는 `OPS-002`(접근 통제 없음 — 수용 리스크)가 기록한다.

## AUTH-001 인증 부재 선언

### 기본 정보

| 항목 | 내용 |
|------|------|
| 정책명 | 인증 부재 선언 |
| 분류 | AUTH |
| 적용 범위 | 허브의 모든 외부 표면 — 사용자 진입 경로와 서버 대면 API 4종 |
| 우선순위 | 높음 |
| 관련 정책 | `OPS-002`(수용 리스크) · `SEC-003`(자가진단 경로) |
| 적용 PROC | PROC-101 · PROC-103 · PROC-201 · PROC-202 · PROC-203 · PROC-204 |
| 관련 IA 항목 | 공통 |

### 정책 규칙

| 규칙 ID | 규칙 내용 | 적용 조건 | 적용 지점 | 위반 시 처리 (HTTP·EX 코드) |
|---------|-----------|-----------|-----------|----------------------------|
| AUTH-001-01 | **관리자 경로·관리자 인증·관리자 화면을 두지 않는다.** 연동 구성 변경은 화면 조작이 아니라 상수 갱신·재배포로만 이뤄진다 | 상시 | 검증 | 관리자 인증을 전제한 사양·구현은 교차검증에서 반려(차단 사유) |
| AUTH-001-02 | **사용자 계정·로그인·세션을 두지 않는다.** 사용자는 발송처가 만든 연동 요청 URL 로 진입할 뿐이며, 신원 확인은 `AUTH-002` 의 본인확인이 전부다 | 상시 | 검증 | 계정·세션을 도입한 사양은 반려. 세션 만료·재로그인 흐름을 정의하지 않는다 |
| AUTH-001-03 | **서버 대면 API 4종**(처리상태 확인·연동 완료 확인·완료 콜백·자가진단)에 **인증·자격 검증을 두지 않는다.** 인증 헤더·서명·API 키를 요구하거나 검증하지 않으며 401·403 응답을 정의하지 않는다 | 서버 대면 API 요청 처리 | 검증 | 인증 자격을 요구하는 사양·구현은 반려. 자격이 담긴 요청이 와도 검증하지 않고 무시한다 |

### 예외 사항

- **EXC-AUTH-01 (경로 비공개는 인증이 아니다)**: 자가진단 API 의 비공개 경로(`SEC-003`)는 인증 수단이 아니라 **노출 축소 장치**다. 경로를 아는 요청은 그대로 처리된다.
- **EXC-AUTH-02 (IP 기반 제한 없음)**: IP 기반 접속 제한도 두지 않는다([`../../prd/devspec/infra.md`](../../prd/devspec/infra.md) §접근 제어).
- **EXC-AUTH-03 (후속 보완)**: 인증·요청 제한·발송처 서명 검증의 도입은 후속 보완 항목이며 이번 범위가 아니다([`../../prd/PRD.md`](../../prd/PRD.md) §미결·확인 필요 ⑮).

### 적용 지점 매핑

| 규칙 ID | 적용 PROC | 적용 단계 (PROC 의사코드 단계명) | 적용 위치 |
|---------|----------|-------------------------------|--------------------------------|
| AUTH-001-01 | — (설계 제약) | 사양·구현 게이트 | 검증 |
| AUTH-001-02 | PROC-101 · PROC-103 | 진입 처리·승인 제출 | 검증 |
| AUTH-001-03 | PROC-201 · PROC-202 · PROC-203 · PROC-204 | 요청 진입 | 검증 |

### 구현 가이드

- 인증 미들웨어·가드를 두지 않는다. 두지 않는 것이 규칙이므로 "통과시키는 인증 계층"도 만들지 않는다.
- 오류 응답 코드 집합에 401·403 을 넣지 않는다([`spec-policies.md`](spec-policies.md) §예외(EX) 코드 카탈로그).
- 이 결정으로 남는 위험은 `OPS-002` 의 수용 리스크 4종으로 관리한다.

## AUTH-002 본인확인(생년월일)

### 기본 정보

| 항목 | 내용 |
|------|------|
| 정책명 | 본인확인(생년월일) |
| 분류 | AUTH |
| 적용 범위 | 사용자 진입 후의 신원 확인 절차 |
| 우선순위 | 높음 |
| 관련 정책 | `SEC-001`(규약) · `SEC-002`(판정) · `BIZ-001`(결과 구분) · `BIZ-002`(추적 레코드) |
| 적용 PROC | PROC-102 |
| 관련 IA 항목 | `USR-03` |

### 정책 규칙

| 규칙 ID | 규칙 내용 | 적용 조건 | 적용 지점 | 위반 시 처리 (HTTP·EX 코드) |
|---------|-----------|-----------|-----------|----------------------------|
| AUTH-002-01 | 이 제품의 **유일한 신원 확인 수단은 생년월일 입력에 의한 복호화 성공**이다 — 사용자가 넣은 생년월일로 복호화 판정 1·2단계가 통과하면 본인으로 인정한다. 별도의 인증 요소를 두지 않는다 | 본인확인 단계 | 검증 | 다른 인증 요소를 요구하는 사양은 반려(`AUTH-001-02`) |
| AUTH-002-02 | 생년월일 입력값은 **`yyMMdd` 형식의 숫자 6자리**여야 한다. 형식을 벗어나면 복호화를 시도하지 않는다 | 생년월일 제출 시 | 검증 | 400 `EX-AUTH-001` + 형식 안내. 결과 미확정 |
| AUTH-002-03 | 복호화 판정 **1·2단계 실패는 전부 본인확인 실패**로 다룬다 — 결과 구분을 확정하지 않고 재입력 안내로 되돌린다(`SEC-002-04`) | 판정 1·2단계 실패 시 | 검증 | 400 `EX-AUTH-002` + 재입력 안내. 추적 레코드·지표 집계 갱신 없음 |
| AUTH-002-04 | 본인확인 **재입력 횟수에 제한을 두지 않는다.** 잠금·지연·차단을 도입하지 않는다 | 재입력 시 | 검증 | 제한을 도입한 사양은 반려([`../../prd/PRD.md`](../../prd/PRD.md) §수행 범위 — 제외 "요청 제한") |

### 예외 사항

- **EXC-AUTH-04 (본인확인은 인증이 아니다)**: 생년월일은 **복호화의 나머지 키**이지 인증 자격이 아니다. 허브는 생년월일이 맞는지 대조할 원본을 갖고 있지 않고, 복호화가 되는지로만 판단한다. 그래서 저장하지 않고(`DATA-001-02`) 실패해도 잠그지 않는다.
- **EXC-AUTH-05 (본인확인 성공 = 추적 레코드 기점)**: 본인확인이 최초로 성공한 시점에 추적 레코드가 만들어진다(`BIZ-002-01`). 본인확인 이전에는 허브가 그 연동을 식별할 수단이 없다.
- **EXC-AUTH-06 (전수대입 수용)**: 생년월일은 경우의 수가 작아 반복 시도에 약하다. 요청 제한이 없으므로 온라인 반복 시도를 막는 장치도 없다 — 수용 리스크다(`OPS-002-01`·`OPS-002-03`).

### 적용 지점 매핑

| 규칙 ID | 적용 PROC | 적용 단계 (PROC 의사코드 단계명) | 적용 위치 |
|---------|----------|-------------------------------|--------------------------------|
| AUTH-002-01 | PROC-102 | 복호화 판정 | 검증 |
| AUTH-002-02 | PROC-102 | 입력 검증 | 검증 |
| AUTH-002-03 | PROC-102 | 복호화 판정 1·2단계 | 검증 |
| AUTH-002-04 | PROC-102 | 재입력 안내 | 검증 |

### 구현 가이드

- 생년월일은 화면 입력 상태로만 보유하고 URL·로그·저장소 어디에도 남기지 않는다(`DATA-001-02`·`DATA-001-04`).
- 형식 검증(`AUTH-002-02`)은 화면과 서버 양쪽에서 수행한다. 화면 검증은 사용자 편의이고 판정 근거는 서버 검증이다.
- 재입력 안내 문구·필드 상태(값 유지 여부·포커스 이동)는 화면 도메인이 정한다. 정책은 **횟수 제한을 두지 않는다**는 것만 규정한다.
