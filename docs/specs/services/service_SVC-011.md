# 연동 완료 확인 기능 정의

정본 목록은 [`spec-services.md`](spec-services.md). 용어는 [`../../../wiki/WIKI.md`](../../../wiki/WIKI.md).

## 개요

- **서비스 목적**: 발송처가 **수신처의 처리까지 끝났는지**를 확인하게 한다. 허브가 전달에 성공한 것과 수신처가 자기 처리를 마친 것은 다른 사실이므로, 처리상태 확인과 분리된 조회를 둔다.
- **관련 PRD 요구사항**:
	- [`../../prd/devspec/external-apis.md`](../../prd/devspec/external-apis.md) §5 — "발송처가 **연동 추적 키**를 기준으로 수신처(B)의 정보연계 처리완료 여부를 확인하는 서버 대면 API다 … 처리상태 확인 API와 통합하지 않는다 — 발송처의 호출 시점과 판단 대상(허브의 처리 vs 수신처의 처리)이 다르다."

### 사용자 정의

- **발송처** — 주 호출 주체다. 인증이 없으므로 허브는 호출자가 발송처인지 확인하지 않는다.
- **수신처** — 이 조회의 답을 만드는 쪽이지만 직접 호출하지 않는다. 완료 콜백으로 사실을 남길 뿐이다.

### 관련 서비스

- `SVC-012` — 이 조회가 읽는 완료 콜백 수신 여부를 기록한다.
- `SVC-010` — 허브 쪽 처리 결과를 답한다. 판단 대상이 달라 통합하지 않는다.
- `SVC-014` — 응답 근거가 되는 레코드를 보유한다.

### 예외 사항

- **완료 콜백이 오지 않으면 영원히 미완료로 답한다.** 허브는 수신처의 처리를 재촉하거나 대신 판단하지 않는다.
- **전달이 실패한 연동도 조회할 수 있다.** 이때는 콜백이 올 수 없으므로 항상 미완료로 답한다.
- **이 조회는 보관 기간에 영향을 주지 않는다.** 기산을 시작시키는 것은 처리상태 확인뿐이다. 두 조회의 부작용이 다르다는 점이 통합하지 않는 또 하나의 이유다.
- **완료 콜백은 추적 키를 아는 쪽이면 보낼 수 있다.** 따라서 이 조회의 "완료"는 수신처가 보냈다는 것을 증명하지 않는다 — 수용 리스크다(`OPS-002-02`).

### 구현 가이드

- 판정은 레코드의 완료 콜백 수신 여부 하나만 본다. 결과 구분·처리 성공 여부를 함께 보고 판단하지 않는다.
- 조회 처리에서 레코드를 갱신하지 않는다. 갱신이 생기면 보관 기산·결과 확정 규칙과 충돌한다.
- 응답 형태는 처리상태 확인과 별도로 둔다. 두 응답을 하나로 합치면 발송처가 판단 대상을 혼동한다.
