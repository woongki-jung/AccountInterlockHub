# 처리상태 확인 기능 정의

정본 목록은 [`spec-services.md`](spec-services.md). 용어는 [`../../../wiki/WIKI.md`](../../../wiki/WIKI.md).

## 개요

- **서비스 목적**: 발송처가 **연동 추적 키 하나로** 자기가 보낸 연동이 어떻게 처리됐는지 확인하게 한다. 결과 통지 경로를 두지 않기로 했으므로 이 조회가 발송처가 결과를 얻는 기본 수단이다.
- **관련 PRD 요구사항**:
	- [`../../prd/devspec/external-apis.md`](../../prd/devspec/external-apis.md) §4 — "발송처가 **연동 추적 키**를 기준으로 연동 요청의 처리·결과 확인 상태를 조회하는 서버 대면 API다 … 허브는 결과를 담아 응답한 시점에 그 레코드를 결과 확인 완료로 표시하고 확인 일시를 남긴다. 이 시점이 보관 기간의 기산점이다."
	- [`../../prd/PRD.md`](../../prd/PRD.md) §수행 범위 — 제외 — "**연동 결과의 발송처 푸시 통지** — 발송처는 조회 API로 결과를 확인한다."

### 사용자 정의

- **발송처** — 주 호출 주체다. 다만 인증이 없으므로 **허브는 호출자가 발송처인지 확인하지 않는다**.
- 추적 키를 아는 누구든 이 조회를 할 수 있고, 조회로 보관 기간 기산을 시작시킬 수 있다 — 수용 리스크다(`OPS-002-04`).

### 관련 서비스

- `SVC-014` — 응답의 근거가 되는 레코드를 만들고 이어 쓴다.
- `SVC-005` — 사용자에게 같은 결과 구분을 화면으로 안내한다. 두 표면이 같은 값을 쓴다.
- `SVC-011` — 수신처의 처리완료 여부는 이 서비스가 아니라 그쪽이 답한다.
- `SVC-017` — 이 서비스가 시작한 기산을 근거로 삭제 대상을 산정한다.

### 예외 사항

- **레코드 없음은 두 상태를 합친 응답이다** — 진입한 사용자가 없었던 경우와 보관 기간이 지나 삭제된 경우. 둘을 구별하면 삭제된 레코드의 존재를 드러내게 되므로 합친다.
- **인증이 없어 조회가 기산을 앞당길 수 있다.** 발송처가 결과를 받아 가기 전에 제3자의 조회로 삭제 시점이 앞당겨질 수 있으며, 생성 기산 절대 상한과 함께 이 수준을 수용한다.
- **결과 구분이 아직 확정되지 않은 레코드**도 조회할 수 있다. 이때 결과 확인 표시를 할지는 "결과를 담아 응답했는가"로 판단한다 — 판단의 구체 기준은 기능·API 도메인이 확정한다.
- **요청 제한이 없다.** 반복 조회를 막는 장치를 두지 않는다.

### 구현 가이드

- 응답 구성과 결과 확인 표시를 같은 처리 경계에 두어, 응답은 갔는데 표시가 남지 않는 상태가 생기지 않게 한다.
- 결과 구분 값은 화면·집계와 **같은 상수 정의**를 가져다 쓴다. 응답 전용 값 변환을 만들지 않는다.
- 인증 미들웨어·가드를 두지 않는다. 통과시키기만 하는 인증 계층도 만들지 않는다.
- 오류 응답 코드 집합에 401·403 을 넣지 않는다.
