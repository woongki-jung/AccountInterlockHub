# 완료 콜백 수신 기능 정의

정본 목록은 [`spec-services.md`](spec-services.md). 용어는 [`../../../wiki/WIKI.md`](../../../wiki/WIKI.md).

## 개요

- **서비스 목적**: 수신처가 자기 처리를 마쳤다는 사실을 허브에 남기게 한다. 이 기록이 있어야 발송처가 **"수신처까지 끝났는지"** 를 확인할 수 있다. 허브는 통지를 받아 적을 뿐 결과 구분을 바꾸지 않는다.
- **관련 PRD 요구사항**:
	- [`../../prd/devspec/external-apis.md`](../../prd/devspec/external-apis.md) §6 — "수신처 B가 정보연계 처리를 완료한 뒤, **전달받은 연동 추적 키**를 기준으로 완료를 허브에 통지하는 서버 대면 API다 … 허브는 수신한 완료 통지를 추적 레코드에 기록한다."
	- [`../../prd/PRD.md`](../../prd/PRD.md) §서비스 이용 대상 2 — "수신처 … 처리 완료를 허브에 콜백으로 통지한다."

### 사용자 정의

- **수신처** — 주 호출 주체다. 다만 인증이 없으므로 **허브는 호출자가 수신처인지 확인하지 않는다** — 추적 키를 아는 쪽이면 누구든 통지할 수 있다(`OPS-002-02` 수용 리스크).
- **발송처** — 이 기록을 `SVC-011` 로 읽는다. 직접 호출하지 않는다.

### 관련 서비스

- `SVC-004` — 수신처에 전달을 수행해 통지의 전제를 만든다.
- `SVC-011` — 이 서비스가 남긴 기록을 읽어 완료 여부를 답한다.
- `SVC-014` — 같은 레코드에 이어 쓰는 기록 규칙을 담당한다.

### 예외 사항

- **위조 통지를 막을 수단이 없다.** 발송처 서명 검증·인증을 두지 않기로 했으므로 추적 키를 아는 쪽이면 완료를 통지할 수 있다 — 수용 리스크이며 이 서비스가 완화 장치를 추가하지 않는다.
- **전달이 실패한 연동에도 통지가 올 수 있다.** 허브는 통지와 결과 구분의 정합을 검사하지 않고 사실만 기록한다. 두 값의 해석은 발송처 몫이다.
- **통지 자체를 별도 이력으로 남기지 않는다.** 저장 대상은 셋뿐이며 통지는 추적 레코드의 항목으로만 남는다.
- **레코드가 삭제된 뒤의 통지는 받을 곳이 없다.** 없음으로 응답하고 레코드를 되살리지 않는다.

### 구현 가이드

- 기록은 조회한 레코드에 이어 쓰는 형태로만 수행한다. 없으면 만들지 않는다는 규칙이 이 서비스에서 가장 자주 어겨지는 지점이다.
- 중복 통지의 멱등성은 "이미 수신 상태면 아무것도 바꾸지 않는다"로 확보한다. 최근 시각으로 덮으면 발송처가 보는 완료 시각이 흔들린다.
- 통지 요청에 추적 키 외의 값이 실려 와도 저장하지 않는다.
- 오류 응답 코드 집합에 401·403 을 넣지 않는다.
