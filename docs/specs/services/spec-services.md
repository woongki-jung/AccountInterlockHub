# 서비스 기능 정의서 (목록)

AccountInterlockHub 가 제공하는 서비스 기능의 단일 출처다. 방향 근거는 [`../../prd/PRD.md`](../../prd/PRD.md), 정보 구조는 [`../../prd/ia/IA.md`](../../prd/ia/IA.md), 준수 규칙은 [`../policies/spec-policies.md`](../policies/spec-policies.md), 용어는 [`../../../wiki/WIKI.md`](../../../wiki/WIKI.md) 를 따른다.

본 문서는 **사용자 정의·시나리오 요약·서비스 목록·의존관계**를 담고, 개별 기능 정의는 `service_<SVC 코드>.md` 가, 분기·예외·데이터 모델·화면의 코드 카탈로그는 [`spec-services-codes.md`](spec-services-codes.md) 가 갖는다.

## 사용자 정의

### 사용자 역할

| 역할 | 설명 | 주요 목적·사용 맥락 |
|---|---|---|
| **발송처** | 서비스 A 운용사. 연동을 요청하는 주체 | 자기 회원을 서비스 B 와 연동시킨다. 연동 라이브러리로 암호값·연동 요청 URL 을 만들어 사용자를 허브로 보내고, 이후 서버 대면 API 로 결과를 확인한다 |
| **수신처** | 서비스 B 운용사. 연동을 받는 주체 | 허브가 전달한 사용자 키로 회원을 확인해 자기 서비스에 연결하고, 처리 완료를 허브에 통지한다 |
| **사용자** | 서비스 A 의 고객 | 발송처가 준 링크로 진입해 생년월일로 본인을 확인하고, 자기 정보가 어디에 제공되는지 확인한 뒤 승인하거나 거부한다 |
| **허브 운영자** | 허브의 **배포 주체**(서비스 이용 대상이 아니다) | 연동 구성 상수를 주입해 배포하고, 라이브러리 배포 패키지를 발송처에 전달하며, 보관 배치를 운용한다 |

### 역할별 서비스 범위

| 역할 | 접근 표면 | 사용 가능한 서비스 |
|---|---|---|
| 발송처 | 연동 라이브러리(파일)·연동 요청 URL 발행·서버 대면 API 3종 | `SVC-006`·`SVC-007`·`SVC-008`·`SVC-009`·`SVC-010`·`SVC-011`·`SVC-013` |
| 수신처 | 허브의 전달 호출 수신·완료 콜백 API | `SVC-004`(전달 대상)·`SVC-012` |
| 사용자 | 사용자 진입 경로 | `SVC-001`·`SVC-002`·`SVC-003`·`SVC-004`·`SVC-005` |
| 허브 운영자 | 배포 절차·보관 배치 수동 실행 진입점 | `SVC-008`·`SVC-009`·`SVC-016`(지표 산출)·`SVC-017`·`SVC-018` |

### 역할 간 관계

1. **상하위·위임 관계가 없다.** 어떤 역할도 다른 역할의 권한을 대신 갖지 않는다.
2. **시스템은 역할을 식별·검증하지 않는다.** 관리자 인증·사용자 계정·서버 대면 API 인증이 모두 없으므로(`AUTH-001-01`~`AUTH-001-03`) 역할은 **접근 표면으로만** 구분된다. 요청이 어느 역할에서 왔는지는 확인하지 않으며, 그로 인한 위험은 수용 리스크로 관리한다(`OPS-002`).
3. **사용자는 발송처가 만든 링크로만 진입한다.** 허브에 사용자 목록·계정이 없으므로 링크 없이는 진입 경로가 성립하지 않는다.
4. **수신처는 두 방향으로 관계한다** — 허브가 호출하는 전달 대상이면서, 완료 콜백의 호출자다.
5. **허브 운영자는 화면을 갖지 않는다.** 구성 변경은 상수 갱신·재배포로만 이뤄지고, 배치 수동 실행은 배포 단위 안의 명령 진입점으로만 수행한다.

## 서비스 시나리오 요약

### 사용자 — 연동 본체 (`SVC-001`~`SVC-005`)

1. 발송처가 만든 연동 요청 URL 로 진입하면 허브가 암호값의 **구조만** 먼저 판정한다(`SVC-001`).
2. 사용자가 생년월일을 넣고, 그 값으로 전달 데이터가 복원되면 본인으로 인정한다(`SVC-002`). 이 최초 성공 시점에 연동 추적 레코드가 만들어진다.
3. 상수로 고정된 동의 항목을 확인하고 승인 또는 거부를 제출한다(`SVC-003`). 승인 시점에 동의 증적 1건이 남는다.
4. 승인이면 허브가 다시 복호화해 전달 데이터를 수신처에 전달한다(`SVC-004`).
5. 결과를 네 경로 중 하나로 안내한다(`SVC-005`). 결과가 확정된 링크로 다시 들어오면 같은 경로를 다시 보여 준다.

### 발송처 — 통합·조회 (`SVC-006`~`SVC-011`·`SVC-013`)

1. 배포 패키지를 받아 무결성을 확인하고 C# 프로젝트에 라이브러리를 참조한다(`SVC-008`).
2. 규약 테스트 벡터로 자기 환경의 출력이 규약과 맞는지 대조한다(`SVC-009`).
3. 전달 데이터·발송처키·생년월일로 암호값을 만들고(`SVC-006`) 연동 요청 URL 을 만든다(`SVC-007`).
4. 필요하면 자가진단으로 자기가 만든 암호값의 규약 적합성을 확인한다(`SVC-013`).
5. 연동 이후 처리상태(`SVC-010`)와 수신처 완료 여부(`SVC-011`)를 추적 키로 조회한다.

### 수신처 — 완료 통지 (`SVC-012`)

1. 허브의 서버 간 호출로 전달 데이터를 받는다(`SVC-004` 의 전달 대상).
2. 자기 처리를 마친 뒤 전달받은 추적 키로 완료를 통지한다(`SVC-012`).

### 허브 운영자 — 기록·보관·기동 (`SVC-014`~`SVC-018`)

1. 연동 진행·결과는 추적 레코드에(`SVC-014`), 동의 사실은 증적에(`SVC-015`), 건수는 지표 집계에(`SVC-016`) 남는다.
2. 보관 기간이 지난 기록은 일 단위 배치가 지운다(`SVC-017`). 스케줄과 수동 실행이 같은 로직을 쓴다.
3. 배포 시 주입된 상수가 충족되지 않으면 애플리케이션이 기동을 중단한다(`SVC-018`).

## 서비스 코드 체계

- **서비스 코드**: `SVC-<순번 3자리>` — 본 문서의 목록이 정본이다.
- **기능 번호**: `F-<순번 3자리>` — **각 SVC 안에서만 유효한 지역 번호**다. 다른 문서에서 인용할 때는 `SVC-004 F-002` 형태로 소속 SVC 를 함께 적는다.
- **분기 코드**: `BR-<순번 3자리>` — 전 SVC 를 통틀어 유일하며 프로세스 정의서가 같은 코드로 인용한다. 카탈로그는 [`spec-services-codes.md`](spec-services-codes.md).
- **예외 코드**: `EX-<그룹>-<순번 3자리>` — **정책이 정본**이며 서비스는 참조만 한다([`../policies/spec-policies.md`](../policies/spec-policies.md) §예외(EX) 코드 카탈로그). 새 코드를 만들지 않는다.
- **정책 규칙 ID**: `<그룹>-<순번 3자리>-<리비전 2자리>` — 각 SVC 의 연관 정책 표가 인용한다.
- **후행 도메인 코드**(`PROC`·`MDL`·`SCR`)는 아직 작성 전이라 **예약 채번**하며, 실재 확인은 교차검증 시점이다. 예약 목록은 [`spec-services-codes.md`](spec-services-codes.md).

## 서비스 간 의존관계

### 선행·후행 (사용자 본체)

1. `SVC-001` → `SVC-002` → `SVC-003` → `SVC-004` → `SVC-005` 순서로만 진행한다. 앞 단계를 건너뛴 진입은 성립하지 않는다.
2. `SVC-002` 가 추적 키를 확보해야 `SVC-014` 가 레코드를 만들 수 있다 — 그 이전 단계의 실패는 레코드를 남기지 않는다(`BIZ-002-02`).
3. `SVC-003` 의 승인 확정이 `SVC-015` 의 유일한 기록 계기다. 거부·실패는 증적을 만들지 않는다.
4. `SVC-005` 는 `SVC-001`·`SVC-002`·`SVC-004` 중 어디에서든 진입할 수 있다 — 실패는 단계와 무관하게 네 경로 중 하나로 모인다.

### 제공·소비 (라이브러리·API·기록)

1. `SVC-006` 의 출력이 `SVC-007` 의 입력이다. 둘의 결과가 `SVC-001` 의 진입 값이 된다.
2. `SVC-008` 은 `SVC-006`·`SVC-007`·`SVC-009` 의 산출물을 하나로 묶어 전달한다.
3. `SVC-010`·`SVC-011` 은 `SVC-014` 가 만든 레코드가 있어야 답할 수 있다. 없으면 "진입한 사용자가 없었다"로 응답한다(`BIZ-002-05`).
4. `SVC-011` 의 판단 근거는 `SVC-012` 가 기록한 완료 콜백 수신 여부다.
5. `SVC-012` 는 `SVC-014` 를 통해 같은 레코드에 이어 쓴다. 결과 구분은 바꾸지 않는다(`BIZ-001-04`).
6. `SVC-013` 은 `SVC-002`·`SVC-004` 와 **같은 복호화 판정 절차**를 쓰되 전달·기록·계수를 하지 않는다(`SEC-003-03`).
7. `SVC-016` 은 `SVC-014` 의 레코드 생성·결과 확정과 같은 트랜잭션 경계에서 갱신된다.
8. `SVC-017` 은 `SVC-014`·`SVC-015` 의 저장분을 지우고 `SVC-016` 의 집계는 지우지 않는다(`DATA-002-03`).
9. `SVC-018` 은 나머지 전 서비스의 선행 조건이다 — 상수가 충족되지 않으면 어떤 표면도 열리지 않는다.

## 확정 사항 반영

- **담당자 확인 대기 — 기본안 적용 2건**: 수신처 전달 실패 후의 재시도 경로(`SVC-004`)와 자가진단 API 의 운영 환경 노출(`SVC-013`)은 [`../../prd/PRD.md`](../../prd/PRD.md) §미결·확인 필요 ⑦·⑧ 의 **기본안대로** 사양화했다. 다르게 정해지면 해당 SVC 만 개정한다.
- **잠정값 참조**: `<RECEIVER_DELIVERY_URL>`·`<HUB_BASE_URL_PROD>`·`<HUB_BASE_URL_DEV>`·`<SELFCHECK_PATH>`·`<CONSENT_NOTICE>`·`<CONSENT_PROOF_RETENTION_MONTHS>` 는 잠정값이며 본 사양은 **상수 주입으로만 참조**한다(값의 단일 출처는 [`../../../CLAUDE.env.md`](../../../CLAUDE.env.md) §연동 구성 상수). 잠정 상태의 운영 배포 금지는 `OPS-001-03` 이 갖는다.
- **성과 지표 목표치**는 상수가 아니므로 본 사양에 수치를 옮겨 적지 않고 [`../../prd/PRD.md`](../../prd/PRD.md) §성과 지표를 참조한다.
- **범위 밖**: 링크 만료(TTL)·1회성 사용·발송처 서명 검증·요청 제한·관리자 화면·결과 푸시 통지·Delphi 직접 호출은 서비스로 정의하지 않는다([`../../prd/PRD.md`](../../prd/PRD.md) §수행 범위 — 제외).
