# 본인확인 화면 정의

정본 목록은 [`spec-screens.md`](spec-screens.md). 디자인 토큰·컴포넌트는 [`design-system.md`](design-system.md) · [`design-system-components.md`](design-system-components.md). 용어는 [`../../../wiki/WIKI.md`](../../../wiki/WIKI.md).

## 개요

- **화면 목적**: 발송처 링크로 들어온 사용자가 **생년월일 여섯 자리**를 넣어 본인임을 확인하게 한다. 이 값은 전달 데이터를 여는 나머지 열쇠이며, 값이 맞아야 연동이 다음 단계로 넘어간다. 링크 자체가 깨진 경우는 이 화면이 열리기 전에 결과 안내로 끝난다.
- **관련 PRD 요구사항**:
	- [`../../prd/PRD.md`](../../prd/PRD.md) §수행 범위 4 — "**사용자 진입·본인확인·동의·승인**: 발송처 링크로 고정 진입 경로에 진입, **생년월일 입력**, 상수로 고정된 동의 항목 노출, **전 항목 동의를 조건으로 승인 제출**."
	- [`../../prd/PRD.md`](../../prd/PRD.md) §제공 가치 — "전달 데이터는 이중 암호화(encX/encY)되어 전달되고 **사용자의 생년월일 입력으로만 복원**된다."

## SCR-001 본인확인

### 기본 정보

| 항목 | 내용 |
|------|------|
| 화면명 | 본인확인 |
| 화면 경로 | `<INTERLOCK_ENTRY_PATH>` (쿼리 `encX`·`encY`) — 단계 `IDENTITY`. 여정 내내 경로가 바뀌지 않는다 |
| 접근 권한 | `Public` — 링크를 가진 누구나. 계정·로그인이 없다(`AUTH-001-02`). 출처를 검증하지 않는 것은 수용 리스크다(`OPS-002-02`) |
| 관련 서비스 | [`SVC-001`](../services/service_SVC-001.md) 연동 링크 진입 · [`SVC-002`](../services/service_SVC-002.md) 본인확인 |
| 트리거 PROC | PROC-102(본인확인 제출) |
| 선행 화면 | 없음(발송처 링크가 유일한 진입 수단). `SCR-003` 에서 되돌아올 수 있다 |
| 관련 IA 항목 | `USR-01` · `USR-03` |

- 이 화면을 그리게 만든 **PROC-101** 은 진입 응답을 만들 때 서버가 이미 수행한 것이며, 화면이 호출하는 것이 아니다.

### 레이아웃 구성

카드 하나에 세로 한 줄로 쌓는다([`design-system.md`](design-system.md) §레이아웃).

1. **제목 영역** — StageTitle. 제목 "본인 확인", 보조 설명 "생년월일 여섯 자리를 입력하면 연동을 계속할 수 있습니다."
2. **입력 영역** — TextField(생년월일 변형). 레이블 "생년월일 여섯 자리", 도움말 "예: 1990년 3월 5일 → 900305".
3. **알림 영역** — InlineAlert. 오류가 있을 때만 입력 영역 **아래**에 나타난다(§조건부 표시).
4. **액션 영역** — Button `primary` "확인"(전체 폭).

- 폭이 넓어져도 구조는 같고 카드 폭·여백만 커진다. 2단 배치를 만들지 않는다.
- 이 화면에는 진행 단계 표시(스텝 인디케이터)를 두지 않는다 — 단계 수가 셋뿐이고 각 화면이 다음에 할 일을 문장으로 알린다.

### 데이터 표시

| 표시 항목 | 데이터 모델(MDL) | 속성 | 표시 형식 | 마스킹 규칙 |
|-----------|-----------------|------|-----------|-------------|
| (허브가 표시하는 항목) | — | — | — | **표시 대상 개인정보 없음** — 허브는 사용자 정보를 보관하지 않으므로 되돌려 줄 값이 없다(`DATA-001-01`·`DATA-001-02`) |
| 생년월일 입력 값 | [`MDL-006`](../datas/model_MDL-004-006.md) | `birthDate` | 숫자 6자리(고정폭·자간 넓힘) | 사용자가 방금 넣은 값이라 **입력 필드 안에서만** 보인다. 오류 문구·다른 화면·주소창·브라우저 저장소로 옮기지 않는다(`DATA-001-02`·`DATA-001-04`) |
| 암호값 쌍 | [`MDL-004`](../datas/model_MDL-004-006.md) | `encX`·`encY` | **표시하지 않음** | 화면이 자기 URL 쿼리에서 읽어 메모리로만 보유한다. 어떤 요소에도 그리지 않는다(`DATA-001-04`) |

### 사용자 인터랙션

| 인터랙션 | 대상 요소 | 동작 | 호출 접점(인터페이스) | **트리거 PROC** | 결과 |
|----------|-----------|------|----------------------|----------------|------|
| 문서 수신(최초 렌더) | (자동) | 진입 응답의 초기 상태에서 `stage` 를 읽어 단계를 고른다 | 없음 — 진입 응답에 이미 실려 있다 | (PROC-101 은 서버가 이미 수행) | `IDENTITY` → 이 화면, `RESULT` → SCR-004 |
| 입력 | 생년월일 필드 | 숫자만 여섯 자리까지 받는다 | 없음(화면 안 처리) | (없음) | 입력 값 반영·오류 알림 해제 |
| 클릭·엔터 | 확인 버튼 | 본인확인을 제출한다 | `POST <INTERLOCK_ENTRY_PATH>/verify`([`spec-functions-api-user.md`](../functions/spec-functions-api-user.md) §본인확인 제출) | **PROC-102** | 성공 → SCR-002 / 재입력 → 이 화면 유지 / 확정·오류 → SCR-004 |

- 요청 본문에는 화면이 보유한 **암호값 쌍과 생년월일**을 함께 싣는다(허브가 요청 사이에 아무것도 보관하지 않기 때문이다 — [`spec-functions-api-user.md`](../functions/spec-functions-api-user.md) §생년월일 재수신 규약).
- **재시도 횟수를 세지 않는다**(`AUTH-002-04`). 시도 횟수·남은 횟수를 화면에 표시하지 않는다.

### 화면 상태 전이

| 상태 | 진입 조건 | PROC 단계 매핑 | 표시 내용 |
|------|----------|---------------|-----------|
| Initial | 진입 응답의 `stage` 가 `IDENTITY` | PROC-101 다음 단계 이관 | 카드 + 빈 입력 필드. **스켈레톤을 쓰지 않는다**(첫 그림에 이미 내용이 있다) |
| Editing | 사용자가 입력 중 | (트리거 전) | 입력 값 표시·확인 버튼 활성 |
| Submitting | 확인 제출 후 응답 대기 | PROC-102 입력 검증 진입 직후 | 버튼에 Spinner·문구 "확인 중"·필드 잠금 |
| ReEntry(형식) | 화면 검증 실패 또는 400 `EX-AUTH-001` | PROC-102 입력 검증 | InlineAlert + 필드 포커스. 단계 유지 |
| ReEntry(불일치) | 400 `EX-AUTH-002` | PROC-102 복호화 판정 1·2단계 | InlineAlert + 필드 포커스·**값 유지(전체 선택)**. 단계 유지 |
| Retryable | 500 `EX-BIZ-003`, 또는 **본인확인 제출의 응답 미수신**(전송 계층 단절) | PROC-301 추적 키 기준 사전 조회 실패 · 응답 미수신은 (해당 없음 — 서버 단계와 무관) | InlineAlert + 버튼 재활성. 결과 미확정이므로 그대로 다시 제출할 수 있다 |
| Handoff | 200 `stage = CONSENT` | PROC-102 다음 단계 이관 | 카드 내용을 SCR-002 로 교체 |
| Result | 200 `stage = RESULT` 또는 400 `EX-SEC-001`·`EX-SEC-002` | PROC-105 결과 경로 선택 | 카드 내용을 SCR-004 로 교체 |

- 단계 라벨(F1·F2 등)은 프로세스 도메인이 확정한다. 본 표는 정책·서비스가 쓴 **단계명** 으로 매핑한다.
- **본인확인 제출의 응답 미수신도 `Retryable` 이 받는다** — 이 제출은 **어떤 결과도 확정하지 않는다.** 같은 추적 키로 다시 제출해도 서버는 같은 레코드를 이어 쓸 뿐이라(`BIZ-002-03` ②) 그대로 다시 시도하는 것이 안전하고, 이미 같은 성질(결과 미확정·재시도 가능)의 상태가 서 있어 새 상태를 만들지 않는다. 다루는 것은 **전송 계층이 끊긴 경우**뿐이며 화면 쪽 요청 타임아웃을 새로 두지 않는다([`screen_SCR-003.md`](screen_SCR-003.md) §구현 가이드와 같다).
- **승인 제출의 응답 미수신과는 다른 상태로 간다** — 승인 제출은 **서버가 이미 결과를 확정했을 수 있어** 재전송이 아니라 **재진입 안내**(`SCR-003` 의 `Unconfirmed` — 같은 링크로 다시 들어오면 확정 결과가 재안내된다)가 맞다. 이 비대칭 때문에 두 접점의 응답 미수신은 서로 다른 상태로 가며, 하나로 합치지 않는다.

### 입력 폼 정의

| 필드명 | 입력 유형 | 데이터 모델(MDL) | 필수 | 유효성 규칙 (FE 검증 의사코드) | 에러 메시지 |
|--------|-----------|-----------------|------|--------------------------------|-------------|
| 생년월일 | text input(`inputmode="numeric"`·최대 6자) | [`MDL-006`](../datas/model_MDL-004-006.md)`.birthDate` | Y | `/^\d{6}$/.test(value)` — 정책 `AUTH-002-02` | "생년월일을 여섯 자리 숫자로 입력해 주세요." |

- **달력 유효성(존재하지 않는 월·일)을 검사하지 않는다** — 생년월일은 인증 자격이 아니라 복호화의 나머지 키이며, 발송처가 키 원문에 쓴 값과 판정 기준이 갈리면 안 된다([`function_FN-005-006.md`](../functions/function_FN-005-006.md) §FN-005 구현 가이드).
- **화면 검증은 사용자 편의이고 판정 근거는 서버 검증**이다(`AUTH-002-02`). 화면 검증을 통과한 값도 서버가 다시 검증한다.
- 오류 문구는 오류 응답 엔벨로프의 기본 문구를 그대로 쓴다([`function_FN-014-015.md`](../functions/function_FN-014-015.md) §오류 메시지 기본값) — 화면이 문구를 새로 만들면 같은 실패가 자리마다 달리 읽힌다.
- 확인 버튼은 **입력이 비어 있어도 활성**이다. 비활성으로 막으면 무엇이 잘못됐는지 알 수 없어, 제출 시 형식 안내를 보여 주는 쪽을 택했다(필수 동의처럼 정책이 제출 차단을 요구하는 자리가 아니다).

|-----------|-----------|-----------|
| InlineAlert(형식 안내) | 화면 검증 실패 또는 직전 응답이 `EX-AUTH-001` | `AUTH-002-02` |
| InlineAlert(재입력 안내) | 직전 응답이 `EX-AUTH-002` — 문구 "입력하신 생년월일로 확인되지 않았습니다. 다시 확인해 주세요." | `AUTH-002-03`·`SEC-002-04` |
| InlineAlert(재시도 안내) | 직전 응답이 `EX-BIZ-003`, 또는 본인확인 제출의 **응답을 받지 못함**(전송 계층 단절). 두 경우 모두 문구는 `EX-BIZ-003` 기본 문구 **"처리 중 문제가 발생했습니다. 잠시 후 다시 시도해 주세요."** 하나다 — 응답이 없는 쪽은 엔벨로프에서 가져올 값이 없어 같은 문구를 그대로 쓰고, 사유를 구분해 알리지 않는다 | `BIZ-003-04`(EX 정의 규칙) · `SEC-002-05` |
| 시도 횟수·잠금 안내 | **표시하지 않는다** — 횟수 제한·잠금·지연이 없어 표시할 개념이 없다 | `AUTH-002-04` |
| 링크 만료·1회성 안내 | **표시하지 않는다** — 이번 범위에 그런 장치가 없다 | `OPS-002-05` |

- **이 화면으로 돌아오는 경로**: SCR-003 에서 승인 시점 재복호화의 1·2단계가 실패하면(`EX-AUTH-002`) 본인확인 재입력으로 되돌아온다([`spec-functions-api-user.md`](../functions/spec-functions-api-user.md) §동의·승인 제출 에러 처리).
- 뒤로 가기로 단계를 되돌릴 수 없다 — 리다이렉트를 쓰지 않아 브라우저 이력에 단계가 쌓이지 않는다.

### 구현 가이드

- **암호값은 자기 URL 쿼리에서 읽는다.** 진입 응답의 초기 상태에는 암호값이 없다(`DATA-001-04`). 읽은 값은 페이지 메모리 상태로만 보유하고 제출마다 요청 본문에 싣는다.
- **생년월일은 페이지 메모리에만 둔다.** 주소창·숨은 필드·`localStorage`·`sessionStorage`·쿠키 어디에도 쓰지 않는다(`DATA-001-02`·`DATA-001-03`). 승인 단계까지 같은 메모리 상태를 이어 쓴다.
- **재입력 시 입력 값을 지우지 않고 전체 선택 상태로 포커스**를 준다 — 한 자리 오타는 그대로 고치고, 완전히 다시 넣을 사람은 바로 덮어쓸 수 있다.
- 새로고침·재진입은 **진입부터 다시 시작**한다. 허브에 세션이 없으므로 화면 상태를 되살리지 않는다.
- 제출 중 중복 클릭·엔터 연타를 막는다(버튼 잠금). 같은 요청이 두 번 가도 서버는 같은 레코드를 이어 쓰지만(`BIZ-002-03` ②), 화면 상태가 어긋난다.
- 숫자 외 입력은 받는 즉시 걸러 내고, 붙여넣기도 같은 규칙으로 정리한다.
