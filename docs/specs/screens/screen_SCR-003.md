# 연동 진행 안내 화면 정의

정본 목록은 [`spec-screens.md`](spec-screens.md). 디자인 토큰·컴포넌트는 [`design-system.md`](design-system.md) · [`design-system-components.md`](design-system-components.md). 용어는 [`../../../wiki/WIKI.md`](../../../wiki/WIKI.md).

## 개요

- **화면 목적**: 승인을 제출한 뒤 **결과가 확정되기까지 사용자가 무엇을 기다리는지** 알린다. 이 구간에서 허브는 전달 데이터를 다시 복호화해 수신처로 보내고, 실패하면 정해진 횟수만큼 즉시 재시도한다. 그 시간 동안 사용자가 창을 닫거나 다시 제출하지 않게 하는 것이 이 화면의 역할이다.
- **관련 PRD 요구사항**:
	- [`../../prd/PRD.md`](../../prd/PRD.md) §수행 범위 5 — "**연동 실행 (복호화·전달)**: 승인 시 허브가 생년월일로 복호화해 X를 얻고, 상수로 고정된 수신처(B) 주소로 전달한다."
	- [`SVC-004`](../services/service_SVC-004.md) §사용 시나리오 — "승인 제출부터 결과 확정까지 사용자는 대기 표시(SCR-003)를 보게 된다."

## SCR-003 연동 진행 안내

### 기본 정보

| 항목 | 내용 |
|------|------|
| 화면명 | 연동 진행 안내 |
| 화면 경로 | `<INTERLOCK_ENTRY_PATH>` (쿼리 `encX`·`encY`) — 단계 `PROCESSING`. 경로는 바뀌지 않는다 |
| 접근 권한 | `Public` — 승인을 제출한 진행 상태에서만 열린다 |
| 관련 서비스 | [`SVC-004`](../services/service_SVC-004.md) 연동 실행 |
| 트리거 PROC | 없음 — 이 화면에는 사용자 인터랙션이 없다. 표시되는 동안 수행되는 처리는 PROC-103 이 내부에서 부르는 PROC-104·PROC-301·PROC-302·PROC-303 이다 |
| 선행 화면 | SCR-002 동의·승인(승인 제출) |
| 관련 IA 항목 | `USR-02` |

- **`PROCESSING` 은 화면이 소유한 단계**다. 서버 응답의 `stage` 값에 대응하는 값이 없다 — 승인 요청을 보낸 시점에 시작되고 응답이 오면 끝난다.
- **이 화면에 오는 제출은 승인뿐이다.** 미동의 제출은 동의 화면이 유효성 안내로 막아 서버로 가지 않으므로(`BIZ-003-01`·`BIZ-003-03`) 기다릴 처리가 없고, 이 화면을 거칠 일도 없다.

### 레이아웃 구성

카드 안을 ProgressPanel 하나로 채운다. 앞 단계의 폼·목록은 남기지 않는다.

1. **진행 표시** — Spinner(32px), 가운데 정렬.
2. **제목 영역** — StageTitle(기본 변형). 제목 "연동을 진행하고 있습니다".
3. **보조 문구** — 같은 StageTitle 의 보조 설명. "창을 닫거나 새로 고치지 마세요. 잠시만 기다려 주세요."
4. **알림 영역** — InlineAlert. 응답을 받지 못했을 때만 나타난다(§조건부 표시).

- **조작 요소를 두지 않는다** — 취소 버튼을 두면 이미 진행 중인 서버 처리와 화면이 어긋난다. 허브에는 진행을 되돌리는 수단이 없다.
- 진행률 막대·퍼센트·남은 시간을 표시하지 않는다. 서버가 어느 단계인지 화면이 알 수 없다.

| 표시 항목 | 데이터 모델(MDL) | 속성 | 표시 형식 | 마스킹 규칙 |
|-----------|-----------------|------|-----------|-------------|

### 사용자 인터랙션

| 인터랙션 | 대상 요소 | 동작 | 호출 접점(인터페이스) | **트리거 PROC** | 결과 |
|----------|-----------|------|----------------------|----------------|------|
| (없음) | — | 이 화면에는 조작 요소가 없다 | — | (없음) | 응답 수신으로만 다음 상태가 결정된다 |

### 화면 상태 전이

| 상태 | 진입 조건 | PROC 단계 매핑 | 표시 내용 |
|------|----------|---------------|-----------|
| Waiting | 승인 요청 발신 직후 | PROC-103 승인 요청 재검증 → PROC-104 수신처 전달 호출·전달 실패 재시도 | Spinner + 제목 + 보조 문구 |
| Result | 200 결과 응답 또는 502 `EX-BIZ-002` | PROC-105 결과 경로 선택 | 카드 내용을 SCR-004 로 교체 |
| BackToConsent | 400 `EX-BIZ-001` 또는 500 `EX-BIZ-003` | PROC-103 승인 요청 재검증 · PROC-302 동의 증적 기록 | 카드 내용을 SCR-002 로 교체(알림 표시) |
| BackToIdentity | 400 `EX-AUTH-001`·`EX-AUTH-002` | PROC-104 입력 검증(형식) · PROC-104 복호화 판정(재복호화) — 판정 1·2단계 실패 | 카드 내용을 SCR-001 로 교체(재입력 안내) |
| Unconfirmed | 응답을 받지 못함(전송 계층 단절·창 이탈 후 복귀) | (해당 없음 — 서버 단계와 무관) | InlineAlert "처리 결과를 확인하지 못했습니다. 받으신 링크로 다시 들어오면 결과를 확인할 수 있습니다." |

- **`Unconfirmed` 는 승인 제출(`approve()`) 전용이다.** 본인확인 제출의 응답 미수신은 결과를 확정하지 않아 그대로 다시 시도하는 것이 안전하므로 `SCR-001` 의 `Retryable`(재시도 안내)이 받는다([`screen_SCR-001.md`](screen_SCR-001.md) §화면 상태 전이).
- **`Unconfirmed` 는 네 번째 결과 경로가 아니다.** 결과는 서버에서 이미 확정됐을 수 있으며, 같은 링크로 다시 들어오면 그 결과가 재안내된다(`BIZ-002-03` ③). 화면이 결과 구분을 추측해 만들어 내지 않는다(`BIZ-001-02`).
- **대기 시간의 상한은 정책 `BIZ-004-02`(전달 재시도 총 소요 상한)가 결정한다.** 화면은 자체 시간 임계값을 두지 않는다 — 화면 타임아웃이 서버 상한보다 짧으면 서버가 확정한 결과를 사용자만 못 보게 된다.
- 대기가 길어져도 문구를 바꾸지 않는다. 서버가 재시도 중인지 화면은 알 수 없고, 임의 시간 기준을 만들면 정책의 상한과 두 기준이 생긴다.

### 입력 폼 정의

해당 없음 — 입력 요소가 없다.

### 구현 가이드

- **화면 쪽 요청 타임아웃을 두지 않는다.** 응답 시점을 지배하는 것은 서버의 전달 재시도 상한이며(`BIZ-004-02`), 화면이 먼저 끊으면 결과를 확정한 서버와 어긋난다. 전송 계층이 끊긴 경우만 `Unconfirmed` 로 다룬다.
- 승인 요청은 **한 번만 보낸다.** 화면이 자동으로 다시 보내지 않는다 — 같은 추적 키의 재요청은 확정 결과 재안내로 처리되지만(`BIZ-002-04`), 이중 발신은 화면 상태를 어긋나게 한다.
- 진행 영역에 `role="status"`·`aria-live="polite"`·`aria-busy="true"` 를 주고, 전환 시 제목으로 포커스를 옮긴다.
- 감소 모션 설정에서는 회전 주기를 늦추되 진행 표시를 없애지 않는다([`design-system.md`](design-system.md) §간격·크기·모양).
- 이 단계에서도 암호값·생년월일은 **페이지 메모리에만** 남아 있다. 대기 중 어떤 저장소에도 쓰지 않는다(`DATA-001-02`).
