# 동의·승인 화면 정의

정본 목록은 [`spec-screens.md`](spec-screens.md). 디자인 토큰·컴포넌트는 [`design-system.md`](design-system.md) · [`design-system-components.md`](design-system-components.md). 용어는 [`../../../wiki/WIKI.md`](../../../wiki/WIKI.md).

## 개요

- **화면 목적**: 사용자가 **자기 정보가 어디에 어떤 항목으로 제공되는지 확인한 뒤 스스로 승인하거나 거부**하게 한다. 노출하는 항목·문구는 배포 상수 그대로이며 화면이 바꾸지 않는다. 필수 항목에 모두 동의하지 않으면 승인을 제출할 수 없다.
- **관련 PRD 요구사항**:
	- [`../../prd/PRD.md`](../../prd/PRD.md) §제공 가치 — "**동의 기반 투명성**: 사용자가 어떤 항목에 동의하는지 화면에서 확인하고 스스로 승인·거부를 결정한다."
	- [`../../prd/PRD.md`](../../prd/PRD.md) §수행 범위 4 — "… 상수로 고정된 **동의 항목 노출·동의 후 승인 또는 거부**."

## SCR-002 동의·승인

### 기본 정보

| 항목 | 내용 |
|------|------|
| 화면명 | 동의·승인 |
| 화면 경로 | `<INTERLOCK_ENTRY_PATH>` (쿼리 `encX`·`encY`) — 단계 `CONSENT`. 경로는 바뀌지 않는다 |
| 접근 권한 | `Public` — 본인확인을 통과한 진행 상태에서만 열린다. 계정·세션은 없다(`AUTH-001-02`) |
| 관련 서비스 | [`SVC-003`](../services/service_SVC-003.md) 동의·승인 |
| 트리거 PROC | PROC-103(동의·승인 제출) |
| 선행 화면 | SCR-001 본인확인 |
| 관련 IA 항목 | `USR-04` |

### 레이아웃 구성

카드 하나에 세로 한 줄로 쌓는다.

1. **제목 영역** — StageTitle. 제목 "연동 동의", 보조 설명 "아래 내용을 확인하고 연동을 진행할지 선택해 주세요."
2. **안내 영역** — NoticeBlock. 동의 안내 문구 상수를 단락 그대로 렌더한다. **값이 비면 이 영역 자체를 그리지 않는다**(`EXC-BIZ-07`). 레이아웃 전제(최대 400자·3단락·평문)는 [`design-system.md`](design-system.md) §안내 영역 레이아웃 전제.
3. **동의 항목 영역** — ConsentList. 항목이 1건이어도 목록 구조로 렌더한다.
4. **알림 영역** — InlineAlert. 조건부(§조건부 표시).
5. **액션 영역** — Button `primary` "동의하고 연동하기"(전체 폭) → 그 아래 Button `secondary` "동의하지 않고 종료"(전체 폭) → 그 아래 보조 문구 한 줄 "동의하지 않으면 연동이 취소되며, 이 링크로는 다시 진행할 수 없습니다."
	- 보조 문구의 근거는 **거부가 최종**이라는 규칙이다([`SVC-003`](../services/service_SVC-003.md) §예외 사항 · `BIZ-002-03` ③ · `BIZ-004-04`). 되돌릴 수 없는 선택이므로 누르기 전에 알린다.
	- 거부에 **확인 대화상자를 두지 않는다** — 모달은 이 표면의 유일한 포커스 가둠 요소가 되고, 위 보조 문구가 같은 목적을 달성한다.

### 사용자 인터랙션

| 인터랙션 | 대상 요소 | 동작 | 호출 접점(인터페이스) | **트리거 PROC** | 결과 |
|----------|-----------|------|----------------------|----------------|------|
| 단계 진입 | (자동) | 본인확인 응답이 실어 준 동의 항목 구성을 그대로 렌더 | 없음 — 직전 응답에 이미 실려 있다 | (PROC-103 동의 항목 구성) | 안내·목록·액션 렌더 |
| 체크 | 동의 항목 행 | 항목별 동의 여부를 토글 | 없음(화면 안 처리) | (없음) | 필수 충족 여부로 승인 버튼 활성 판정 |
| 클릭 | 동의하고 연동하기 | 승인(`APPROVE`)을 제출 | `POST <INTERLOCK_ENTRY_PATH>/approve`([`spec-functions-api-user.md`](../functions/spec-functions-api-user.md) §동의·승인 제출) | **PROC-103** | SCR-003 진행 화면으로 전환 |
| 클릭 | 동의하지 않고 종료 | 거부(`REJECT`)를 제출 | 같은 접점 | **PROC-103** | 버튼 안 진행 표시 후 SCR-004 경로 ② |

- 한 인터랙션은 하나의 PROC 를 트리거한다. 승인 이후의 복호화·전달·기록·결과 선택(PROC-104·PROC-301·PROC-302·PROC-303·PROC-105)은 **PROC-103 내부의 호출 관계**이며 화면이 따로 부르지 않는다.
- 요청 본문에는 화면이 보유한 **암호값 쌍·생년월일·`decision`·동의한 항목 코드 목록**을 싣는다. 값 이름과 표현은 기능·API 정본을 그대로 따르며 화면이 별칭을 만들지 않는다.
- **거부는 진행 화면으로 넘기지 않는다** — 수신처 전달도 증적 기록도 하지 않고 결과가 곧 확정되므로(`BIZ-003-03`) 기다림이 없다. 버튼 안 진행 표시로 충분하다.

### 입력 폼 정의

| 필드명 | 입력 유형 | 데이터 모델(MDL) | 필수 | 유효성 규칙 (FE 검증 의사코드) | 에러 메시지 |
|--------|-----------|-----------------|------|--------------------------------|-------------|
| 동의 항목(항목마다 1개) | checkbox | [`MDL-007`](../datas/model_MDL-007-010.md)`.agreedItemCodes` | 필수 항목만 Y | `items.filter(i => i.required).every(i => agreed.has(i.code))` — 정책 `BIZ-003-01` | "필수 동의 항목에 모두 동의해 주세요." |
| 승인·거부 선택 | button | [`MDL-007`](../datas/model_MDL-007-010.md)`.decision` | Y | 두 버튼이 각각 확정 값을 보낸다 — 화면이 값을 조합하지 않는다 | (해당 없음) |

- 제출 값 `agreedItemCodes` 는 **체크된 항목의 코드 배열**이다. 거부 제출이면 빈 배열이어도 되고 서버가 검증하지 않는다(`BIZ-003-03`).
- **선택 항목은 승인을 막지 않는다**(`EXC-BIZ-06`). 현재 상수의 항목은 필수 1건이지만 화면은 필수·선택을 구분해 판정한다.
- 화면의 활성 판정은 **1차 방어**이고 판정 근거는 서버 재검증이다(`BIZ-003-02`). 화면 검증만 두면 정책 위반이다.

### 구현 가이드

- **문구를 가공하지 않는다**(`DATA-003-05`). 항목명·설명·안내 문구를 자르거나 요약하거나 다시 쓰지 않는다 — 화면에 보인 내용과 동의 증적의 스냅샷이 어긋나면 증적이 무의미해진다.
- 항목 순서는 **응답이 준 순서 그대로**다(이미 코드 오름차순으로 정렬돼 온다 — [`MDL-008`](../datas/model_MDL-007-010.md) 구현 가이드). 화면에서 다시 정렬하지 않는다.
- 승인·거부 값은 **두 버튼이 각각 확정 값을 보내는 형태**로 구현한다. 라디오 선택 + 제출 버튼으로 나누면 "아무것도 고르지 않은 제출" 상태가 생긴다.
- **본인확인으로 되돌아가면 동의 선택 상태를 비운다** — 승인은 제출 시점의 명시적 행위이고 증적이 그 시점을 기록한다(`DATA-003-04`).
- 안내 문구의 단락 구분(빈 줄)을 문단으로 바꿔 렌더하되 그 밖의 서식 해석은 하지 않는다.
- 제출 중 중복 클릭을 막는다. 승인과 거부가 연달아 발신되면 화면 상태와 확정 결과가 어긋난다.
