# 동의·승인 화면 정의

정본 목록은 [`spec-screens.md`](spec-screens.md). 디자인 토큰·컴포넌트는 [`design-system.md`](design-system.md) · [`design-system-components.md`](design-system-components.md). 용어는 [`../../../wiki/WIKI.md`](../../../wiki/WIKI.md).

## 개요

- **화면 목적**: 사용자가 **자기 정보가 어디에 어떤 항목으로 제공되는지 확인한 뒤 스스로 동의 여부를 결정**하게 한다. 노출하는 항목·문구는 배포 상수 그대로이며 화면이 바꾸지 않는다. **필수 항목에 모두 동의해야만 승인을 제출할 수 있고**, 미동의 제출은 이 화면의 **유효성 안내**로 막아 결과 단계로 보내지 않는다(§조건부 표시).
- **관련 PRD 요구사항**:
	- [`../../prd/PRD.md`](../../prd/PRD.md) §제공 가치 — "**동의 기반 투명성**: 사용자가 어떤 항목에 동의하는지 화면에서 확인하고 스스로 동의 여부를 결정한다. **전 항목 동의가 진행 조건**이므로 동의 없이 연동이 실행되는 경로가 없다."
	- [`../../prd/PRD.md`](../../prd/PRD.md) §수행 범위 4 — "… 상수로 고정된 동의 항목 노출, **전 항목 동의를 조건으로 승인 제출**. 동의하지 않은 채 제출하면 동의 화면의 **유효성 안내**("모든 항목에 동의해 주셔야 합니다")로 막고 결과 단계로 보내지 않는다 — **사용자 거부는 결과 경로가 아니다**. 동의하지 않으려는 사용자의 종료 수단은 창을 닫는 것이며, 그 연동은 결과 미확정으로 남아 보관 기한에 삭제된다."

### 레이아웃 구성

카드 하나에 세로 한 줄로 쌓는다.

1. **제목 영역** — StageTitle. 제목 "연동 동의", 보조 설명 "아래 내용을 확인하고 모든 항목에 동의해 주세요."
2. **안내 영역** — NoticeBlock. 동의 안내 문구 상수를 단락 그대로 렌더한다. **값이 비면 이 영역 자체를 그리지 않는다**(`EXC-BIZ-07`). 레이아웃 전제(최대 400자·3단락·평문)는 [`design-system.md`](design-system.md) §안내 영역 레이아웃 전제.
3. **동의 항목 영역** — ConsentList. 항목이 1건이어도 목록 구조로 렌더한다.
4. **알림 영역** — InlineAlert. 조건부(§조건부 표시). **이 화면의 인라인 알림은 유형과 무관하게 전부 이 한 곳에 나타난다** — 화면 게이팅의 유효성 안내도, 서버가 돌려준 오류도 같은 자리다([`design-system.md`](design-system.md) §상태 표현).
5. **액션 영역** — Button `primary` "동의하고 연동하기"(전체 폭) **하나뿐이다.**
	- **거부·취소 버튼을 두지 않는다** — 사용자 거부가 결과 경로에서 폐지돼(`BIZ-003-03`) 제출할 거부가 없고, **거부 제출 인터페이스를 두는 사양은 반려**된다. 동의하지 않으려는 사용자의 종료 수단은 **창을 닫는 것**이다(§조건부 표시).
	- **확인 대화상자를 두지 않는다** — 모달은 이 표면의 유일한 포커스 가둠 요소가 되고, 승인은 되돌릴 수 없다는 사실을 한 번 더 묻는 것으로 알리지 않는다.

### 사용자 인터랙션

| 인터랙션 | 대상 요소 | 동작 | 호출 접점(인터페이스) | **트리거 PROC** | 결과 |
|----------|-----------|------|----------------------|----------------|------|
| 단계 진입 | (자동) | 본인확인 응답이 실어 준 동의 항목 구성을 그대로 렌더 | 없음 — 직전 응답에 이미 실려 있다 | (PROC-103 동의 항목 구성) | 안내·목록·액션 렌더 |
| 체크 | 동의 항목 행 | 항목별 동의 여부를 토글 | 없음(화면 안 처리) | (없음) | 필수 충족 여부로 승인 버튼 활성 판정 |
| 클릭 | 동의하고 연동하기 (**활성**) | 승인을 제출 | `POST <INTERLOCK_ENTRY_PATH>/approve`([`spec-functions-api-user.md`](../functions/spec-functions-api-user.md) §동의·승인 제출) | **PROC-103** | SCR-003 진행 화면으로 전환 |
| 클릭 | 동의하고 연동하기 (**`aria-disabled`**) | **제출하지 않는다** — 알림 영역에 유효성 안내를 띄우고 첫 미충족 항목으로 포커스를 옮긴다 | 없음 — 서버를 부르지 않는다 | (PROC-103 승인 버튼 활성 판정 · BR-004 화면 게이팅) | 단계 유지 · 알림 표시 |

- 한 인터랙션은 하나의 PROC 를 트리거한다. 승인 이후의 복호화·전달·기록·결과 선택(PROC-104·PROC-301·PROC-302·PROC-303·PROC-105)은 **PROC-103 내부의 호출 관계**이며 화면이 따로 부르지 않는다.
- 요청 본문에는 화면이 보유한 **암호값 쌍·생년월일·동의한 항목 코드 목록**을 싣는다 — [`MDL-007`](../datas/model_MDL-007-010.md) 의 속성은 `agreedItemCodes` **하나뿐**이고 **진행 의사 값(`decision`)은 없다**(`BIZ-003-01` — 진행 의사를 별도로 받지 않는다). 값 이름과 표현은 기능·API 정본을 그대로 따르며 화면이 별칭을 만들지 않는다.
- **미동의 제출은 서버로 가지 않는다** — 화면이 막는 것이 1차 방어이고(BR-004), 서버 재검증(BR-005)은 화면을 우회한 요청을 위해 그대로 남는다(`BIZ-003-02`). 두 방어는 같은 조건을 두 곳에서 판정한다.

### 화면 상태 전이

| 상태 | 진입 조건 | PROC 단계 매핑 | 표시 내용 |
|------|----------|---------------|-----------|
| Initial | 본인확인 응답 `stage = CONSENT` | PROC-102 다음 단계 이관 | 안내 + 항목 목록 + 액션. 필수 미충족이면 승인 버튼 비활성 |
| Editing | 체크 토글 | (트리거 전) | 필수 전부 충족 시 승인 버튼 활성 |
| Gated | **필수 미충족 상태에서 승인 버튼(`aria-disabled`)을 누름** | PROC-103 승인 버튼 활성 판정(BR-004 — 서버 호출 없음) | InlineAlert **"모든 항목에 동의해 주셔야 합니다"** + 첫 미충족 항목으로 포커스. 단계 유지 |
| SubmittingApprove | 승인 클릭 후 응답 대기 | PROC-103 승인 요청 재검증 진입 직후 | 카드 내용을 SCR-003 으로 교체 |
| Blocked | 400 `EX-BIZ-001` | PROC-103 승인 요청 재검증(BR-005) | InlineAlert "필수 동의 항목에 모두 동의해 주세요." + 첫 미충족 항목으로 포커스. 단계 유지 |
| Retryable | 500 `EX-BIZ-003` | PROC-103 `B3` 레코드 확보 · PROC-103 `B6` 동의 증적 기록·전달 시도 표지 검사(PROC-302) · **PROC-104 `B6` 결과 확정**(전달 **이후**) | InlineAlert + 버튼 재활성. 결과 미확정이라 그대로 다시 제출할 수 있다(아래 — 재제출이 전달을 되풀이하지 않는 근거) |
| BackToIdentity | 400 `EX-AUTH-001`·`EX-AUTH-002` | PROC-104 입력 검증(형식) · PROC-104 복호화 판정(재복호화) — 판정 1·2단계 실패 | 카드 내용을 SCR-001 로 교체(재입력 안내) |
| Result | 200 결과 응답 · 502 `EX-BIZ-002` · 400 `EX-SEC-001`·`EX-SEC-002` | PROC-105 결과 경로 선택 | 카드 내용을 SCR-004 로 교체 |

- **`Gated` 와 `Blocked` 는 같은 조건의 두 방어이고 같은 알림 영역을 쓴다.** `Gated` 는 화면이 막은 것(1차 방어 · `BIZ-003-01`)이고 `Blocked` 는 서버가 막은 것(재검증 · `BIZ-003-02`)이다. **문구는 서로 다르다** — `Gated` 의 문구는 PRD 가 정한 유효성 안내 문구이며 **본 화면 사양이 정본**이고, `Blocked` 의 문구는 오류 응답 엔벨로프의 기본 문구를 그대로 쓴다([`function_FN-014-015.md`](../functions/function_FN-014-015.md) §오류 메시지 기본값 — 화면이 서버 문구를 다시 쓰지 않는다는 [`screen_SCR-001.md`](screen_SCR-001.md) §입력 폼 정의의 규칙과 같다).
- **정상 흐름에서 `Blocked` 에 도달하지 않는다.** 화면이 먼저 막으므로 `EX-BIZ-001` 은 화면을 우회해 접점에 직접 도달한 요청에서만 돌아온다([`SVC-003`](../services/service_SVC-003.md) 예외 흐름). 그래도 상태를 지우지 않는다 — 서버 재검증이 실제 게이트이고 그 응답을 받을 자리가 필요하다.
- **거부 제출 상태를 두지 않는다.** 거부 경로가 폐지돼(`BIZ-003-03`) 제출이 하나뿐이므로 대기 상태도 `SubmittingApprove` 하나이며, 그 상태에서 카드 내용은 즉시 SCR-003 으로 바뀐다.
- **`Retryable` 에서 다시 제출해도 수신처에 두 번 전달되지 않는다.** `EX-BIZ-003` 의 뜻은 **결과 미확정**이며, 발생 지점은 전달 **이전**(PROC-103 `B3` 레코드 확보·`B6` 증적 기록)일 수도 전달 **이후**(PROC-104 `B6` 결과 확정 실패)일 수도 있어 **전달 수행 여부가 갈린다** — 이 상태가 "전달 미수행"을 뜻한다고 읽지 않는다. 어느 쪽이든 재제출은 PROC-103 `B6` 의 **전달 시도 표지 검사**(이번 레코드의 동의 증적이 이미 있는지 — 증적이 전달 **직전**에 커밋되므로 그 존재가 곧 전달 시도 표지다)가 증적·전달을 되풀이하지 않게 막으므로 안전하다(`BIZ-003-04` · [`../processes/process_PROC-103.md`](../processes/process_PROC-103.md) §실행 제약사항 §멱등성). 그래서 화면은 버튼을 되살리는 것으로 충분하고 **재제출을 스스로 막지 않는다** — 중복 방지는 서버가 판정한다.

### 입력 폼 정의

| 필드명 | 입력 유형 | 데이터 모델(MDL) | 필수 | 유효성 규칙 (FE 검증 의사코드) | 에러 메시지 |
|--------|-----------|-----------------|------|--------------------------------|-------------|
| 동의 항목(항목마다 1개) | checkbox | [`MDL-007`](../datas/model_MDL-007-010.md)`.agreedItemCodes` | 필수 항목만 Y | `items.filter(i => i.required).every(i => agreed.has(i.code))` — 정책 `BIZ-003-01` | **"모든 항목에 동의해 주셔야 합니다"** |

- **입력 필드는 이 하나뿐이다** — 진행 의사를 고르는 입력이 없다. [`MDL-007`](../datas/model_MDL-007-010.md) 의 속성이 `agreedItemCodes` 하나로 줄었고(진행 의사 `decision` 폐지), **제출 자체가 곧 승인 의사**이며 그 유효성은 위 규칙 하나로 판정된다(`BIZ-003-01`).
- 제출 값 `agreedItemCodes` 는 **체크된 항목의 코드 배열**이다. 위 규칙을 통과해야만 제출이 나가므로 **필수 항목이 모두 들어 있지 않은 배열이 화면에서 발신되는 경우가 없다.**
- **선택 항목은 승인을 막지 않는다**(`EXC-BIZ-06`). 현재 상수의 항목은 **필수 1건**이라 "모든 항목"과 "필수 항목 전부"가 같은 집합을 가리키고, 그래서 위 에러 문구가 규칙과 어긋나지 않는다. **상수에 선택 항목이 추가되면 게이팅 기준은 필수 항목이고 이 문구를 함께 정정한다**(`EXC-BIZ-06` 가 그 정정을 화면 사양의 몫으로 둔다).
- 화면의 활성 판정은 **1차 방어**이고 판정 근거는 서버 재검증이다(`BIZ-003-02`). 화면 검증만 두면 정책 위반이다.

| InlineAlert(필수 미충족 · 서버 재검증) | 응답이 `EX-BIZ-001` — 문구는 오류 응답 엔벨로프의 기본 문구 | `BIZ-003-02` |
| InlineAlert(재시도 안내) | 응답이 `EX-BIZ-003` | `BIZ-003-04` |
| **거부·취소 종료 수단** | **두지 않는다** — 버튼·링크·닫기 아이콘 어느 형태로도 두지 않는다. 동의하지 않으려는 사용자의 종료 수단은 **창을 닫는 것**이며, 그 연동은 **결과 미확정**으로 남아 보관 기한에 삭제된다 | `BIZ-003-03`(거부 제출 인터페이스를 둔 사양은 반려) · `EXC-BIZ-05` |
| 동의 항목 버전·추적 키 | **표시하지 않는다** | `DATA-001-04` |

- **승인 버튼은 완전한 `disabled` 가 아니라 `aria-disabled="true"` 다**([`design-system-components.md`](design-system-components.md) §Button). 눌러도 제출되지 않지만 **포커스를 받고 클릭 이벤트가 살아 있어** 그 순간 유효성 안내를 띄울 수 있다. 완전히 `disabled` 로 두면 키보드 탭 순서에서 사라져 **스크린리더 사용자가 왜 진행할 수 없는지 알 방법이 없다** — 버튼이 회색이라는 사실만으로는 이유가 전달되지 않는다.
- **유효성 안내는 누른 뒤에 뜬다.** 첫 그림부터 오류를 띄우지 않는다 — 아직 아무것도 하지 않은 사용자에게 실패를 먼저 보이지 않는다. 안내가 뜬 뒤 필수 항목을 모두 체크하면 안내를 지우고 버튼을 활성으로 바꾼다.
- **"창을 닫는 것"은 화면이 제공하는 조작이 아니라 브라우저의 기능**이다. 그래서 종료를 돕는 안내 문구·닫기 버튼을 두지 않는다 — 두는 순간 그것이 사실상의 거부 인터페이스가 되어 `BIZ-003-03` 에 걸린다.

### 구현 가이드

- **문구를 가공하지 않는다**(`DATA-003-05`). 항목명·설명·안내 문구를 자르거나 요약하거나 다시 쓰지 않는다 — 화면에 보인 내용과 동의 증적의 스냅샷이 어긋나면 증적이 무의미해진다.
- 항목 순서는 **응답이 준 순서 그대로**다(이미 코드 오름차순으로 정렬돼 온다 — [`MDL-008`](../datas/model_MDL-007-010.md) 구현 가이드). 화면에서 다시 정렬하지 않는다.
- **진행 의사를 값으로 만들지 않는다.** 버튼이 하나이고 요청 본문에도 진행 의사 필드가 없다 — 제출이 곧 승인이다(`BIZ-003-01` · [`spec-functions-api-user.md`](../functions/spec-functions-api-user.md) §동의·승인 제출). 라디오 선택 + 제출 버튼으로 나누면 "아무것도 고르지 않은 제출" 상태가 되살아난다.
- **필수 충족 판정을 한 곳에 둔다.** 버튼 활성 여부와 클릭 시 유효성 안내는 **같은 판정 결과**를 쓴다 — 두 곳에서 따로 계산하면 버튼은 활성인데 안내가 뜨는 어긋남이 생긴다.
- **본인확인으로 되돌아가면 동의 선택 상태를 비운다** — 승인은 제출 시점의 명시적 행위이고 증적이 그 시점을 기록한다(`DATA-003-04`).
- 안내 문구의 단락 구분(빈 줄)을 문단으로 바꿔 렌더하되 그 밖의 서식 해석은 하지 않는다.
- 제출 중 중복 클릭을 막는다. 같은 승인이 두 번 발신되면 화면 상태와 확정 결과가 어긋난다.
