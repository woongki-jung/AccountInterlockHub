# 연동 추적 레코드 데이터 정의

정본 목록은 [`spec-datas.md`](spec-datas.md). 용어는 [`../../../wiki/WIKI.md`](../../../wiki/WIKI.md).

## 개요

- **데이터 목적**: 연동 1건의 진행과 결과를 **추적 키 기준 단일 레코드 하나**에 모은다. 사용자 화면·발송처 조회·수신처 통지가 모두 이 한 행을 근거로 같은 사실을 말하게 하는 것이 목적이다. 사용자 정보·복호화 원문은 담지 않는다.
- **관련 PRD 요구사항**:
	- [`../../prd/PRD.md`](../../prd/PRD.md) §수행 범위 9 — "연동 추적 키 기준 **단일 추적 레코드**를 **사용자가 진입한 시점에 생성**하고, 승인·거부·복호화 결과·수신처 전달 결과·결과 확인·완료 콜백을 같은 레코드에 이어 기록한다. 일 단위 배치로 보관 기간 경과분을 삭제한다."
	- [`../../prd/devspec/database.md`](../../prd/devspec/database.md) §연동 추적 레코드 · §추적 키 중복 수신 · §보관 정책.
- **관련 법규**: 개인정보 보호법 제3조(개인정보 보호 원칙) — 최소 수집·보유 기간 준수. 본 엔터티는 개인정보를 담지 않으나 보유 기간을 두어 이 원칙을 구조로 만족한다.

### 속성 정의

| 속성명 | 데이터 타입 | 길이/precision | NULL | 기본값 | CHECK 제약 | 키 | 설명 |
|--------|-----------|----------------|------|--------|-----------|----|------|
| tracking_key | VARCHAR | 255 | NOT NULL | - | `char_length(btrim(tracking_key)) >= 1` | PK | 연동 추적 키. 전달 데이터 X 의 `trackingKey` 필드값을 **변형 없이** 그대로 담는다 |
| result_code | VARCHAR | 20 | NULL | NULL | `IN ('SUCCESS','USER_DENIED','DECRYPT_FAILED','DELIVERY_FAILED')` | - | 결과 구분. **NULL = 결과 미확정**이며 이 값의 존재 여부가 확정 판정 기준이다 |
| result_at | TIMESTAMPTZ | - | NULL | NULL | (테이블 제약 `ck_result_pair` 참조) | - | 처리 일시 — 결과 구분이 확정된 시각 |
| result_confirmed_at | TIMESTAMPTZ | - | NULL | NULL | - | - | 결과 확인 일시. **NULL = 미확인**이며 값이 채워진 시점이 보관 기간 기산점이다 |
| callback_received_at | TIMESTAMPTZ | - | NULL | NULL | - | - | 수신처 완료 콜백 수신 일시. **NULL = 미수신**이며 최초 수신 시각을 유지한다 |
| created_at | TIMESTAMPTZ | - | NOT NULL | `now()` | - | - | 생성 일시. 생성 기산 절대 상한(`DATA-002-01` ②)의 기준이다 |

- **테이블 제약 `ck_result_pair`**: `(result_code IS NULL) = (result_at IS NULL)` — 결과 구분과 처리 일시는 항상 함께 채워진다. 한쪽만 채워진 행이 생기면 조회 응답과 지표가 어긋난다.
- **CHECK 열거형은 4종을 유지하나 `DECRYPT_FAILED` 는 이 컬럼에 기록되는 경로가 없다** — 그 값이 확정되는 세 자리(진입 단계 구조 위반 · 본인확인 복호화 판정 3·4단계 실패 · 승인 시점 재복호화 3·4단계 실패)가 모두 **추적 키를 알 수 없는 실패**라 채워 넣을 행을 지목할 수 없다(`BIZ-002-02`·EXC-BIZ-14 — 추적 키는 그 복호화를 통과해야만 얻어진다). 그럼에도 열거형을 3종으로 줄이지 않는 이유는 지표 집계([`data_ENT-003.md`](data_ENT-003.md) `decrypt_failed_count`)·조회 응답·화면 경로가 **같은 값 체계**를 써야 하기 때문이다(`BIZ-001-03`). 이 컬럼에 `DECRYPT_FAILED` 가 담긴 행은 검증 시드처럼 **직접 INSERT 한 경우뿐**이며, 응용 계층에는 그 값을 쓰는 UPDATE 자리가 없다.
- **여부 컬럼을 두지 않는다** — 처리 성공 여부는 `result_code`, 결과 확인 여부는 `result_confirmed_at`, 완료 콜백 수신 여부는 `callback_received_at` 에서 각각 결정되는 파생값이다. 별도 boolean 컬럼을 두면 두 값이 어긋날 수 있어 두지 않는다([`spec-datas.md`](spec-datas.md) §데이터 설계 원칙 6).
- **승인 여부 컬럼을 두지 않는다** — 거부는 `result_code = 'USER_DENIED'` 로 남고, 승인 사실은 동의 증적([`data_ENT-002.md`](data_ENT-002.md))이 갖는다. 개발사양이 정한 기록 항목 범위 밖의 컬럼을 늘리지 않는다.
- **`result_confirmed_at` 에 `result_code` 전제 조건을 걸지 않는다** — 결과가 아직 확정되지 않은 레코드도 조회할 수 있고, 그때 결과 확인 표시를 할지의 판단 기준은 기능·API 도메인이 확정한다(`SVC-010` 예외 사항). 데이터가 그 판단을 미리 막지 않는다.

### 인덱스 정의

| 인덱스명 | 대상 컬럼 | 유형 | 카디널리티 추정 | 조회 패턴 (인용 PROC) |
|----------|-----------|------|-----------------|----------------------|
| 기본 키(자동) | tracking_key | UNIQUE BTREE | 높음(near-unique) | PROC-102 · PROC-301 추적 키 기준 사전 조회 · PROC-201 · PROC-202 · PROC-203 추적 키 사전 조회 · PROC-304 삭제 수행 (`WHERE tracking_key = ?`) |
| idx_interlock_tracking_result_confirmed_at | result_confirmed_at (부분 — `WHERE result_confirmed_at IS NOT NULL`) | BTREE | 높음(시각) | PROC-304 삭제 대상 산정 — 결과 확인 완료 기산 (`WHERE result_confirmed_at < ?`) |
| idx_interlock_tracking_created_at | created_at | BTREE | 높음(시각) | PROC-304 삭제 대상 산정 — 생성 기산 절대 상한 (`WHERE created_at < ?`) |

- 부분 인덱스로 둔 이유: 결과 확인이 아직 없는 행은 이 기준의 대상이 아니라 인덱스에 담을 필요가 없다. 미확인 행은 생성 기산 인덱스가 담당한다.
- **추적 키에 기본 키를 둔 것이 "허브가 유일성을 강제하는 설계"에 해당하지 않는 이유**: 제약의 범위가 `DATA-004-02` 가 허용한 **"보관 중인 레코드로 판정할 수 있는 범위"** 와 정확히 같다. 삭제된 뒤 같은 키가 다시 들어오면 제약이 비어 있어 새 레코드가 만들어지고(EXC-BIZ-04), 허브는 어떤 요청도 키가 이미 쓰였다는 이유로 거절하지 않는다 — `BIZ-002-03` 의 3분기로 보낼 뿐이다. 오히려 이 제약이 없으면 같은 키에 살아 있는 행이 둘 생겨 3분기 판정이 성립하지 않고 확정 결과가 덮일 수 있다(`BIZ-001-04` 위반). 물리 키 설계는 데이터 도메인 소관이다(`DATA-004` 구현 가이드).

### 데이터 생명주기

- **생성 조건**: PROC-301 `레코드 생성·이어쓰기` — PROC-102 `본인확인 성공 후 레코드 확보` 계기에서, 같은 추적 키의 레코드가 없을 때 1건 INSERT 한다(`BIZ-002-01`·`BIZ-002-03` ①). 진입 단계 구조 위반과 복호화 판정 3·4단계 실패는 추적 키를 알 수 없어 **INSERT 하지 않는다**(`BIZ-002-02`).
- **수정 조건**:
	- PROC-301 `결과 확정·기록` — `result_code`·`result_at` 을 **레코드당 한 번만** 채운다(`BIZ-001-04`). 계기는 거부 제출(PROC-103), 수신처 전달 성공·실패(PROC-104)다. **복호화 실패는 이 계기 목록에 없다** — 그 실패는 추적 키를 모르는 상태라 갱신 대상 행을 지목할 수 없고 지표 집계에만 계수된다(EXC-BIZ-14·`BIZ-005-02` ②).
	- PROC-301 `완료 콜백 기록` — `callback_received_at` 을 최초 수신 시에만 채운다(BR-012 멱등). 결과 확정 이후에도 이어 쓰며 `result_code` 는 건드리지 않는다(BR-021).
	- PROC-201 `결과 확인 표시` — `result_confirmed_at` 을 아직 비어 있을 때만 채운다(BR-010). 이미 채워져 있으면 그대로 둔다.
	- **확정 결과 재안내(PROC-105)는 어떤 컬럼도 갱신하지 않는다**(`BIZ-002-04`) — 결과·일시·결과 확인 상태가 모두 유지되어 보관 기산점이 밀리지 않는다.
- **삭제/보관 조건**: PROC-304 `삭제 대상 산정` → `삭제 수행` 에서 **하드 삭제**한다. 두 기준 중 먼저 도달한 쪽을 적용한다(`DATA-002-01`). 논리 삭제 컬럼을 두지 않으므로 삭제된 행은 조회에서 미진입과 구별되지 않는다(`DATA-002-05` → 404 `EX-DATA-001`).

### 구현 가이드

- **결과 확정·결과 확인·콜백 기록은 모두 조건부 UPDATE 로 만든다** — 각각 "아직 비어 있을 때만" 채우는 형태여야 재요청·중복 통지가 자연스럽게 멱등해진다. 조회 후 조건 판정을 응용 코드에만 두면 동시 요청에서 값이 덮인다.
- **레코드 생성은 기본 키 충돌을 정상 경로로 다룬다** — 같은 추적 키의 동시 진입에서 한쪽 INSERT 가 충돌하면 오류가 아니라 `BIZ-002-03` ②(이어쓰기)로 이어 간다.
- 결과 구분 값은 화면·API·집계가 **같은 상수 정의**를 쓴다. 저장 계층에서 별칭·대소문자 변형을 만들지 않는다(`BIZ-001-03`).
- 삭제는 대상별 건수를 세어 배치 결과 요약에 담는다(`OPS-003-04`). 대량 삭제는 나눠 수행해도 되며 멱등성만 유지하면 된다.
- DDL 변환 시 컬럼 순서는 위 표 순서를 따르고, 두 인덱스는 테이블 생성 직후 함께 만든다. 마이그레이션 순서 의존이 없다(FK 부재).
