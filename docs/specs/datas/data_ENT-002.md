# 동의 증적 데이터 정의

정본 목록은 [`spec-datas.md`](spec-datas.md). 용어는 [`../../../wiki/WIKI.md`](../../../wiki/WIKI.md).

## 개요

- **데이터 목적**: 사용자가 **어느 시점의 어떤 동의 항목에 동의했는지**를 개인정보 없이 남겨 사후에 입증할 수 있게 한다. 동의 항목은 배포 상수라 시간이 지나면 내용이 바뀌므로 버전 식별자만으로는 사후에 내용을 알 수 없다 — 그래서 그 시점의 항목 내용을 함께 보존한다.
- **관련 PRD 요구사항**:
	- [`../../prd/PRD.md`](../../prd/PRD.md) §수행 범위 10 — "**동의 증적 기록**: 사용자가 **어느 시점의 어떤 동의 항목에 동의했는지**를 개인정보 없이 남긴다(추적 키·동의 시각·동의 항목 버전). 추적 레코드와 별도 보존 기간을 갖는다."
	- [`../../prd/devspec/database.md`](../../prd/devspec/database.md) §동의 증적 · §보관 정책.
- **관련 법규**: **개인정보 보호법 제17조(개인정보의 제공)** — 제3자 제공 시 정보주체의 동의를 받아야 하며, 그 동의 사실을 입증할 수 있어야 한다. 본 엔터티가 그 입증 수단이다(`DATA-003`).

- **대리 키를 쓰는 이유**: 추적 키를 키로 쓸 수 없다. 보관 기간이 지나 추적 레코드가 삭제된 뒤 같은 키가 다시 들어오면 새 승인이 새 증적을 남기는데(EXC-BIZ-04), 그때 앞선 증적은 아직 보존 기간 안이다. 즉 **같은 추적 키의 증적이 둘 이상 공존할 수 있다.**
- **생성 일시 컬럼을 따로 두지 않는다** — 증적은 승인 확정 시점에만 만들어지고 이후 바뀌지 않으므로 `consented_at` 이 곧 생성 시각이다. 같은 값을 두 컬럼에 두지 않는다.
- **`agreed_item_codes` 를 스냅샷 안에 섞지 않는 이유**: 스냅샷은 **배포 상수에서 온 값**이고 동의한 항목 목록은 **사용자 입력에서 온 값**이다. 출처가 다른 두 값을 한 컬럼에 섞으면 사후 입증에서 "무엇이 제시됐고 무엇을 골랐는지"를 가려 읽을 수 없다.

### 스냅샷 구조

`consent_snapshot` 은 화면이 실제로 노출한 내용을 그대로 담는다(`DATA-003-05`). 최상위 속성은 둘이다.

- `notice` — 그 시점 `<CONSENT_NOTICE>` 원문 문자열. 값이 설정되지 않았으면 빈 문자열(안내 영역 미표시 — EXC-BIZ-07).
- `items` — 그 시점 `<CONSENT_ITEMS>` 의 항목 배열. 각 항목은 상수표가 정의한 속성 전부(항목 코드·항목명·필수 여부·설명)를 담고, **`code` 오름차순**으로 정렬한다 — 비교 기준은 §버전 식별자 산출 규칙 3 과 **같다**(UTF-8 바이트열의 사전식 순서). 두 곳의 기준이 갈리면 스냅샷 순서와 해시 입력 순서가 어긋난다.

값 자체는 배포 상수에서 오므로 본 사양에 옮겨 적지 않는다([`../../../CLAUDE.env.md`](../../../CLAUDE.env.md) §동의 항목 값이 단일 출처 — `OPS-001-04`). 스냅샷 보존은 **연동 구성의 저장이 아니라 증적**이며, 서비스가 참조하는 구성은 언제나 배포된 상수다(EXC-DATA-02).

### 버전 식별자 산출 규칙

`consent_version` 은 **상수 값에서 결정적으로 산출하는 해시**다. 산출은 기동 시 1회 수행하며(`PROC-901` 기동 시 버전 식별자 산출 · `SVC-018` F-004) 증적 기록은 그 값을 가져다 쓴다(`PROC-302` 버전 식별자 확보).

1. `<CONSENT_ITEMS>` 를 파싱한다.
2. **개행 코드를 정규화한다** — 파싱 결과의 **모든 문자열 속성 값**과 `<CONSENT_NOTICE>` **원문** 양쪽에서 `\r\n`·`\r` 을 `\n`(LF) 하나로 바꾼다.
3. 항목을 **항목 코드 오름차순**으로 정렬한다 — 비교는 두 항목 코드의 **UTF-8 바이트열을 앞에서부터 부호 없는 바이트로 견주는 사전식 순서**(= 코드 포인트 오름차순)이며, 한쪽이 다른 쪽의 접두면 짧은 쪽이 앞선다. **언어·로케일 규칙을 반영하는 비교를 쓰지 않는다** — 관측 요건으로는 ASCII 범위에서 숫자 → 대문자 → 소문자 순으로 앞선다(로케일 인식 비교는 이 순서를 지키지 않는다).
4. 각 항목을 상수표가 정의한 속성 순서(항목 코드 · 항목명 · 필수 여부 · 설명)의 객체로 재구성한다. 상수표에 없는 속성은 넣지 않는다.
5. **공백 없는 JSON** 으로 재직렬화한다(들여쓰기·개행 없음).
6. `<CONSENT_NOTICE>` 는 2에서 정규화한 값을 쓰되 **끝의 공백·개행만 제거**한다. 값이 없으면 빈 문자열로 둔다.
7. `5의 결과` + `0x1F`(Unit Separator 1바이트) + `6의 결과` 를 UTF-8 바이트열로 이어 붙인다.
8. 그 바이트열의 **SHA-256 다이제스트를 소문자 16진수 64자**로 표기한 값이 동의 항목 버전 식별자다.

- **왜 해시인가** — 항목 또는 안내 문구가 바뀌면 식별자도 반드시 바뀌어야 한다(`DATA-003-03`). 해시는 이 규칙을 자동으로 지키지만, 수동 채번은 사람이 갱신을 잊으면 **같은 식별자가 다른 내용을 가리키는 위반**이 조용히 발생한다.
- **왜 정규화(2~6)가 필요한가** — 정규화 없이 상수 문자열을 그대로 해시하면 공백 한 칸·속성 순서 차이만으로 식별자가 달라져 **같은 내용에 다른 식별자**가 붙는다. 이는 반대 방향의 정합 위반이다.
- **왜 개행 코드까지 정규화하는가(2)** — 상수는 배포 환경·편집 도구·운영체제에 따라 개행이 갈리므로, 정규화가 없으면 **눈에 완전히 같은 문구가 개행 코드 차이만으로 다른 식별자**를 낳는다. 근거는 셋이다. ① 바로 위 근거가 이미 **같은 내용에는 같은 식별자**를 요구하므로, 규칙을 그 근거에 맞춘다. ② 절차 통제(배포 시 개행 코드를 고정한다)는 사람·편집 도구·배포 파이프라인에 의존하고 **위반해도 애플리케이션이 감지하지 못한다** — `PROC-901` `B3` 는 형태만 볼 뿐 개행 코드를 판별하지 않으므로, 증적의 사후 입증력이 절차 준수 여부에 매달리게 된다. ③ 개행 코드는 **화면에 그려지는 문자가 아니므로** 정규화가 표시 내용을 바꾸지 않는다 — 따라서 `DATA-003-03`(내용이 바뀌면 식별자도 바뀐다)을 약화시키지 않는다.
- **항목 쪽을 정규화 대상에서 빼면 안 된다** — JSON 문자열 안의 개행은 **재직렬화해도 이스케이프로 그대로 살아남는다**. 5의 공백 제거는 구조의 공백만 걷어낼 뿐 값 안의 개행 코드를 건드리지 않으므로, 안내 문구만 정규화하면 설명이 여러 줄인 항목에서 같은 문제가 그대로 남는다.
- **스냅샷은 원문을 그대로 보존한다** — 정규화는 **해시 입력에만** 적용하고 `consent_snapshot` 은 화면이 노출한 원문을 그대로 담는다(§스냅샷 구조 · `DATA-003-05`). 개행 코드는 표시 내용이 아니므로 둘이 어긋나지 않는다 — 스냅샷과 식별자는 개행 코드가 무엇이든 같은 내용을 가리킨다.
- **왜 코드 포인트 비교인가(3)** — 정렬 결과가 곧 해시 입력 순서라, 비교 기준이 갈리면 바로 위와 **같은 뿌리의 위반**(같은 내용에 다른 식별자)이 난다. 로케일 인식 비교는 대·소문자·기호·숫자의 선후가 실행 환경 설정에 따라 달라져 **같은 배포가 환경마다 다른 식별자**를 내므로 결정적 산출 요구(`PROC-901` §실행 제약사항 — 같은 상수에서 같은 결과·멱등성)를 지킬 수 없고, 항목 코드는 사람이 읽는 문구가 아니라 식별자여서 언어별 정렬 규칙을 적용할 이유도 없다.
- **왜 `0x1F` 구분자인가** — 항목 내용에 나타나지 않는 제어문자를 경계로 써야 항목 끝과 문구 시작이 섞여 서로 다른 조합이 같은 바이트열이 되는 일을 막는다.
- 산출이 실패하면 기동을 중단한다(`OPS-001-02` → `EX-OPS-001`).

- **`tracking_key` 조회 PROC 가 1건 생겼다 — 인덱스 신설 여부는 미결이다.** 사후 입증 목적의 조회는 여전히 0건이지만(조회 화면·API 없이 저장분을 직접 확인 — `SVC-015` 사용자 정의), PROC-103 `B6` 의 **전달 시도 표지 검사**가 `tracking_key` + `consented_at` 으로 건수를 센다(§구현 가이드). 이 조회는 **추적 레코드 행 잠금을 쥔 채** 수행되므로 순차 스캔이면 행이 쌓일수록 잠금 점유가 길어진다. 다만 **정확성은 인덱스에 의존하지 않으므로**(결과가 달라지지 않는다) 신설은 성능 판단이며, 대상은 `(tracking_key, consented_at)` 복합 인덱스가 후보다. 신설 기준(사용 PROC 1개 이상)은 이제 충족한다 — **데이터 도메인이 판단해 확정한다**(EXC-OPS-08).

### 데이터 생명주기

- **생성 조건**: PROC-302 `동의 증적 기록` — PROC-103 `승인 확정` 계기에서만 1건 INSERT 한다(`DATA-003-04`). **미동의 이탈**(필수 동의 미충족 제출·창을 닫은 이탈 — `BIZ-003-03`)·본인확인 실패·진입 단계 실패에는 만들지 않는다(BR-022). **승인 1건당 증적 1건을 넘기지 않는다.**
- **수정 조건**: **없다.** 증적은 생성 후 불변이다 — 사후 입증 수단이 나중에 바뀌면 증적으로서 성립하지 않는다. 어떤 PROC 도 UPDATE 하지 않는다.
- **삭제/보관 조건**: PROC-304 `삭제 대상 산정` → `삭제 수행` 에서 동의 일시 기산 `<CONSENT_PROOF_RETENTION_MONTHS>` 경과분을 **하드 삭제**한다(`DATA-002-02`). 추적 레코드와 **다른 기준**을 쓰며, 추적 레코드가 지워진 뒤 증적만 남은 상태가 정상이다.

### 구현 가이드

- **증적 기록과 승인 확정을 같은 처리 경계에 둔다** — 증적 없는 승인이나 승인 없는 증적이 생기지 않게 한다(`BIZ-003-04`).
- **중복 증적은 "행 잠금 + 기존 증적 확인"으로 막는다 — 잠금만으로는 막히지 않는다.** 같은 추적 키의 동시 승인에서 추적 레코드 행 잠금은 두 요청의 **순서를 세울 뿐** 뒤선 요청을 멈추지 않으므로, 잠금을 얻은 자리(PROC-103 `B6`)에서 **이번 레코드의 증적이 이미 있는지 확인해야** 비로소 1건이 보장된다([`../processes/process_PROC-103.md`](../processes/process_PROC-103.md) §구현 가이드). 증적 테이블에 유일 제약을 두어 대신할 수 **없는** 이유는 §관계 정의에 있다 — 보관 주기를 넘어 같은 키의 증적이 공존하는 것이 정상이라 제약 자체가 성립하지 않는다.
- **그 확인은 `tracking_key` 만으로 하지 않는다.** 앞선 보관 주기의 증적이 아직 남아 있을 수 있으므로(§관계 정의 · EXC-BIZ-04) `consented_at >= 대상 추적 레코드의 created_at` 을 함께 걸어 **이번 레코드에 속한 증적만** 센다. 키만으로 세면 삭제 후 재수신된 정상 연동이 승인되지 않는다.
- 🔴 **`consented_at` 은 반드시 컬럼 기본값 `now()` 로 기록한다 — 응용에서 계산한 시각을 INSERT 에 싣지 않는다.** 위 술어가 비교하는 `ENT-001.created_at` 도 같은 기본값 `now()` 로 기록되므로, 두 값이 **같은 DB 시계**에서 나와야 비교가 성립한다. 응용 시계를 쓰면 `PROC-103` `B6` 이 레코드를 만든 직후 승인하는 갈래에서 **두 시각의 간격이 밀리초**라, 시계가 조금만 어긋나도 표지 검사가 **자기 증적을 세지 못하고 조용히 통과**해 증적 2행·수신처 이중 전달이 되살아난다. 그래서 `PROC-302`·`FN-012` 는 승인 확정 시각을 **인자로 받지 않고** `RETURNING consented_at` 으로 실제 기록 값을 돌려준다([`../functions/function_FN-012-013.md`](../functions/function_FN-012-013.md) FN-012 §시그니처). 같은 시계라면 앞선 트랜잭션이 먼저 커밋된다는 사실만으로 술어가 성립한다.
- `agreed_item_codes` 의 각 코드는 같은 행 `consent_snapshot.items` 의 항목 코드 안에 있어야 한다. 이 정합은 응용 계층에서 확인한다 — JSONB 간 참조를 DB 제약으로 강제하면 스냅샷 구조 변경이 곧 제약 변경이 되어 유지가 어려워진다.
- 스냅샷·동의 목록은 JSONB 로 두어 항목 속성이 늘어나도 스키마 변경 없이 담긴다. 다만 **버전 식별자 산출 규칙은 상수표의 속성 집합을 따르므로**, 상수표에 속성이 추가되면 산출 규칙 4의 순서 정의를 함께 갱신해야 한다.
- 증적에는 추적 키 외의 어떤 사용자 식별 값도 넣지 않는다. 넣을 자리가 스키마에 없는 것이 1차 방어다.
- DDL 변환 시 FK 가 없으므로 마이그레이션 순서 의존이 없다. `gen_random_uuid()` 는 PostgreSQL 13 이상 기본 제공이라 별도 확장이 필요하지 않다.
