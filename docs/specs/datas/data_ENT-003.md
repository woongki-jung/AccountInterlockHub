# 연동 지표 집계 데이터 정의

정본 목록은 [`spec-datas.md`](spec-datas.md). 용어는 [`../../../wiki/WIKI.md`](../../../wiki/WIKI.md).

## 개요

- **데이터 목적**: 추적 레코드가 보관 기간이 지나 지워진 뒤에도 **사용량·성공률을 낼 수 있게** 개인정보 없는 일자별 건수만 따로 쌓는다. 추적 키를 담지 않아 개별 연동으로 환원되지 않으므로 삭제 대상이 아니다.
- **관련 PRD 요구사항**:
	- [`../../prd/PRD.md`](../../prd/PRD.md) §수행 범위 11 — "**연동 지표 집계**: 일자 단위 요청·성공·실패 건수만 누적한다. 추적 키를 포함하지 않아 개별 연동으로 환원되지 않으며 보관 기간 삭제의 영향을 받지 않는다."
	- [`../../prd/devspec/database.md`](../../prd/devspec/database.md) §연동 지표 집계 — "누적 항목은 요청 수와 결과 구분별 건수(성공·복호화 실패·전달 실패)다. **미동의 이탈은 결과가 확정되지 않아 어느 결과 구분에도 계수되지 않는다**(요청 수에만 남는다)."
	- [`../../prd/PRD.md`](../../prd/PRD.md) §성과 지표 — 지표 정의와 산출 근거. **목표치 수치는 그 문서를 참조하며 본 사양에 옮겨 적지 않는다.**
	- [`../../prd/devspec/database.md`](../../prd/devspec/database.md) §보관 정책.
- **관련 법규**: 개인정보 보호법 제3조(개인정보 보호 원칙) — 개인을 알아볼 수 없는 형태의 처리. 본 엔터티는 추적 키·개인정보를 담지 않아 개별 정보주체로 환원되지 않으므로 보유 기간 제한의 대상이 아니다.

## ENT-003 연동 지표 집계

### 기본 정보

| 항목 | 내용 |
|------|------|
| 엔터티명 | 연동 지표 집계 |
| 물리 테이블명 | `tbl_interlock_metric_daily` |
| 분류 | 집계 (일자당 1행) |
| 관련 서비스 | `SVC-016`(집계 주체) · `SVC-001`·`SVC-002`·`SVC-004`(계수 계기) · `SVC-014`(같은 처리 경계) |
| 보존 정책 | **삭제하지 않는다**(`DATA-002-03`). 보관 배치의 대상이 아니다 |
| 개인정보 여부 | **비해당** — 추적 키·개인정보를 담지 않아 개별 연동으로 환원되지 않는다(`DATA-001-01`) |
| CRUD 수행 PROC | C·U: PROC-303 / R: PROC-303 / D: 없음 |
| 관련 IA 항목 | `BAT-06` (소비 노드: `USR-01`·`USR-03`·`USR-02`) |

### 속성 정의

| 속성명 | 데이터 타입 | 길이/precision | NULL | 기본값 | CHECK 제약 | 키 | 설명 |
|--------|-----------|----------------|------|--------|-----------|----|------|
| metric_date | DATE | - | NOT NULL | - | - | PK | 집계 일자. 경계 기준 시간대는 `Asia/Seoul` 고정(§일자 경계 기준) |
| request_count | BIGINT | - | NOT NULL | 0 | `>= 0` | - | 요청 수. 계수 시점은 두 가지뿐이다(§계수 규칙) |
| success_count | BIGINT | - | NOT NULL | 0 | `>= 0` | - | 결과 구분 `SUCCESS` 확정 건수 |
| decrypt_failed_count | BIGINT | - | NOT NULL | 0 | `>= 0` | - | 결과 구분 `DECRYPT_FAILED` 확정 건수(추적 키 미확보 실패 포함) |
| delivery_failed_count | BIGINT | - | NOT NULL | 0 | `>= 0` | - | 결과 구분 `DELIVERY_FAILED` 확정 건수 |

- **카운터는 요청 수 1개 + 결과 구분 3종 각각 1개 = 4개로 분리 저장**한다(`BIZ-005-01`). 성공률 같은 **파생 비율을 컬럼으로 두지 않는다** — 정의가 바뀌어도 과거 데이터를 다시 만들 필요가 없게 하기 위함이다.
- **거부 카운터를 두지 않는다**(`BIZ-005-01`) — `USER_DENIED` 는 값 체계에 없다(`BIZ-001-01`). 미동의 이탈은 결과가 확정되지 않아 **요청 수에만 남고 어느 결과 구분 카운터에도 계수되지 않는다**(`BIZ-005-04`). 항상 0 인 컬럼을 남기면 발송처·운영이 그 값을 지표로 읽는다.
- **감사 컬럼(생성·수정 일시)을 두지 않는다** — 행의 정체성이 곧 일자이고 삭제 기준도 없어 어떤 PROC 도 시각 컬럼을 조건절·정렬에 쓰지 않는다.
- **결과 구분 카운터 합계에 등식 제약을 걸지 않는다.** 아래 §행 단위 합계에 제약을 두지 않는 이유 참조.

### 일자 경계 기준

집계 일자의 경계는 **`Asia/Seoul`(UTC+09:00) 고정**이다. 계기 발생 시각(`TIMESTAMPTZ`)을 이 시간대로 변환한 날짜가 `metric_date` 가 된다.

- **왜 고정 시간대인가** — 지표를 읽는 주체가 국내 운영 주체이고 목표가 월 단위 사람 해석 단위다. 애플리케이션 기동 시간대·데이터베이스 세션 시간대에 따라 경계가 달라지면 같은 데이터에서 다른 지표가 나온다.
- **왜 `Asia/Seoul` 인가** — 한국은 서머타임이 없어 오프셋이 고정이므로 하루가 23시간·25시간이 되는 경계 사고가 없다. 저장 시각이 모두 `TIMESTAMPTZ` 라 변환이 결정적이다.
- 일자 산출 시 **시간대를 명시적으로 지정**한다. 서버·세션 기본 시간대에 의존하면 배포 환경에 따라 결과가 달라진다.

### 계수 규칙

정본은 `BIZ-005` 이며 본 절은 저장 형태와의 대응만 적는다.

| 계기 | 갱신 대상 | 근거 |
|---|---|---|
| 추적 레코드 **최초 생성** | `request_count` +1 | `BIZ-005-02` ① |
| **추적 키를 알 수 없는 실패**로 종료 | `request_count` +1 **및** `decrypt_failed_count` +1 | `BIZ-005-02` ② |
| 결과 구분 확정 | 해당 결과 구분 카운터 +1 (레코드당 1회) | `BIZ-005-04` |
| **미동의 이탈**(결과 미확정 종료) | **결과 구분 카운터 갱신 없음** — 요청 수는 레코드 최초 생성 시점에 이미 올랐다 | `BIZ-005-04`·`BIZ-003-03` |
| 재진입 · 본인확인 재시도 · 확정 결과 재안내 | **갱신 없음** | `BIZ-005-03` |
| 자가진단 호출 | **갱신 없음** | EXC-BIZ-11 |

- 감산·이동이 없다 — 결과 구분은 레코드당 한 번만 확정되고 바뀌지 않는다(`BIZ-001-04`).
- 추적 키를 알 수 없는 실패는 같은 요청인지 판정할 수단이 없어 **시도마다 계수된다**. 이 중복은 수용 한계이며 결함이 아니다(`BIZ-005-05`).

### 성과 지표 산출 (진입 게이트 🟡 G-05 대응)

저장된 4개 카운터만으로 **두 성공률 정의를 모두 산출할 수 있다.** 갈리는 지점은 **결과 미확정으로 끝난 요청을 분모에 넣느냐**다(`BIZ-005-06`).

- **전체 요청 기준 성공률**(미확정 포함) = `success_count` ÷ `request_count`
- **결과 확정 건 기준 성공률**(미확정 제외) = `success_count` ÷ (`success_count` + `decrypt_failed_count` + `delivery_failed_count`)
- **사용량** = 기간 내 `request_count` 합계

어느 정의를 목표치 판정에 쓸지의 확정은 **담당자 이월** 사항이며 본 사양은 정하지 않는다(`BIZ-005-06`). 목표 수치도 옮겨 적지 않고 [`../../prd/PRD.md`](../../prd/PRD.md) §성과 지표를 참조한다.

### 행 단위 합계에 제약을 두지 않는 이유

한 행에서 `success_count + decrypt_failed_count + delivery_failed_count` 와 `request_count` 는 **같지 않을 수 있다.** 따라서 둘을 묶는 CHECK 제약을 두면 정상 데이터가 거부된다.

1. **결과가 확정되지 않은 채 끝난 연동이 있다** — 사용자가 **동의하지 않고 창을 닫으면** 요청 수만 오르고 결과 카운터는 오르지 않는다(`BIZ-003-03`). 본인확인 미완료 이탈도 같다. 그래서 **결과 구분 3종의 합은 요청 수보다 작을 수 있으며 이 차이는 결함이 아니다**(`BIZ-005-04`).
2. **요청 수 계수와 결과 확정이 다른 일자에 일어날 수 있다** — 자정 직전에 진입해 자정 직후에 결과가 확정되면 요청 수는 앞 일자에, 결과는 다음 일자에 쌓인다. 그래서 어떤 행에서는 결과 합계가 요청 수를 넘어설 수도 있다.

정합은 **기간 합계 수준에서 근사로만 성립**하며, 행 단위 등식으로 강제할 성질이 아니다. 각 카운터는 0 이상이라는 제약만 갖는다.

### 데이터 생명주기

- **생성 조건**: PROC-303 `요청 수 계수` 또는 `결과 구분 카운터 갱신` — 해당 일자의 행이 없으면 그 시점에 만들어진다. 일자 행을 미리 만들어 두지 않는다(빈 행이 지표를 왜곡하지 않는다).
- **수정 조건**: PROC-303 `요청 수 계수`(`request_count`) · `결과 구분 카운터 갱신`(해당 결과 구분 컬럼). 계기당 +1 만 수행하며 감산·재계수가 없다.
- **삭제/보관 조건**: **삭제하지 않는다**(`DATA-002-03`·EXC-BIZ-12). 보관 배치는 이 테이블을 건드리지 않는다(`SVC-017` F-005).

### 구현 가이드

- **카운터 갱신은 한 번의 원자적 UPSERT 로 만든다** — 일자 행을 조회한 뒤 없으면 만들고 있으면 더하는 2단계로 나누면 동시 요청에서 계수가 유실된다. 일자를 충돌 대상으로 삼아 삽입과 증가를 한 문장으로 처리한다.
- **카운터 갱신은 추적 레코드 생성·결과 확정과 같은 트랜잭션 경계에서 처리한다**(`SVC-014` F-008) — 이중 계수·누락을 막는다. 한쪽이 실패하면 함께 되돌린다.
- 결과 구분 값에서 갱신할 컬럼을 고르는 대응표는 한 곳에만 둔다. 저장 계층에서 별칭·대소문자 변형을 만들지 않는다.
- `BIGINT` 를 쓰는 이유는 삭제가 없어 누적치가 계속 늘기 때문이다. 지표 산출 시 나눗셈은 정수 나눗셈이 되지 않도록 실수 연산으로 수행한다.
- DDL 변환 시 FK·추가 인덱스가 없어 테이블 하나만 만들면 된다.
