# 서버 대면·전달·명령 인터페이스 정의

정본 목록은 [`spec-functions.md`](spec-functions.md). 공통 규약은 [`spec-functions-api.md`](spec-functions-api.md). 용어는 [`../../../wiki/WIKI.md`](../../../wiki/WIKI.md).

본 문서는 서버가 서버를 부르는 자리를 정의한다 — 발송처·수신처가 호출하는 **서버 대면 API 4종**, 허브가 밖으로 거는 **수신처 전달**, 그리고 사람이 실행하는 **명령 진입점** 하나다.

## 메서드 선택 근거

서버 대면 API 4종을 **모두 POST** 로 확정한다. 조회 2종에 GET 을 쓰지 않은 이유는 셋이다.

1. **처리상태 확인은 응답이 상태를 바꾼다.** 결과를 담아 응답한 시점에 결과 확인 일시가 남고 보관 기간 기산이 시작된다(`DATA-002-01` ①). 부작용이 있는 접점을 안전한(safe) 메서드로 두면 중간 캐시·프리페치·자동 재시도가 기산을 앞당길 수 있다.
2. **연동 추적 키는 불투명 문자열**이다(`DATA-004-01`). 발송처가 어떤 문자든 쓸 수 있어 경로 세그먼트·쿼리에 실으면 인코딩 사고가 나고, 중간 로그에 값이 그대로 남는다.
3. **세 접점이 같은 요청 형상을 공유한다.** 추적 키 하나를 본문에 담는 형태가 같으므로 발송처·수신처 구현이 단순해지고, `MDL-011` 하나로 셋을 모두 표현할 수 있다.

- 목록 조회가 없어 캐시 이득이 없다는 점도 함께 고려했다.

## 공통 요청 형상 (추적 키 3종)

`API-01`·`API-02`·`API-03` 은 같은 요청 본문을 쓴다([`MDL-011`](../datas/model_MDL-011-015.md)).

```
{ "trackingKey": "<1~255자·공백만 불가>" }
```

- 형식 판정은 FN-006 이 담당하고, 위반은 400 `EX-DATA-002` 다(`DATA-004-03`).
- 본문을 JSON 으로 해석할 수 없으면 **입력 부재**와 같이 다뤄 400 `EX-DATA-002` 로 끝낸다.
- 사전 조회(FN-007)에서 대상이 없으면 404 `EX-DATA-001` 이며, **미진입과 보관 만료 삭제를 구별하지 않는다**(`BIZ-002-05`·`DATA-002-05`).
- **응답의 추적 키는 입력값을 변형 없이 그대로 되돌린다**(`DATA-004-01`).

## 처리상태 확인 API

| 항목 | 내용 |
|------|------|
| 엔드포인트 | `POST /api/interlock/status` |
| 담당 IA | `API-01` |
| 호출 PROC | PROC-201 · PROC-301 |
| 인증 요구 | `Public`(`AUTH-001-03`) |
| 요청 DTO | [`MDL-011`](../datas/model_MDL-011-015.md) |
| 응답 DTO (200) | [`MDL-012`](../datas/model_MDL-011-015.md) — `trackingKey` · `isSuccess` · `resultCode` · `isResultConfirmed` · `resultAt` · `resultConfirmedAt` |
| 응답 DTO (4xx/5xx) | 오류 응답 엔벨로프 |
| Rate Limiting | **미적용 — 수용 리스크**(`OPS-002-03`) |

### 처리 순서

1. 추적 키 형식 판정 — FN-006(위반 400 `EX-DATA-002`).
2. 사전 조회 — FN-007(`NONE` 이면 404 `EX-DATA-001`).
3. 응답 구성 — 결과 구분은 **단일 열거형 값을 변환 없이** 싣는다(`BIZ-001-03`).
4. 결과 확인 표시 — FN-010. **응답의 `resultCode` 가 `null` 이 아닐 때만** 최초 1회 기록한다(판정 기준은 [`function_FN-009-011.md`](function_FN-009-011.md) §결과 확인 표시 판정 기준).
5. 표시와 응답 구성을 같은 처리 경계에 둔다 — 표시가 실패하면 응답도 내보내지 않는다.

### 에러 처리

| HTTP status | EX 코드 | 발생 조건 | 사용자 메시지 | 개발자 노트 |
|---|---|---|---|---|
| 400 | `EX-DATA-002` | 추적 키 부재·공백만·255자 초과·본문 해석 불가 | "연동 추적 키 형식이 올바르지 않습니다." | 조회를 수행하지 않는다 |
| 404 | `EX-DATA-001` | 대상 레코드 없음 | "해당 연동 추적 키로 진입한 요청이 없습니다." | 미진입·삭제를 구별하지 않는다 |
| 500 | `EX-BIZ-003` | 결과 확인 표시 갱신 실패 | "처리 중 문제가 발생했습니다. 잠시 후 다시 시도해 주세요." | 응답을 내보내지 않는다 |
| 500 | `EX-OPS-002` | 위로 분류되지 않는 내부 처리 실패 | "처리 중 문제가 발생했습니다. 잠시 후 다시 시도해 주세요." | 내부 사유·스택을 담지 않는다(`SEC-002-05`) |

- **인증이 없어 추적 키를 아는 누구든 보관 기산을 시작시킬 수 있다** — 수용 리스크이며 조회 자격 검증을 추가하지 않는다(`OPS-002-04`).

### 응답 형상 확정

**연동 완료 확인 API 와 같은 형상([`MDL-013`](../datas/model_MDL-011-015.md))을 쓴다.** 통지 직후의 상태를 그대로 되돌려 주는 자리이므로 새 모델을 만들지 않는다.

- `isCallbackReceived` 는 기록 후이므로 항상 `true` 다.
- `callbackReceivedAt` 은 **최초 수신 일시**다. 중복 통지에도 같은 값을 돌려주므로 수신처는 자기 통지가 이미 반영됐음을 알 수 있다(BR-012 멱등).
- 추적 키 에코로 요청·응답 대응을 확인한다.

### 처리 순서

1. 추적 키 형식 판정 — FN-006.
2. 사전 조회 — FN-007(`NONE` 이면 404 `EX-DATA-001`). **없는 레코드를 새로 만들지 않는다**(`BIZ-002-03`).
3. 콜백 기록 — FN-011. 결과 구분은 건드리지 않는다(BR-021).
4. 추적 키 외의 값이 본문에 실려 와도 저장하지 않는다(`DATA-001-01`).

| Rate Limiting | **미적용 — 수용 리스크**(`OPS-002-03`·EXC-SEC-09). 경로 비공개가 유일한 완화 장치다 |

### 사유 코드 체계 (확정)

**판정 결과 + 사유 코드**로 응답하며, 사유 코드는 **정책 예외 코드 카탈로그의 EX 코드 값을 그대로** 쓴다. **연동 라이브러리의 오류 사유 코드와 같은 값 체계**이므로 발송처는 라이브러리와 자가진단 두 경로에서 같은 진단을 얻는다(`SVC-013` F-007).

| `isConform` | `reasonCode` | 판정 의미 |
|---|---|---|
| `true` | `null` | 복호화 판정 4단계를 모두 통과하고 X 평문 크기 상한도 충족 |
| `false` | `EX-SEC-001` | 암호값 구조 위반 — 디코드 실패·암호문 길이가 16의 배수 아님 |
| `false` | `EX-AUTH-002` | 판정 1·2단계 실패 — 키 불일치. 연동에서는 재입력 대상이 되는 상태다 |
| `false` | `EX-SEC-002` | 판정 3·4단계 실패 — X JSON 파싱 실패·`trackingKey` 부재·형식 위반 |
| `false` | `EX-SEC-004` | 복원된 X 의 UTF-8 직렬화 크기가 평문 상한 초과(`SEC-001-09`) |

- **부적합 판정도 HTTP 200 이다.** 판정이 정상적으로 수행된 결과이지 요청 오류가 아니다. 요청 자체가 성립하지 않는 경우만 4xx 다.
- `protocolVersion` — 허브의 규약 버전 문자열(`SEC-001-11`). 발송처가 라이브러리 공개 상수와 대조해 **MAJOR 불일치 = 비호환**으로 판정한다(BR-017).
- **복호화 원문·키·중간 값·단계 번호를 응답에 절대 담지 않는다**(`SEC-003-03`·`SEC-002-05`·`DATA-001-04`). 담을 속성이 응답 모델에 없다.
- **어떤 기록도 남기지 않는다** — 추적 레코드·동의 증적·지표 집계 어느 것도 만들지 않고 수신처 전달도 하지 않는다(`SEC-003-03`·EXC-BIZ-11).

### 처리 순서

1. **경로 판정** — 요청 경로가 `<SELFCHECK_PATH>` 가 아니면 **경로의 존재를 드러내지 않는 일반 404** 로 끝낸다. 메서드가 달라도 404 다(`SEC-003-02`).
2. 입력 존재 검증 — 셋 중 하나라도 없으면 400 `EX-SEC-003`(`SEC-003-04`).
3. 생년월일 형식 검증 — FN-005(위반 400 `EX-AUTH-001`).
4. 복호화 판정 — FN-004. 던져진 EX 코드를 **사유 코드로 옮겨** 200 부적합으로 응답한다.
5. 판정 통과 시 X 평문 크기 상한 검사 — 초과면 200 부적합 + `EX-SEC-004`.
6. 응답 구성 후 종료. 기록·전달·계수를 하지 않는다.

### 전달 성공 판정 기준 (확정)

**응답의 HTTP 상태 코드가 200~299 이면 성공, 그 밖은 모두 실패**로 판정한다. 본문 내용은 판정에 쓰지 않는다.

1. **본문 조건을 두지 않는 이유** — 수신처와 별도 응답 계약을 맺어야 하고, 그 계약이 어긋나면 전달은 됐는데 실패로 기록되는 상태가 생긴다. 정책이 이미 "2xx 아닌 응답"을 실패로 규정했다(`BIZ-004-02`).
2. **응답 본문을 읽지도 저장하지도 않는다.** 전달한 원문이 되비쳐 로그에 남을 위험을 없앤다([`MDL-010`](../datas/model_MDL-007-010.md) 속성 정의).
3. **리다이렉트(3xx)를 따라가지 않는다.** 전달 주소는 상수 하나이며, 추종하면 데이터가 예상치 못한 곳으로 나갈 수 있다. 3xx 는 실패로 판정한다.
4. **연결 실패·이름 해석 실패·보안 연결 실패·응답 대기 상한 초과**도 실패다.
5. 판정은 결과 구분과 **1:1** 로 이어진다 — 성공 → `SUCCESS`, 재시도 소진 실패 → `DELIVERY_FAILED`. 중간 상태를 결과 구분으로 승격시키지 않는다(`BIZ-004-03`).

- **허브 서버가 직접 호출한다.** 사용자 브라우저를 경유하지 않는다(`BIZ-004-01`) — 몇 안 되는 실질 완화 장치다(EXC-OPS-05).
- **재시도 중에도 X 는 메모리에만 둔다.** 큐·파일에 적재하면 무저장 원칙이 깨진다(`DATA-001-03`).
- **X 를 재직렬화하지 않는다.** 파싱한 객체를 다시 직렬화하면 숫자 표현·유니코드 이스케이프·필드 순서가 달라질 수 있다. 허브는 내용의 업무적 유효성을 판단하지 않으므로(`BIZ-004-05`) 복호화 결과 바이트열을 그대로 보낸다.
- **잠정 전달 주소 상태에서는 전달이 항상 실패해 `DELIVERY_FAILED` 로 끝나는 것이 정상 동작**이다(EXC-BIZ-10). 이 상태로 운영 배포하지 않는다(`OPS-001-03`).

## 명령 진입점 — 보관 배치 수동 실행

| 항목 | 내용 |
|------|------|
| 형태 | 애플리케이션 배포 단위 안의 **CLI 진입점**. 애플리케이션 컨텍스트를 기동해 보관 배치 로직을 1회 실행하고 종료한다 |
| 담당 IA | `BAT-02` |
| 호출 PROC | PROC-304 |
| 실행 명령 | `node dist/cli/retention.js` (배포 산출물 기준). 개발 편의 별칭 `npm run retention:run` |
| 인자·옵션 | **없다** |
| 표준 출력 | 마지막 줄에 처리 결과 요약 **JSON 1줄**([`MDL-021`](../datas/model_MDL-019-022.md)) |
| 표준 오류 | 진단 문구는 전부 여기로 내보낸다 — 표준 출력이 항상 파싱 가능하도록 |
| 종료 코드 | `0` = 성공 / `0` 이외 = 실패(`OPS-003-04`) |

### 출력 스키마 (확정)

```
{"baseAt":"2026-07-25T00:00:00+09:00","trackingDeletedCount":12,"consentProofDeletedCount":3,"failureReason":null}
```

- 키 4개 고정이며 순서를 바꾸지 않는다. 실패 시 `failureReason` 에 사유 문자열을 담고 나머지 건수는 그 시점까지 실제로 지운 수를 담는다.
- **지표 집계 삭제 건수 항목이 없다** — 삭제 대상이 아니라 셀 것이 없다(`DATA-002-03`).
- **스케줄 실행과 수동 실행이 같은 요약·같은 종료 코드 규칙을 쓴다.** 진입 경로만 다르고 삭제 로직·산정 기준은 같다(`DATA-002-04`·BR-015).

### 실행 규약

1. **인자를 두지 않는 이유** — 기준 일시를 인자로 받으면 스케줄 실행과 산정 기준이 갈려 `DATA-002-04`(같은 산정 기준)가 깨진다. 검증은 시드 데이터의 일시를 조정해 수행한다.
2. **멱등하다** — 같은 날 여러 번 실행해도 데이터가 손상되지 않고, 두 번째부터 건수가 0 이 된다.
3. **필수 상수가 충족되지 않으면 기동 단계에서 중단**된다(`OPS-001-02` → `EX-OPS-001`). 이때는 요약 JSON 을 낼 주체가 없으므로 **표준 출력에 미충족 상수명을 남기고** 0 이외 코드로 끝난다. 검증 절차는 종료 코드로 먼저 분기하고, 요약 JSON 이 없으면 기동 실패로 판독한다.
4. **HTTP 관리 경로를 만들지 않는다** — 관리자 경로·관리자 인증을 두지 않기로 했고 공개 표면을 사용자 진입 경로와 서버 대면 API 로 한정했다(`AUTH-001-01`). 인증 없는 삭제 트리거를 공개 표면에 추가하면 그 결정과 정면 충돌한다.
5. **별도 실행 이력 저장소를 두지 않는다.** 이 요약과 종료 코드가 유일한 관측 수단이다(`OPS-003-04`).
