# 사용자 진입 표면 인터페이스 정의

정본 목록은 [`spec-functions.md`](spec-functions.md). 공통 규약은 [`spec-functions-api.md`](spec-functions-api.md). 용어는 [`../../../wiki/WIKI.md`](../../../wiki/WIKI.md).

본 문서는 사용자가 링크로 들어와 결과를 보기까지의 세 접점을 정의한다 — **연동 요청 진입** · **본인확인 제출** · **동의·승인 제출**. 화면 구성·표시 형식은 화면 도메인 소관이며, 본 문서는 **주고받는 값과 프로토콜**만 정한다.

## 프로토콜 확정 — 리다이렉트를 쓰지 않는다

진입부터 결과 안내까지 **경로가 바뀌지 않는다.** 사용자는 발송처가 준 URL 하나에 머무르고, 단계 진행은 그 화면이 두 접점을 호출해 수행한다.

1. **리다이렉트를 두지 않는 이유** — 리다이렉트하면 암호값이 다시 URL 에 실려 브라우저 이력·중간 로그에 사본이 늘고(`DATA-001-04`), 뒤로 가기로 이전 단계에 돌아오는 경로가 생겨 단계 판정이 흔들린다.
2. **결과 안내도 같은 경로에서 표시한다.** 결과 경로 3종은 응답이 실어 주는 상태 값으로 구분되며 별도 URL 을 갖지 않는다(`BIZ-001-02`).
3. **새로고침은 진입부터 다시 시작한다.** 허브에 세션이 없으므로(`AUTH-001-02`) 화면은 상태를 잃고, 사용자는 생년월일을 다시 넣는다. 이미 결과가 확정된 연동이면 본인확인 제출이 확정 결과 재안내를 돌려준다(`BIZ-002-03` ③).

## 생년월일 재수신 규약 (확정)

승인 시점의 재복호화(`BIZ-002-06`)에 필요한 생년월일을 **승인 요청이 다시 실어 온다.**

1. 허브는 생년월일을 **요청 사이에 보관하지 않는다** — 저장소·세션·캐시 어디에도 두지 않는다(`DATA-001-02`·`DATA-001-03`).
2. 화면은 본인확인에서 입력받은 값을 **그 페이지의 메모리 상태로만** 보유했다가 승인 요청 본문에 다시 싣는다. **URL 파라미터·숨은 필드·브라우저 저장소로 옮기지 않는다**([`MDL-006`](../datas/model_MDL-004-006.md) 구현 가이드).
3. 암호값 쌍도 같은 방식으로 다시 싣는다. 화면은 진입 URL 의 쿼리에서 읽어 보유한다.
4. **왜 서버가 보관하지 않는가** — 보관하려면 요청을 잇는 식별자(세션)가 필요하고, 그 식별자는 곧 사용자 계정 없는 상태 보존이 되어 `AUTH-001-02`·`DATA-001-03` 과 정면으로 충돌한다. 값을 다시 받는 쪽이 무저장 원칙을 지키는 유일한 방법이다.
5. 재수신한 값은 **매번 처음처럼 검증한다**(FN-005 → FN-004). 앞 단계의 통과 사실을 신뢰하지 않는다.

- 화면 도메인은 이 규약을 그대로 소비한다 — 본인확인 단계에서 받은 값을 승인 제출까지 페이지 메모리로 유지하는 흐름이 화면 사양의 전제다.

## 복귀 주소 응답 규약 (확정)

**연동 완료 결과**에서 사용자를 출발지로 돌려보낼 **복귀 주소**를 응답에 싣는 규약이다. **세 접점이 이 절 하나를 공유한다** — 접점별 절에 같은 설명을 다시 두지 않는다(`BIZ-001-06` · [`SVC-005`](../services/service_SVC-005.md) F-007·F-008·BR-025 · [`MDL-009`](../datas/model_MDL-007-010.md)).

### 필드명 확정 — `returnUrl`

복귀 주소를 싣는 응답 필드 이름을 **`returnUrl`** 로 확정한다([`../../prd/PRD.md`](../../prd/PRD.md) §미결·확인 필요 ⑫ 가 spec 에 위임한 판단). 근거 넷이다.

1. **`redirect` 를 쓰지 않는다** — 본 문서 §프로토콜 확정이 **리다이렉트를 쓰지 않는다**를 명시적으로 못박았다. 필드명에 `redirect` 가 들어가면 서버 3xx 리다이렉트로 읽혀 그 확정과 정면 충돌한다. 실제 동작은 서버의 응답 전환이 아니라 **화면이 스스로 수행하는 브라우저 이동**이다.
2. **도메인 용어가 "복귀 주소"다** — PRD §수행 범위 6 과 IA `USR-05` 가 쓰는 말이며 `return` 이 그 대응이다.
3. **출처 중립** — 상수명 `<COMPLETION_REDIRECT_URL>` 을 그대로 옮기면(`completionRedirectUrl`) "현재 값이 상수에서 온다"는 **구현 사정이 외부 계약 이름에 박힌다.** 출처가 수신처 응답·발송처 전달 값으로 바뀌면(§미결·확인 필요 ⑦) 상수명 기반 이름이 사실과 어긋나는데, 그때 바뀌는 것은 **값을 얻는 자리**뿐이고 **필드가 뜻하는 바(사용자를 되돌려 보낼 주소)는 그대로**다. 계약 이름은 뜻을 따르고 출처를 따르지 않는다.
4. **기존 계약 명명 관습과 같다** — camelCase + 도메인 서술어(`resultPath`·`isReAnnouncement`·`trackingKey`·`agreedItemCodes`).

- **대상이 경로 ① 하나로 좁혀진 뒤에도 이름을 바꾸지 않는다** — 동봉 대상이 연동 완료뿐이 되면서(`EXC-BIZ-15`) `completion` 이 대상 범위와 어긋난다는 근거는 사라졌다. 그래도 근거 1(리다이렉트 오해)·2(도메인 용어)·3(출처 중립)·4(명명 관습)가 그대로 서 있어 **`returnUrl` 을 유지**한다. 이름을 바꾸면 후행 도메인(화면·프로세스·TC)의 인용을 전부 갱신해야 하는데, 그 비용을 정당화하는 근거가 새로 생기지 않았다.
- **내부 상수 모델은 다른 이름을 쓴다** — [`MDL-022`](../datas/model_MDL-019-022.md) 의 `completionRedirectUrl` 은 **주입 상수의 이름**이라 상수명을 그대로 쓰는 것이 정합하다. 외부 응답 계약의 이름(`returnUrl`)과 다른 것은 **의도된 분리**이며, 값이 상수에서 응답으로 옮겨 실리는 지점에서 이름이 한 번 바뀐다.

### 싣는 규칙

1. **선택 필드다** — 응답 DTO 에 자리가 늘 있는 것이 아니라 조건이 맞을 때만 **나타난다.**
2. **경로 ①(연동 완료) 에만 싣는다.** 경로 ②(링크·복호화 오류)·③(수신처 전달 실패)과 오류 응답 엔벨로프(502 `EX-BIZ-002` 포함)에는 싣지 않는다 — 완료가 아닌 결과는 이동할 주소를 받지 못해 화면에 머문다.
3. **판정은 서버 한 곳**(`PROC-105` 결과 안내 구성)**에서만 한다.** 화면이 보는 **유일한 신호는 필드 존재 여부**다 — 있으면 이동, 없으면 잔류이며 경로 번호로 다시 판정하지 않는다.
4. **절대 URL 한정** — `https://`·`http://` 로 시작하는 값만 싣는다. 미달이면 경로 ① 이라도 **필드를 싣지 않는다**(`SVC-005` F-008). 화면도 받은 값을 같은 기준으로 다시 확인하고 미달이면 이동하지 않는다.
5. **없음의 표현은 속성 부재다** — 빈 문자열·`null` 로 채우지 않는다. 채우면 있음·없음을 가르는 신호가 둘(존재 여부·값의 내용)이 되어 화면 판정이 갈린다.
6. **확정 결과 재안내도 같은 거동이다** — `isReAnnouncement` 값은 동봉 여부를 바꾸지 않는다. 재안내라도 경로가 ① 이면 실리고 ③ 이면 실리지 않는다(`BIZ-002-04` ③ · BR-025 — 재안내 대상은 결과가 확정된 경로 ①·③ 이다).
7. **값은 상수 `<COMPLETION_REDIRECT_URL>` 에서 온다** — 본 사양·예시에 실값을 복제하지 않고 플레이스홀더로만 쓴다(`OPS-001-04`). **주소의 출처 자체가 미확정**이라(§미결·확인 필요 ⑦) 확정 시 값을 얻는 자리가 바뀔 수 있으나, 위 규칙과 필드 형상은 그대로 선다.
8. **대기 시간을 응답에 싣지 않는다** — 결과를 보여 주고 이동하기까지의 시간은 화면 사양([`../screens/screen_SCR-004.md`](../screens/screen_SCR-004.md))이 정본이다. 계약에 시간 값을 두면 정본이 둘이 된다.

- **마스킹 대상이 아니다** — 개인정보·비밀 값이 아닌 상수 유래 URL 이라 금지 항목에 넣지 않는다([`function_FN-014-015.md`](function_FN-014-015.md) §FN-015 금지 항목의 예외).

## 연동 요청 진입

| 항목 | 내용 |
|------|------|
| 엔드포인트 | `GET <INTERLOCK_ENTRY_PATH>` |
| 담당 IA | `USR-01` |
| 호출 PROC | PROC-101 |
| 인증 요구 | `Public` |
| 요청 | 쿼리 파라미터 `encX`·`encY`([`MDL-004`](../datas/model_MDL-004-006.md)) |
| 응답(200) | `text/html; charset=utf-8` — 진입 화면 문서 + 초기 상태 |
| 응답(4xx/5xx) | 없음 — 진입 실패도 200 화면으로 안내한다(아래 참조) |
| Rate Limiting | **미적용 — 수용 리스크**(`OPS-002-03`) |

### 처리·응답 규약

1. 허브가 진입 경로 요청을 **직접 처리**한다(정적 자산 서빙보다 앞선다).
2. **요청 URL 전체 길이**를 판정한다(`SEC-001-10`). 상한 초과면 결과 경로 ② 다(`EX-SEC-004`).
3. **암호값 구조**를 판정한다(FN-003). 위반이면 결과 경로 ② 다(`EX-SEC-001`).
4. 판정 실패면 **지표에만 계수**하고 추적 레코드를 만들지 않는다 — FN-013 `UNIDENTIFIED_FAILURE`(`BIZ-002-02`·`BIZ-005-02` ②).
5. 판정 결과와 무관하게 **200 + 화면 문서**를 반환하고, 문서에 **초기 상태**를 실어 준다. 사용자가 보는 것은 언제나 화면이지 오류 본문이 아니기 때문이다.

	```
	{ "stage": "IDENTITY" }
	{ "stage": "RESULT", "resultPath": 2, "reasonCode": "EX-SEC-001", "isReAnnouncement": false }
	```

	- `stage` — `IDENTITY`(본인확인으로 진행) 또는 `RESULT`(결과 안내로 종료).
	- `resultPath`·`isReAnnouncement` — [`MDL-009`](../datas/model_MDL-007-010.md) 와 같은 값 체계.
	- `reasonCode` — 결과 경로 ② 의 사유 EX 코드. 화면이 안내를 고르는 데만 쓴다.
	- `returnUrl` — **선택 필드로 계약에 두되 이 접점에서는 나타나지 않는다.** 진입 단계의 `stage: RESULT` 는 진입 판정 실패, 곧 **항상 경로 ②** 라 동봉 조건(①)이 성립하지 않는다(§복귀 주소 응답 규약 — 싣는 규칙 2). 계약에 자리를 두는 이유는 **화면 어댑터가 세 접점의 결과 상태를 같은 방식으로 다루게** 하려는 것이다 — 접점마다 다른 모양을 읽지 않고, 어디서 온 결과든 "필드가 있으면 이동"이라는 한 규칙만 쓴다.
6. **초기 상태에 암호값을 담지 않는다**(`DATA-001-04`). 화면은 자기 URL 의 쿼리에서 읽는다.
7. 진입 응답에 **연동 추적 키를 담지 않는다.** 사용자에게 필요 없는 값이며, 이 단계에서는 아직 복호화 전이라 알 수도 없다.

### 에러 처리

| HTTP status | EX 코드 | 발생 조건 | 화면 처리 | 개발자 노트 |
|---|---|---|---|---|
| 200 | `EX-SEC-001` | 암호 파라미터 부재·빈 값·디코드 실패·암호문 길이가 16의 배수 아님 | 결과 경로 ② | 추적 레코드 미생성·지표만 계수 |
| 200 | `EX-SEC-004` | 요청 URL 전체 길이 상한 초과 | 결과 경로 ② | 위와 같다 |
| 200 | `EX-OPS-002` | 위 코드로 분류되지 않는 내부 처리 실패 | 결과 경로 ② | 결과 미확정·기록 없음. 실패 사실은 운영 로그에만 남긴다(`OPS-003-03`) |
| 404 | — | 진입 경로가 아닌 요청 | 본문 없는 일반 404 | `SEC-003-02` 와 같은 취급 |

- **`EX-OPS-002` 만 이 접점에서 HTTP 매핑이 다르다.** EX 카탈로그의 `EX-OPS-002` 는 500 이지만, 진입 접점은 **4xx·5xx 본문을 만들지 않는다**(위 §처리·응답 규약 5) — 사용자가 보는 것은 언제나 화면이므로 내부 실패도 200 화면 + 결과 경로 ② 로 안내한다. 내부 사유·스택은 담지 않는다(`OPS-003-05`). `PROC-101` §분기 및 예외 흐름과 TC `USR-01_013` 이 같은 취급을 쓴다.

## 본인확인 제출

| 항목 | 내용 |
|------|------|
| 엔드포인트 | `POST <INTERLOCK_ENTRY_PATH>/verify` |
| 담당 IA | `USR-03` |
| 호출 PROC | PROC-102 · PROC-301 · PROC-303 |
| 인증 요구 | `Public` |
| 요청 DTO | `{ encX: string, encY: string, birthDate: string(6) }` — [`MDL-004`](../datas/model_MDL-004-006.md) + [`MDL-006`](../datas/model_MDL-004-006.md) |
| 응답 DTO (200) | `{ stage, consent? , resultPath?, isReAnnouncement?, returnUrl? }` (아래 참조) |
| 응답 DTO (4xx/5xx) | 오류 응답 엔벨로프([`spec-functions-api.md`](spec-functions-api.md) §공통 응답 포맷) |
| Rate Limiting | **미적용 — 수용 리스크**(`OPS-002-03`) |

### 처리 순서

1. `birthDate` 형식 검증 — FN-005(`EX-AUTH-001`).
2. 복호화 판정 — FN-004. 실패는 EX 코드에 따라 재입력 안내(`EX-AUTH-002`) 또는 결과 경로 ②(`EX-SEC-001`·`EX-SEC-002`)다.
3. `EX-SEC-002` 로 끝나면 **추적 키를 알 수 없으므로** 레코드를 만들지 않고 지표만 계수한다 — FN-013 `UNIDENTIFIED_FAILURE`.
4. 판정을 통과하면 X 에서 **추적 키만 취하고 X 를 즉시 폐기**한다(`BIZ-002-06`).
5. 추적 레코드 확보 — FN-008. 최초 생성이면 요청 수가 함께 계수된다.
6. 확보 결과가 `FIXED` 면 **확정 결과 재안내**로 응답한다(`BIZ-002-03` ③). 레코드를 갱신하지 않고 요청 수도 올리지 않는다. 이 재안내의 경로가 **① 이면 `returnUrl` 이 함께 실리고 ③ 이면 실리지 않는다**(§복귀 주소 응답 규약 — 재안내도 같은 거동). 이 접점의 재안내가 경로 ② 로 나오는 일은 없다 — `DECRYPT_FAILED` 는 레코드에 확정되지 않는다(EXC-BIZ-14).
7. 그 밖에는 동의 항목 구성([`MDL-008`](../datas/model_MDL-007-010.md))을 실어 동의 단계로 넘긴다.

### 응답 본문

```
{ "stage": "CONSENT",
  "consent": { "version": "<64자 16진수>", "notice": "<문자열·비면 미표시>",
               "items": [ { "code": "...", "label": "...", "required": true, "description": "..." } ] } }

{ "stage": "RESULT", "resultPath": 1, "isReAnnouncement": true,
  "returnUrl": "<COMPLETION_REDIRECT_URL>" }

{ "stage": "RESULT", "resultPath": 3, "isReAnnouncement": true }
```

- **예시의 `returnUrl` 값은 플레이스홀더다** — 실값은 상수 단일 출처에만 있고 사양 본문에 복제하지 않는다(`OPS-001-04`). 위 두 예시의 차이는 **경로 번호와 필드 유무뿐**이며, 경로 ③ 재안내에는 속성 자체가 없다(§복귀 주소 응답 규약 — 싣는 규칙 5).
- 동의 항목 구성은 **상수 파싱 결과를 그대로** 싣는다. 화면이 문구를 가공하지 않는다(`DATA-003-05`).
- **응답에 연동 추적 키·복호화 원문·암호값·생년월일을 담지 않는다**(`DATA-001-04`). 승인 단계는 추적 키를 다시 복호화로 얻는다.

### 미동의 게이팅 규약 (확정)

**거부를 제출하는 인터페이스가 없다.** 이 접점이 받는 제출은 승인 하나뿐이며, 그 성립 조건은 **필수 동의 항목 충족**으로 일원화된다(`BIZ-003-01`·`BIZ-003-02`).

| 속성 | 전송 표현 | 값 |
|---|---|---|
| `agreedItemCodes` | 문자열 배열 | 사용자가 동의한 동의 항목 코드. **필수 항목이 모두 들어 있어야 제출이 성립**한다([`MDL-007`](../datas/model_MDL-007-010.md) — 속성은 이 하나뿐이다) |

1. **진행 의사 필드(`decision`)를 두지 않는다.** 거부 제출 경로가 없어 진행 의사가 하나뿐이므로 **분기가 성립하지 않는다** — 값이 하나인 필드를 남기면 도달 불가 경로가 외부 계약에 남고, 발송처·화면이 쓸모없는 처리 분기를 만든다(`BIZ-003-01`·`BIZ-003` 구현 가이드 · `BIZ-001-01` 구현 가이드 — 거부 값을 되살리지 않는다).
2. **거부 제출 인터페이스를 두는 사양은 반려된다**(`BIZ-003-03`). 미동의 제출은 결과가 아니므로 결과 구분·결과 경로 어느 쪽도 부여되지 않는다.
3. **1차 방어는 화면 유효성 안내다.** 필수 미충족 상태의 제출은 동의 화면이 막고 결과 단계로 보내지 않는다(`BIZ-003-01`). **안내 문구·표시 위치는 화면 사양이 정본**이며 본 계약은 문구를 복제하지 않는다.
4. **서버 재검증은 그대로 남는다.** 화면 게이팅은 1차 방어일 뿐이라 이 접점은 필수 동의 충족을 다시 검증하고, 미충족이면 400 `EX-BIZ-001` 로 종료한다(`BIZ-003-02` · 아래 §처리 순서 4 · 에러 표).
5. **동의하지 않는 사용자의 종료 수단은 창을 닫는 것이다.** 이 접점에 종료를 알리는 요청이 오지 않으며, 그 연동은 **결과 미확정**으로 남는다(`EXC-BIZ-05`) — 계약에 종료 통지 필드·엔드포인트를 두지 않는다.

### 처리 순서

1. `birthDate` 형식 검증 — FN-005.
2. 복호화 판정 — FN-004(재복호화). 추적 키를 다시 얻는다(`BIZ-002-06`·EXC-SEC-07).
3. 추적 레코드 확보 — FN-008. `FIXED` 면 **확정 결과 재안내**로 응답하고 아무것도 갱신하지 않는다(`BIZ-002-04`).
4. 필수 동의 충족을 **서버가 다시 검증**한다(`BIZ-003-02`). 미충족이면 400 `EX-BIZ-001` — 결과를 확정하지 않고 동의 화면을 유지한다.
5. 동의 증적 1건을 기록한다 — FN-012. 실패하면 결과를 확정하지 않고 전달도 하지 않는다(`BIZ-003-04`).
6. 수신처로 전달한다 — [`spec-functions-api-server.md`](spec-functions-api-server.md) §수신처 전달 접점. 성공이면 `SUCCESS`, 재시도 소진이면 `DELIVERY_FAILED` 를 확정한다(FN-009).
7. 복호화 원문·중간 값을 폐기하고 결과 경로를 응답한다. **복귀 주소는 이 응답 구성 단계에서만 실린다** — 확정된 결과 경로가 ① 이면 `returnUrl` 을 함께 싣고, ③ 이면 싣지 않는다(`PROC-105` 결과 안내 구성 · §복귀 주소 응답 규약 — 싣는 규칙 3). 3단계의 확정 결과 재안내도 같은 자리에서 같은 규칙을 적용한다.

- **이 접점이 만드는 결과 경로는 ①·③ 둘뿐이다.** 경로 ②(링크·복호화 오류)는 정상 응답이 아니라 400 `EX-SEC-001`·`EX-SEC-002` 오류 응답 엔벨로프로 나가며, 화면이 그 EX 코드로 경로 ② 안내를 고른다(아래 에러 표).
