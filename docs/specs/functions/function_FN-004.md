# 복호화 판정 공통 기능 정의

정본 목록은 [`spec-functions.md`](spec-functions.md). 용어는 [`../../../wiki/WIKI.md`](../../../wiki/WIKI.md).

## 개요

- **기능 목적**: 사용자가 넣은 생년월일로 전달 데이터가 복원되는지를 **한 절차로** 판정한다. 본인확인·연동 실행·자가진단 세 경로가 이 기능 하나를 공유하므로, 자가진단이 통과시킨 값이 실제 연동에서 실패하는 사고가 구조적으로 생기지 않는다.
- **관련 PRD 요구사항**:
	- [`../../prd/PRD.md`](../../prd/PRD.md) §제공 가치 — "전달 데이터는 이중 암호화(encX/encY)되어 전달되고 **사용자의 생년월일 입력으로만 복원**된다."
	- [`../../prd/devspec/external-apis.md`](../../prd/devspec/external-apis.md) §암호화 연동 규약 — "생년월일을 키로 `encY`를 복호화해 encX 복호화용 키를 복원한다 … 복원한 키로 `encX`를 복호화해 X를 얻는다."

## FN-004 복호화 판정

### 기본 정보

| 항목 | 내용 |
|------|------|
| 기능명 | 복호화 판정 |
| 분류 | POL |
| 사용 서비스 | SVC-002 · SVC-004 · SVC-013 |
| 호출 PROC | PROC-102 · PROC-104 · PROC-204 |
| 연관 정책 | `SEC-002-01` · `SEC-002-03` · `SEC-002-04` · `SEC-002-05` · `SEC-001-01` · `SEC-001-03` · `SEC-001-04` · `SEC-001-05` · `SEC-001-06` · `SEC-001-07` · `AUTH-002-01` · `AUTH-002-03` · `DATA-001-03` |
| 참조 데이터 | [`MDL-004`](../datas/model_MDL-004-006.md) · [`MDL-005`](../datas/model_MDL-004-006.md) · [`MDL-006`](../datas/model_MDL-004-006.md) |
| 관련 IA 항목 | `USR-03` · `USR-02` · `API-04` |

### 시그니처

```
function FN-004 (
  encPair: MDL-004,         // 암호값 쌍·필수
  birthDate: string(6),     // 생년월일 `yyMMdd`·필수·FN-005 로 형식을 먼저 통과시킨다
): MDL-005                  // 복원된 전달 데이터 X
  throws ProtocolFormatError    { code: EX-SEC-001,  http: 400 }
       | IdentityMismatchError  { code: EX-AUTH-002, http: 400 }
       | ProtocolViolationError { code: EX-SEC-002,  http: 400 }
```

### 입력/출력 정의

| 구분 | 항목명 | 데이터 타입 | 필수 | 제약 | 설명 |
|------|--------|------------|------|------|------|
| 입력 | encPair | MDL-004 | Y | FN-003 판정을 통과해야 한다 | 발송처가 만든 암호값 쌍 |
| 입력 | birthDate | string(6) | Y | `^\d{6}$` (`AUTH-002-02`) | 복호화의 나머지 키. 인증 자격이 아니다 |
| 출력 | payload | MDL-005 | - | `trackingKey` 필드를 갖는 JSON 객체 | 복원된 전달 데이터. 호출 처리 종료와 함께 폐기한다 |

### 처리 흐름 (의사코드)

```
0. 구조 판정 — FN-003 (validate)
   cipher = FN-003(encPair)                       // 실패 시 EX-SEC-001 그대로 전파

1. encY 키 산출 — POL SEC-001-06 · SEC-001-03 · SEC-001-04 (transform)
   keyY = FN-001(birthDate)                       // 6바이트 + `_` 26개로 정규화된다

2. 판정 1단계 — encY 복호화 · POL SEC-002-01 ① (validate)
   try  keyXBytes = AES256_CBC_PKCS7_DECRYPT(cipher.y, keyY.key, keyY.iv)
   catch (패딩 검증 실패·복호화 실패)               → throw EX-AUTH-002 (400)
   if (LENGTH(keyXBytes) != 32)                   → throw EX-AUTH-002 (400)

3. encX 초기화 벡터 도출 — POL SEC-001-07 · SEC-001-04 (transform)
   ivX = keyXBytes[0 .. 15]                       // 재정규화하지 않는다

4. 판정 2단계 — encX 복호화 · POL SEC-002-01 ② (validate)
   try  plain = AES256_CBC_PKCS7_DECRYPT(cipher.x, keyXBytes, ivX)
   catch (패딩 검증 실패·복호화 실패)               → throw EX-AUTH-002 (400)

5. 판정 3단계 — UTF-8 JSON 파싱 · POL SEC-002-01 ③ · SEC-002-03 (validate)
   try  payload = JSON_PARSE(UTF8_TEXT(plain))
   catch (UTF-8 해석 실패·JSON 구문 오류)          → throw EX-SEC-002 (400)
   if (payload 가 객체가 아니다)                    → throw EX-SEC-002 (400)

6. 판정 4단계 — 추적 키 검증 · POL SEC-002-01 ④ · SEC-002-03 (validate)
   if (!FN-006(payload.trackingKey))              → throw EX-SEC-002 (400)

7. 중간 값 폐기 — POL DATA-001-03 (transform)
   keyY · keyXBytes · ivX · plain 을 지역 값으로만 두고 호출 처리 종료와 함께 버린다

8. 반환
   return payload
```

### 에러 처리 (에러 코드 카탈로그)

| HTTP status | EX 코드 | 발생 조건 | 사용자 메시지 | 개발자 노트 |
|-------------|---------|-----------|---------------|-------------|
| 400 | `EX-SEC-001` | 단계 0 구조 판정 실패(FN-003 전파) | "연동 링크가 올바르지 않습니다." | 결과 구분 미확정. 진입 단계 실패와 같은 취급(`SEC-002-02`) |
| 400 | `EX-AUTH-002` | 단계 2·4 실패 — 생년월일 불일치와 구별되지 않는다 | "입력하신 생년월일로 확인되지 않았습니다. 다시 확인해 주세요." | **결과를 확정하지 않고 재입력 안내**(`SEC-002-04`·`BIZ-001-05`). 추적 레코드·지표 갱신 없음. 횟수 제한 없음(`AUTH-002-04`) |
| 400 | `EX-SEC-002` | 단계 5·6 실패 — X JSON 파싱 실패·`trackingKey` 부재·형식 위반 | "연동 요청 정보가 규약과 맞지 않습니다." | 발송처 페이로드의 규약 위반 → 결과 구분 `DECRYPT_FAILED`(`SEC-002-03`). 추적 키를 알 수 없어 레코드는 만들지 않는다(`BIZ-002-02`) |

- **응답에는 EX 코드만 싣는다.** 어느 단계에서 실패했는지의 단계 번호는 내부 사유로만 유지하고 응답·로그에 담지 않는다(`SEC-002-05`).
- **복호화 원문·키·초기화 벡터·중간 값을 어떤 응답에도 담지 않는다**(`DATA-001-04`). 자가진단 응답에도 담지 않는다(`SEC-003-03`).

### 판정 경계에 대한 확정 사항

1. **단계 2 에서 32바이트가 아닌 평문을 얻으면 `EX-AUTH-002`** 로 다룬다. `SEC-002-01` ① 이 "32바이트 키 획득"까지를 1단계로 규정하므로, 길이 불일치는 1단계 실패다. 잘못된 생년월일이 패딩 검증을 통과했으나 키 길이가 맞지 않는 경우가 여기에 해당한다.
2. **X 평문 크기 상한(`SEC-001-09`)은 본 기능이 검사하지 않는다.** `SEC-001-09` 의 위반 시 처리가 **라이브러리 예외와 허브 자가진단**만 지정하고 있고, 서비스 도메인의 예외 사용 매핑도 `EX-SEC-004` 를 `SVC-001`·`SVC-006`·`SVC-007`·`SVC-013` 에만 배정한다. 상한의 목적인 URL 길이 억제는 진입 시점의 `SEC-001-10` 판정이 이미 담당한다. 자가진단은 규약 적합성 판정이 목적이므로 본 기능 반환 후 `PROC-204` 가 크기 상한을 별도로 검사한다([`spec-functions-api-server.md`](spec-functions-api-server.md) §연동 규약 자가진단 API).
3. **승인 시점의 재복호화도 같은 기능을 쓴다**(EXC-SEC-07·`BIZ-002-06`). 본인확인에서 얻은 X 를 요청 사이에 보관하지 않고 다시 복원하므로, 이 기능은 한 연동에서 최소 두 번 호출된다.

### 의존 기능

| FN 코드 | 호출 시점 | 동기/비동기 | 실패 시 처리 |
|---------|----------|------------|--------------|
| FN-003 | 단계 0 | 동기 | `EX-SEC-001` 전파 |
| FN-001 | 단계 1 | 동기 | 예외 없음 |
| FN-006 | 단계 6 | 동기 | 판정 `false` → `EX-SEC-002` 로 변환해 던진다 |

- FN-002 는 FN-003 을 거쳐 간접 호출된다. 순환 의존이 없다(FN-004 → FN-003 → FN-002, FN-004 → FN-001, FN-004 → FN-006).

### 구현 가이드

- **세 경로가 같은 절차를 공유한다.** 본인확인(`PROC-102`)·연동 실행(`PROC-104`)·자가진단(`PROC-204`)이 서로 다른 판정을 쓰면 자가진단의 존재 의의가 사라진다(`SEC-002` 구현 가이드).
- **패딩 검증을 끄지 않는다.** 패딩 검증이 잘못된 키를 걸러 내는 1차 판정 수단이며, 이것을 끄면 `EX-AUTH-002` 와 `EX-SEC-002` 의 경계가 무너진다.
- **`encY` 복호화 결과를 재정규화하지 않는다**(`SEC-001-07`). 허브는 발송처키를 갖지 않아 `encX` 키를 직접 만들 수 없고, 항상 이 결과를 그대로 쓴다(EXC-SEC-04).
- 복호화 결과는 **지역 값으로만** 다루고 전역 상태·요청 컨텍스트 저장소·세션·캐시에 넣지 않는다(`DATA-001-02`·`DATA-001-03`).
- `trackingKey` 를 제외한 나머지 필드는 **해석·검증하지 않는다**(`BIZ-004-05`·`DATA-004-01`). 발송처가 필드를 늘려도 허브를 고치지 않아야 한다.
- 대상 런타임의 표준 대칭 암호 기능만으로 성립하는 조합이므로 별도 암호 라이브러리를 강제하지 않는다.
