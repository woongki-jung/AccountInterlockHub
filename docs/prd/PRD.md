# 방향 정의서 (PRD) — AccountInterlockHub

본 문서는 AccountInterlockHub 프로젝트의 방향(무엇을·왜)을 정의하는 directing 단계 산출물이다. 상세 요구사항·사양은 이후 spec 단계가 본 문서를 입력으로 작성한다. 추적 일감: `accountinterlockhub#468`.

- 정보 구조(IA): [`ia/IA.md`](ia/IA.md)
- 개발사양: [`devspec/infra.md`](devspec/infra.md) · [`devspec/database.md`](devspec/database.md) · [`devspec/external-apis.md`](devspec/external-apis.md)
- 연동 구성 상수: [`CLAUDE.env.md`](../../CLAUDE.env.md) §연동 구성 상수

## 제품 정의 (한 줄)

**하나의 발송처와 하나의 수신처 사이에 고정된 1:1 사용자 연동**을, 발송처가 암호화해 전달한 값을 **사용자 동의·본인확인(생년월일)으로 복원**해 중개하는 단일 서비스. 연동 구성은 **배포 시점 상수**로 고정하고, 발송처가 쓸 **암호화·요청 URL 생성 라이브러리**를 함께 제공한다. 허브는 사용자 정보를 **지속 보관하지 않는다**.

## 목적·배경

- 개인정보를 지속 보관하지 않고 운영되는 B2B 솔루션(이하 '서비스 A')의 **회원 식별 정보**를, 지정된 외부 서비스(이하 '서비스 B')와 연동해야 한다.
- 연동 대상이 **하나로 고정**되어 있으므로, 연동을 런타임에 구성·변경하는 장치(관리자 화면·구성 저장소)는 서비스가 감당할 가치보다 비용·공격면이 크다. 구성을 **배포 시점 상수**로 고정해 서비스를 단순화한다.
- 발송처가 암호화 규약을 매번 직접 구현하면 통합 비용과 규약 이탈 위험이 크다. 허브가 **암호화·요청 URL 생성을 수행하는 라이브러리**를 제공해 발송처의 통합 부담을 없앤다.
- 전달 값의 기밀성은 **단일 암호화 JSON + 사용자 본인확인(생년월일)** 결합으로 확보한다.

## 목표

- 서비스 A의 회원을 서비스 B와 연동하는 과정을, **관리자 조작 없이** 배포된 상수 구성만으로 안정적으로 수행한다.
- 발송처가 **라이브러리 호출만으로** 연동 요청 URL을 만들 수 있게 해, 규약 문서 해석·자체 구현 없이 통합을 마치게 한다.
- 연동 중개 과정에서 **사용자 정보를 보관하지 않고**(복호화한 원문 포함 미저장), 추적에 필요한 최소 기록만 한시적으로 남긴다.
- 저장 구조·구성 요소를 **연동 1건 단위로 단순화**해 운영 비용을 낮춘다.

## 서비스 이용 대상

1. **발송처 (서비스 A 운용사 · 연동 요청 주체)** — 전달 데이터(X)를 만들고, 허브가 제공한 **연동 라이브러리**로 암호화·요청 URL 생성을 수행해 사용자를 허브로 유도한다. 이후 처리 상태·완료 여부를 서버 대면 API로 조회한다.
2. **수신처 (서비스 B 운용사 · 연동 대상)** — 허브가 전달한 사용자 키로 회원 여부를 판단해 자체 서비스에 연결하고, 처리 완료를 허브에 콜백으로 통지한다.
3. **사용자 (서비스 A의 고객)** — 발송처가 전달한 링크로 진입해 **생년월일을 입력**하고, 동의 항목을 확인한 뒤 연동을 승인하거나 거부한다.

> 허브 운영자는 서비스 이용 대상이 아니라 **배포 주체**다. 연동 구성 변경은 화면 조작이 아니라 상수 갱신·재배포로 이뤄진다(§시스템 제약사항).

## 제공 가치

- **구성 없는 운용**: 연동 대상이 고정이므로 운영 중 구성 조작이 필요 없다. 관리자 화면·구성 저장소·관리자 인증이 없어 운영 부담과 공격면이 함께 줄어든다.
- **통합 부담 없는 발송처 연동**: 발송처는 암호화 규약을 구현하지 않고 **연동 라이브러리 호출**로 암호값과 요청 URL을 얻는다. 라이브러리는 **Delphi 프로젝트와 C# 프로젝트 양쪽**에서 그대로 호출할 수 있다.
- **암호화 전송 + 본인확인**: 전달 데이터는 이중 암호화(encX/encY)되어 전달되고 **사용자의 생년월일 입력으로만 복원**된다. 허브는 값을 저장하지 않고 연동 실행 시점에만 복호화한다.
- **동의 기반 투명성**: 사용자가 어떤 항목에 동의하는지 화면에서 확인하고 스스로 승인·거부를 결정한다.
- **처리 추적**: 발송처가 연동 추적 키로 처리·결과 확인·수신처 완료 여부를 조회할 수 있다.

## 성과 지표

각 지표의 산출 근거를 함께 정한다 — 추적 레코드는 보관 기간이 지나면 삭제되므로, 삭제 이후에도 지표를 낼 수 있는 근거가 필요하다.

| 지표 | 정의 | 산출 근거 |
|---|---|---|
| 서비스 사용량 | 기간 내 연동 처리 요청 건수 | 연동 추적 레코드 |
| 연동 성공률 | 연동 요청 대비 정상 복호화·전달·완료 비율 | 연동 추적 레코드의 결과 구분 |
| 발송처 통합 소요 | 발송처가 라이브러리를 받아 첫 연동 요청을 성공시키기까지 걸린 기간 | 발송처 통합 기록(수기) |

- 목표 수치는 담당자 확정 대기 항목이다(§미결·확인 필요).
- 앞의 두 지표는 추적 레코드가 보관 기간 경과로 삭제되면 산출 근거를 잃는다. 삭제 이후의 지표 보존 방법도 확정 대기 항목이다(§미결·확인 필요).

## 수행 범위

### 포함

1. **연동 구성 상수화**: 사용자 진입 경로·수신처(B) 전달 주소·사용자 노출 동의 항목·보관 기간을 [`CLAUDE.env.md`](../../CLAUDE.env.md) §연동 구성 상수를 단일 출처로 고정하고, 배포 시점에 애플리케이션 설정으로 주입한다.
2. **암호화 연동 규약 (허브 정의)**: 전달 데이터 X(JSON) → `encX`·`encY` 이중 암호화 규약을 정의한다. 이 규약은 **연동 라이브러리(암호화)와 허브(복호화)가 공유하는 단일 계약**이다. 상세 [`devspec/external-apis.md`](devspec/external-apis.md).
3. **연동 라이브러리 (발송처 제공)**: 발송처의 Delphi·C# 프로젝트에서 호출할 수 있는 라이브러리로 **데이터 암호화**와 **연동 요청 URL 생성**을 제공한다.
4. **사용자 진입·본인확인·동의·승인**: 발송처 링크로 진입, 생년월일 입력, 상수로 고정된 동의 항목 노출·동의 후 승인 또는 거부.
5. **연동 실행 (복호화·전달)**: 승인 시 허브가 생년월일로 복호화해 X를 얻고, 상수로 고정된 수신처(B) 주소로 전달한다.
6. **연동 결과 안내**: 완료·거부·링크 오류 등 결과를 사용자에게 표시한다.
7. **처리상태 확인 API · 연동 완료 확인 API · 완료 콜백 API**: 발송처의 상태·완료 조회와 수신처의 완료 통지.
8. **연동 추적 기록·보관**: 연동 추적 키 기준 **단일 추적 레코드**를 **사용자가 진입한 시점에 생성**하고, 승인·거부·복호화 결과·수신처 전달 결과·완료 콜백을 같은 레코드에 이어 기록한다. 일 단위 배치로 보관 기간 경과분을 삭제한다.

### 제외

- **연동 구성의 런타임 변경** — 관리자 화면·구성 저장소·관리자 인증을 두지 않는다. 구성 변경은 상수 갱신·재배포로만 이뤄진다.
- **다중 연동** — 복수 발송처·복수 수신처 구성, 연동 추가 절차는 다루지 않는다.
- **사용자 정보·복호화 원문의 지속 보관** — 허브는 사용자 정보와 복호화한 전달 데이터(X) 원문을 저장하지 않는다(추적 레코드의 추적 키값은 예외).
- **암호화 키(발송처키)의 생성·배포·관리** — 발송처키의 생성·보관은 발송처 소관이다. 허브는 규약과 라이브러리를 제공한다.
- **전달 데이터(X)의 업무적 유효성 판단** — 허브는 규약대로 복호화·중개하되 X 내용의 업무 신뢰성은 판단하지 않는다.
- **보안 강화 기능** — 링크 만료(TTL)·1회성 사용·발송처 서명 검증은 이번 범위에서 다루지 않는다(§미결·확인 필요).

## 우선순위

암호화 규약은 연동 라이브러리와 허브가 함께 구현하는 공유 계약이므로 **모든 작업의 선행 조건**이다. 규약 확정 이후는 다음 순서를 따른다.

1. **사용자 연동 본체** — 상수 기반 진입, 본인확인·동의·승인, 복호화·수신처 전달, 결과 안내. 제품의 핵심 가치가 여기서 성립한다.
2. **연동 라이브러리** — 발송처의 통합 수단. 1과 동일 규약의 반대 방향(암호화)을 구현하므로 1의 규약 확정에 의존한다.
3. **연동 API·추적 기록·보관 배치** — 연동 실행 이후의 조회·통지·정리.

## 시스템 제약사항

- **기술 스택**: 백엔드 NestJS(API) + 프런트엔드 ReactJS, 기본 언어 TypeScript. 연동 라이브러리는 별도 스택이다(§프로그램 구성·기술스택·검증 방법). 상세 [`devspec/infra.md`](devspec/infra.md).
- **배포 형태**: ReactJS 정적 빌드를 NestJS가 정적 콘텐츠로 서빙해 **하나의 Azure App Service**로 배포한다. 연동 라이브러리는 발송처에 **파일로 배포**되며 App Service 배포 단위에 포함되지 않는다.
- **연동 구성 = 배포 시점 상수**: 진입 경로·수신처 전달 주소·동의 항목·보관 기간은 [`CLAUDE.env.md`](../../CLAUDE.env.md) §연동 구성 상수가 단일 출처이며, 값 변경은 **재배포**로만 반영된다. 런타임 변경 수단을 두지 않는다.
- **공개 표면**: 사용자 진입 경로와 서버 대면 API만 외부에 노출된다. 관리자 경로·관리자 인증·IP 기반 접속 제한은 두지 않는다.
- **데이터 원칙**: 허브는 사용자 정보·복호화 원문(X)을 지속 보관하지 않는다. 복호화는 **연동 실행 시점에 메모리 상에서만** 수행하고 전달 후 폐기한다. 저장은 **연동 추적 키 기준 단일 추적 레코드**로 한정하며 보관 기간 경과분은 일 배치로 삭제한다. 상세 [`devspec/database.md`](devspec/database.md).
- **암호화·복호화 규약 대칭**: 연동 라이브러리가 암호화하고 허브가 복호화한다. 두 구현은 **같은 규약의 양쪽**이므로 규약이 바뀌면 함께 바뀌어야 한다. 상세 [`devspec/external-apis.md`](devspec/external-apis.md).
- **연동 라이브러리 호출 호환성**: 발송처의 **Delphi·C# 프로젝트에서 모두 호출 가능**해야 한다. 이 제약이 라이브러리 형태·기술스택 선택을 규정한다.
- **보안 강도 한계(알려진 제약)**: 두 가지를 수용 대상으로 명시한다. 강화는 후속 보완 항목이다(§미결·확인 필요).
	- **기밀성** — `encX`·`encY`가 URL 파라미터로 노출되고 생년월일(yyMMdd)은 경우의 수가 작아, 링크와 암호값을 확보한 자가 오프라인 전수대입으로 원문을 복원할 수 있다.
	- **무결성·출처** — 허브는 발송처키를 갖지 않아 진입한 요청이 정당한 발송처에서 왔는지 검증하지 못한다. 규약대로 만든 암호값이면 출처와 무관하게 복호화·중개된다.
- **데이터베이스**: PostgreSQL. 운영은 Azure Database for PostgreSQL, 개발·로컬은 별도 PostgreSQL 서버.
- **신뢰 위임**: 발송처키의 관리와 전달 데이터의 업무적 유효성은 발송처(서비스 A)가 책임진다.

## 프로그램 구성·기술스택·검증 방법

서비스를 이루는 프로그램과 각 기술스택·검증 방법(qa 케이스)이다. qa 단계가 이 표로 프로그램별 검증 케이스를 선택한다([`qa-execution.md`](../../ai/strategies/qa-execution.md) §케이스 선택).

| 프로그램 | 기술스택 | 검증 방법(qa 케이스) |
|---|---|---|
| 사용자 웹 (진입·본인확인·동의·승인·결과) | ReactJS(TS) + NestJS 정적 서빙 | 웹·SPA UI |
| 백엔드 API 서버 (복호화·전달·상태/완료/콜백 API) | NestJS(TypeScript) | API·서버 |
| 보관 배치 | NestJS 스케줄 작업 | CLI·배치 |
| 연동 라이브러리 (암호화·요청 URL 생성) | 네이티브 라이브러리(C 호출 규약 내보내기) — Delphi·C# 공용 | **미확정** — 케이스 카탈로그에 대응 항목 없음 |

- 사용자 웹·API·배치는 **단일 App Service**로 배포되는 하나의 애플리케이션 안에 함께 구성된다(배포 단위 1개, 논리 프로그램 3종).
- 연동 라이브러리는 **별도 배포 단위**다 — 발송처에 파일로 전달되며 허브 애플리케이션과 함께 배포되지 않는다.
- **연동 라이브러리의 검증 방법은 확정되지 않았다.** 이 프로그램은 명령 실행·종료 코드로 검증하는 대상이 아니라 **호출하는 쪽의 언어에서 함수를 부르는** 대상이라, 기존 케이스 카탈로그([`qa-execution.md`](../../ai/strategies/qa-execution.md) §케이스 카탈로그)의 어느 항목에도 맞지 않는다. 검증에는 **Delphi·C# 양쪽 호출 하네스**와 **암호화·복호화 왕복 대조**가 필요하다. 케이스 신설 여부와 Delphi 검증 환경 확보는 담당자 확정 대기 항목이다(§미결·확인 필요). 확정 전까지 이 표는 qa 케이스 선택 입력으로 완결되지 않는다.
- 보관 배치는 인앱 스케줄 작업이므로, CLI·배치 케이스를 적용하려면 **수동 실행 진입점**이 필요하다. 진입점 제공 여부는 spec 단계에서 확정한다.

## 미결·확인 필요

담당자 확정이 필요한 항목이다. 확정 전에는 각 항목의 기본안으로 진행한다. **굵게 표시한 5건은 기본안 없이 담당자 결정이 있어야 진행할 수 있다.**

### 보안·리스크 수용

1. **서버 대면 API의 인증 여부** — 관리자 경로가 없어져 접근 통제 수단이 남지 않았다. 처리상태 확인·연동 완료 확인·완료 콜백 세 API에 인증을 둘지 결정이 필요하다. **인증을 두지 않으면 추적 키를 아는 누구나 조회할 수 있고, 완료 통지도 위조할 수 있다.** 인증을 둔다면 자격 값의 보관 위치도 함께 정해야 한다(비밀 값이라 `CLAUDE.env.md` 대상이 아니다).
2. **무결성·출처 리스크의 수용 여부** — 허브가 발송처를 검증하지 못하므로 규약대로 만든 암호값이면 출처와 무관하게 수신처로 중개된다(§시스템 제약사항). 이 수준을 이번 범위에서 수용하는지 확인이 필요하다.
3. **요청 제한의 범위 포함 여부** — 공개된 진입 경로·API에 과부하·반복 시도 제한을 둘지 결정이 필요하다. 포함한다면 대상·임계값도 함께 정한다.
4. **동의 증적의 보존 필요 여부** — 동의 항목이 상수라 배포에 따라 바뀌는데, 사용자가 **어느 시점의 어떤 항목에 동의했는지**를 남기지 않으면 사후 입증이 불가능하다. 보존이 필요하면 무저장 원칙에 예외를 두어야 한다.
5. **보안 이벤트 기록의 유지 여부** — 사용자 연동 경로의 보안 이벤트(복호화 실패·전달 차단 등)를 남길지 결정이 필요하다. 남긴다면 "저장 대상은 추적 레코드 하나"라는 원칙에 예외를 명시해야 한다. 기본안: 남기지 않는다.
6. **보안 강화(후속 보완)** — 링크 만료(TTL)·1회성 사용·발송처 서명 검증은 이번 범위 밖이며 후속 반영 대상이다.

### 연동 구성·상수

7. **발송처키의 위치** — "전체 상수화" 지시를 따르면 발송처키도 상수 대상이 되나, 발송처키는 **비밀 값**이라 git 관리 문서인 `CLAUDE.env.md`에 둘 수 없다. 기본안: 발송처키는 상수화 대상에서 **제외**하고 비밀 값 관리 경로로 분리한다(허브는 복호화에 발송처키가 필요하지 않으므로 허브 측 보관 자체가 불필요하다).
8. **사용자 진입 경로의 식별자** — 연동이 1:1로 고정되면 발송처를 구분하던 진입 식별자는 정보를 담지 않는다. 기본안: **식별자 구간을 두지 않고** 고정 진입 경로를 쓴다.
9. **상수 값의 확정 시점** — [`CLAUDE.env.md`](../../CLAUDE.env.md) §연동 구성 상수의 미정 값 가운데 **동의 항목·동의 안내 문구는 사용자 화면 사양의 직접 입력**이라 spec 진입 전에 확정돼야 한다. 수신처 전달 주소·허브 기준 URL은 외부사 협의가 필요할 수 있어 확정 시점을 별도로 정한다.

### 데이터·추적

10. **연동 추적 키의 생성 주체와 유일성** — 기본안: 발송처가 만들어 전달 데이터(X)에 담고, 라이브러리는 생성을 강제하지 않는다. 단일 레코드 통합은 **키가 연동 1건마다 유일**하다는 전제 위에 서므로, 유일성 책임과 같은 키가 다시 들어왔을 때의 동작을 함께 정해야 한다.
11. **결과 확인이 오지 않는 레코드의 삭제 상한** — 보관 기간이 "결과 확인 완료 후 3개월"뿐이면 발송처가 조회하지 않은 레코드는 삭제되지 않는다. 기본안: 생성 후 절대 상한을 두어 결과 확인 여부와 무관하게 삭제한다(기본값 6개월).
12. **보관 기간** — 기본안: 결과 확인 완료 후 3개월.
13. **연동 완료 확인과 처리상태 확인의 통합 여부** — 저장이 단일 추적 레코드로 합쳐지면 두 조회 API가 같은 레코드를 본다. 기본안: **두 API를 그대로 유지**한다(발송처의 호출 시점·의미가 다르다).
14. **성과 지표의 목표 수치와 보존 방법** — 목표치가 정해지지 않았고, 추적 레코드가 삭제되면 사용량·성공률의 산출 근거가 사라진다(§성과 지표).

### 연동 라이브러리

15. **구현 기술스택·빌드 환경** — Delphi·C# 공용 제약을 만족하는 기본안은 **C 호출 규약으로 내보내는 네이티브 라이브러리**다. 구현 언어·대상 플랫폼(32/64비트)·빌드 도구·배포 구성(래퍼·샘플 동봉 범위) 확정이 필요하다. 이 스택은 허브(TypeScript)와 완전히 달라 **빌드 환경을 새로 갖춰야 한다.**
16. **검증 방법과 Delphi 검증 환경** — 라이브러리에 맞는 qa 케이스가 카탈로그에 없다(§프로그램 구성·기술스택·검증 방법). 케이스를 신설할지, 그리고 **Delphi 호출 검증 환경을 제공 가능한지** 확인이 필요하다(불가하면 Delphi 호출 검증은 수행할 수 없다).
17. **암호화 규약 세부** — 블록 모드·키 32바이트 정규화·패딩·IV 규칙·`encX` 전달 형식(URL 길이 한계)은 spec 단계에서 확정한다. 확정값은 라이브러리와 허브 양쪽 구현의 단일 출처가 된다.
