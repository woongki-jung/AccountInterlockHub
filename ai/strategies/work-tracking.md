# 업무 티켓 관리 전략

본 문서는 담당자 요청부터 완료까지 업무 1건의 **생애주기를 Redmine 이슈(정본)로 단계 횡단 추적**하는 정책을 정의한다. 접속·식별자·프로젝트 생성 등 운영 세부는 하위문서 [`work-tracking-redmine.md`](work-tracking-redmine.md) 가 담당한다.

- **정본 = Redmine 이슈** — 업무 단위마다 Redmine 프로젝트를 두고(요청·작업 = 이슈), 담당자는 Redmine 에서 진행을 직접 조회한다.
- **산출물 원본은 워크스페이스 파일** — 사양·코드·목업의 정본(SoT)은 `docs/`·`apps/`·`mockup/` 등 워크스페이스 파일이다. Redmine 일감은 그 작업을 **추적·공유**하고 산출물 내용을 **미러링**한다(§단계별 미러링).
- 세션 대화·디스패치는 휘발성이므로, 접수·진행의 영속 기록은 이슈가 담당한다.

## 프로젝트·이슈 구조

- **Redmine 프로젝트 = 업무 단위 1개** — 제품 프로젝트는 1:1 로 생성하고(절차 [`work-tracking-redmine.md`](work-tracking-redmine.md) §프로젝트 생성 표준 절차), 워크스페이스 운영·메타 업무는 운영 프로젝트(`ai-workgroup-ops`)에서 추적한다.
- **이슈 1건 = 작업 1건** — 한 요청이 종류·범위에 따라 여러 일감으로 나뉠 수 있다([`ai-pm.md`](ai-pm.md) §디스패치 계약). 단계가 넘어가도 같은 작업은 같은 이슈를 유지한다.
- **작업세션 이슈 = 업무 트리의 루트** — 그 업무에서 파생된 모든 일감(그룹·사양·기능·오류·검증·목업·report)은 작업세션 이슈의 하위 계층에 둔다. **프로젝트 루트에 일감을 만들지 않는다**(§계층·연관).
- **연관·계층으로 연결** — 상위-하위 이슈로 업무 소속을, 일감 관계(연관)로 사양↔구현↔검증의 근거를 잇는다(§일감 유형·계층).
- **이슈 범주 = IA 노드** — 이슈가 어느 IA 노드(서비스 제공 기능단위)에 속하는지 Redmine **카테고리**로 표시한다([`ia.md`](ia.md)). 작업 범위 선별·이력이 같은 IA 좌표로 정렬된다.

## 일감 유형 (트래커)

작업 종류를 트래커로 구분한다. 숫자 id·생성 방법은 [`work-tracking-redmine.md`](work-tracking-redmine.md) 가 관리한다(인스턴스를 재구축해도 정책은 유지).

| 트래커 | 용도 |
|---|---|
| **그룹** | 업무 묶음·부모(우산) 일감, 워크스페이스 ops·메타 |
| **오류** | 결함·장애 해소 |
| **기능** | 기능·구현 작업 (build Phase 미러) |
| **사양** | 사양정의서(`docs/specs/`)의 Redmine 미러 (spec 산출) |
| **검증** | 검증 TC — 검증 대상 일감의 **하위 이슈**로 등록 (qa) |
| **report** | 완료된 작업의 수행 이력 요약 보고 (§작업 보고) — 산출이 아니라 **기록**이므로 다른 일감의 진행을 좌우하지 않는다 |

### 계층·연관

**모든 산출 일감은 그 업무의 작업세션 이슈를 뿌리로 하는 하나의 트리에 속한다.** 프로젝트 루트에 일감을 만들지 않는다 — 루트는 담당자가 여는 **작업세션 이슈뿐**이다. 업무 1건에 딸린 일감이 목록에서 흩어지지 않고, 작업세션 이슈 하나만 열면 그 업무의 전모가 계층으로 보인다.

```
작업세션 (담당자 생성) ─ 업무 1건의 루트
├─ 그룹 (제품 루프 우산)
│  ├─ 사양 (spec)
│  ├─ 기능 (build Phase)
│  │  └─ 검증 (qa TC)
│  ├─ 오류 (qa Fail·유지보수 결함)
│  ├─ 목업
│  └─ report (레그)
├─ directing 산출 일감
└─ report (세션)
```

- **부모 지정은 생성 시점의 필수 항목이다** — `parent_issue_id` 를 반드시 담아 생성하고, 생성 직후 `GET` 으로 `parent` 를 실측 확인한다([`work-tracking-redmine.md`](work-tracking-redmine.md) §이슈 조작). 빠뜨려도 Redmine 은 오류를 내지 않고 **루트 일감으로 만들어 버리므로**, 실측하지 않으면 누락을 알아채지 못한다([`work-tracking-redmine.md`](work-tracking-redmine.md) §도구 함정).
- **그룹 일감 = 작업세션의 하위.** 업무 단위의 우산이며, **제품 루프는 이 그룹 일감을 루프 우산**으로 삼아 spec·build·qa 산출 일감을 묶는다. 제품 루프 오케스트레이터가 그 상태로 루프 위치를 판독한다([`../agents/product-loop.md`](../agents/product-loop.md)).
- **사양·기능·오류·목업 일감 = 그룹의 하위.** 그룹 일감이 없는 작업(directing·운영/메타)은 **작업세션 직속**으로 둔다.
- **검증 일감 = 검증 대상(기능 등) 일감의 하위.** 대상 일감을 특정할 수 없으면 그룹 직속으로 둔다.
- **report 일감 = 보고 대상의 하위** — 세션 report 는 **작업세션 이슈**의, 레그 report 는 **루프 그룹 일감**의 하위다. **등록과 동시에 `완료`(닫힘)** 이므로(§등록 규칙) 부모를 닫을 때 열린 하위로 걸리지 않는다.
- **연관은 계층과 별개다** — build·qa 일감은 참조한 **사양 일감**을 연관 일감(relations)으로 추가해 사양↔구현↔검증을 잇는다([`stages/build.md`](stages/build.md)·[`stages/qa.md`](stages/qa.md)). 계층은 "어느 업무에 속하는가", 연관은 "무엇을 근거로 삼는가"를 나타낸다.
- **qa 단계에서 🔴 Fail 판정된 TC 는 검증 실행 주체가 `오류` 일감을 생성**한다 — 그룹(없으면 작업세션) 하위에 두고 해당 검증·사양 일감을 연관으로 단다. 결함이 일감으로 남아 후속 처리·유지보수 경로([`delivery.md`](delivery.md))로 이어진다. build 단계 내부 회귀(Phase 루프)는 오류 일감 없이 해당 기능 일감 노트로 기록한다.
- **깊이가 곧 닫기 사슬이다** — 하위가 열려 있으면 부모를 닫을 수 없으므로(§닫을 때 지킬 것), 계층을 위 4단계보다 깊게 늘리지 않는다.

## 단계별 미러링

각 단계 산출물을 일감으로 미러링한다. 원본 정본은 워크스페이스 파일이고 일감은 그 사본·추적이다(원본 갱신 시 일감 갱신). 단계별 상세는 각 stages 문서가 정본.

| 단계 | 미러 단위 → 일감 | 상위 일감(부모) | 상태 동기화 |
|---|---|---|---|
| spec | 도메인별 사양정의서 1건 → **사양** 일감 1건 | 그룹 | 작성·확정 |
| build | Phase 1건 → **기능** 일감 1건 | 그룹 | 진척(작성→리뷰→검증→완료) |
| qa | 검증 TC 1건 → **검증** 일감 1건 | 검증 대상(기능 등) | 검증 결과(5종 판정) |

directing 작업 자체도 이슈로 추적한다 — 그룹 일감을 두지 않으므로 산출 일감을 **작업세션 직속 하위**로 등록한다([`stages/directing.md`](stages/directing.md)).

## 작업 보고 (report)

완료된 작업의 **수행 이력을 사람이 읽는 서술로 남긴다.** 일감·노트는 작업 단위로 흩어져 있어 "그래서 무엇을 했고 무엇이 남았는가"가 한눈에 안 보이므로, 그 답을 `report` 트래커 일감 1건으로 모은다. 산출물 정본이 아니라 **기록**이므로 다른 일감의 진행·승인을 좌우하지 않는다.

### 2계층 — 레그 report · 세션 report

| 구분 | 주체 | 시점 | 상위 일감(부모) |
|---|---|---|---|
| **레그 report** | spec·build·qa **단계 오케스트레이터**(자기 레그) | 자기 레그 산출을 마치고 다음 레그로 넘기기 직전 | 제품 루프 **그룹 일감** |
| **세션 report** | **`session-reporter`**(ai-pm 이 디스패치 — [`../agents/session-reporter.md`](../agents/session-reporter.md)) | **작업세션 이슈를 종결**(`완료`·`거절`)하기 직전 | 해당 **작업세션 이슈** |

- **세션 report 가 공백을 메운다** — 단계 오케스트레이터가 없는 작업(directing·운영/메타 작업)은 레그 report 가 생기지 않는다. 세션 report 는 작업세션 이슈 단위라 그 경우에도 반드시 남는다.
- **중복이 아니라 층위가 다르다** — 레그 report 는 그 레그의 상세(무엇을 만들었고 어떤 판정이 났는지), 세션 report 는 업무 1건의 종합(요청부터 종결까지의 경위·결정·잔여)이다. 세션 report 는 같은 내용을 옮겨 적지 말고 **레그 report 를 인용**한다.
- **작성 주체가 4종이므로 양식은 아래 하나로 강제한다** — 주체마다 서술 구조가 갈리면 보고를 모아 읽을 수 없다.

### 본문 양식

```markdown
**대상**: <작업세션 이슈 / 그룹 일감 번호> · **주체**: <에이전트명> · **구간**: <착수>~<종료>

## 1. 요청과 결론
<무엇을 요청받아 어떻게 끝났는지 3~5줄. 이 절만 읽어도 결과를 알 수 있게 쓴다>

## 2. 수행 경과
<시간 순 주요 단계. 되돌아간 지점·회귀가 있었으면 그 사유를 포함한다>

## 3. 산출물
<생성·변경된 산출물과 그 위치(일감 번호·브랜치·commit). 링크로 건다>

## 4. 담당자 결정 사항
<진행 중 담당자가 내린 결정과 그 근거 위치(이슈·노트). 없으면 "없음">

## 5. 잔여·후속
<남은 작업·미결·후속 권고. 없으면 "없음">

## 6. 실행 프로파일
<서브에이전트별 호출 횟수(등급 병기)·회귀 횟수. 직접 수행분은 "직접". 소비량을 실측으로 아는 경우에만 함께 적는다>
```

- **1절은 결론부터** — 담당자가 이 절만 읽고 판단할 수 있어야 한다([`prompt-conversation.md`](prompt-conversation.md) §응답 구성).
- **경위를 미화하지 않는다** — 실패·회귀·오판이 있었으면 그대로 적는다. 보고의 목적은 다음 판단의 근거이지 성과 요약이 아니다.
- **정본을 옮겨 적지 않는다** — 사양·코드 내용을 복사하지 말고 그 위치를 가리킨다(산출물 정본은 워크스페이스 파일, §단계별 미러링).

#### 6절 실행 프로파일 — 작성 규칙

이 절의 목적은 **model·effort 배치와 호출 규약을 재조정할 근거를 모으는 것**이다([`agents.md`](agents.md) §모델·추론 강도(effort) 정책·§되돌림 기준). 과금액 산출이 아니다.

- **호출 횟수가 본체다** — 실행 주체는 자기가 몇 번 무엇을 디스패치했는지 정확히 안다. 등급을 병기해 어느 층에서 비용이 나가는지 보이게 한다.
- **모르는 숫자를 채우지 않는다** — 토큰 소비량은 실측 값이 있을 때만 적는다. 없으면 그 칸을 비우고 호출 횟수만 적는다. **추정치를 지어내면 이 절이 근거로서 무가치해진다.**
- **회귀를 반드시 남긴다** — 회귀 횟수는 증분 회귀 규약이 작동하는지 판별하는 유일한 신호다. 0회면 `0`으로 명시한다(생략 금지).
- 서술 예:
	```
	prd-to-policies(T2) 1 · prd-to-datas(T2) 1 · prd-to-qa(T3) 1 · spec-reviewer(T1) 3(증분2+전체1) · mockup-builder(T4) 1
	회귀: 데이터 1회(교차검증 오류 — 지적 2개 절만 수정) · 그 외 0
	소비량: 미실측
	```

### 등록 규칙

- **계층** — 보고 대상의 **하위 이슈**로 등록한다(생성 시 `parent_issue_id` 지정 — [`work-tracking-redmine.md`](work-tracking-redmine.md) §이슈 조작).
- **상태** — 등록과 동시에 **`완료`(닫힘)**. 보고는 추가 확인을 요구하는 작업이 아니다(§단계 산출 일감 상태 매핑 — 추가 확인이 필요 없는 건은 실행 주체가 완료까지 정리한다). 열린 일감 목록을 보고물로 채우지 않는다.
- **순서 (엄수)** — report 를 **`완료` 로 만든 뒤에 부모를 닫는다.** 하위가 열려 있으면 부모 close 가 거부되므로(§닫을 때 지킬 것), 보고를 열린 채로 두면 대상 작업세션 이슈·그룹 일감을 종결할 수 없다.
- **제목** — `[report] <구분> — <대상 요약> (#<대상 이슈번호>)`. 예: `[report] spec 레그 — 요구사항 제품 적용 (#469)` · `[report] 세션 — 전체 프로젝트 리셋 (#467)`.
- **상태 아이콘을 붙이지 않는다** — 5종 판정 아이콘(§제목 상태 아이콘)은 판정 대상 일감의 것이다. 보고는 판정이 아니다.
- **프로젝트·카테고리** — 대상 이슈와 같은 프로젝트에 등록하고, 대상의 IA 카테고리를 그대로 승계한다.
- **실패해도 본 작업을 막지 않는다** — 보고 등록에 실패하면(트래커 미구성·API 오류) 그 사실을 대상 이슈 노트로 남기고 진행한다. 보고 때문에 작업 종결이 막히지 않는다.

> **선행 조건** — `report` 트래커는 Redmine admin 전용이라 REST 로 만들 수 없다. 담당자가 1회 생성해야 이 정책이 실제로 동작한다([`work-tracking-redmine.md`](work-tracking-redmine.md) §트래커 구성).

## 상태 어휘

| 상태 | 의미 | 진입 시점 |
|---|---|---|
| 신규 | 접수됨·미착수 | 이슈 생성 |
| 진행 | 작업 중 | 디스패치·착수 |
| 해결 | 평가·리뷰 대기 | 실행 완료 보고 후 — **추가 확인이 남은 경우** |
| 완료 (닫힘) | 완료 | 확정 통과(추가 확인 불필요) 또는 평가·담당자 확인 |
| 보류 | 외부 응답 대기 | 검토 협의 질의 등 — 응답 시 이전 상태 복귀 |
| 거절 (닫힘) | 취소·철회 | 담당자 결정(사유 노트) |

위 6종이 정본이며 새 어휘를 늘리지 않는다. **Redmine 표시명·id 는 이 이름과 다르다** — 대응은 [`work-tracking-redmine.md`](work-tracking-redmine.md) §요소 식별자가 단일 출처다(특히 `보류` 는 Redmine `Needs Feedback`=4 에 매핑된다). 상태를 바꾸기 전에 같은 문서 §전이 사전 확인으로 그 전이가 지금 가능한지 조회한다.

### 단계 산출 일감 상태 매핑

단계별 미러 일감의 상태 전이 기준. 세부 진척(예: build 의 작성→리뷰→검증 구간)은 상태 어휘를 늘리지 않고 **이슈 노트**로 기록한다.

| 일감 | 신규 | 진행 | 해결 | 완료 |
|---|---|---|---|---|
| 사양 (spec) | 등록·작성 착수 전 | 작성·보완 중 | 교차검증 통과 | 단계 완료·담당자 승인 |
| 기능 (build Phase) | Phase 편성 등록 | 작성~리뷰~검증 진행(구간은 노트) | 세 책임 통과 + **잔여 확인 항목 있음** | 세 책임 통과 + **잔여 확인 항목 없음** |
| 검증 (qa TC) | TC 등록 | 실행 중 | 잠정 Pass(🔵🟣 — 재검증 사유 노트 필수) | 🟢 **Pass**(실 환경 확정) |

**원칙 — 추가 확인이 필요 없는 건은 실행 주체가 `완료`(닫힘)까지 정리한다.** `해결`은 "확인이 더 남았다"는 뜻으로만 쓴다. 판정이 확정된 건을 `해결`에 쌓아두면 담당자가 무엇을 봐야 하는지 흐려진다.

- 🟢 **Pass**(실 환경 round-trip 확정) → **`완료`(닫힘)**. 검증 실행 주체(tester·qa 오케스트레이터)가 직접 닫는다 — 추가 확인 여지가 없는 판정이기 때문.
- 🔵🟣 **잠정 Pass** → `해결` + **재검증 사유·해소 조건 노트 필수**. 재검증으로 🟢 확정되거나 담당자가 수용 판정할 때 `완료`로 닫는다(잠정 상태로 닫지 않는다).
- 🔴 **Fail** → `진행` 유지 + 판정 노트. qa 단계의 Fail 은 `오류` 일감을 생성해 연관한다(§계층·연관).
- 🟠 **Block·명시적 이월** → `보류` + 해소 조건 노트. 해소 시 `진행` 복귀.
- **기능(build Phase)** → 세 책임(작성·리뷰·기능검증)을 모두 통과하고 **잔여 확인 항목이 없으면 `완료`**. 잔여 확인 항목(잠정 Pass 🔵🟣 · 보류 항목 · 사양 결함 제기 · 담당자 판단 대기)이 하나라도 있으면 `해결` + 그 항목을 노트로 명시한다.
- 리뷰·검증 결함으로 회귀하면 상태는 `진행` 을 유지하고 회귀 사유·시도 횟수를 노트로 남긴다(최대 3회 — [`base-workflow.md`](base-workflow.md) §개요 공통 흐름).

**개별 일감 종결 ≠ 단계 승인** — 위 `완료`는 일감 1건의 종결일 뿐이다. **단계 이행·배포 가능 판정은 여전히 담당자 승인 사항**이며([`stages/qa.md`](stages/qa.md) §다음 단계 이행 조건), 그 승인은 단계 그룹 일감·작업세션 이슈에서 받는다. 개별 TC·Phase 를 닫는 것이 단계 통과를 뜻하지 않는다.

**닫을 때 지킬 것** — ① **하위 일감을 먼저 닫고 부모를 닫는다**(열린 하위가 있으면 부모 close 가 거부된다). 계층이 작업세션까지 이어지므로(§계층·연관) 닫기 사슬은 `검증 → 기능 → 그룹 → 작업세션` 순이다. ② 상태 전이 응답의 성공 표시를 믿지 말고 `GET /issues/<id>.json` 의 `status`·`closed_on` 으로 **실측 검증**한다([`work-tracking-redmine.md`](work-tracking-redmine.md) §도구 함정).

### 작업세션 종결 — 열린 하위가 남으면 닫지 않는다

작업세션 이슈가 업무 트리의 루트이므로, 그 아래 일감이 하나라도 열려 있으면 작업세션을 닫을 수 없다. 그런데 정책상 **열린 채로 남는 것이 정상인 일감**이 있다 — 🔵🟣 잠정 Pass 검증(`해결`) · 🟠 Block·이월(`보류`) · 미해소 `오류` 일감 · 잔여 확인 항목이 있는 기능 일감(`해결`).

- **열린 하위가 남으면 작업세션을 `해결` 로 두고 닫지 않는다.** 담당자 확인 대기 상태이며, 그 자체가 "업무는 보고됐으나 잔여가 있다"는 표시다. **닫기 위해 하위를 임의로 종결하거나 부모에서 떼어내지 않는다** — 잔여를 감추는 것이지 해소하는 것이 아니다.
- **회신 노트에 열린 하위를 전부 나열한다** — 일감 번호·상태·열린 사유(잠정 Pass 재검증 조건, 보류 해소 조건, 오류 후속 경로)를 적는다. 담당자가 무엇을 기다리는지 작업세션 이슈 하나에서 보이게 한다.
- **세션 report 는 실제로 종결하는 사이클에만 남긴다** — 닫지 않으면 업무가 끝난 것이 아니므로 등록하지 않는다([`ai-pm.md`](ai-pm.md) §디스패치 계약 6). 잔여가 해소돼 닫는 사이클에서 남긴다.
- **잔여가 해소되면 그때 닫는다** — 후속 작업으로 하위가 모두 닫히면 작업세션을 `완료` 로 종결한다.
- **담당자가 잔여를 수용하고 종결을 지시한 경우** — Redmine 제약상 하위를 먼저 정리해야 닫을 수 있다. 각 열린 하위를 어떻게 할지(수용 종결 / 후속 작업세션으로 이관)를 담당자 지시에 따라 처리하고, 그 결정과 처리 내역을 작업세션 이슈 노트에 남긴 뒤 닫는다.

### 제목 상태 아이콘

build·qa 산출 일감은 **최종 판정이 확정되는 시점에 제목 맨 앞에 상태 아이콘 1개를 붙인다.** 목록에서 상태를 색으로 즉시 훑기 위한 장치다 — Redmine 상태(`해결`/`완료`)만으로는 "무엇이 잠정이고 무엇이 실패인지"가 제목 줄에서 보이지 않는다.

| 아이콘 | 의미 |
|---|---|
| 🟢 | 확정 통과 — 실 환경 Pass / build 세 책임 통과·잔여 없음 |
| 🔵 | 잠정 통과 (Mock 의존) |
| 🟣 | 잠정 통과 (Static — 코드 정합 trace) |
| 🔴 | 실패 — Fail / 미해소 결함으로 중단 |
| 🟠 | 차단·이월 — Block / 보류 |

- **어휘를 새로 만들지 않는다** — 5종 판정 아이콘을 그대로 쓴다(§단계 산출 일감 상태 매핑). build 기능 일감도 같은 팔레트로 매핑한다(세 책임 통과·잔여 없음 = 🟢, 잠정 Pass 잔여 = 🔵🟣, 보류 = 🟠, 미해소 결함 중단 = 🔴).
- **형식** — `<아이콘><공백><기존 제목>` (예: `🟢 [qa] USR-01_006 승인(AGREE)·복호화·전달 성공`). 아이콘은 **정확히 1개**이며 다른 접두 표기를 추가하지 않는다.
- **멱등** — 재검증·재디스패치로 판정이 바뀌면 **기존 선두 아이콘을 교체**한다. 절대 덧붙여 쌓지 않는다(`🔴🟢 …` 금지). 제목 선두가 위 5종 중 하나면 교체, 아니면 삽입으로 처리한다.
- **갱신 시점·방법** — 최종 판정과 **같은 PUT 한 번**에 `subject` 를 상태·노트와 함께 보낸다(아이콘 때문에 별도 갱신 이력을 만들지 않는다). 중간 진행 상태로는 붙이지 않는다 — **최종 판정 시점에만**.
- **적용 대상** — 검증(qa TC)·기능(build Phase) 일감, 그리고 단계 그룹 일감(정리 단계에서 종합 판정으로). `사양` 일감은 대상이 아니다.

## 티켓 ID

- ID = Redmine 이슈 번호 `<프로젝트식별자>#NNN`(예: `ai-workgroup-ops#14`). 별도 채번 없음.
- 발급 후 불변. 대화·디스패치·산출물·이력 어디서든 이 번호로 참조한다.

## 표준 이슈 양식

- **제목**: 작업을 한 줄로 요약(한글 허용).
- **상위 일감 (필수)**: 생성 시 `parent_issue_id` 를 반드시 지정한다(§계층·연관). 작업세션 이슈를 제외한 모든 일감이 대상이며, 생성 후 `parent` 를 실측 확인한다.
- **설명 첫 줄 메타 머리말**: 요청자·요청 출처·단계(spec/build/qa). 이어 배경·산출물 링크·검토 협의 기록.
- **진행 로그 = 이슈 노트**: 상태 전이·산출물 생성 시점마다 노트 1건(모든 행위를 적지 않음). 작성자·시각은 Redmine 이 자동 기록한다.

## 생애주기·갱신 책임

| 시점 | 주체 | Redmine 동작 |
|---|---|---|
| 요청 접수 | 담당자 | **작업세션 이슈 생성**(상태 `신규`) — 대화 스레드를 여는 것은 담당자 몫이다([`ai-pm.md`](ai-pm.md) §Slack→Redmine 매핑) |
| 인식·접수 확인 | ai-pm | 작업세션 이슈에 접수 노트 + 상태 `진행`. **봇은 작업세션 이슈를 생성하지 않는다**(산출 일감은 그 하위로 생성 가능) |
| 디스패치 | ai-pm | 서브에이전트 기동 — **작업세션 이슈 번호를 부모 좌표로 전달**(§계층·연관). 산출 일감(사양·기능·오류·검증) 생성은 서브에이전트 소관 |
| directing 산출 | ai-pm | 방향 도출 작업을 **작업세션 직속 하위 일감**으로 등록·갱신(그룹 일감을 두지 않는다 — [`stages/directing.md`](stages/directing.md)) |
| 진행·미러 | 서브에이전트 | 산출물 작성과 함께 해당 일감 등록·갱신(미러·노트), 상태 동기화. **생성 시 `parent_issue_id` 필수**(§계층·연관) |
| 완료 보고 | 서브에이전트 | 추가 확인 불필요분은 상태 `완료`(닫힘)까지, 잔여 확인이 있는 건만 `해결` + 잔여 항목 노트(§단계 산출 일감 상태 매핑) |
| 평가·전달 | ai-pm | 남은 `해결` 건을 평가 — 통과 → `완료`(산출물·링크 노트), 보완 → `진행` 복귀. 결과를 작업세션 이슈로 담당자에 회신 |
| 레그 보고 | 단계 오케스트레이터 | 자기 레그 종료 직전 **레그 report 일감 생성**(그룹 일감의 하위, `완료`로 등록 — §작업 보고) |
| 세션 보고 | `session-reporter`(ai-pm 디스패치) | 작업세션 이슈 종결 직전 **세션 report 일감 생성**(작업세션 이슈의 하위, `완료`로 등록 후 부모 종결) |
| 보류 | 질의 주체 | `보류` + 검토 협의 링크 노트. 응답 수신 시 이전 상태 복귀 |
| 취소 | ai-pm(담당자 지시) | `거절` + 사유 노트 |

- 상태·담당자를 바꾼 주체가 같은 동작의 노트로 사유를 남긴다. 별도 보드 갱신은 불필요하다(§조회).
- 단계 이행·게이트의 **담당자 승인·반려는 ai-pm 이 해당 (그룹) 일감 노트로 기록**한다 — 작업세션 이슈 대화는 통로이고 증적 정본은 일감 노트다([`ai-pm.md`](ai-pm.md) §질의·승인 릴레이).

## 티켓 생성 기준

다음 중 하나면 생성한다 — 산출물 생성·변경이 따르는 요청 / 서브에이전트 디스패치가 발생하는 작업 / 후속 추적(진행·완료 확인)이 필요한 요청. 단답으로 끝나는 질문·조회·인사는 티켓 없이 즉답한다. 애매하면 만들지 않고, 후속 작업이 실제 발생하는 시점에 만든다.

## 조회

별도 INDEX 파일을 두지 않는다 — Redmine 이슈 목록·필터가 보드 역할을 한다. 상태·담당자·카테고리·트래커로 걸러 본다. 자주 보는 뷰(진행 중·대기·완료)는 Redmine **저장 쿼리**로 만들어 담당자와 공유한다([`work-tracking-redmine.md`](work-tracking-redmine.md) §저장 쿼리).
